# 5.3. Session Drilldown

**Date**: 2026-08-24
**Status**: Accepted

## Summary

`STATUS.md` describes 5.3 as: *"View a session's ledger state and the Findings that fed it (demonstrates the 'why did this get blocked' story — the defensibility point from Fork #3's rationale)."* Today the console has no way to see a session at all: 5.1's dashboard only shows aggregate counts, 5.2 manages workloads, and nothing lets an operator (or a demo audience) pick a real session and see why it was blocked or escalated.

This spec adds two new read-only backend endpoints (`GET /api/console/sessions`, `GET /api/console/sessions/{session_id}`) plus two new console pages — `/sessions` (a list, with a "jump to a session" lookup) and `/sessions/:sessionId` (the drilldown: ledger state, escalation status, and every execution's findings in order). It reuses 5.2's nav shell (one more link) and the existing `is_escalated()` predicate from `app/redis_client.py`.

## Context

Mapped against the current code (`app/models/session.py`, `execution.py`, `finding.py`, `app/redis_client.py`, `app/routers/console.py`, `console/src/*`) for this spec:

- **`Session`** (Postgres): `session_id` (PK), `workload_id` (FK), `cumulative_risk` (float), `strikes` (JSONB, all six categories always present), `ttl_expires_at`, `created_at`. Per its own code comment and the 4.1/4.3-era `decisions.md` entries, this is the **durable** copy of the ledger — 4.3 already made it a live mirror of Redis's ledger, written on every `apply_ledger_update` call.
- **`Execution`**: `execution_id` (PK), `session_id`/`workload_id` (FKs), `tokens`, `latency_ms`, `retries`, `tool_loop_count` (operational signals, Fork #2), `execution_risk_score`, `created_at`. No `blocked` column — 5.1 already established the derivation: an execution is "blocked" if it has ≥1 `Finding` with `evaluator_tier != expensive` (2.5's async judge never actually blocks anything, per Fork #4). This spec reuses that exact definition.
- **`Finding`**: `finding_id` (PK), `execution_id` (FK), `category`, `confidence`, `evaluator_tier`, `evidence_ref` (JSONB, carries `{side: "request"|"response", pattern, span}` per the 1.5/2.x-era `decisions.md` entries), `timestamp`.
- **`app/redis_client.py`'s `is_escalated(ledger)`**: a pure predicate, no Redis calls inside it, takes any `{"cumulative_risk": float, "strikes": dict}`-shaped input and returns Fork #3's exact `cumulative_risk > 0.7 OR any strikes[category] >= 3` condition. `Session`'s Postgres columns are already shaped exactly this way, so this function is reused as-is against Postgres data — no new escalation logic.
- **Redis's ledger is explicitly not the source here**: it carries a 15 minute TTL (0.3) and holds only the *current* live state; it cannot answer "what happened in this session historically," and an inactive session's key may already be gone by the time someone drills into it. `Session`/`Execution`/`Finding` in Postgres are the durable audit trail (4.1/4.2/4.3's whole point) — this spec reads Postgres exclusively.
- **`app/routers/console.py`** / **`app/schemas/console.py`**: hold 5.1's `GET /summary` and 5.2's `GET/POST /workloads` + `PATCH /workloads/{id}`. Convention to match: `router = APIRouter(prefix="/api/console")`, `Depends(get_db)`, explicit schema construction (not `from_attributes`, since `Workload.metadata_`/`metadata` already differ in name).
- **`console/`**: `App.tsx` is the nav shell (Dashboard, Workloads) built in 5.2, wrapping `<Routes>` via `react-router-dom`; a shared footer renders once below it. `Workloads.tsx` set the list-page pattern (loading/error/empty states, a semantic `<table>`, bordered pill badges for enum-like values) this spec continues. No detail/nested-route page exists yet.
- **`app/main.py`**: `CORSMiddleware` already allows `GET`/`POST`/`PATCH` (5.2) — both new endpoints are `GET`, no change needed.

## Requirements

- **AC-1**: `GET /api/console/sessions` returns the 50 most recent sessions (by `created_at`, most recent first), each with `cumulative_risk`, `strikes`, a correctly-derived `escalated` flag, and `execution_count`.
- **AC-2**: `GET /api/console/sessions/{session_id}` returns the session's full executions with their findings, ordered oldest to newest (executions) and each execution's findings ordered oldest to newest (timestamp); an unknown `session_id` returns `404`.
- **AC-3**: `escalated` matches `is_escalated()`'s exact Fork #3 condition — verified against a real session with `cumulative_risk > 0.7` and a real session with a strike count `>= 3`, plus a real non-escalated session.
- **AC-4**: `blocked` on each execution in the detail response matches 5.1's existing definition (true iff ≥1 `Finding` with `evaluator_tier != expensive`).
- **AC-5**: The console nav shell shows a third link, **Sessions**; `/sessions` lists real data (name-or-truncated-id, workload, escalated badge, cumulative risk, execution count, last activity) and each row links to `/sessions/:id`; a "jump to a session" input navigates directly to `/sessions/:id` for a pasted id.
- **AC-6**: `/sessions/:id` renders the ledger summary (cumulative risk, per-category strikes), the escalation state (with a visible caveat when escalated: escalation-only blocks write no `Execution`/`Finding` row, so this page cannot always show the specific turn that tripped it), and every execution's findings in order — matching a direct Postgres query for that session.
- **AC-7**: `GET /health`, `POST /v1/chat/completions`, `GET /api/console/summary`, and 5.2's workload endpoints are unaffected (regression).

## Decision

**Chosen option**: two new read-only endpoints on the existing `app/routers/console.py` router, reading Postgres exclusively (not Redis), plus two new console pages (`/sessions` list, `/sessions/:sessionId` detail) reusing 5.2's nav shell and list-page conventions.

**Implementation skills**: none — no new library; `react-router-dom`'s dynamic route param (`useParams`) is already a dependency from 5.2.

### Backend

- **`app/schemas/console.py`** (extend): add
  - `SessionSummary { session_id: uuid.UUID; workload_id: uuid.UUID; workload_name: str | None; cumulative_risk: float; strikes: dict; escalated: bool; execution_count: int; ttl_expires_at: datetime; created_at: datetime }`
  - `FindingOut { finding_id: uuid.UUID; category: str; confidence: float; evaluator_tier: str; evidence_ref: dict | None; timestamp: datetime }`
  - `ExecutionOut { execution_id: uuid.UUID; tokens: int | None; latency_ms: int | None; retries: int; tool_loop_count: int; execution_risk_score: float | None; blocked: bool; created_at: datetime; findings: list[FindingOut] }`
  - `SessionDetail` — `SessionSummary`'s fields plus `executions: list[ExecutionOut]`.
- **`app/routers/console.py`** (extend, same `router`):
  - `GET /sessions` → `list[SessionSummary]`. Query: `select(Session).order_by(Session.created_at.desc()).limit(50)`; `workload_name` via a join/lookup against `Workload.metadata_.get("name")`; `execution_count` via a grouped `count(Execution.execution_id)` keyed by `session_id` (one query, merged in Python — same merge style 5.1's `over_time` already uses for two grouped queries); `escalated` via `is_escalated({"cumulative_risk": s.cumulative_risk, "strikes": s.strikes})` (imported from `app.redis_client`).
  - `GET /sessions/{session_id}` → `db.get(Session, session_id)`; `404` if `None`. Loads `Execution`s for that session (`order_by(Execution.created_at)`) and, per execution, its `Finding`s (`order_by(Finding.timestamp)`) — either two queries merged in Python (matching the list endpoint's own merge style) or a single joined query, whichever reads simplest; `blocked` computed the same way as `list_workloads`' sibling endpoint (`GET /summary`) already computes `blocked_count`: any finding with `evaluator_tier != expensive`. `escalated` via the same `is_escalated()` reuse as the list endpoint.
- No `app/main.py` change (both new routes are `GET`, already CORS-allowed).

**Value sourcing** (every displayed value has a named source):

| Value | Source |
|---|---|
| `cumulative_risk` / `strikes` (per session) | `Session.cumulative_risk` / `Session.strikes` (Postgres, kept durable by 4.3) |
| `escalated` | `is_escalated()` (`app/redis_client.py`), applied to the session's Postgres-sourced `{cumulative_risk, strikes}` |
| `execution_count` | `count(Execution)` grouped by `session_id` |
| `workload_name` | `Workload.metadata_["name"]` (5.2's convention), `None` if unset |
| `blocked` (per execution) | `count(Finding) where evaluator_tier != expensive` > 0, same rule as 5.1's `blocked_count` |
| `findings[].*` | `Finding` columns verbatim, ordered by `timestamp` |

### Frontend

- `console/src/App.tsx`: nav gains a third `NavLink`, **Sessions**, routed to `/sessions`; add a `<Route path="/sessions/:sessionId" element={<SessionDetail />} />` alongside the existing routes.
- **`console/src/Sessions.tsx`** (new, list page): a "jump to a session" text input + button that navigates to `/sessions/<pasted id>` on submit (client-side navigation only — the detail page's own `404` handling covers an invalid id); a table of the 50 most recent sessions (name-or-truncated-id, workload, an "Escalated" pill when true, cumulative risk, strikes summary, execution count, last activity), loading/error/empty states matching `Workloads.tsx`. Each row is a link to `/sessions/:id`.
- **`console/src/SessionDetail.tsx`** (new, detail page): reads `sessionId` via `useParams()`. Header (session id, workload, an "Escalated" banner with the caveat text when true), a ledger summary block (cumulative risk, per-category strike badges), then a chronological list of executions — each showing its operational signals (tokens, latency) and its findings (category, confidence badge, evaluator tier, request/response side from `evidence_ref.side`, timestamp). `404` from the API renders a "Session not found" state, not a generic error.
- **`console/src/lib/format.ts`** (new, small shared helper): `displayId(uuid, name?)` — extracted from `Workloads.tsx`'s existing inline `displayName()` so both pages use one implementation; `Workloads.tsx` is refactored to import it instead of keeping its own copy.
- `console/src/api.ts`: add `fetchSessions()`, `fetchSessionDetail(sessionId)` (the latter must surface a `404` distinctly so the page can render "not found" rather than a generic error).
- `console/src/types.ts`: add `SessionSummary`, `FindingOut`, `ExecutionOut`, `SessionDetail` mirroring the new schemas exactly.
- `console/design.md` gets a short addendum during the build describing the list/detail composition, continuing 5.1/5.2's precedent.

## Rationale

Reading Postgres exclusively (not Redis) is the only choice consistent with what Phase 4 already built: Redis is explicitly the 15-minute-TTL *live* ledger (0.3), while `Session`/`Execution`/`Finding` in Postgres are the durable audit trail 4.1–4.3 spent three milestones making complete and consistent. A drilldown feature is, by definition, about looking at what already happened — sourcing it from a store that forgets after 15 minutes would make the feature unreliable for exactly the sessions most worth showing in a demo (ones from earlier in the run). Reusing `is_escalated()` rather than re-deriving the threshold check avoids a second, potentially-drifting copy of Fork #3's escalation math — it was already written as a pure predicate for exactly this kind of reuse.

The list-then-detail navigation (two pages, not one page with just a search box) matches what 5.2 already established for a page with nested/richer content: a session's findings-per-execution structure is too deep to fit a modal the way a flat workload edit form did, so a dedicated route is the natural fit, and `react-router-dom` (added in 5.2) already supports dynamic params with no new dependency.

## Consequences

**Positive**:
- Closes the last major "wow factor" gap before 5.4 (Live Feed): a real audience can now see the actual reasoning behind a block, not just an aggregate count.
- Establishes the console's first detail/nested route, which 5.4 (or any future drilldown) can follow the same pattern for.

**Negative / tradeoffs**:
- A session escalated purely by strikes/risk accumulated over turns that themselves cleanly passed can show an "Escalated" banner with no single execution's findings that "explains" it by itself — the story is the accumulation across turns, not one row. Documented, not hidden.
- Escalation-block turns (3.2) still write no `Execution`/`Finding` row at all (a known, already-ratified gap from 5.1), so the exact turn that *tripped* escalation is not separately visible in the timeline — only the ledger's resulting state is. The UI caveat says this plainly.
- Fixed 50-session cap, no pagination/filtering — a demo with far more than 50 sessions in flight would need a follow-up change to find an older one (the jump-to-session input is the workaround: paste the id directly).

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-check described below.
- No database schema change; no new dependency.

## Follow-up

- If a live demo needs to browse beyond the 50 most recent sessions, or filter by workload, revisit pagination/filtering then — not built now, matching 5.1's fixed-window precedent.
- 5.4 Live Feed is the next milestone — write its spec first via `/architect`. It can reuse this milestone's execution/finding rendering conventions (badges, side labels) for its own real-time rows.
