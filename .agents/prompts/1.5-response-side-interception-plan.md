# 1.5. Response-side interception

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec adds a response-side cheap-tier gate to `POST /v1/chat/completions`: after 1.4 forwards a clean prompt and gets a real model response back, that response's content is scanned before it reaches the caller. A clean response releases exactly as it does today. A match persists `Finding`(s) on the `Execution` row 1.4 already created for this call, updates the session's Redis ledger per Fork #3's exact math (same formula 1.3 already applies on the request side), and returns `403` instead of releasing the unsafe content — the caller never sees it. This closes the last gap in the core demo path: block-on-cheap-tier now works on both sides of the model call, not just the request side.

## Context

`forks.md` Fork #4 locks the response-side shape: "Cheap tier always runs synchronously, on every response, and gates release... A request-side block counts as a strike, same `Finding` schema, same category, same ledger mechanics as a response-side finding. Input and output are NOT treated differently." `STATUS.md`'s 1.5 line: "Intercept the model's response before returning it to the caller. Do not release yet."

Two structural gaps existed before this milestone, not just wiring:
- **`Execution.execution_risk_score` has sat at `None` since 1.4**, explicitly logged as "pending 1.5's response evaluation" (`decisions.md`, 2026-08-23). Nothing has evaluated a model's actual output yet.
- **Phase 2.3 ("confirm 2.1/2.2 detectors run on OUTPUT text too, not just input") hasn't formally landed**, though `app/evaluators/cheap.py`'s own docstring already anticipates it: "Reused for both request-side (1.3) and response-side (2.3) text." This milestone satisfies that reuse requirement ahead of its own phase number, the same way 1.3 already satisfied 2.1/2.2 ahead of schedule.

A third, genuinely new distinction surfaces here that 1.3 never had to handle: a **request-side** block (1.3) happens *before* the model is ever called, so its `Execution` row has null `tokens`/`latency_ms` — there was no real call to measure. A **response-side** block happens *after* a real, completed model call (1.4 already ran it, already paid the latency/token cost). Fork #4 is explicit that a released response can't be unsent; the same reasoning extends to the call itself — blocking release doesn't undo the fact that the call happened. So a response-side block's `Execution` row must carry the real `tokens`/`latency_ms` from that actual call, unlike 1.3's block shape.

## Requirements

**User stories**:
- As the operator of a workload, I want an unsafe model response (leaking PII, echoing an injection-style phrase) blocked before it reaches the caller, so cheap-tier governance protects the output side, not just the input side.
- As the engineer who will build Phase 3 next, I want response-side findings to update the ledger with the exact same mechanics as request-side ones, so 3.1/3.2's escalation logic can treat both uniformly.
- As an AI application developer integrating with ControlPlane, I want a response-side block to look like the same kind of error as a request-side block, so my error handling doesn't need a second code path.

**Acceptance criteria**:
- **AC-1**: A clean model response (no cheap-tier match on the output) releases to the caller unchanged — the real `200` response 1.4 already returns.
- **AC-2**: A model response containing a PII-shaped string returns `403` with `code: "pii"` instead of releasing the real content.
- **AC-3**: A model response containing a prompt-injection-style phrase returns `403` with `code: "prompt_injection"`.
- **AC-4**: A response matching both categories returns `403` listing both in `message`, `code` set to whichever finding has the highest confidence (tie-break: scan order, same rule 1.3 already uses, since all cheap-tier confidences are the fixed `0.95`).
- **AC-5**: A response-side block persists on the **same** `Execution` row 1.4 already created for this call (not a second row) — with real `tokens`/`latency_ms` populated from the completed model call — plus one `Finding` per matched category, and `execution_risk_score` set to the max confidence across those findings.
- **AC-6**: A response-side block updates the session's Redis ledger exactly per Fork #3: `cumulative_risk = cumulative_risk * 0.7 + execution_risk_score`; `strikes[category]` increments once per finding with `confidence > 0.7`.
- **AC-7**: A response-side block still carries the `X-Workload-Id`/`X-Session-Id` response headers.
- **AC-8**: A clean response sets `Execution.execution_risk_score = 0.0` (evaluated, nothing found) — not `None` — and leaves the Redis ledger untouched.
- **AC-9**: 1.2's `400`s, 1.3's request-side `403`, and 1.4's model-call-failure `502` are all unaffected by this change.
- **AC-10**: `/health` still returns `200`.

## Options considered

### Option 1: Dedicated `_run_response_side_interception` helper in `app/routers/chat.py` (recommended)

Mirrors the router's existing internal structure — `_resolve_workload`, `_resolve_session`, `_run_request_side_interception`, `_model_error_response` are already separate helpers, not inlined into `chat_completions`.

**Pros**: Consistent with the file's own established pattern; keeps `chat_completions` readable as an orchestration sequence.
**Cons**: None material — this is router-internal orchestration, not reusable logic that needs its own module (unlike `app/evaluators/` or `app/model_client.py`, which later milestones explicitly reuse).

### Option 2: Inline the response scan directly in `chat_completions`'s success branch

**Pros**: One fewer function.
**Cons**: Breaks the file's own precedent of extracting each interception step into its own helper; would make the success branch's already-multi-step flow (call model, build Execution, scan response, decide) harder to read as one block.

### Option 3: Touch the Redis ledger only on a response-side violation (recommended)

Matches 1.3's own precedent exactly: the ledger is only written when there's something to record.

**Pros**: Consistent, minimal-scope behavior; doesn't reach into Phase 3.1's explicitly named job ("Ledger Update Logic").
**Cons**: `forks.md` Fork #3 frames `cumulative_risk` as a *continuous* decay, which arguably implies it should tick on every turn (including clean ones) so risk actually fades over a session — this option leaves that gap open until 3.1.

### Option 4: Touch the ledger on every execution, clean or not (decays `cumulative_risk` by `*0.7 + 0.0` on a clean turn)

**Pros**: Properly implements Fork #3's "continuous" framing starting now.
**Cons**: Quietly expands 1.5's scope into work `STATUS.md` explicitly assigns to Phase 3.1 ("Ledger Update Logic... per-category strikes with window expiry" — the two are meant to land together), before strike-window expiry exists to bound it; risks 1.5 and 3.1 landing inconsistent, hard-to-reconcile ledger semantics.

### Option 5: `execution_risk_score = 0.0` on a clean response (recommended)

**Pros**: `0.0` accurately means "cheap tier ran, found nothing" — a real, meaningful evaluation result. Once 1.5 ships, `None` is unreachable on the success path (cheap tier always runs), so keeping `None` there would be a stale, misleading placeholder.
**Cons**: None material.

### Option 6: `execution_risk_score = None` on a clean response

**Pros**: Reuses 1.4's existing placeholder value with no code change to that field's default.
**Cons**: Conflates "not evaluated" with "evaluated, clean" — the two are no longer the same state once 1.5 exists, and a future reader (or Phase 4's audit trail) can't tell them apart from the column alone.

## Decision

**Chosen**: Option 1 (dedicated helper) + Option 3 (ledger touched only on violation) + Option 5 (`0.0` on a clean response).

## Rationale

Option 1 costs nothing and keeps the file internally consistent — there's no reason to break the established one-helper-per-interception-step pattern for this one. Option 3 over Option 4: Fork #3's continuous-decay framing is real, but `STATUS.md` names "Ledger Update Logic" as Phase 3.1's explicit job, paired with strike-window expiry in the same checklist line — implementing continuous decay now, without the window expiry that bounds it, risks building half of 3.1's design under a different milestone number and having to reconcile it later. Staying narrow here (matching 1.3's own precedent of violation-only ledger writes) keeps the gap contained and explicitly flagged (Follow-up below) rather than silently deciding it. Option 5 over Option 6: since Fork #4 requires cheap tier to run on *every* response starting now, `None`'s only honest meaning ("not evaluated") stops being reachable on the success path — keeping it would misrepresent what actually happened.

## Feature design

**Data model sketch**: no schema change. Reuses `Execution` (now populating `execution_risk_score` for the first time on the success path) and `Finding` exactly as defined in 0.2/1.3.

**Changed file**: `app/routers/chat.py` — the success branch of `chat_completions` (currently: build `Execution`, commit, return `parsed`) becomes:
1. `call_model(request)` succeeds → `parsed`, `latency_ms` (unchanged from 1.4).
2. Build the `Execution` object (`session_id`, `workload_id`, `tokens=parsed.usage.total_tokens`, `latency_ms`, `retries=0`, `tool_loop_count=0`) — **no `execution_risk_score` yet**. `db.add(execution)`; `await db.flush()` to obtain `execution.execution_id` without committing.
3. Call `_run_response_side_interception(db, session, workload, execution, parsed)`.
4. If it returns a `JSONResponse` (a match): attach `X-Workload-Id`/`X-Session-Id` headers (same pattern as 1.3/1.4's other early-return paths) and return it.
5. If it returns `None` (clean): return `parsed`.

**New helper** `_run_response_side_interception(db, session, workload, execution, parsed) -> JSONResponse | None`, mirroring `_run_request_side_interception`'s return contract exactly:
1. Extract `response_text = parsed.choices[0].message.content` (always exactly one choice — 1.4's schema, non-streaming).
2. `candidates = run_cheap_tier(response_text)`.
3. No candidates: `execution.execution_risk_score = 0.0`; `await db.commit()`; return `None`. **No ledger write.**
4. Candidates found: `execution.execution_risk_score = max(candidate.confidence for candidate in candidates)`; create one `Finding` per candidate (`execution_id=execution.execution_id`, `category`, `confidence`, `evaluator_tier=EvaluatorTier.cheap`, `evidence_ref`); commit. Update the Redis ledger via `get_ledger`/`set_ledger` using the same `LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD` constants `_run_request_side_interception` already defines at module level (no duplication). Return a `403` `JSONResponse`:
```json
{"error": {"message": "Response blocked by ControlPlane: <categories> detected in output.", "type": "controlplane_policy_violation", "param": null, "code": "<primary category>"}}
```
Same envelope shape as 1.3's request-side block (Fork #4: "input and output are NOT treated differently"), with "Response blocked"/"in output" wording so logs stay distinguishable from a request-side block.

**Value sourcing**:
- `execution_risk_score` (violation path) = `max(candidate.confidence for candidate in candidates)`, per Fork #2 — identical rule to 1.3.
- `execution_risk_score` (clean path) = `0.0` — a new, deliberate value (see Decision/Option 5).
- `Execution.tokens`/`latency_ms` on a response-side block = the real values from the already-completed `call_model()` call (unlike 1.3's block, which has neither, since no model call ever happened on that path).
- The response-side block's `code` field uses the same highest-confidence-then-scan-order tie-break as 1.3's `_run_request_side_interception`.

**Key invariants** (explicit scope boundaries):
- No escalation check (`cumulative_risk > 0.7 OR strikes >= 3`, Fork #3) gates the block decision — a response-side cheap-tier match blocks unconditionally, same as 1.3's request-side behavior. Escalation logic is Phase 3.2's job.
- No strike-window expiry — Phase 3.1's job; strikes only ever accumulate within the 15-minute session TTL for now.
- The Redis ledger is **not** touched on a clean response — only on a violation. Fork #3's "continuous decay" framing (decaying `cumulative_risk` even on clean turns) is a real, known gap, explicitly deferred to Phase 3.1 (see Follow-up), not silently decided here.
- No medium/expensive tier — cheap tier has no "inconclusive" state (deterministic regex/keyword match or no match), so Fork #4's "if cheap tier inconclusive, run medium/expensive within `latency_budget_ms`" branch doesn't apply yet. Phase 2.4/2.5's job once those tiers exist.
- No regenerate/route behavior on a match — 1.5 only ever hard-blocks with `403`. Regenerate/route requires the escalation trigger (Phase 3.2) and the release-decision logic (Phase 3.4), neither of which exist yet.
- No `fail_open`/`fail_closed` branching — Phase 3.3's job (and doesn't naturally apply here: cheap-tier regex scanning doesn't fail the way a network call can), named for consistency with 1.3/1.4's own scope-boundary discipline.
- Only `pii`/`prompt_injection` are detectable in the response today — `app/evaluators/` doesn't yet cover `toxicity`/`bias`/`custom_policy` (Phase 2.6). A response-side block can currently only ever carry one or both of these two categories.

**Security model**: unchanged from 1.3. A response-side block's body reveals only the triggering category, never the actual (unsafe) model-generated content.

**Configuration required**: none beyond what 0.2/0.3/1.3/1.4 already require.

**Critical test scenarios**:
- Clean prompt → clean response → `200`, real content unchanged, `Execution.execution_risk_score == 0.0`, Redis ledger unchanged. Verifies **AC-1**, **AC-8**.
- A prompt engineered to make the model echo a PII-shaped string verbatim (e.g. "reply with exactly this text: contact me at test@example.com") → `403`, `code: "pii"`, the same `Execution.execution_id` from this call now carries real `tokens > 0`/`latency_ms > 0` plus one new `Finding` (`category=pii`, `evaluator_tier=cheap`), Redis ledger `cumulative_risk` increased and `strikes.pii == 1`. Verifies **AC-2**, **AC-5**, **AC-6**.
- A prompt engineered to make the model echo an injection-style phrase → `403`, `code: "prompt_injection"`, same persistence/ledger shape under `prompt_injection`. Verifies **AC-3**, **AC-5**, **AC-6**.
- A prompt engineered to make the model echo both → `403`, message lists both categories, both `Finding` rows written, both strikes incremented. Verifies **AC-4**, **AC-5**, **AC-6**.
- Every response-side block still carries `X-Workload-Id`/`X-Session-Id`. Verifies **AC-7**.
- 1.2's unknown-workload `400`, 1.3's request-side `403`, and 1.4's model-unreachable `502` all unchanged. Verifies **AC-9**.
- `/health` unaffected. Verifies **AC-10**.

## Build plan

1. Add `_run_response_side_interception` to `app/routers/chat.py`, reusing the module-level `LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD` constants and the existing `get_ledger`/`set_ledger` imports. Satisfies the detection half of **AC-2** through **AC-6**, **AC-8**.
2. Reorder `chat_completions`'s success branch: build `Execution` and `flush()` (not commit) before calling the model response through the new helper; branch on its return. Satisfies **AC-1**, **AC-5**, **AC-7**.
3. Self-check: run the Critical test scenarios above via `curl` against a running `uvicorn` instance backed by the real Neon database, real Upstash Redis, and the real local Ollama instance, inspecting the HTTP response plus the resulting Postgres/Redis state for each. Confirm 1.2/1.3/1.4/`/health` all unaffected. Satisfies **AC-9**, **AC-10**.
4. Log the decisions above (Options 1/3/5 chosen, and the continuous-decay gap) to `decisions.md`.
5. Update `STATUS.md`: check off 1.5, append a Session Handoff Notes entry, set Next Action to Phase 2 as appropriate.

## Consequences

**Positive**:
- The core demo path ("block on cheap-tier PII", per `STATUS.md`'s Notes for the Agent) is now real on both the request and response side, matching Fork #4's full request/response symmetry claim.
- Phase 2.3 is effectively satisfied ahead of its own phase number, same as 2.1/2.2 were by 1.3.
- `Execution.execution_risk_score` now carries a real, meaningful value on every successful call (0.0 or a real score) instead of the `None` placeholder 1.4 left behind — makes Phase 4's audit trail immediately more useful.

**Negative / tradeoffs**:
- The continuous-decay gap (Option 3 vs 4) means `cumulative_risk` still only ever grows or stays flat within a session until Phase 3.1 ships strike-window expiry and (if chosen then) per-turn decay — a session with one early violation and many later clean turns will look riskier than it currently is until 3.1 lands.
- A response-side block is the first place in the codebase where a *blocked* request still carries real `tokens`/`latency_ms` — Phase 4.2's audit trail design should be aware the "was it blocked" and "did it cost tokens/latency" questions are now independent, not correlated the way 1.3's request-side blocks (always null tokens/latency) suggested.
- Only `pii`/`prompt_injection` coverage on output, same evaluator-recall limitation 1.3 already accepted for input.

**Neutral**:
- No automated tests written for this milestone, per `AGENTS.md` Section 8; manual `curl`-plus-database/Redis-inspection self-check only, matching every prior phase.

## Follow-up

- [ ] Phase 3.1 ("Ledger Update Logic") should decide whether `cumulative_risk` should decay on every execution (clean or not), not just on violations — this spec deliberately left that open (Option 3 vs 4) rather than deciding it under the wrong milestone number. Strike-window expiry (also 3.1's job) should land in the same change, since per-turn decay without a bounded strike window is an incomplete implementation of Fork #3.
- [ ] Phase 4.2 ("Execution Persistence") should account for response-side blocks carrying real `tokens`/`latency_ms` unlike request-side blocks — the audit trail's notion of "operational cost" and "was blocked" are independent dimensions from this milestone onward.
- [ ] Phase 2.6 (toxicity/bias/custom_policy) will extend `run_cheap_tier`'s coverage; once it does, response-side blocks automatically gain those categories too, since 1.5 calls the same shared orchestrator 1.3 does — no router change needed then.
