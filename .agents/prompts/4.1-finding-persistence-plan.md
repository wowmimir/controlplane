# 4.1. Finding Persistence

**Date**: 2026-08-24
**Status**: Accepted

## Summary

This milestone required no new persistence code. `STATUS.md` describes 4.1 as: *"Every `Finding` (cheap, medium, expensive; request-side and response-side) written to Postgres, not just Redis. Redis = hot ledger, Postgres = durable record."* By the time 4.1 was reached, this was already true for every evaluator path that can actually produce a finding today: 1.3 built request-side cheap-tier persistence, 1.5 built response-side cheap-tier persistence, and 2.5 built expensive-tier async persistence — each commits `Finding` row(s) to Postgres independently of the Redis ledger write. This is the same shape 2.3 and 3.4 already had (a milestone satisfied by prior work, documented rather than rebuilt).

One real, if currently dormant, bug was found and fixed as part of this milestone: the dead medium-tier-violation branch in `_run_response_side_interception` hardcoded `evaluator_tier=EvaluatorTier.cheap` regardless of which tier actually produced the candidates. Unreachable today (medium tier is a permanent stub returning `[]`), but a direct correctness issue in exactly what 4.1 is about — a medium-tier finding would have been mislabeled as `cheap` the moment medium tier is ever implemented for real. Fixed by tracking `tier` alongside `candidates` in both branches and using it instead of the hardcoded value.

## Context

Verified directly against the current code (`app/routers/chat.py`, pre-fix) for this spec, not just prior session notes:

- **Request-side cheap-tier violation** (`_run_request_side_interception`, lines 298–316): creates `Execution`, `db.add` + `flush`, then one `Finding` per candidate (`evaluator_tier=EvaluatorTier.cheap`, `evidence_ref.side="request"`), `await db.commit()` at line 316 — before the `403` is returned.
- **Response-side cheap-tier violation** (`_run_response_side_interception`, lines 415–425 pre-fix): reuses the `Execution` row 1.4 already created for the model call, sets `execution_risk_score`, writes one `Finding` per candidate, `await db.commit()` — before the `403` is returned.
- **Expensive-tier async finding** (`_run_expensive_tier_task`, lines 476–485): runs after the response has already released, on its own DB session (`async_session()`, not the closed request-scoped session), sets `execution_risk_score`, writes `Finding` row(s) (`evaluator_tier=EvaluatorTier.expensive`), `await db.commit()`.
- **Medium tier** (`app/evaluators/medium.py`): a permanent stub, `run_medium_tier(...)` always returns `[]` (2026-08-23 decision — real hallucination detection lives in the expensive tier instead). The response-side function's medium-tier-violation branch (`chat.py`, then lines 406–421) is structurally present but dead code — it can never execute while the stub stands.
- **Escalation blocks** (request-side pre-check and response-side clean-cheap-tier branch, both call `_escalation_block_response()`): touch only Redis (`apply_ledger_update` with an empty strikes list). No `FindingCandidate` is produced on these paths at all — they block on the session's *already-accumulated* ledger state without scanning this turn's content — so there is nothing to persist to Postgres here. Not a gap in 4.1's scope.
- **`app/redis_client.py`**: confirmed the ledger blob (`cumulative_risk`, `turn`, `strikes`, `strike_events`) is the only thing this module writes; nothing in it touches Postgres, and nothing in `chat.py`'s `Finding`/`Execution` writes touches Redis. The two stores are written independently, matching Fork #3's "Redis = hot ledger, Postgres = durable record" split as actually implemented, not just as designed.
- **The bug**: `_run_response_side_interception`'s `if not cheap_candidates: ... candidates = medium_candidates \n else: candidates = cheap_candidates` block fed a single `Finding`-creation loop that hardcoded `evaluator_tier=EvaluatorTier.cheap`, line 421 (pre-fix), regardless of which branch set `candidates`. Confirmed by direct read before fixing.

`forks.md`'s Consolidated Data Model already defines `Finding.evaluator_tier` as a required field distinguishing `cheap | medium | expensive`; nothing in `forks.md` or the "explicitly not locked" list left this ambiguous — the fix restores what the locked schema already implies, it does not introduce a new decision.

## Requirements

**Verification criteria** (already met by prior milestones, or fixed here; this documents that they are met, not a build to perform):

- **AC-1**: every cheap-tier finding, request-side or response-side, is committed to Postgres before its `403` response is returned. Met — 1.3/1.5.
- **AC-2**: every expensive-tier finding is committed to Postgres in its own background-task transaction, independent of the request's own (already-closed) DB session. Met — 2.5.
- **AC-3**: a medium-tier finding, if one is ever produced, is written to Postgres tagged `evaluator_tier=medium`, not mislabeled as `cheap`. Not met before this milestone (the bug) — fixed here.
- **AC-4**: Redis (the ledger) and Postgres (`Execution`/`Finding`) are written independently, with no conflation between the two stores. Met — confirmed via `redis_client.py`.
- **AC-5**: no code path exists where an evaluator produces a non-empty `FindingCandidate` list that is silently dropped without a Postgres write. Met — every producer (cheap request-side, cheap response-side, expensive) has a corresponding `Finding` + `db.commit()` in the same function or its owning background task; the two escalation-block paths never produce a `FindingCandidate` at all, so they don't fall under this AC.

## Decision

**Chosen option**: No new architectural decision — this documents already-shipped Finding persistence behavior, plus one narrowly-scoped correctness fix (`tier` tracking in `_run_response_side_interception`) directly on-topic for this milestone. Ratified with the user before writing: document as already-built (matching 2.3/3.4's precedent) and fix the hardcoded-tier bug now rather than deferring it as a Follow-up, since it's small and squarely about "every Finding tier written to Postgres correctly."

## Rationale

1.3, 1.5, and 2.5 each independently built the `Finding` persistence their own milestone needed, and all three land on the same shape 4.1 asks for: commit to Postgres, tagged with the correct `evaluator_tier`, independent of the Redis ledger write. Building a second, dedicated "finding persistence layer" now would duplicate already-correct control flow for no reason, against `AGENTS.md`'s guidance not to add abstractions beyond what the task requires — same reasoning 3.4's spec used for an analogous "already satisfied" milestone. The one thing genuinely missing — correct tier attribution on the (currently unreachable) medium-tier branch — is a one-line-scoped bug directly inside this milestone's own subject, so fixing it here rather than deferring it avoids leaving a known, on-topic correctness gap unaddressed under the wrong milestone's name.

## Consequences

**Positive**:
- Phase 4's first milestone closes with a single narrowly-scoped fix and zero new architecture, zero new risk.
- The medium-tier persistence path is now correctly labeled by construction, so if/when medium tier is ever implemented for real, no separate fix is owed at that point.

**Negative / tradeoffs**:
- The medium-tier persistence path (including this fix) cannot be exercised through real traffic today, since the stub never returns a candidate — self-check below verifies it by calling the affected logic directly rather than via a live request. This is a standing limitation of the stub itself (2.4's decision), not new to this milestone.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is a targeted self-check (below) plus the standing regression suite already exercised by prior phases.
