# 2.1. Cheap: PII regex extension

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec extends the cheap tier PII scanner (`app/evaluators/pii.py`, already built and wired into both the request side, 1.3, and the response side, 1.5) to detect two more common shapes of personal data: credit card numbers and IP addresses. A card number is only flagged if it also passes a Luhn checksum (the standard check digit test used by real card numbers), and an IP address is only flagged if every number in it is a valid address segment (0 to 255). Both checks exist so the scanner does not repeat the mistake the phone number pattern made once already: matching on shape alone, then blocking harmless text such as an order number. The plan also formally accepts, rather than chases further, the phone scanner's one remaining known false positive, and it explicitly leaves secret or API key detection for a later milestone, since that kind of value is not personal data about a person.

## Context

`STATUS.md` names the next task as "2.1 Cheap: PII Regex", but 1.3 and 1.5 already shipped a real, reusable PII scanner as part of building the request side and response side blocking path. Today it only covers three shapes: email addresses, US style phone numbers, and social security numbers. `forks.md`'s own closing list marks the exact regex patterns as free to decide during the build, so widening this coverage is fair game, not a locked decision.

Two loose ends already exist against this exact scanner and are explicitly named as this milestone's job to close: the phone pattern still matches a dot separated or space grouped ten digit run that is not really a phone number (for example, a version like string), a gap the prior code review flagged and `decisions.md` deferred here by name. And the taxonomy question of where a secret or API key would even belong (it is not personal data about a person, so it does not fit the `pii` category the way email or phone do) has never been settled.

This is a small, low risk, fully reversible change: two new regex patterns plus one small validation helper in an existing file, no new endpoint, no schema change, and nothing that cannot be undone by reverting the one commit. No migration plan is needed.

## Requirements

**User stories**:
- As the operator of a workload, I want the cheap tier scanner to catch more of the personal data shapes that show up in real prompts and model output, such as card numbers and IP addresses, so the governance story is not limited to the first three shapes chosen for the MVP.
- As the engineer who built 1.3 and 1.5, I want any new pattern to use the exact same `scan()` and `FindingCandidate` shape the scanner already has, so the response side path (1.5, and Phase 2.3's confirmation) inherits it automatically with no router change.
- As an AI application developer integrating with ControlPlane, I do not want an ordinary digit heavy string, such as an order number or a version string, to trigger a policy block just because it happens to look like a card number or an address, so a deterministic validation step should filter out the false shape matches that can be filtered cheaply.

**Acceptance criteria**:
- **AC-1**: A prompt or model response containing a real looking, Luhn valid card number (a recognized network prefix such as Visa, Mastercard, Amex, or Discover, digits only or grouped with spaces or dashes) is detected as a `credit_card` finding.
- **AC-2**: The same digit string with one digit changed so the Luhn checksum fails is NOT flagged as `credit_card`. Proves the checksum step actually filters, not just the shape regex.
- **AC-3**: A prompt or model response containing a real looking IPv4 address (every one of the four numbers between 0 and 255) is detected as an `ip_address` finding.
- **AC-4**: A dotted four number string where at least one number is out of range (over 255) is NOT flagged as `ip_address`.
- **AC-5**: Both new patterns feed `FindingCategory.pii` and are picked up by the existing `run_cheap_tier` orchestrator with no change to `app/evaluators/cheap.py`, `app/evaluators/types.py`, or `app/routers/chat.py` — the same `Execution`/`Finding` write, the same Redis ledger update, and the same `403` envelope shape 1.3/1.5 already use for email/phone/ssn.
- **AC-6**: The phone pattern's known dot separated / space grouped false positive is left as is, not further tightened, and is written into `decisions.md` as a permanent, accepted limitation rather than carried forward again as an open item.
- **AC-7**: No secret or API key detection is added in this milestone. Draft pattern ideas and the reason they are deferred are recorded as a new `STATUS.md` Known Follow up pointing at Phase 2.6.
- **AC-8**: Full regression: 1.1 through 1.5's existing behavior (the original three PII shapes, the five prompt injection phrases, the request side block, the response side block, the `400`/`502` paths) is unaffected.
- **AC-9**: `/health` still returns `200`.

## Options considered

### Option 1: Extend `app/evaluators/pii.py` in place with two new patterns plus a small validator map

Add `ip_address` and `credit_card` to the existing `_PATTERNS` dict in `pii.py`. Since a regex alone cannot express a Luhn checksum, add one small `_luhn_valid(digits)` helper and a `_VALIDATORS: dict[str, Callable]` map that `scan()` consults after a regex match, skipping the candidate if a validator exists for that pattern name and returns false.

**Pros**: Minimal, in keeping with how the file already works (one file, one category, several shape patterns). No new module, no new dependency, no router change.
**Cons**: `pii.py` grows a little, and the validator map is a small new concept alongside the plain pattern dict.

### Option 2: Split card and IP detection into their own new files (e.g. `financial.py`, `network.py`)

**Pros**: Cleaner separation if the file keeps growing with many more shapes later.
**Cons**: Card numbers and IP addresses are still genuinely personal data under the same `pii` category as email, phone, and SSN — unlike a secret or API key, there is no category reason to split them out. Splitting now is indirection with no present benefit, for two more patterns in the same category the existing file already owns.

### Option 3: Use a third party validation library for card numbers instead of a hand written Luhn check

**Pros**: Potentially covers more edge cases (specific issuer rules) than a hand rolled check.
**Cons**: `forks.md`'s locked tech stack table states cheap evaluators are "Regex/rule based only, no ML dependency"; while a Luhn library is not machine learning, adding any new dependency for a ten line, well known checksum algorithm is unjustified. IP range validation is already expressible directly inside the regex itself, needing no library at all.

## Decision

**Chosen option**: Option 1: extend `app/evaluators/pii.py` in place with two new patterns plus a small validator map.

## Rationale

Option 3 is ruled out directly by `forks.md`'s lock on cheap tier evaluators staying regex and rule based with no new dependency; a Luhn check is a ten line function, not a library worth adding. Between Option 1 and Option 2, the deciding force is the category, not the file's size: card numbers and IP addresses belong to the same `pii` category the file already exists to serve, so splitting them into new files buys no clarity today. A genuine category difference, such as a secret or API key not being personal data about a person, is the kind of thing worth a new file and is exactly why that case is deferred to Phase 2.6 rather than folded in here.

## Feature design

**Data model sketch**: no schema change. Reuses `Finding` and `Execution` exactly as defined in 0.2, with two new values appearing in `Finding.evidence_ref.pattern` (`"credit_card"`, `"ip_address"`).

**Changed file**: `app/evaluators/pii.py`.

New pattern (added to `_PATTERNS`, octet range built directly into the regex so an out of range number cannot match at all):
```python
"ip_address": re.compile(
    r"\b(?:(?:25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d)\.){3}(?:25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d)\b"
),
```

New pattern (added to `_PATTERNS`, narrowed to real card network prefixes so it cannot degrade into "any digit run"):
```python
"credit_card": re.compile(
    r"(?<!\d)(?:4\d{3}|5[1-5]\d{2}|3[47]\d{2}|6011|65\d{2})"
    r"[ -]?\d{4}[ -]?\d{4}(?:[ -]?\d{1,4})?(?!\d)"
),
```

New helper and validator map, plus one added conditional in `scan()`'s existing loop (the only control flow change):
```python
def _luhn_valid(digits: str) -> bool:
    total = 0
    for i, ch in enumerate(reversed(digits)):
        d = int(ch)
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0

_VALIDATORS: dict[str, Callable[[str], bool]] = {
    "credit_card": lambda raw: _luhn_valid(re.sub(r"[ -]", "", raw)),
}
```
Inside `scan()`, after a pattern match: if `pattern_name in _VALIDATORS` and the validator returns `False` on the matched text, skip that candidate instead of appending it. Every other pattern (`email`, `phone`, `ssn`, `ip_address`) has no entry in `_VALIDATORS`, so behaves exactly as before.

**No changes**: `app/evaluators/cheap.py`, `app/evaluators/types.py`, `app/evaluators/prompt_injection.py`, `app/routers/chat.py`. `run_cheap_tier` already concatenates `pii.scan()` output regardless of how many patterns `pii.py` defines, and both `_run_request_side_interception` and `_run_response_side_interception` already call it identically on request and response text — this is what makes AC-5 true by construction.

**Value sourcing**:
| Action | Value produced | Source |
|---|---|---|
| `scan(text)`, `credit_card` finding | `evidence_ref = {"pattern": "credit_card", "span": [start, end]}` | regex match span in `text`, gated by `_luhn_valid` on the matched digits |
| `scan(text)`, `ip_address` finding | `evidence_ref = {"pattern": "ip_address", "span": [start, end]}` | regex match span in `text`; octet range already enforced by the pattern itself |
| both new findings | `category` | `FindingCategory.pii` (fixed, matches every existing pattern in this file, per Decision) |
| both new findings | `confidence` | `CONFIDENCE = 0.95` (existing constant, `app/evaluators/types.py`, unchanged) |

**Key invariants**:
- The `_VALIDATORS` gate applies only to patterns that opt in (`credit_card` today); every other pattern's behavior is untouched.
- No new `FindingCategory` value is introduced; the locked six category taxonomy is unchanged.
- The phone pattern's dot separated / space grouped false positive, and the new `ip_address` pattern's symmetrical limitation (a version like string such as `"1.2.3.4"` is indistinguishable from a real address by regex alone), are both accepted permanently, not chased further: dots and spaces are legitimate real formatting for both phone numbers and addresses, so narrowing the pattern enough to exclude the false shape would also exclude real true positives in that same shape.
- Secret or API key detection is out of scope this milestone; see Follow up.

**Security model**: unchanged from 1.3/1.5. A block still reveals only the triggering category in its response body, never the matched text.

**Configuration required**: none.

**Critical test scenarios** (each maps to an acceptance criterion above):
- A prompt containing a Luhn valid test card number (e.g. `4111 1111 1111 1111`) → `403`, `code: "pii"`, `Finding.evidence_ref.pattern == "credit_card"`. Verifies **AC-1**.
- The same digits with the last digit changed (breaks Luhn) → `200`, no block. Verifies **AC-2**.
- A prompt containing a real looking IPv4 address (e.g. `"the server is at 192.168.1.1"`) → `403`, `code: "pii"`, `evidence_ref.pattern == "ip_address"`. Verifies **AC-3**.
- A prompt containing an out of range dotted string (e.g. `"999.999.999.999"`) → `200`, no block. Verifies **AC-4**.
- A prompt clean on input but engineered to make the model echo a Luhn valid card number or a real looking IP in its response → response side `403` on the same `Execution` row 1.5 already creates, carrying real `tokens`/`latency_ms`, plus a new `Finding`. Verifies **AC-5**.
- Full regression pass: clean prompt → `200` unchanged; email/phone/ssn prompts → `403` as before; an injection phrase prompt → `403` as before; unknown workload header → `400`; unreachable model → `502`. Verifies **AC-8**.
- `/health` → `200`. Verifies **AC-9**.

6. Update `STATUS.md`: check off 2.1, add a Session Handoff Notes entry summarizing the two new patterns and the self-check results, remove the now resolved phone regex Known Follow up, add a new Known Follow up for Phase 2.6's secret/API key patterns, and set Next Action to writing the 2.2 spec (Cheap: Prompt Injection Heuristic) next.

## Consequences

**Positive**:
- Real world PII coverage widens (card numbers, IP addresses) with no new dependency and no router change.
- The response side (1.5) inherits both new patterns automatically, since it already calls the same `run_cheap_tier` orchestrator 1.3 does — this effectively extends Phase 2.3's guarantee ahead of its own milestone number, the same way 1.3 already covered part of 2.1/2.2 and 1.5 covered 2.3 itself.

**Negative / tradeoffs**:
- Card and IP detection still cannot distinguish every legitimate look alike (a version string, a non PII dotted decimal value) from the real thing; this is accepted, not solved, and documented as a permanent limitation.
- Secret or API key leakage remains fully undetected until Phase 2.6 builds a `custom_policy` evaluator for it.
- Strikes from these new patterns still accumulate with no window expiry, same limitation every existing pattern already has; Phase 3.1 remains the owner of that fix.

**Neutral**:
- No automated tests written for this milestone, per `AGENTS.md` Section 8; manual `curl` plus database/Redis inspection self-check only, matching every prior phase.
