# 8.3. Finding Feedback Loop + Trust Metric

**Date**: 2026-08-27
**Status**: Proposed

## Summary

The Round 2 rubric's Feedback Loop complexity wants the system to *learn* from
operator corrections, not just detect. Today nothing in the codebase records
whether a `Finding` was right or wrong, and nothing acts on that judgment. 8.3
closes that gap:

1. `Finding.review_status` (`unreviewed` / `confirmed` / `false_positive`), a
   native Postgres enum defaulting to `unreviewed`.
2. `PATCH /api/console/findings/{finding_id}` — set a finding's review status.
3. Confirm / Mark-false-positive controls on each finding in Session Drilldown.
4. A Dashboard "false-positive rate (of reviewed findings)" stat.
5. `GET /api/console/findings` — a filterable finding list, plus a `/review`
   console page listing unreviewed findings with inline Confirm/FP controls, so
   nobody has to trawl sessions one at a time (the brief cites "tens of thousands
   of interactions/week").
6. `GET /api/console/detection-health` — per-pattern confirmed/FP/unreviewed
   counts and FP rate, plus a `/detection-health` console page. A pattern at
   ≥30% FP rate over ≥5 reviewed findings is flagged "needs attention" and gets
   a "Suppress for workload…" control that writes
   `metadata.category_overrides[category].suppressed_patterns` on the chosen
   workload — 8.6's mechanism, extended by one field. This is the actual
   feedback *loop*: a correction fed back into detection.

No behavior change to the proxy path except the new per-pattern suppression
filter at `run_cheap_tier`'s call sites: a suppressed pattern's candidate is
dropped before it becomes a `Finding`, so it produces no finding, no strike, no
block, no ledger contribution for that workload.

Per `STATUS.md`, 8.3 is sequenced **last** in Phase 8 (after 8.6), because the
suppress toggle calls 8.6's `Workload.metadata.category_overrides` mechanism
rather than inventing a second config surface. Core scope (review_status, the
PATCH endpoint, the FP-rate stat) has no dependency; only the suppress toggle
needs 8.6.

**Three decisions ratified with the user before writing this spec:**
1. The Dashboard FP-rate denominator **excludes unreviewed findings**
   (rate = `false_positive / (confirmed + false_positive)`), labeled "of reviewed
   findings" — an unreviewed backlog can't dilute it to a misleading ~0%. This
   clears the "Assumed Decisions Pending Ratification" entry `STATUS.md` flags
   for 8.3.
2. The suppress toggle operates **per pattern**, not per category — 8.3 extends
   the override map 8.6 introduces with a `suppressed_patterns` list, so an
   operator can silence `ip_address` without turning off all of `pii` for that
   workload.
3. Detection Health flags a pattern "needs attention" at **≥30% FP rate with at
   least 5 reviewed findings** for that pattern (agent's call, per the user): a
   pattern wrong in ≥30% of the cases a human actually checked is clearly too
   noisy for cheap tier's unconditional-block behavior; the min-5 floor keeps one
   mislabel from dominating while staying reachable in a seeded demo.

## Requirements

**User stories**
- As an operator reviewing a session, I want to mark a finding right or wrong, so
  my judgment is recorded and counts toward a trust metric.
- As someone assessing whether to rely on ControlPlane, I want to see what share
  of reviewed findings were false positives, so I know how much to trust a block.
- As an operator with thousands of interactions a week, I want one page listing
  every finding still needing review, so I don't have to open sessions one by one.
- As an operator seeing a pattern that's wrong more often than right, I want to
  suppress just that pattern for the workload where it's noisy, without losing
  the rest of that category's coverage.

**Acceptance criteria**
- **AC-1**: `finding` has a real `review_status` column in Postgres (native enum
  `unreviewed` / `confirmed` / `false_positive`, `NOT NULL DEFAULT
  'unreviewed'`); every pre-migration row reads `unreviewed`.
- **AC-2**: `PATCH /api/console/findings/{id}` with `{"review_status":
  "confirmed"}` returns `200` and the updated finding; a direct Postgres check
  shows the new value. Any of the three values is accepted; any transition is
  allowed (including back to `unreviewed`). Unknown id → `404`; invalid value →
  `422`.
- **AC-3**: `GET /api/console/sessions/{id}` surfaces `review_status` on every
  finding in every execution.
- **AC-4**: Session Drilldown shows each finding's review status and, for an
  `unreviewed` finding, a Confirm and a Mark-false-positive control; clicking one
  PATCHes and the row reflects the new status without a full page reload. A
  reviewed finding shows its status with a control to change it.
- **AC-5**: `GET /api/console/summary` returns `reviewed_findings`,
  `false_positive_findings`, and `false_positive_rate` (float 0–1, or `null` when
  `reviewed_findings == 0`); the rate excludes `unreviewed` from the denominator.
  The Dashboard renders it as a stat tile labeled "of reviewed findings."
- **AC-6**: `GET /api/console/findings?review_status=unreviewed` returns
  unreviewed findings only, newest first, each carrying enough context to review
  it (category, confidence, tier, pattern, side, the owning execution's
  disposition, session id, workload id + name, timestamp). Omitting the filter
  returns all findings. `limit` caps the result (default 100).
- **AC-7**: A `/review` console page lists the unreviewed findings from AC-6 with
  inline Confirm / Mark-false-positive controls and a link to each finding's
  session; acting on one removes it from the list.
- **AC-8**: `GET /api/console/detection-health` returns one row per detection
  pattern (`evidence_ref->>'pattern'`, or `<category>:<tier>` for findings
  without a pattern, e.g. the expensive-tier judge), with `confirmed`,
  `false_positive`, `unreviewed` counts, `reviewed` (= confirmed + FP),
  `false_positive_rate` (`null` if `reviewed == 0`), `needs_attention` (true iff
  `false_positive_rate >= 0.30 AND reviewed >= 5`), and `suppressed_by` (list of
  workload ids currently suppressing this pattern).
- **AC-9**: A `/detection-health` console page renders that table, sorted
  FP-rate-desc with `needs_attention` rows visually marked. Each row exposes a
  "Suppress for workload…" control that PATCHes the chosen workload's
  `metadata.category_overrides[<category>].suppressed_patterns` to include the
  pattern; the row then lists that workload under "suppressed by."
- **AC-10**: With `pii` → `suppressed_patterns: ["ip_address"]` set on a
  workload, a request to that workload containing an IP address is **not** blocked
  or flagged for `ip_address`, produces **no** `ip_address` `Finding`, and does
  **not** strike/contribute to that session's ledger — while `email` in the same
  request still blocks as before, and the identical IP against a workload without
  the suppression still blocks. (Verifies the filter runs on both request and
  response sides.)
- **AC-11**: Full regression — `/health` `200`, unknown-workload `400`, a clean
  `balanced` pass-through `200`, request-side and response-side PII blocks still
  `403`, an escalation block still `403`, the Dashboard's existing tiles and
  charts unchanged, `tsc -b` / `npm run build` clean.

## Options considered

### review_status storage

**Option A (recommended): a native Postgres enum column on `finding`**, set via a
manual `CREATE TYPE` / `ALTER TABLE` scratch script. Matches every other
fixed-choice field in this codebase (`Disposition` one milestone ago,
`PolicyProfile` / `FailMode` / `EvaluatorTier` / `FindingCategory`).
Database-level rejection of bad values; `str`-Enum serializes as a plain string
for the console API automatically.

**Option B: a nullable `reviewed_ok: bool` column** — `null` = unreviewed,
`true` = confirmed, `false` = false positive. Smaller. Rejected: a boolean can't
grow a fourth state cleanly, reads worse at every call site, and breaks this
codebase's established one-enum-per-fixed-choice convention for no real benefit.

**Option C: a separate `finding_review` table** (finding_id, status, reviewer,
timestamp). More "correct" for an audit history of who-reviewed-what-when.
Rejected for this hackathon MVP: no auth means no reviewer identity to record,
and a one-to-one side table is pure overhead versus a column when there's no
history requirement. Noted as a follow-up if review provenance is ever needed.

### suppress granularity — per pattern vs per category

**Chosen: per pattern.** Detection Health's whole point is that noise is usually
one pattern (`ip_address`, `fake_role_marker` — both already documented in
`decisions.md` as false-positive-prone), not a whole category. Suppressing all of
`pii` to silence `ip_address` would throw away `email` / `ssn` / `credit_card`
coverage. 8.3 adds a `suppressed_patterns: list[str]` field alongside 8.6's
existing `enabled` / `confidence_floor` in each category entry. The alternative
(reuse 8.6 verbatim, category-only) was rejected by the user directly.

### Detection Health scope — global vs per-workload

**Chosen: global aggregation, per-workload suppression.** The FP-rate table
aggregates across all workloads (a pattern's precision is a property of the
pattern, and per-workload slices would be too sparse to be meaningful in a demo).
The suppress *action* targets one workload, because that's where 8.6's override
lives and because a pattern noisy for one use case may be fine for another.

## Decision

**Chosen option**: Option A, plus per-pattern suppression and global-aggregation
Detection Health as above.

**Implementation skills**: none (no community skill in `AGENTS.md` governs this
area).

### 6. `GET /api/console/detection-health` + `/detection-health` page

One grouped query over `finding`, keyed by
`COALESCE(evidence_ref->>'pattern', category || ':' || evaluator_tier)` ×
`review_status`, plus `category` carried through (a pattern maps to exactly one
category). Aggregate in the handler into:
```
DetectionHealthPattern:
  pattern: str
  category: str
  confirmed: int
  false_positive: int
  unreviewed: int
  reviewed: int
  false_positive_rate: float | None
  needs_attention: bool          # fp_rate >= 0.30 AND reviewed >= 5
  suppressed_by: list[uuid.UUID]  # workloads whose category_overrides suppress this pattern
```
`suppressed_by` comes from scanning every
`Workload.metadata_["category_overrides"]` for `[category]["suppressed_patterns"]`
containing this pattern — small N, done in Python.

Threshold constants at module scope in `console.py`:
```python
DETECTION_HEALTH_FP_THRESHOLD = 0.30
DETECTION_HEALTH_MIN_REVIEWED = 5
```

`console/src/DetectionHealth.tsx` at `/detection-health`: table sorted by
`false_positive_rate` desc (nulls last), `needs_attention` rows marked with an
error-toned accent. Each row has a "Suppress for workload…" control — a
`<select>` of workloads (from `fetchWorkloads`) + a Suppress button that:
1. reads the chosen workload's current `metadata`,
2. sets `metadata.category_overrides[category].suppressed_patterns` to include
   the pattern (creating the nested objects if absent, preserving `enabled` /
   `confidence_floor` and any other categories),
3. calls the existing `updateWorkload(id, { metadata })` PATCH,
4. refetches detection health so `suppressed_by` updates.
An "Unsuppress" affordance next to each entry in `suppressed_by` does the
inverse. Satisfies **AC-8**, **AC-9**.

### 7. Per-pattern suppression filter in the proxy path

8.6 already reads `category_overrides` at (or just before) each `run_cheap_tier`
call in `chat.py` — presumed shape: a helper like
`apply_category_overrides(candidates, overrides)` or category-skip logic in an
`app/evaluators/overrides.py` module. 8.3 adds **one field and one filter**:

- **Field**: each category entry may carry `suppressed_patterns: list[str]`
  alongside 8.6's `enabled` / `confidence_floor`.
- **Filter**: after `run_cheap_tier(text)` returns, drop any `FindingCandidate`
  whose `evidence_ref["pattern"]` appears in
  `category_overrides.get(candidate.category.value, {}).get("suppressed_patterns", [])`.
  Because a dropped candidate never becomes a `Finding`, it produces no strike,
  no block, no ledger contribution for that workload — suppression is total for
  that pattern on that workload.

Concretely, a `_filter_suppressed(candidates, overrides)` function co-located
with 8.6's override code, called at **both** `run_cheap_tier` sites (request-side
L471, response-side L614). If 8.6's actual structure differs from the presumed
shape, adapt to it — the contract that matters is "a per-pattern skip list under
each category entry, honored at both cheap-tier call sites." Satisfies **AC-10**.

## Rationale

`review_status` as a native enum column is the same call 8.2 made for
`Disposition` one milestone earlier — consistency with an established, working
pattern beats re-deciding it. A side table (Option C) buys an audit history this
hackathon build has no requirement for and no reviewer identity to populate.

Excluding unreviewed findings from the FP-rate denominator is what makes the
number *mean* something during a demo: every finding is born `unreviewed`, so a
denominator of "all findings ever" would sit near 0% purely because the backlog
outnumbers the reviewed set, telling you nothing about detector quality. "Of
reviewed findings" is the honest framing and the label says so.

Per-pattern suppression matches where noise actually comes from. The two patterns
most likely to need it (`ip_address`, `fake_role_marker`) are already documented
in `decisions.md` as carrying permanent, accepted false-positive risk —
category-level suppression would be a sledgehammer for a problem that lives in
one regex. Extending 8.6's map by one optional list field is a small,
backward-compatible change (a workload with no `suppressed_patterns` behaves
exactly as 8.6 built it).

Dropping a suppressed candidate *before* it becomes a `Finding` (rather than
tagging it suppressed and filtering at read time) means suppression correctly
cascades to strikes, blocks, and the ledger — the operator's intent is "stop
acting on this pattern here," not just "hide it from a report."

Detection Health aggregating globally while suppressing per-workload reflects
that a pattern's precision is a property of the pattern, but the decision to live
with its noise is a property of the use case.

**Value sourcing**

| Action | Value produced | Source |
|---|---|---|
| Mark a finding | `Finding.review_status` | `PATCH /findings/{id}` body, validated against `ReviewStatus` |
| Dashboard FP rate | `false_positive / (confirmed + false_positive)`, or `null` | grouped count over `finding.review_status`; unreviewed excluded from denominator |
| Review queue rows | finding + execution disposition + session/workload context | `Finding ⨝ Execution ⨝ Session ⨝ Workload`, filtered by `review_status`, newest first |
| Detection Health key | `evidence_ref->>'pattern'`, else `<category>:<tier>` | the finding's own `evidence_ref`; cheap-tier findings always have `pattern`, the judge never does |
| `needs_attention` | bool | `fp_rate >= DETECTION_HEALTH_FP_THRESHOLD (0.30) AND reviewed >= DETECTION_HEALTH_MIN_REVIEWED (5)` |
| `suppressed_by` | list of workload ids | scan of every `Workload.metadata.category_overrides[cat].suppressed_patterns` |
| Suppress action | updated `Workload.metadata` | frontend merges the pattern into `category_overrides[cat].suppressed_patterns`, calls existing `PATCH /workloads/{id}` |
| Proxy-path effect of suppression | fewer `FindingCandidate`s | `_filter_suppressed` drops candidates whose `pattern` is suppressed for the resolved workload, at both `run_cheap_tier` call sites |

**Key invariants**
- A finding's `review_status` is the only thing 8.3 mutates on an existing
  `Finding`; category/confidence/tier/evidence_ref/timestamp are never touched.
- Suppression is enforced at candidate time, so a suppressed pattern is invisible
  to strikes, blocks, the ledger, *and* every console query — there is no
  "suppressed but still recorded" state.
- The FP-rate denominator is always `confirmed + false_positive`; `unreviewed` is
  never in it. `null` (not `0`) when nothing is reviewed.
- Extending `category_overrides` is additive: a workload with no
  `suppressed_patterns` key behaves exactly as 8.6 built it.

**Security model**: unchanged. The console write surface already has no auth
(standing hackathon decision, documented in `README.md`); `PATCH /findings` and
the suppress action join `PATCH /workloads` under that same accepted gap. Marking
a false positive or suppressing a pattern is an operator action with no
caller-facing effect beyond "that pattern stops blocking on that workload," which
is the intent.

**Configuration required**: two module constants in `console.py`
(`DETECTION_HEALTH_FP_THRESHOLD = 0.30`, `DETECTION_HEALTH_MIN_REVIEWED = 5`);
not env-configurable (a hackathon tuning knob, not a deployment setting).

**Critical test scenarios**
- `PATCH` a finding to `confirmed`, then `false_positive`, then back to
  `unreviewed`; Postgres reflects each. Bad id → 404, bad value → 422. → AC-2.
- `GET /sessions/{id}`; every finding carries `review_status`. → AC-3.
- Session Drilldown: click Confirm on an unreviewed finding; row updates, no
  reload; reload the page and it's still confirmed. → AC-4.
- Seed a mix of confirmed/FP/unreviewed findings; `GET /summary` FP rate =
  FP / (confirmed + FP); Dashboard tile matches; with zero reviewed, tile shows
  "—". → AC-5.
- `GET /findings?review_status=unreviewed` returns only unreviewed, newest first,
  with full context; `limit=1` caps it; no filter returns all. → AC-6.
- `/review` page: act on a row, it disappears; empty state when the queue clears.
  → AC-7.
- `GET /detection-health`: force one pattern to 3 FP / 2 confirmed (5 reviewed,
  60%) → `needs_attention: true`; another to 1 FP / 1 confirmed → `false` (below
  min-reviewed). → AC-8.
- `/detection-health`: suppress a needs-attention pattern for the default
  workload; row shows it under "suppressed by"; unsuppress reverses it. → AC-9.
- With `pii.suppressed_patterns = ["ip_address"]` on a workload: send
  `"my ip is 8.8.8.8 and email a@b.com"` → `403` on `email` only, **no**
  `ip_address` finding, session ledger shows no `ip_address` strike; same request
  to the default workload → `ip_address` finding present. Repeat with the IP in
  the model's *response* (crafted prompt) → same result, proving both call sites

## Consequences

**Positive**
- The rubric's Feedback Loop complexity is genuinely addressed: correction in
  (mark FP) → measurement (trust metric) → action (suppress) → detection change.
- A real trust number replaces an implicit "assume every block was right."
- The review queue makes the audit trail usable at the volume the brief cites.
- Per-pattern suppression gives 8.4's differentiated demo workloads another axis
  of real difference, and gives the two known noisy patterns a remedy.

**Negative / tradeoffs**
- Six console pages now; nav is getting wide (accepted — still one row).
- Detection Health aggregates in the handler after a grouped fetch; fine at
  hackathon volume, would need pagination/materialization at real scale
  (follow-up).
- Suppressing a pattern is a genuine coverage cut — a suppressed `ip_address`
  means that workload no longer catches *any* IP address, including a real leak.
  The operator owns that call; Detection Health shows the FP rate they're trading
  against, and `suppressed_by` keeps it visible.
- 8.3 specifies a one-field extension to 8.6's not-yet-built override map. If
  8.6's final shape diverges, step 7 adapts — the spec names the contract, not
  the exact code.

**Neutral**
- No automated tests (AGENTS.md §8); manual `curl` + Postgres/Redis inspection.
- No change to the ledger math, escalation, disposition logic, or the expensive
  tier.
- Marking a finding a false positive does **not** retroactively undo the strike
  or block it already caused (the Redis ledger is likely TTL-expired by review
  time anyway) — suppression changes *future* behavior only. Follow-up.
