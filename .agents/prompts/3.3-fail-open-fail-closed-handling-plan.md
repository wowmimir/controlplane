# 3.3. Fail-Open/Fail-Closed Handling

**Date**: 2026-08-24
**Status**: Accepted

## Summary

Wraps ControlPlane's own request-side and response-side interception logic (Redis, Postgres, and evaluator calls) in error handling, and routes any unhandled internal failure through the resolved workload's `fail_mode` (`fail_open` / `fail_closed`), per `forks.md` Fork #4. Today, an exception anywhere in that path — a dropped Redis connection, a Postgres write failure, a bug in evaluator code — propagates straight to FastAPI's default handler and returns a raw, unstyled `500`, ignoring `Workload.fail_mode` entirely (the field exists on the model and is seeded, but is read nowhere in code). This milestone makes that failure mode deliberate and configurable per workload instead of accidental.

**Explicitly in scope:** exceptions raised anywhere inside `_run_request_side_interception` / `_run_response_side_interception` (Redis calls, Postgres calls, evaluator `scan()` calls).

**Explicitly out of scope, named rather than silently dropped:**
- Model-API failures (`ModelCallError` → `502` via `_model_error_response`) — unaffected, still unconditional per 1.4/Fork #4 ("never routed through `Workload.fail_mode`... explicitly Phase 3.3's job" for ControlPlane's *own* errors, not the upstream model's).
- `_resolve_workload` / `_resolve_session` Postgres failures — these happen *before* a `Workload` row is known, so there is no `fail_mode` to read yet. Remains a raw `500` today; logged as a Follow-up below, not solved here.
- `_run_expensive_tier_task` (the async `BackgroundTasks` callback) — already has its own catch-log-swallow (`except Exception: logger.error(..., exc_info=True)`); it runs after the response has already released, so there is no caller left to route a `fail_mode` decision to. No change.

## Context

- `forks.md` Fork #4: *"Fail-open / Fail-closed: This is a workload-level policy setting (part of the policy profile), not a global constant. If ControlPlane itself errors or times out: `fail_open` (let the response through) or `fail_closed` (block), per workload."*
- `STATUS.md` Phase 3.3: *"Wrap the evaluation call path in error handling; on ControlPlane internal failure, honor the workload's `fail_mode`."*
- `Workload.fail_mode` (`app/models/workload.py`, `FailMode` enum in `app/models/enums.py`: `fail_open | fail_closed`) has existed since Phase 0.4, seeded as `fail_open` for the default workload (`decisions.md`, 2026-08-23: *"A hackathon live demo must not go fully dark if ControlPlane's own internals... hiccup"*), but is read nowhere in the codebase today — this milestone is the first to actually branch on it.
- A direct read of `app/routers/chat.py` and `app/redis_client.py` confirms **zero** existing `try/except` around any Redis call (`get_ledger`, `set_ledger`, `apply_ledger_update`), any Postgres call inside the interception functions (`db.add`, `db.flush`, `db.commit`), or any evaluator call (`run_cheap_tier`, `run_medium_tier`). The only existing exception handling in `chat.py` is the `ModelCallError` catch around `call_model` (lines 78–84, explicitly model-API-scoped, out of this milestone's remit) and `_run_expensive_tier_task`'s own blanket `except Exception` (lines 459–460, background-task-scoped, also out of remit).
- `workload` (the resolved `Workload` object) is already in scope in `chat_completions` (resolved at line 66) and passed as a parameter into both `_run_request_side_interception` (line 229) and `_run_response_side_interception` (line 296) — no new plumbing needed to make `workload.fail_mode` readable at either call site.
- Existing response-builder precedent this milestone follows: `_model_error_response` (`502`, model failures), `_policy_block_response` (`403`, content violation), `_escalation_block_response` (`403`, ledger escalation, 3.2) — all small, zero/low-argument `JSONResponse` builders returning the same OpenAI-style `{"error": {"message", "type", "param", "code"}}` envelope, with the real failure detail logged server-side only (`logger.error(...)`) and a fixed, generic message returned to the caller. `_model_error_response`'s own docstring is explicit about why: echoing raw exception text/upstream detail to an unauthenticated caller is an information-disclosure risk.
- **Ratified with the user** (via `/architect`'s staged design conversation, not silently decided): internal-failure handling wraps each interception call **as a whole** — one `try/except` at each of the two call sites in `chat_completions` — rather than wrapping every individual Redis/DB/evaluator call inside those functions separately. The accepted consequence, surfaced and confirmed explicitly: if an evaluator has already found a real violation (a `Finding` row already committed to Postgres) but the *subsequent* Redis `apply_ledger_update` call then throws, the whole function raises before its `403` is ever returned to the call site — under a `fail_open` workload, that specific turn's request would proceed despite a violation already having been detected and persisted. This is judged an acceptable, narrow, documented edge case for a hackathon build, matching this codebase's existing precedent of accepting similar narrow quirks in writing rather than building more machinery to close them (e.g. 3.1's accepted "same turn's `cumulative_risk` can decay twice" quirk).

## Requirements

- **User stories**:
  - As the operator of a workload configured `fail_open`, I want a ControlPlane-internal failure (Redis, Postgres, or evaluator error) during evaluation to not block my traffic, so a ControlPlane bug or an Upstash/Neon outage doesn't take my application down with it.
  - As the operator of a workload configured `fail_closed`, I want a ControlPlane-internal failure during evaluation to block the request, so ungoverned traffic never silently passes through when ControlPlane can't do its job.
  - As an on-call engineer, I want every internal failure logged server-side with enough detail to diagnose it (which side, which session, the real exception/stack trace), without any of that detail ever reaching the caller.

- **Acceptance criteria**:
  - **AC-1**: An unhandled exception raised anywhere inside `_run_request_side_interception` (Redis, Postgres, or evaluator code) is caught at its call site in `chat_completions`, never reaches FastAPI's default exception handler, and never produces a raw `500`.
  - **AC-2**: Same as AC-1, for `_run_response_side_interception`.
  - **AC-3**: On a caught internal failure, if `workload.fail_mode == FailMode.fail_open`, the request proceeds exactly as if that interception stage had returned `None` (no violation found) — request-side: the model is called normally; response-side: the already-computed response releases to the caller unchanged.
  - **AC-4**: On a caught internal failure, if `workload.fail_mode == FailMode.fail_closed`, the request is blocked with a new `503` response using a distinct OpenAI-style envelope (`type: "controlplane_internal_error"`, `code: "internal_error"`), with a fixed, generic message. No exception detail, upstream error text, or stack trace is ever included in the response body.
  - **AC-5**: Every caught internal failure is logged server-side via `logger.error(..., exc_info=True)`, including which side (request/response) and the session id, regardless of which `fail_mode` branch was taken.
  - **AC-6**: Model-API failures (`ModelCallError` → `_model_error_response`, `502`) are completely unaffected by this change — still unconditional, never routed through `fail_mode`.
  - **AC-7**: Caller-misconfiguration paths (`400` for an unknown workload, `400` for a cross-workload session) are completely unaffected.
  - **AC-8**: A legitimate content-policy block (`403` via `_policy_block_response`, either side) and a legitimate ledger-escalation block (`403` via `_escalation_block_response`) are completely unaffected when the interception function completes normally (returns a value rather than raising) — the new `try/except` only activates on an actual unhandled exception, never on a function that ran to completion and returned its own block response.
  - **AC-9**: `_run_expensive_tier_task` is unchanged — its existing catch-log-swallow behavior is untouched by this milestone; `fail_mode` branching does not apply there since it runs after the response has already released.
  - **AC-10**: `_resolve_workload` and `_resolve_session` are unchanged — a Postgres failure during either still surfaces as a raw `500` today. Not silently accepted as fine — named explicitly in Follow-up below.

## Options considered

### Option 1: Whole-function wrap at the two call sites (recommended)

Wrap `blocked = await _run_request_side_interception(...)` and `blocked = await _run_response_side_interception(...)` each in one `try/except Exception` at their call sites in `chat_completions`. Any exception raised anywhere inside either function — regardless of whether it came from Redis, Postgres, or an evaluator — is caught in exactly one place per side, logged, then routed through `workload.fail_mode`.

- **Pros**: Minimal surface area (2 new `try/except` blocks, 1 new helper function, 1 import). Matches this file's existing precedent of small, explicit helper functions and call-site-level handling (`_model_error_response`'s `try/except ModelCallError` around `call_model` is the exact same shape). Trivial to reason about: "did this interception stage run to completion, yes or no."
- **Cons**: The accepted edge case above (a detected-but-not-yet-ledger-recorded violation can slip through under `fail_open`) — ratified with the user as acceptable for this build.

### Option 2: Granular per-call wrapping inside both interception functions

Wrap every individual Redis call, Postgres call, and evaluator call inside `_run_request_side_interception`/`_run_response_side_interception` in its own `try/except`, so a `Finding` already detected and committed could still force a block regardless of `fail_mode` — only a genuinely inconclusive failure (before any violation was found) would hit the `fail_mode` branch.

- **Pros**: Closes the Option 1 edge case precisely; more "correct" in the sense of never discarding an already-detected violation.
- **Cons**: Touches many more call sites inside both interception functions (at least 5–6 wrap points each), a meaningfully bigger and more error-prone change for a hackathon build. Directly against `AGENTS.md`'s "don't add error handling for scenarios beyond what's needed" and "don't design for hypothetical future requirements" guidance — the failure window this closes (evaluator succeeds, then Redis specifically fails on the very next call) is narrow. Rejected; user confirmed Option 1 during design.

### Option 3: A decorator or context-manager guard

A `@fail_mode_guard` decorator (or `async with fail_mode_guard(workload):` context manager) wrapping both interception functions declaratively, centralizing the catch/log/branch logic in one reusable construct.

- **Pros**: DRY if a third interception stage is ever added.
- **Cons**: Premature abstraction for exactly two call sites — `AGENTS.md`: "three similar lines is better than a premature abstraction." This file has never used a decorator or context manager for this kind of control flow anywhere else (every prior cross-cutting concern — `_policy_block_response`, `_model_error_response`, `_escalation_block_response` — is a small explicit function, not metaprogramming). Rejected.

## Decision

**Option 1: whole-function wrap at the two call sites**, ratified with the user, including the explicit acceptance of its one named edge case.

## Rationale

`forks.md` Fork #4 defines fail_mode at the level of "ControlPlane itself errors" — a coarse-grained concept, not a per-subsystem one. The interception functions are ControlPlane's entire "control layer" for one side of one request; wrapping them as a unit matches the granularity Fork #4 actually describes, without inventing a finer-grained taxonomy of failure types that neither `forks.md` nor `STATUS.md` asks for. `AGENTS.md`'s own guidance ("don't add abstractions beyond what the task requires," "don't design for hypothetical future requirements") argues directly against Option 2's extra machinery for a narrow edge case that's cheaper to document than to engineer around. The edge case itself was surfaced to and confirmed by the user rather than assumed away.

## Feature design

- **Changed file only**: `app/routers/chat.py`. No new file, no schema change, no new environment variable — `fail_mode` and its `FailMode` enum already exist (Phase 0.2/0.4).

- **Import change**: add `FailMode` to the existing line `from app.models import EvaluatorTier, Execution, Finding, Session, Workload` → `from app.models import EvaluatorTier, Execution, FailMode, Finding, Session, Workload`.

- **New helper**, placed beside `_escalation_block_response()`:

  ```python
  def _internal_error_response() -> JSONResponse:
      """A ControlPlane-internal failure (Redis, Postgres, or evaluator code)
      on a fail_closed workload -> 503. Distinct type/code from
      _model_error_response (502, the upstream MODEL API failed) and from
      _policy_block_response/_escalation_block_response (403, a real policy
      decision was made) - this means ControlPlane itself could not complete
      its own evaluation. The real exception is logged server-side only
      (see the call sites in chat_completions); this body is always the
      same fixed, generic message. See
      .agents/prompts/3.3-fail-open-fail-closed-handling-plan.md.
      """
      return JSONResponse(
          status_code=503,
          content={
              "error": {
                  "message": "ControlPlane encountered an internal error while evaluating this request.",
                  "type": "controlplane_internal_error",
                  "param": None,
                  "code": "internal_error",
              }
          },
      )
  ```

- **Call-site change #1**, in `chat_completions`, replacing the current bare call:

  ```python
  try:
      blocked = await _run_request_side_interception(db, session, workload, request)
  except Exception:
      logger.error(
          "request-side interception failed for session %s", session.session_id, exc_info=True
      )
      blocked = _internal_error_response() if workload.fail_mode == FailMode.fail_closed else None
  if blocked is not None:
      blocked.headers["X-Workload-Id"] = str(workload.workload_id)
      blocked.headers["X-Session-Id"] = str(session.session_id)
      return blocked
  ```

- **Call-site change #2**, same shape around the `_run_response_side_interception` call (log message says `"response-side"` instead of `"request-side"`). No other line in `chat_completions` changes — the existing `if blocked is not None: ...` handling immediately after each call site is reused unmodified, since both branches still produce either `None` or a `JSONResponse`, exactly the type that code already expects.

- **Value sourcing**:

  | Action | Value produced | Source |
  |---|---|---|
  | Decide fail_open vs fail_closed on internal failure | `workload.fail_mode` | Already-resolved `Workload` row (Postgres), no new lookup |
  | Fail-closed response status/envelope | `503` / `controlplane_internal_error` / `internal_error` | New fixed constant, this spec |
  | Server-side diagnostic detail | real exception + traceback | `exc_info=True` on the new `logger.error(...)` calls |

- **Key invariants**: exactly one blocked-or-not decision per interception stage per request (unchanged from today — the `try/except` only changes *how* that decision can be reached, not how many times it's made); a caught exception never propagates past `chat_completions`; the log call always fires on a catch, regardless of which `fail_mode` branch is taken.

- **Security model**: no exception message, stack trace, or internal detail (Redis host, SQL error text, etc.) is ever included in the `503` response body — matches `_model_error_response`'s existing precedent exactly.

- **Configuration required**: none new. `fail_mode` is already a column on `Workload`, already seeded.

- **Critical test scenarios** (each maps to an AC, detailed under Build plan step 5 below):
  1. Force an exception inside request-side interception on the default (`fail_open`) workload → `200`, no `500`, log line present. (AC-1, AC-3, AC-5)
  2. Force an exception inside response-side interception on the default (`fail_open`) workload → `200` with the already-computed response, log line present. (AC-2, AC-3, AC-5)
  3. Same two scenarios against a temporary `fail_closed` workload → `503`/`code:"internal_error"`, no leaked detail, log line present. (AC-2, AC-4, AC-5)
  4. Full regression: `200` clean pass-through, `403` content block (both sides), `403` escalation block, `400` unknown workload, `400` cross-workload session, `502` model-unreachable — all unaffected. (AC-6, AC-7, AC-8)
  5. Confirm `_run_expensive_tier_task` code is untouched (diff review, no live test needed — this milestone makes no change there). (AC-9)
  6. Note (not tested further, named for the record): `_resolve_workload`/`_resolve_session` failures remain raw `500`s, unchanged by this milestone. (AC-10)

## Consequences

- **Positive**: Closes the last unimplemented piece of Fork #4's `fail_mode` design — every unhandled exception in the evaluation/ledger path now has a deliberate, per-workload-configurable outcome instead of an accidental raw `500`. The two new `logger.error` call sites partially advance the standing "add real structured logging beyond the one existing call" Follow-up named in `STATUS.md` since the 2026-08-23 review (not a full close — see Follow-up below).
- **Negative / tradeoffs**: The accepted Option 1 edge case — a detected-but-not-yet-ledger-recorded violation can slip through under `fail_open` if the Redis write specifically fails right after a Postgres `Finding` commit. A mid-function partial failure can leave Postgres (the `Finding` row committed) and Redis (the ledger not updated) inconsistent for that one turn — not reconciled by this milestone. Workload/session resolution failures remain raw `500`s (AC-10), a real, named gap.
- **Neutral**: No automated tests written, per `AGENTS.md` Section 8 — live `curl` plus a forced-exception script plus direct Postgres/Redis inspection, matching every prior phase's self-check style.

## Follow-up

- [ ] `_resolve_workload`/`_resolve_session` Postgres failures still surface as raw `500`s — no `Workload` row is known yet at that point in the request to read `fail_mode` from. A future revisit would need either a global fallback `fail_mode` default or an explicit decision to treat total DB unavailability as always-fail-closed regardless of any per-workload setting.
- [ ] The Postgres/Redis partial-failure inconsistency accepted in this milestone (a `Finding` committed but the ledger never updated) is not reconciled — revisit if Phase 4 (Audit Trail) surfaces a real mismatch between the two stores.
- [ ] The broader "add real structured logging beyond isolated `logger.error` calls" Follow-up (named in `STATUS.md`'s Known Follow-ups since the 2026-08-23 review) is only partially advanced by this milestone's two new log sites — a real logging story (structured fields, correlation ids across a request) is still owed, deferred to Phase 4 or a dedicated pass.
