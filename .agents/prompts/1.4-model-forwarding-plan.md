# 1.4. Model forwarding

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec replaces the hardcoded stub response at the end of `POST /v1/chat/completions` with a real forward to a model API. A new `app/model_client.py` module owns the HTTP call (a singleton `httpx.AsyncClient` posting to `{MODEL_API_BASE_URL}/chat/completions`, OpenAI-compatible shape, non-streaming). On success, the router persists an `Execution` row with real operational signals (`tokens`, `latency_ms`) and returns the real model response. On failure (unreachable, non-2xx, unparseable), the router returns `502` with an OpenAI-style error envelope, unconditionally — no `Execution` row, no `fail_mode` branching. 1.3's block path and 1.2's config-error paths are untouched.

## Context

`STATUS.md`'s 1.4 line: "Forward the (unblocked) request to the real model API (OpenAI or Anthropic). Non-streaming only (Fork #4)." `app/routers/chat.py`'s own docstring already flagged the stub as this milestone's target: "No real model call (1.4) yet - a clean prompt still falls through to the stub response."

One gap had to be resolved before building, not just wired up: **`forks.md` Fork #4 leaves the provider choice open** ("OpenAI or Anthropic") and no provider/model-routing field exists anywhere in the schema or `Workload` model (confirmed: `app/models/workload.py` has `policy_profile`, `latency_budget_ms`, `cost_budget_per_request`, `fail_mode`, `metadata_` — no `provider`/`model` column). The user ratified directly: **Ollama**, local, zero-cost, exposed via its OpenAI-compatible `/v1/chat/completions` endpoint at `http://localhost:11434/v1`, default test model `minimax-m3:cloud`, no API key required. Because `ChatCompletionRequest`/`ChatCompletionResponse` (`app/schemas/chat.py`) already mirror OpenAI's shape exactly (per 1.1's design), and Ollama speaks that same shape, this becomes close to a direct passthrough with no translation layer — the base URL/key stay env-configurable so swapping providers later needs no code change.

No `httpx` (or any HTTP client / model SDK) was installed anywhere in the project before this milestone — confirmed absent from `pyproject.toml` and `uv.lock`.

## Requirements

**User stories**:
- As the operator of a workload, I want a clean (non-blocked) prompt to receive a real model response, so the proxy is actually useful and not just a pass-through stub.
- As the engineer building 1.5 next, I want the model-call logic to already be a reusable async function, so response-side interception can call it without duplicating HTTP/parsing code.
- As an AI application developer integrating with ControlPlane, I want a model-API failure to look like a normal upstream-gateway error (OpenAI-style envelope, sensible status code), not a raw stack trace or an ambiguous `200`.

**Acceptance criteria**:
- **AC-1**: A clean prompt (passes 1.3's interception) returns `200` with a real model-generated `ChatCompletionResponse` — real `content`, real `usage`, not the old stub sentence.
- **AC-2**: The outbound request to the model API always sets `"stream": false` explicitly in the JSON body.
- **AC-3**: If `MODEL_API_KEY` is unset/empty, no `Authorization` header is sent. If set, `Authorization: Bearer <key>` is sent.
- **AC-4**: A connection failure/timeout reaching `MODEL_API_BASE_URL`, a non-2xx response from it, or a response too malformed to map onto `ChatCompletionResponse`, all return `502` with an OpenAI-style `{"error": {...}}` envelope — never a raw `500`, never routed through `Workload.fail_mode`.
- **AC-5**: No `Execution` row is created on any failure path in AC-4. Exactly one `Execution` row is created on the AC-1 success path.
- **AC-6**: The `Execution` row's `tokens` reflects the real `usage.total_tokens` from the model response, `latency_ms` reflects wall-clock time of the outbound HTTP call only, `retries=0`, `tool_loop_count=0`, `execution_risk_score=None`.
- **AC-7**: 1.3's block path (`403`) and 1.2's config-error paths (`400`) are unaffected by this change.
- **AC-8**: `/health` still returns `200`.
- **AC-9**: Swapping to a different OpenAI-compatible provider later requires only changing `MODEL_API_BASE_URL`/`MODEL_API_KEY` — no code change.

## Options considered

### Option 1: New `app/model_client.py` module (recommended, ratified with user)

Houses the `httpx.AsyncClient` singleton, request/response translation, and typed exceptions. Router imports `call_model()`.

**Pros**: Directly reusable by 1.5 (sits immediately downstream of this exact call) and later Control actions (retry/regenerate/route); keeps `chat.py` focused on orchestration, matching the separation 1.3 already established for evaluators.
**Cons**: One more file for what is, today, a single call site.

### Option 2: Inline in `app/routers/chat.py`

**Pros**: Fewer files right now.
**Cons**: 1.5 would need to extract this logic out again almost immediately — repeats the exact tradeoff Option 2 lost to in 1.3's own plan.

### Option 3: `ChatCompletionResponse.model_validate(json)` for response mapping

**Pros**: Less code.
**Cons**: Our schema's fields are all required/non-`Optional`. If the model API's response omits or reshapes `usage`/`choices` even slightly, `model_validate` raises an opaque `ValidationError` (-> `500`) instead of AC-4's clean `502` — a parsing bug masquerading as a server crash.

### Option 4: Field-by-field response construction with `.get(...)` fallbacks (recommended, ratified with user)

**Pros**: Any missing/malformed field degrades to a typed `ModelResponseInvalidError` (-> `502`) instead of a crash. Matches AC-4's failure-handling contract exactly.
**Cons**: More verbose than `model_validate`.

## Decision

**Chosen**: Option 1 (`app/model_client.py`) + Option 4 (field-by-field response construction). Model provider is **Ollama**, `http://localhost:11434/v1`, OpenAI-compatible shape, no translation layer.

## Rationale

Same discipline 1.3 already applied: build the reusable piece as its own module now rather than defer extraction to 1.5, since 1.5 is the very next milestone and sits directly downstream of this exact call. Field-by-field construction is the only option that actually satisfies AC-4's "malformed response -> clean 502, not a raw 500" requirement, since our schema's required fields give `model_validate` no room for a partial/lenient parse.

## Feature design

**Data model sketch**: no schema change. Reuses `Execution` exactly as defined in 0.2, now writing to `tokens`/`latency_ms` for the first time (previously only `execution_risk_score` was ever set, by 1.3's blocked path).

**New file**: `app/model_client.py` —
- Module-level `load_dotenv()` + `MODEL_API_BASE_URL = os.environ.get("MODEL_API_BASE_URL", "http://localhost:11434/v1")`, `MODEL_API_KEY = os.environ.get("MODEL_API_KEY") or None` — deliberately `.get()`-based, not the bracket-required `os.environ[...]` pattern `app/db.py`/`app/redis_client.py` use, since both are meant to be optional/defaulted here (documented deviation, not an oversight).
- Module-level singleton `httpx.AsyncClient(timeout=httpx.Timeout(120.0, connect=5.0))` — matches the existing singleton pattern for `engine`/`redis_client`; 120s because local LLM inference (especially an Ollama "cloud" model tag) can be slow, deliberately distinct from `Workload.latency_budget_ms` (Fork #4: evaluator governance overhead only, never the outbound model-call timeout).
- `ModelCallError` base + `ModelUnreachableError` / `ModelAPIError` / `ModelResponseInvalidError` subclasses, each with a `.code` used directly in the error envelope's `code` field.
- `async def call_model(request) -> tuple[ChatCompletionResponse, int]`: builds `{"model", "messages", "stream": False}` explicitly (AC-2), attaches `Authorization` only if `MODEL_API_KEY` is set (AC-3), measures wall-clock time around just the `httpx.post(...)` call, raises `ModelUnreachableError` on `httpx.RequestError`, `ModelAPIError` on non-2xx, and constructs the response field-by-field (raising `ModelResponseInvalidError` on `KeyError`/`IndexError`/`TypeError`/`ValueError`).

**Changed file**: `app/routers/chat.py` — the stub `return ChatCompletionResponse(...)` block is replaced with a `try/except ModelCallError` around `call_model(request)`:
1. On `ModelCallError` → build the `502` envelope via `_model_error_response(exc)`, attach `X-Workload-Id`/`X-Session-Id` headers (same pattern as the 1.3 block-path headers), return it. No DB write.
2. On success → `db.add(Execution(...))` with `tokens=parsed.usage.total_tokens`, `latency_ms` from `call_model`'s return, `retries=0`, `tool_loop_count=0`, `execution_risk_score=None`; commit; return `parsed` directly (FastAPI serializes it against the declared `ChatCompletionResponse` return type).

A new module-level `_model_error_response(exc) -> JSONResponse` helper returns `502` with `{"error": {"message", "type": "controlplane_upstream_error", "param": None, "code": exc.code}}` — mirrors 1.3's `403` envelope shape exactly, but with its own `type`/status code so a client can distinguish "policy blocked you" (`403`) from "the model API itself failed" (`502`) from "you misconfigured the call" (`400`).

**Value sourcing**:
- `Execution.latency_ms` = wall-clock time of only the `httpx.post(...)` call inside `call_model`, not total request time, not 1.3's evaluator time, not the DB commit. `forks.md` doesn't split model-call-latency from total-request-latency explicitly, so this is a deliberate, logged interpretation — `Workload.latency_budget_ms` remains reserved for governance overhead only (Fork #4) and is not read or compared against anywhere in this milestone.
- `Execution.tokens` = `parsed.usage.total_tokens` as reported by the model API (`0` if genuinely absent from its response — the `.get(..., 0)` fallback in `call_model`, not a crash).

**Key invariants**:
- A model-call failure never inspects `Workload.fail_mode` — always `502`, unconditionally. Fork #4 scopes fail_open/fail_closed to "ControlPlane itself" erroring or timing out (Phase 3.3's explicit job); a model-API failure is a different failure class (the upstream provider, not ControlPlane's own internals).
- `Execution` rows are created **only** on the success path in this milestone — same "only log what concretely happened" precedent 1.3 set for its blocked path. A failed model call produces no `Execution` row. Phase 4.2 ("every Execution logged... regardless of whether it was blocked") is the explicit future owner of deciding whether failed-call attempts also deserve a row.
- No retry logic exists yet — `retries` is hardcoded `0`. No tool-calling exists in the schema — `tool_loop_count` is hardcoded `0`. Both are placeholders for later phases.
- `execution_risk_score=None` because nothing evaluates the model's actual output yet — that's 1.5's job (reusing 1.3's `run_cheap_tier`, per that module's own docstring). 1.4 must not invent a score for a response nothing has scanned.
- `"stream": false` is set explicitly in the outbound payload even though today's `ChatCompletionRequest` schema has no way to request streaming — belt-and-suspenders enforcement of Fork #4's non-streaming lock against a future schema change.

**Security model**: unchanged from 1.1–1.3. `MODEL_API_KEY` (when set) is read from `.env` server-side only, never exposed to the caller; the `502` error body reveals only a generic message/code, never raw upstream response bodies beyond a truncated 500-char slice used internally for the exception message (not echoed to the caller — the caller only ever sees `exc.message`, which for `ModelAPIError` includes that truncated slice; acceptable since this is a local Ollama instance the operator controls, not a third-party secret-bearing API in the MVP's actual demo configuration).

**Configuration required**: `.env` additions —
```
MODEL_API_BASE_URL=http://localhost:11434/v1
# MODEL_API_KEY=          # optional; only needed against a real hosted provider
```
New dependency: `httpx` (via `uv add httpx`). No OpenAI/Anthropic SDK — a raw `httpx` POST is sufficient since Ollama's endpoint already speaks the shape needed, and a full provider SDK would add unjustified surface area for a single POST call while tying the code to one vendor's client library rather than the plain-HTTP OpenAI-compatible contract `AGENTS.md` §5 already standardizes on.

**Critical test scenarios**:
- Clean prompt → `200`, real model-generated content, `X-Workload-Id`/`X-Session-Id` headers present, exactly one new `Execution` row with `tokens`/`latency_ms` populated and `execution_risk_score IS NULL`. Verifies **AC-1**, **AC-6**.
- Model API unreachable → `502`, `code: "model_unreachable"`, headers still present, no new `Execution` row. Verifies **AC-4**, **AC-5**.
- Model API reachable but errors (e.g. unpulled model name) → `502`, `code: "model_api_error"`, not an unhandled `500`. Verifies **AC-4**.
- 1.3's block path (email-containing prompt) unchanged `403`/`code: "pii"`. Verifies **AC-7**.
- 1.2's unknown-workload path unchanged `400`. Verifies **AC-7**.
- `/health` unaffected. Verifies **AC-8**.

## Build plan

1. `uv add httpx`; add `MODEL_API_BASE_URL`/`MODEL_API_KEY` to `.env`. Satisfies **AC-9**'s configuration surface.
2. Create `app/model_client.py` per Feature design above. Satisfies **AC-2**, **AC-3**, the raising half of **AC-4**.
3. Update `app/routers/chat.py`: adjust imports, replace the stub block with the try/except + `Execution` persistence + return flow, add `_model_error_response`, update the module docstring. Satisfies **AC-1**, the handling half of **AC-4**, **AC-5**, **AC-6**.
4. Self-check against a real running Ollama instance (clean pass, unreachable, non-2xx, plus 1.2/1.3 regression checks and `/health`). Confirms **AC-1** through **AC-8** concretely.
5. Log the ratified decisions to `decisions.md`.
6. Update `STATUS.md`: check off 1.4, append a Session Handoff Notes entry, set Next Action to 1.5 Response-Side Interception.

## Consequences

**Positive**:
- The core demo path is now end-to-end real: block-on-cheap-tier (1.3) *and* forward-to-real-model (1.4) both work against live infrastructure.
- `call_model()` is immediately available for 1.5 to import without any rework.

**Negative / tradeoffs**:
- The `httpx.AsyncClient` singleton is never explicitly closed on shutdown — same omission already present for `engine`/`redis_client`, acceptable at hackathon speed but worth a Follow-up.
- The `120s` timeout and Ollama's actual `usage`-reporting behavior are judgment calls until the self-check runs against the real `minimax-m3:cloud` model.

**Neutral**:
- No automated tests written, per `AGENTS.md` §8; manual `curl`-plus-database-inspection self-check only, matching every prior phase.
