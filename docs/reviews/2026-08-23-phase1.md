# Review, phase1, 2026-08-23

**Reviewed by**: claude-opus-5 (author on a prior Claude Code session, model not recorded)
**Scope**: 18 files (excl. `uv.lock`), branch `phase1` vs `main` (merge-base `0f93986`), incl. uncommitted + untracked
**Verdict**: Changes requested

## Summary

This branch takes `POST /v1/chat/completions` from a stub to a real governed proxy: workload/session resolution against Neon (1.2), cheap-tier request-side interception with Redis ledger updates (1.3), a real Ollama forward via a new `app/model_client.py` (1.4), and response-side interception that reuses the same `Execution` row (1.5). The core flow is correct — I traced every branch and found no bug that releases unsafe content or calls the model on a blocked request, so `AGENTS.md` §6's hard rule holds on both sides. The 1.5 reordering (build `Execution` → `flush()` → scan → single `commit()`) is the right shape and is implemented cleanly.

Two things should be fixed before merge: the `502` envelope echoes the raw upstream error body and the internal model base URL to any (unauthenticated) caller, and persisted `Finding` rows carry no record of *which side* produced them — audit information that is lost at write time and cannot be backfilled. The rest are minors, mostly latent edges and one real evaluator false-positive class that response-side blocking now makes user-visible.

## Major

### 🟠 The `502` envelope leaks the raw upstream error body and the internal model base URL to the caller, `app/routers/chat.py:101`

**Problem**: `_model_error_response` interpolates `exc.message` straight into the response body. For `ModelAPIError` that message contains `resp.text[:500]` — 500 raw bytes of the upstream provider's error body (`app/model_client.py:53`, `:82`). For `ModelUnreachableError` it contains `MODEL_API_BASE_URL` plus the httpx exception text (`app/model_client.py:78`). The endpoint has no authentication, so this reaches any caller.

The 1.4 spec's Security model section does acknowledge this ("acceptable since this is a local Ollama instance the operator controls"), but that acceptance is explicitly conditioned on the current local-Ollama deployment, while **AC-9 of the same spec promises that swapping to a hosted provider requires only an env change, no code change**. The moment `MODEL_API_BASE_URL` points at OpenAI/Anthropic, this becomes live information disclosure with nothing in the code guarding it, and there is no Follow-up item tracking it (the 1.4 Follow-up list has four entries, none about this).

**Why it matters**: Hosted-provider error bodies routinely carry org/project identifiers, quota and billing state, model-availability details, and on auth failures a partially-redacted key fragment — all straight into an unauthenticated response. The unreachable case additionally discloses internal network topology (host/port) on the easiest-to-trigger failure path.

**Suggested fix**: Split the exception's internal detail from its caller-facing text. Keep the full `resp.text[:500]` / base URL on the exception for server-side logging (there is currently no logging at all — see nits), and have `_model_error_response` emit a fixed generic message per `exc.code` ("the upstream model API was unreachable" / "the upstream model API returned an error"). The `code` field already gives clients everything they need to branch on.

### 🟠 `Finding` rows don't record which side produced them, and `evidence_ref` spans index text that is never stored, `app/routers/chat.py:180-187` and `:241-249`

**Problem**: The request-side and response-side helpers write structurally identical `Finding` rows — same `category`, same `confidence` (`0.95` always), same `evaluator_tier`, and an `evidence_ref` of `{pattern, span}`. Nothing in the row says whether the match came from the caller's prompt or the model's output. The only discriminator today is indirect: a request-side block leaves `Execution.tokens`/`latency_ms` null. The 1.5 spec itself flags that this correlation is exactly what Phase 4.2 will break ("'was it blocked' and 'did it cost tokens/latency' are now independent dimensions"), yet leaves that correlation as the sole means of telling the two apart.

Separately, `span` is a character offset into a text blob that is never persisted anywhere (the joined prompt on one side, `choices[0].message.content` on the other), so the offset is unresolvable after the fact even if you knew which side it belonged to.

**Why it matters**: This is the audit trail — the product's stated defensibility story. Phase 5.3 ("Session Drilldown — demonstrates the 'why did this get blocked' story") cannot answer the single most important governance question about a `pii` finding: did the *user* send PII, or did the *model* leak it? Those are completely different incidents with different remediations. Unlike the deliberately-deferred gaps in this branch (escalation trigger, strike-window expiry, fail_mode), this one is lossy at write time — it cannot be backfilled once Phase 4/5 need it.

**Suggested fix**: Add the provenance to `evidence_ref`, which is already a free-form JSONB dict and needs no schema change: `{"side": "request" | "response", "pattern": ..., "span": [...]}`. Have each helper pass its side through when building the `Finding`. If the span is meant to stay useful, also store the matched substring (or a redacted/hashed form) rather than a bare offset — otherwise consider dropping `span` so it doesn't read as more evidence than it is.

## Minor

### 🟡 `AttributeError` escapes `call_model`'s except tuple, producing the raw `500` AC-4 forbids, `app/model_client.py:115`

**Problem**: The parse block catches `(KeyError, IndexError, TypeError, ValueError)`. If the upstream returns a well-formed JSON object whose `choices[0]` or `choices[0].message` is a non-dict (a bare string, a list), the `.get(...)` call raises `AttributeError`, which is not in the tuple and propagates out of the router as an unhandled `500`. Verified: `{"choices":[{"message":"plain string"}]}` raises `AttributeError: 'str' object has no attribute 'get'` past this handler.

**Why it matters**: 1.4's AC-4 is explicit — "a response too malformed to map onto `ChatCompletionResponse` … return `502` … never a raw `500`". This is precisely the case Option 4 (field-by-field construction) was chosen to prevent, and it slips through the narrow escape hatch. Trigger is a non-conforming upstream rather than an attacker, so impact is degraded error reporting, not a hole.

**Suggested fix**: Add `AttributeError` to the tuple, or catch `Exception` for the whole parse block — the block does nothing but map fields, so a blanket catch here is safe and matches the intent stated in the spec.

### 🟡 The phone regex matches any bare 10-digit run, and response-side blocking now makes that a user-visible hard failure, `app/evaluators/pii.py:17`

**Problem**: Every separator in `\b(?:\+?1[-.\s]?)?\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}\b` is optional, so the pattern reduces to "any 10 consecutive digits". Verified matches: `Order id 1234567890`, `total 9876543210 bytes`, `version 1.234.567.8901`, `ref 123 456 7890`. (Credit-card-length runs and comma-grouped numbers correctly don't match, so the boundary handling itself is fine.)

**Why it matters**: On the request side (1.3) a false positive cost the caller one blocked prompt. Since 1.5, the *model's* output is scanned with the same pattern and a match withholds the entire response after the tokens have already been paid for — so any answer containing an order id, a build number, a large integer, or a dotted version string is hard-blocked with no way for the caller to see what happened, plus a permanent `pii` strike on the session. Ask the model for a 10-digit number and you get a `403`.

`forks.md` explicitly leaves exact patterns unlocked and the 1.3 spec calls this a deliberately minimal set, so this isn't a spec violation — but the *false-positive* direction was only reasoned about as acceptable for input, and the 1.5 change silently raised its cost. Worth naming now since Phase 2.1 (the next milestone) owns this file.

**Suggested fix**: Require at least one separator or a leading `+1`/parenthesized area code so bare digit runs don't match, and treat this as a concrete input to 2.1's pattern work.

### 🟡 Strikes increment per finding, so one turn can hit Phase 3.2's 3-strike threshold on its own, `app/routers/chat.py:192-194` and `:256-258`

**Problem**: `strikes[category] += 1` runs once per candidate, not once per execution. A model response listing three email addresses writes three `pii` findings and increments `strikes.pii` by 3 in a single turn.

**Why it matters**: Fork #3's escalation trigger is `any strikes[category] >= 3`, and the strike counter's whole purpose is to measure *repeated* misbehavior across turns. A single response containing a contact list would trip it immediately — the multi-turn signal collapses into a single-turn one, and Phase 6.1's "ledger-driven multi-turn escalation" demo becomes hard to stage predictably. The 1.3 spec reasons carefully for the per-finding reading of Fork #3's literal wording and I agree it's defensible, but this consequence isn't noted anywhere, and 1.5 amplifies it (model output is far likelier than a prompt to contain several matches of one category).

**Suggested fix**: Either cap the increment at one per category per execution, or leave it as-is and add an explicit note to the Phase 3.1/3.2 follow-ups so the escalation work re-litigates it deliberately rather than inheriting it.

### 🟡 `_resolve_workload` can return `None` and is dereferenced unguarded, `app/routers/chat.py:113`

**Problem**: The no-header branch does `return await db.get(Workload, DEFAULT_WORKLOAD_ID)` with no `None` check, unlike the explicit-id branch below it. If the seeded default row is ever absent, `chat_completions` immediately hits `workload.workload_id` (`:52`) and raises `AttributeError` → unhandled `500`.

**Why it matters**: Unreachable today because `seed_default_workload()` runs in the lifespan — but Phase 5.2 is a workload management view with create/edit/list (and presumably delete), and the sentinel row has nothing marking it undeletable. A deleted default turns every header-less request into an opaque `500` instead of a diagnosable error. The type annotation `-> Workload` also claims a guarantee the body doesn't provide, which typecheck won't catch here since `db.get` is loosely typed.

**Suggested fix**: Check for `None` and raise a `500`-with-explanation or re-seed on the fly; at minimum make the failure legible rather than an `AttributeError`.

### 🟡 The ledger update and `403` envelope are duplicated verbatim across both interception helpers, `app/routers/chat.py:190-212` vs `:252-276`

**Problem**: ~25 lines are near-identical between `_run_request_side_interception` and `_run_response_side_interception`: the `get_ledger` → decay → per-candidate strike loop → `set_ledger` sequence, the `primary`/`categories` derivation, and the `403` JSON envelope. Only the message wording differs. The 1.5 spec was careful to share the `LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD` *constants*, but not the logic that uses them.

**Why it matters**: Two upcoming milestones edit exactly this code. Phase 3.1 changes the ledger math (window expiry, possibly per-turn decay) and Phase 2.6 adds categories — both must now be applied twice, in two places that are easy to let drift. A silent divergence between how request-side and response-side findings feed the ledger would directly violate Fork #4's "input and output are NOT treated differently".

**Suggested fix**: Extract two small helpers — `_update_ledger(session_id, execution_risk_score, candidates)` and `_policy_block_response(candidates, *, side)` — and have both interception functions call them. This is also the natural seam for the `side` marker from the Major finding above, and gives Phase 3.1 a single place to land the real ledger logic.

### 🟡 Workload and session identity are caller-asserted with no auth, which will make the ledger trivially evadable once escalation lands, `app/routers/chat.py:45-46`, `:121-152`

**Problem**: `X-Workload-Id` and `X-Session-Id` are unauthenticated headers with no ownership check. A caller can attach to any existing session under the resolved workload (`_resolve_session` reuses any row whose `workload_id` matches), and — more importantly — can send a fresh random `X-Session-Id` on every request, guaranteeing a clean ledger each turn.

**Why it matters**: Today this is harmless because 1.3/1.5 block unconditionally on any cheap-tier match regardless of ledger state. From Phase 3.2 onward, the ledger *is* the escalation mechanism, and rotating a header defeats it entirely; the shared-session direction lets one caller inflate another's strike counts. I checked `forks.md`, `STATUS.md`, `decisions.md`, and all five specs — unlike the other gaps in this branch (escalation trigger, strike-window expiry, fail_mode, category coverage), authentication is named nowhere and has no owning phase, so it is an undocumented gap rather than a deliberate deferral.

**Suggested fix**: No code change needed in this branch. Log it — either as a `decisions.md` entry accepting "the MVP proxy is unauthenticated and session ids are trusted", or as an explicit prerequisite on Phase 3.2, so the escalation work doesn't get built on an assumption that was never actually made.

## Nits

- ⚪ `app/routers/chat.py:36-38` — `SESSION_TTL = 15min` here and `LEDGER_TTL_SECONDS = 15*60` in `app/redis_client.py:24` are two independent encodings of the same Fork #3 TTL; and `LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD` are Fork #3 ledger constants living in a router. Phase 3.1 will want all four in one place.
- ⚪ `app/routers/chat.py:215-220` — `_run_response_side_interception` drops the `workload` parameter the 1.5 spec's build plan specifies. The implementation is right (it's unused), but the spec is now stale on this point.
- ⚪ No `.env.example` or README anywhere in the repo, while `app/db.py`, `app/redis_client.py`, and `app/model_client.py` now require/consume four env vars between them. `.env` is correctly gitignored and untracked (good), but a fresh clone has no way to learn the variable names.
- ⚪ `app/model_client.py:33` — the `httpx.AsyncClient` singleton is never closed on shutdown. Already a tracked 1.4 Follow-up; noting only so it isn't lost.
- ⚪ Nothing in the app logs anything — no record of a block decision, a `502`, or an upstream failure beyond what reaches the caller. Pairs directly with the first Major finding: moving upstream detail out of the response body needs somewhere for it to go.
- ⚪ `app/model_client.py:82` — `resp.text` materializes and decodes the entire upstream body before slicing to 500 chars. Irrelevant against Ollama, mildly wasteful against a provider that returns a large error payload.

## Strengths

- The 1.5 reordering is genuinely well done: `db.add` → `flush()` (not commit) → scan → single `commit()` gives the `Finding` FK its `execution_id` without prematurely committing an `Execution` whose risk score isn't decided yet, and the whole success path stays in one transaction. Reusing the 1.4 row instead of writing a second one is the right call and is argued correctly in the spec.
- The security model holds on both sides. Neither block body echoes the matched text, the prompt, or the model's generated content — only the triggering category. `MODEL_API_KEY` stays server-side. A request-side block is structurally incapable of reaching `call_model`.
- Field-by-field response construction in `call_model` earned its verbosity, and the self-check proved it: Ollama returns an extra `reasoning` field on `message` that `model_validate` against a strict schema would have turned into a `500`.
- `"stream": False` hardcoded into the outbound payload even though the request schema can't express streaming — correct belt-and-suspenders enforcement of Fork #4.
- The three error classes are cleanly separated by status code and envelope `type` (`400` caller misconfiguration / `403` policy block / `502` upstream failure), all in one OpenAI-shaped `{"error": {...}}` container. A client SDK's existing error handling works unmodified, which is exactly the plug-and-play claim `AGENTS.md` §5 makes.
- Documentation discipline is unusually strong for a hackathon build. Every non-obvious choice in this branch is in `decisions.md` with real rationale, each spec names the owning phase for what it deliberately didn't build, and the deferrals I checked (escalation trigger, strike-window expiry, `fail_mode`, category coverage) are all genuine documented scope boundaries rather than oversights. That made this diff much faster to review honestly.

## Test coverage

`TESTS = none-by-design` per `AGENTS.md` §8 — no findings raised for missing automated tests. The manual `curl` + Postgres/Redis inspection self-checks recorded in `STATUS.md` are thorough and were run against real Neon/Upstash/Ollama, including the negative paths (dead port → `502`, unpulled model → `model_api_error`) and cross-milestone regression checks.

Two gaps the existing gate would not have caught, worth adding to the next `/check verify` pass:

- **Malformed upstream shape.** Every `502` scenario exercised so far is transport-level or non-2xx. Nothing has driven a 2xx response with a structurally wrong body — which is where the `AttributeError` → `500` hole lives. Point `MODEL_API_BASE_URL` at a trivial stub returning `{"choices":[{"message":"plain string"}]}` and confirm `502`, not `500`. Typecheck will not catch this; it's a runtime shape issue.
- **Response-side false positive.** The 1.5 self-check deliberately engineered a phone-shaped output to prove the block works. The inverse is untested: ask the model for a plain 10-digit number (an order id, a large integer) and confirm whether a benign answer is hard-blocked — that determines how urgent the phone-regex fix is before the demo.
