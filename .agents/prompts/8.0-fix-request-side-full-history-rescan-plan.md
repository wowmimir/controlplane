# 8.0. Fix Request-Side Full-History Re-Scan

**Date**: 2026-08-27
**Status**: Accepted

## Summary

`_run_request_side_interception` (`app/routers/chat.py`) scans the caller's **entire** message history on every request — `text = "\n".join(message.content for message in request.messages)` — instead of just the newest turn. A real OpenAI-shaped client resends full conversation history on every call, so a single PII/injection-shaped message sent once at turn 1 re-triggers a fresh `Finding` + ledger strike on every later turn that still includes it in history, even though nothing new happened. This double-counts strikes, can trap a session in an unrecoverable block/escalate cycle, and makes 8.1's planned per-profile strike thresholds meaningless before they're even built. `STATUS.md` names this as milestone 8.0, a prerequisite bug fix ahead of the rest of Phase 8, not new Round 2 scope.

`STATUS.md`'s own note for 8.0 says this is "a bug fix, not a design decision — no `/architect` pass needed." The user explicitly ran `/architect` on 8.0 anyway and pointed it at `.agents/prompts/`, so this spec exists per that direct instruction — largely to record the one genuine judgment call this fix surfaced (see Decision) rather than to relitigate the fix itself.

The fix: scan only `request.messages[-1].content` (with an empty-list guard) instead of the joined history.

## Context

Read directly against the live code (`app/routers/chat.py`, `app/schemas/chat.py`, `app/evaluators/cheap.py`, `app/redis_client.py`) for this spec, not assumed from prior notes:

- **`_run_request_side_interception`** (lines 360–421): the read-only `is_escalated` peek (3.2) runs first; if not escalated, line 388 builds `text` by joining `message.content` for **every** message in `request.messages`, then calls `run_cheap_tier(text)` (line 389). Any match creates an `Execution` + `Finding` row(s) and updates the ledger (`_safe_ledger_update`, `is_new_turn` defaults to `True`) before returning the `403`. This is the buggy line.
- **`_run_response_side_interception`** (lines 424–502+): the response-side cheap-tier scan (line 469, `run_cheap_tier(response_text)`) already correctly scans only `parsed.choices[0].message.content` — the single new assistant reply, not history. No bug here.
- **The same join pattern exists a second time**, at line 488: `context_text = "\n".join(message.content for message in request.messages)`, feeding (a) `run_medium_tier(context_text, response_text, ...)` — the medium tier is a permanent stub (2.4) that always returns `[]`, so this is currently inert — and (b) the async expensive-tier LLM-judge's grounding context (`_run_expensive_tier_task(..., context_text=context_text)`), used to judge whether the model's response is grounded/hallucinated.
- **Ratified scope decision**: this second occurrence does not cause the strike-duplication bug (it never feeds `run_cheap_tier`, and medium tier is inert), and full conversation history is arguably the *correct* input for an LLM judge's groundedness check on a multi-turn conversation. Flagged to the user directly; **the user chose to scope this fix to the request-side scan only** and leave `context_text` as full history. This is recorded here as a deliberate cut, not a silent gap — a future session should not treat `context_text`'s full-history join as an unfixed instance of this same bug.
- **`ChatMessage`/`ChatCompletionRequest`** (`app/schemas/chat.py`): `content: str` (no multimodal/list-of-parts union), `role: str` (unconstrained, no enum). No ordering guarantee is documented or enforced anywhere — nothing asserts the last list item is `role="user"`, and nothing currently guards an empty `messages` list. `"\n".join(...)` over an empty list silently produces `""` today (not a crash); a naive `request.messages[-1]` replacement would raise `IndexError` → an unstyled `500` on that same empty-list input, a real regression risk introduced by the fix itself if left unguarded.
- **`run_cheap_tier(text: str)`** (`app/evaluators/cheap.py`): takes a single string, unchanged by this fix — whatever content is selected just needs to already be one `str`.
- **The ledger's `turn` counter** (`app/redis_client.py`, `apply_ledger_update`): incremented once per request when `is_new_turn=True` (the default, used by both interception functions' synchronous call sites), entirely independent of `request.messages`'s length or content. This fix does not touch turn-counting logic at all — only what text gets fed into `run_cheap_tier`.
- **Existing traffic never exercises this bug**: `scripts/seed_demo.py`'s `post_chat()` always sends `messages` as a single-element list (just the new user turn), including across the multi-turn escalation scenario (two separate calls, one message each, linked only by `X-Session-Id`). `docs/demo-script.md` narrates the same pattern. So today's standing seed/demo traffic happens to dodge the bug entirely — self-check for this fix needs a new scenario that actually resends history (see Follow-up), not a re-run of the existing script.

## Requirements

- **AC-1**: a multi-message request where only an *earlier* message (not the last one) contains PII/injection-shaped content does not trigger a request-side block, and does not create a new `Execution`/`Finding` row or ledger strike.
- **AC-2**: a multi-message request whose *last* message contains violating content still blocks exactly as today (`403`, `Finding` written, ledger strike applied) — no regression, regardless of what earlier messages in the same list contain.
- **AC-3**: a request with an empty `messages` list does not raise a 500 from `_run_request_side_interception` — it falls through as if nothing were found, matching today's incidental behavior (`"\n".join([])` → `""` → no candidates).
- **AC-4**: `_run_response_side_interception` is unaffected: `response_text`'s scan (already correctly scoped) and `context_text`'s full-history join (deliberately unchanged, see Decision) both behave exactly as before.
- **AC-5**: the ledger's `turn` counter behavior is unchanged — still exactly one increment per request that reaches a synchronous ledger touch, independent of message-list length or content.
- **AC-6**: full existing regression suite still passes unaffected: clean prompt → `200`; a single-message PII request → `403`/`code:"pii"`; a single-message prompt-injection request → `403`/`code:"prompt_injection"`; unknown-workload header → `400`; `/health` → `200`.

## Decision

**Chosen option**: in `_run_request_side_interception` (`app/routers/chat.py`, line 388), replace

```python
text = "\n".join(message.content for message in request.messages)
```

with

```python
text = request.messages[-1].content if request.messages else ""
```

Leave `_run_response_side_interception`'s `context_text` (line 488) unchanged. No other file changes.

## Rationale

`request.messages[-1]` is the newest turn in an OpenAI-shaped `chat/completions` request — the position a real resending client places the current user message in — and matches `STATUS.md`'s own literal fix wording ("scan only `request.messages[-1].content`"). The empty-list guard is a one-line defensive addition, not scope creep: without it, the fix would trade a currently-harmless incidental behavior (empty join → `""` → no candidates) for a new crash path (`IndexError` → raw `500`) on the same input, which nothing in the schema currently rules out (`messages: list[ChatMessage]` has no `min_length`).

Leaving `context_text` as full history (per the user's ratified choice) keeps this fix narrowly scoped to the actual reported bug — strike/Finding duplication from re-scanning old content with `run_cheap_tier` — rather than also touching a structurally different consumer (LLM-judge grounding context) that has no duplication problem today and would plausibly get *worse*, not better, grounding quality if truncated to one message. Fixing it "for consistency" would be exactly the kind of scope creep `AGENTS.md` warns against: no rubric item, no downstream Phase 8 milestone, and no bug report ask for it.

No change to `run_cheap_tier`, `apply_ledger_update`, or the `turn` counter is needed — the bug is entirely in what text gets selected before scanning, not in how findings are scored or how turns are counted.

## Consequences

**Positive**:
- Removes the double-counting bug 8.1's per-profile strike thresholds would otherwise be built on top of, and unblocks 10.1's playground plan (a live-typed conversation that resends history can now demo "escalation from accumulated risk" correctly instead of re-triggering as a fresh content violation).
- Minimal, single-line-plus-guard change, in the one file the bug actually lives in.

**Negative / tradeoffs**:
- `context_text` (response-side judge grounding) still joins full history; if this project's real clients ever grow unbounded conversation length, that join could eventually become a real cost/latency concern for the judge call — out of scope here, but worth flagging (see Follow-up) rather than leaving fully implicit.
- The fix cannot be verified against the project's own standing seed/demo traffic (see Context) — self-check requires a new, purpose-built multi-turn scenario.

**Neutral**:
- No schema change, no new dependency, no automated test suite added (per `AGENTS.md` Section 8) — verification is a targeted self-check plus the standing regression suite.

## Follow-up

- **Self-check must use a new scenario**, not `scripts/seed_demo.py` as-is: a multi-turn `curl`/httpx sequence that (a) sends a PII/injection-shaped message on turn 1 of a session, gets blocked as expected, then (b) sends a second request on the same `X-Session-Id` whose `messages` list resends turn 1's violating content *plus* a new, clean final message — confirming this does NOT re-block/re-strike (AC-1) — and separately (c) confirms a violation genuinely present in the *last* message still blocks (AC-2). Neither this fix's build session nor any later Phase 8 session should treat `seed_demo.py`'s existing green run as proof this bug is fixed, since it structurally can't exercise it.
- 8.1 (Policy Profile Enforcement) and 8.2 (Tiered Decision Logic) both build their per-profile strike/threshold behavior on top of correct strike counting — sequence 8.0 strictly before them, as `STATUS.md` already specifies.
- `context_text`'s full-history join (line 488) is intentionally out of scope here (see Decision/Rationale) — if a future session revisits the expensive-tier judge's context-window cost/latency, that's the place to reopen this, not a reason to treat it as an unfixed instance of the 8.0 bug.
