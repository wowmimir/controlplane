# 8.6. Per-Workload Category Overrides

**Date**: 2026-08-27
**Status**: Accepted

## Summary

Every workload today runs all five cheap-tier scanners (`pii`,
`prompt_injection`, `toxicity`, `bias`, `custom_policy`) with identical
per-pattern confidence. 8.6 adds a `category_overrides` map inside
`Workload.metadata` (already JSONB, so **no schema change**) that lets a
single workload turn a category off, raise the confidence bar for a category,
or suppress a specific noisy pattern. It is read at the two `run_cheap_tier`
call sites in `app/routers/chat.py`.

All three levers do the same thing: **drop the candidate before it becomes a
`Finding`**. A dropped candidate produces no `Finding`, no block, no strike,
no ledger contribution for that workload. Everything downstream (disposition,
redaction, escalation, the audit trail) is untouched; it just sees a shorter
candidate list.

The seeded `balanced` default workload has no `category_overrides` key and
behaves byte-identically to today (regression guardrail). 8.4's demo
workloads gain a real structural difference: the `fast` "Customer Support
Bot" suppresses the `ip_address` and `phone` PII patterns (noise for a
support use case), while the `strict` "EU Decision-Support Assistant" relaxes
nothing. 8.3's Detection Health "suppress this pattern" toggle gets a real
config target (`disabled_patterns`) instead of a second config surface.

## Context

The Round 2 rubric's Governance/Complexity list, item 6, is "rigid,
hard-coded rules age quickly." Phases 8.1 / 8.2 / 8.5 made the three policy
profiles take different *actions* (block / redact / flag) and different
*escalation thresholds*. What is still hard-coded is *which categories a
workload evaluates at all* and *how confident a match must be* — those are
global constants (`_PATTERNS` / `_CONFIDENCE` per evaluator file,
`STRIKE_THRESHOLD` in `redis_client.py`), identical for every tenant.

Two concrete gaps:

1. **8.4's demo workloads are cosmetically, not structurally, different.**
   "Customer Support Bot" (`fast`), "Internal Knowledge Copilot"
   (`balanced`), "EU Decision-Support Assistant" (`strict`) differ only by
   profile and a `metadata` label. The "regulatory expectations differ by
   geography / one size does not fit all" story the rubric rewards needs the
   workloads to actually evaluate content differently.
2. **8.3 (next milestone) needs a per-workload pattern-suppression
   mechanism.** Its Detection Health view groups false-positive labels by
   `evidence_ref.pattern` and offers a per-workload suppress toggle for a
   pattern above threshold. STATUS.md's 8.3 line says that toggle "should
   call 8.6's category-override mechanism below rather than inventing a
   second config surface." So 8.6 must expose something 8.3 can write to at
   pattern granularity, not just category granularity.

`Workload.metadata` is already a free-form JSONB column
(`app/models/workload.py`, mapped as the `metadata_` attribute) and is
already passed through untyped end to end: `WorkloadOut` / `WorkloadCreate` /
`WorkloadUpdate` type it as `dict | None` (`app/schemas/console.py`), and
`console.py`'s `_to_workload_out` / `create_workload` / `update_workload`
never inspect its contents. STATUS.md's Phase 8 gotcha note confirms
explicitly: *"8.6's `Workload.metadata.category_overrides` needs neither
[`ALTER TABLE` nor `ALTER TYPE`] — it lives inside an existing JSONB column,
no schema change at all."*

1. **Scope is cheap tier only.** The async LLM-as-judge (`hallucination`,
   `app/evaluators/expensive.py`) always runs; a `hallucination` key in
   `category_overrides` is accepted and silently ignored. Matches STATUS.md's

   nothing to gate.
2. **A match below a `confidence_floor` (or in a disabled category, or in
   `disabled_patterns`) is dropped entirely** — no `Finding`, no block, no
   strike. `enabled: false` is the limiting case of an infinite floor. One

   the mechanism 8.3's suppress toggle will append to, even though 8.6 only

   for "suppress `phone`, keep `ssn`".

## Requirements

**User stories**
- As the owner of a customer-support assistant, I want IP-address-shaped and
  phone-number-shaped strings to stop tripping the PII filter, because my
  agents legitimately handle customer contact details and internal host
  references all day, without also disabling SSN or credit-card detection.
- As the owner of an EU decision-support tool, I want to relax nothing and
  have the console show that my workload has zero category overrides, so
  "this workload is the strict one" is visible, not just asserted.
- As a security reviewer, I want two workloads to produce different findings
  on the identical prompt, so "governance varies by use case" is
  demonstrated end to end.
- As the 8.3 Detection Health view, I want a per-workload place to record
  "suppress pattern X" that the evaluation path already reads, so I don't
  invent a parallel config store.

**Acceptance criteria**
- **AC-1 (regression)**: `run_cheap_tier(text)` called with no second
  argument returns results byte-identical to pre-8.6 for inputs that hit
  each of the five categories (same candidates, same order: `pii`,
  `prompt_injection`, `toxicity`, `bias`, `custom_policy`). The seeded
  default workload (`balanced`, no `category_overrides` in `metadata`)
  behaves identically to pre-8.6 on every path: clean pass-through,
  request-side block, response-side redact, escalation. Verified by a direct
  call plus the AC-11 sweep.
- **AC-2 (disable a category)**: a workload whose
  `metadata.category_overrides == {"toxicity": {"enabled": false}}` — an
  input containing `"you are worthless"` produces zero `toxicity` findings,
  no block, no strike. The same input on a workload without the override
  still blocks. Verified request-side and response-side.
- **AC-3 (confidence floor)**: `{"pii": {"confidence_floor": 0.8}}` — a
  response or prompt whose only PII match is an `ip_address` (confidence
  0.6) produces no `Finding` and no block; a prompt containing an `ssn`
  (0.95) on the same workload still blocks. Verified at both call sites.
- **AC-4 (pattern suppression — the 8.3 hook)**:
  `{"pii": {"disabled_patterns": ["phone"]}}` — a `phone` match is dropped
  while an `email` match on the same workload still fires. Verified by a
  direct call and an HTTP round trip.
- **AC-5 (both call sites)**: an override takes effect in both
  `_run_request_side_interception` and `_run_response_side_interception`
  (the request-side `is_escalated` early return does not scan and is
  therefore unaffected — documented, not tested).
- **AC-6 (no strike / no escalation)**: three would-be-strike hits on a
  disabled or fully-floored category in one session do not escalate it
  (`escalated: false` in `GET /api/console/sessions/{id}`). The same three
  hits on a workload without the override escalate on the third.
- **AC-7 (defensive)**: none of these produce a `500` — they all fall back
  to "no override for this category": `category_overrides` not a dict; a
  category value not a dict; `confidence_floor: "high"` (non-numeric);
  `enabled: "no"` (non-bool — treated as enabled, only literal `false`
  disables); `disabled_patterns` not a list.
- **AC-8 (hallucination ignored)**: `{"hallucination": {"enabled": false}}`
  is accepted, changes nothing, and the async judge still schedules and
  runs. Documented as a known limitation.
- **AC-9 (console)**: `GET /api/console/workloads` returns
  `category_overrides` inside `metadata` unchanged; the Workloads table
  shows an "Overrides" summary cell for a workload that has them and `—` for
  one that does not; opening an override-carrying workload in `WorkloadForm`,
  changing an unrelated field, and saving does **not** drop the
  `category_overrides` key; `tsc -b` and `npm run build` are clean; every
  other Workloads column is unchanged.
- **AC-10 (script)**: `scripts/simulate_use_cases.py` — the "Customer
  Support Bot" workload spec carries `category_overrides`; `ensure_workload`
  reconciles `metadata` onto an already-existing workload row (a second run
  makes no further change); a full run shows the `10.0.0.5` benign prompt
  reported as a clean pass on Customer Support Bot and still blocked on the
  EU workload; the script exits `0`.
- **AC-11 (regression sweep)**: `/health` `200`; unknown-workload `400`;
  clean `balanced` pass-through `200`; request-side PII block `403`;
  response-side PII redact on `balanced` `200` / `disposition=redacted`;
  `strict` response-side block `403`; two-turn escalation `403` /
  `session_escalated`.

## Options considered

### Option 1: filter inside `run_cheap_tier`, overrides passed from the call site (recommended)

`run_cheap_tier(text, category_overrides=None)`. `chat.py` reads
`workload.metadata_["category_overrides"]` and passes it. The function keeps
a category→scanner map, skips a disabled category, and drops any candidate
below the floor or in `disabled_patterns`.

**Pros**
- One place. Both call sites already exist and already have `workload`.
- Everything downstream of the candidate list is untouched — disposition,
  redaction, ledger, escalation, `_finding_evidence`, the audit trail all
  just receive fewer candidates.
- The default call (`run_cheap_tier(text)`) is provably unchanged.
- `disabled_patterns` gives 8.3 exactly the granularity it needs with no
  extra surface.

**Cons**
- `run_cheap_tier` gains a category→scanner map it did not have before (the
  five scanners were previously an unlabelled splat). Minor.
- Overrides are only enforced for the cheap tier; a reader might expect them
  to cover `hallucination` too. Mitigated by the docstring, AC-8, and a
  Follow-up.

### Option 2: filter after the fact, in `chat.py`

Keep `run_cheap_tier` unchanged; have each call site filter the returned
list against the workload's overrides.

**Pros**
- `run_cheap_tier`'s signature is untouched.

**Cons**
- The same filter logic is duplicated at two call sites (three, once 8.3 or
  a future medium tier joins).
- A disabled category's scanner still runs (wasted work), only its output is
  discarded — a worse fit for "the scanner is skipped entirely for that
  workload" (STATUS.md's own wording).
- `chat.py` is already the largest, most-revised file; adding filter logic
  there rather than in the evaluator layer is the wrong direction.

### Option 3: promote `category_overrides` to a real column + typed model now

A `category_overrides JSONB` column on `workload`, a pydantic sub-model on
`WorkloadCreate` / `WorkloadUpdate`, validation.

**Pros**
- Rejects malformed overrides at the API boundary; self-documenting schema.

**Cons**
- Needs a manual `ALTER TABLE` (the exact migration friction STATUS.md's
  gotcha note points out is avoidable here).
- `metadata` is already the sanctioned home for per-workload config that is
  not one of Fork #1's locked fields; Fork #1 itself calls category
  overrides "optional ... post-MVP" and names `metadata` as the carrier for
  non-locked workload attributes.
- More surface for a hackathon build with no editor yet. Kept as a Follow-up
  for if/when a real editor lands.

## Decision

**Chosen option**: Option 1 — filter inside `run_cheap_tier`, overrides
passed from the call site.

**Implementation skills**: none (`AGENTS.md` names no community skill for
this area).

### The override shape

In `Workload.metadata_` (Postgres JSONB column `metadata`), a new optional
top-level key `category_overrides`:

```json
{
  "category_overrides": {
    "pii":      { "confidence_floor": 0.8, "disabled_patterns": ["ip_address"] },
    "toxicity": { "enabled": false },
    "bias":     { "confidence_floor": 0.7 }
  }
}
```

- **Category keys** are `FindingCategory` string values that have a
  cheap-tier scanner: `pii`, `prompt_injection`, `toxicity`, `bias`,
  `custom_policy`. `hallucination` has no cheap scanner; a `hallucination`
  key is accepted and ignored (AC-8).
- **`enabled`** (bool, default `true`): only a literal `false` disables the
  category's scanner for this workload. Any other value = enabled.
- **`confidence_floor`** (number in `[0.0, 1.0]`, default `0.0`): a
  candidate from this category whose `confidence < confidence_floor` is
  dropped. A non-numeric value is treated as `0.0`.
- **`disabled_patterns`** (list of pattern-name strings, default `[]`): a
  candidate whose `evidence_ref["pattern"]` is in this list is dropped. This
  is the surface 8.3's Detection Health suppress toggle appends to.
- An **absent** category key, an absent `category_overrides`, or a `null`
  `metadata` → today's behavior exactly for that category.

### `app/evaluators/cheap.py`

```python
from app.evaluators import bias, pii, prompt_injection, secrets, toxicity
from app.evaluators.types import DEFAULT_CONFIDENCE, FindingCandidate
from app.models import FindingCategory

__all__ = ["DEFAULT_CONFIDENCE", "FindingCandidate", "run_cheap_tier"]

# Category -> its cheap-tier scanner. Order is the pre-8.6 fan-out order
# (pii, prompt_injection, toxicity, bias, secrets) so a no-override call is
# byte-identical to before. hallucination has no cheap scanner (expensive
# tier only) and is deliberately absent - an override key for it is ignored.
_SCANNERS = {
    FindingCategory.pii: pii.scan,
    FindingCategory.prompt_injection: prompt_injection.scan,
    FindingCategory.toxicity: toxicity.scan,
    FindingCategory.bias: bias.scan,
    FindingCategory.custom_policy: secrets.scan,
}


def _rule(overrides: dict, category: FindingCategory) -> dict:
    rule = overrides.get(category.value)
    return rule if isinstance(rule, dict) else {}


def _floor(rule: dict) -> float:
    value = rule.get("confidence_floor")
    return float(value) if isinstance(value, (int, float)) else 0.0


def run_cheap_tier(
    text: str, category_overrides: dict | None = None
) -> list[FindingCandidate]:
    """Run every cheap-tier scanner against one text blob.

    8.6: an optional per-workload `category_overrides` map (read from
    Workload.metadata by the chat.py call sites) can, per category:
      - disable the scanner entirely (`{"enabled": false}`),
      - drop matches below a confidence bar (`{"confidence_floor": 0.8}`),
      - drop specific patterns (`{"disabled_patterns": ["ip_address"]}` -
        the surface 8.3's Detection Health suppress toggle writes to).
    All three just shorten the returned candidate list; nothing downstream
    (Finding rows, ledger strikes, disposition, redaction) changes shape.
    A None/absent map, or an absent category key, is exactly pre-8.6
    behavior. Malformed values degrade to "no override", never raise. See
    .agents/prompts/8.6-per-workload-category-overrides-plan.md.
    """
    overrides = category_overrides if isinstance(category_overrides, dict) else {}
    candidates: list[FindingCandidate] = []
    for category, scan in _SCANNERS.items():
        rule = _rule(overrides, category)
        if rule.get("enabled") is False:
            continue
        floor = _floor(rule)
        disabled = set(rule.get("disabled_patterns") or [])
        for candidate in scan(text):
            if candidate.confidence < floor:
                continue
            if (candidate.evidence_ref or {}).get("pattern") in disabled:
                continue
            candidates.append(candidate)
    return candidates
```

### `app/routers/chat.py`

One helper and one changed argument at each of the two call sites:

```python
def _category_overrides(workload: Workload) -> dict | None:
    """8.6: the workload's per-category cheap-tier override map, if any,
    from its free-form metadata JSONB. Passed straight to run_cheap_tier.
    """
    metadata = workload.metadata_ or {}
    return metadata.get("category_overrides")
```

- `_run_request_side_interception`, at the existing scan (after the
  `is_escalated` short-circuit):
  `candidates = run_cheap_tier(text, _category_overrides(workload))`
- `_run_response_side_interception`, at the existing scan:
  `cheap_candidates = run_cheap_tier(response_text, _category_overrides(workload))`

Nothing else in `chat.py` changes. The `is_escalated` early return in
`_run_request_side_interception` never scans, so overrides do not apply to an
already-escalated session (it blocks on ledger state, not this turn's
content) — this is correct and is called out in **Key invariants**.

## Rationale

Filtering inside `run_cheap_tier` (Option 1) wins because the override is
conceptually "this workload's cheap tier is configured differently," which
belongs in the evaluator layer, and because it keeps every downstream
consumer — `_finding_evidence`, `redact_spans`, `_safe_ledger_update`,
`is_escalated`, the disposition logic, the console — completely unaware of
overrides. They already operate on "the list of candidates for this turn";
8.6 only makes that list shorter. `chat.py`, the most-revised file in the
codebase, gains one four-line helper and two one-word argument changes.

Dropping a sub-floor / disabled / suppressed candidate entirely (rather than
recording the `Finding` but suppressing only its strike) is chosen because it
collapses three levers into one code path and because a workload that has
said "I don't evaluate toxicity" should not accumulate a toxicity audit
trail. `STRIKE_THRESHOLD` already provides the "record but don't strike"
behavior for genuinely low-confidence patterns (`ip_address` at 0.6, `bias`
at 0.65) globally; 8.6's floor is a per-workload "don't even record it."

`disabled_patterns` is built now, ahead of 8.3, because STATUS.md's 8.3 line
explicitly routes the Detection Health suppress toggle through "8.6's
category-override mechanism," and category-level `enabled: false` cannot
express "suppress `phone` but keep `ssn`." The cost is two lines in
`run_cheap_tier`. 8.3 still owns the console toggle UI and the per-pattern
false-positive-rate threshold logic that decides *when* to append a pattern
name to the list.

Scope stops at the cheap tier because that is what STATUS.md names, because
the async judge is post-release and cannot block anyway (so gating it is a
cost question, already partially handled by 8.1's `fast`-profile judge
sampling), and because the `medium` tier is a permanent no-op stub.

Keeping `category_overrides` in `metadata` rather than a new column follows
Fork #1 (which names category overrides "optional ... post-MVP" and treats
`metadata` as the carrier for non-locked workload attributes) and avoids the
manual `ALTER TABLE` friction STATUS.md's own gotcha note flags as
avoidable here.

## Feature design

**Data model sketch**
- `workload.metadata` (JSONB): gains an optional top-level key
  `category_overrides: {category: {enabled?: bool, confidence_floor?: number,
  disabled_patterns?: string[]}}`. No column, no enum, no migration.
- No change to `Finding`, `Execution`, `Session`, or the Redis ledger shape.

**State transitions**
None. Overrides are read fresh from `workload.metadata_` on every request;
there is no cached or derived state.

**API surface**
- No new endpoint. `POST /v1/chat/completions` behavior for a workload with
  overrides differs only in which findings it produces.
- `POST /api/console/workloads` and `PATCH /api/console/workloads/{id}`
  already accept an arbitrary `metadata` dict; `category_overrides` rides
  along with zero handler change.
- `GET /api/console/workloads`, `/sessions/{id}`, `/feed` already return
  `metadata` verbatim.

**Value sourcing**

| Value produced | Source |
|---|---|
| the candidate list for a turn | `run_cheap_tier(text, workload.metadata_.get("category_overrides"))` — the pre-8.6 scanner fan-out, minus any candidate whose category is `enabled: false`, whose `confidence` is `< confidence_floor`, or whose `evidence_ref["pattern"]` is in `disabled_patterns` |
| whether a category's scanner runs at all | `overrides[category].get("enabled") is not False` |
| the per-category confidence bar | `overrides[category].get("confidence_floor")` if numeric, else `0.0` |
| the suppressed pattern set | `set(overrides[category].get("disabled_patterns") or [])` |
| everything downstream (disposition, `execution_risk_score`, `Finding` rows, ledger strikes, `is_escalated`, redaction spans, console) | unchanged — computed from the (now possibly shorter) candidate list exactly as today |
| console "Overrides" cell | `formatCategoryOverrides(workload.metadata)` |

**Key invariants**
- `run_cheap_tier(text)` with no second argument is behaviorally identical
  to pre-8.6 (same candidates, same order).
- A workload with no `category_overrides` key is identical to pre-8.6 on
  every path. This specifically includes the seeded `balanced` default.
- A dropped candidate leaves no trace anywhere: no `Finding` row, no ledger
  strike, no `cumulative_risk` contribution, no `disposition` change, no
  console entry.
- Overrides are applied only where content is scanned:
  `_run_request_side_interception`'s cheap-tier scan and
  `_run_response_side_interception`'s cheap-tier scan. The request-side
  `is_escalated` early return blocks on ledger state without scanning and is
  intentionally unaffected.
- Malformed override data degrades to "no override"; it never raises.
- `disabled_patterns` matches against `evidence_ref["pattern"]`, which every
  cheap-tier scanner sets. An expensive-tier `Finding` has no `pattern` and
  is never affected (and is out of scope regardless).

**Security model**
Overrides can only *reduce* what a workload detects, never increase it or
affect another workload. They live in `metadata`, which is already
caller-editable through the unauthenticated console write API — the same
standing, accepted hackathon posture as every other workload field
(`decisions.md`, 2026-08-23, caller-asserted headers / no console auth).
8.6 adds no new caller-facing surface and no new auth question. A workload
that disables `pii` detection is making an explicit, visible (Overrides
column) policy choice, logged in its own `metadata`.

**Configuration required**
None at deploy time. Demo values are set by `scripts/simulate_use_cases.py`.
Ad-hoc values are set with a `PATCH /api/console/workloads/{id}` body of
`{"metadata": {..., "category_overrides": {...}}}`.

## Consequences

**Positive**
- A per-workload tuning surface exists — the rubric's "hard-coded rules age
  quickly" complexity is met with a real mechanism.
- 8.4's demo workloads now evaluate content differently, not just carry
  different labels; the same prompt can produce different findings on
  different workloads.
- 8.3 has a concrete config target (`disabled_patterns`) and does not need a
  second config store.
- Zero schema change, zero new endpoint, ~30 lines of real logic.

**Negative / tradeoffs**
- Overrides only cover the cheap tier. A `hallucination` override key is
  silently ignored — mitigated by the docstring, AC-8, and a Follow-up, but
  a mild surprise.
- `category_overrides` is unvalidated free-form JSON. A typo in a category
  name or pattern name fails silently (the override just does nothing). A
  typed model is a Follow-up.
- A workload can disable `pii` detection entirely through the
  unauthenticated console API. Consistent with every other unauthenticated
  workload field in this hackathon build, but worth noting.
- No editor yet; overrides are set by script or raw API call.

**Neutral**
- `run_cheap_tier` gains an explicit category→scanner map. If a sixth
  cheap-tier category is ever added it must be registered there (previously
  it would just be added to the splat).
- The Workloads table gains a column; nothing else in the console moves.
- `ensure_workload` in the sim script changes from create-only to
  create-or-reconcile.

## Migration plan

**Strategy**: additive, no data migration.
**Phases**:
1. Ship `cheap.py` + `chat.py`. With no workload carrying a
   `category_overrides` key yet, behavior is identical to before across the
   board.
2. Set `category_overrides` on demo workloads via
   `scripts/simulate_use_cases.py` (or an ad-hoc PATCH). Only those
   workloads change behavior.
**Rollback**: revert the `cheap.py` / `chat.py` / console / script commits.
Any `category_overrides` keys left in `workload.metadata` become inert the
moment `run_cheap_tier` ignores the argument again; they can be left in
place or PATCHed out, harmless either way. No row is ever backfilled.
**Risks**: a malformed override silently doing nothing (accepted; AC-7
guarantees no crash). A future sixth cheap-tier category being forgotten in
`_SCANNERS` (mitigated: it would simply not run, and the omission is obvious
in one small map).
