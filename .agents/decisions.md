# DECISIONS — Locked Engineering Choices

| Date | Decision | Rationale |
| :--- | :--- | :--- |
| 2026-08-23 | Use `uv` for the Python dependency/environment manager | Fast, single lockfile, keeps the environment reproducible across the many separate sessions this hackathon build spans; not stated in `forks.md`. See `prompts/0.1-skeleton-plan.md`. |
| 2026-08-23 | Project layout is a package: `app/main.py` as the entry point, with `app/routers/`, `app/models/`, etc. added under it in later phases | Absorbs Phase 1+ additions (proxy routes, evaluators, DB models) without restructuring; a flat single file would need reshuffling almost immediately. |
| 2026-08-23 | `GET /health` returns only `{"status": "ok"}`, no metadata, no dependency checks | Matches `STATUS.md`'s literal wording ("returns 200"); it's a pure liveness probe since DB/Redis aren't wired up until 0.2/0.3, nothing to check yet. |
| 2026-08-23 | Local dev run convention: `uvicorn app.main:app --reload --port 8000` | Standard FastAPI/uvicorn default; documented once so every future session runs it the same way. |
| 2026-08-23 | `Workload`'s `metadata` column is exposed on the model as the Python attribute `metadata_`, via `mapped_column("metadata", ...)` | SQLAlchemy's `DeclarativeBase` already uses the class attribute name `metadata` for the table registry, so a column literally named `metadata` cannot also be a plain attribute on the model. The actual Postgres column is still named `metadata`, matching `forks.md`; only the Python side attribute differs. Anything reading/writing this field in later phases must use `workload.metadata_`, not `workload.metadata`. |
| 2026-08-23 | The four fixed choice fields (`policy_profile`, `fail_mode`, `evaluator_tier`, `category`) are Python `enum.Enum` classes that also inherit from `str` (`class PolicyProfile(str, enum.Enum)`), in `app/models/enums.py` | Lets these values serialize as plain strings automatically (JSON responses in Phase 1's proxy endpoint, the console API in Phase 5) without a custom encoder, while SQLAlchemy still maps them to a native Postgres `ENUM` type for database level rejection of invalid values. |
| 2026-08-23 | Redis client is `redis` (redis-py) using its built-in `redis.asyncio` interface, over the standard TCP/TLS protocol, not Upstash's REST-based `upstash-redis` SDK | This app is a persistent `uvicorn` process, not serverless, so the standard client's connection pool is simpler and lower latency than a REST hop; matches the existing `create_async_engine` connection-pool pattern already used for Postgres in `app/db.py`. |
| 2026-08-23 | Every Redis key this app writes is prefixed `controlplane:` (e.g. `controlplane:session:{session_id}:ledger`) | The `REDIS_URL` in `.env` points at an Upstash database shared with another, unrelated project (flagged by the user, not documented anywhere else); a prefix guarantees no key collision without provisioning a second Upstash database mid-hackathon. |
| 2026-08-23 | The session ledger's Redis value is one JSON blob (`{cumulative_risk, strikes}`) per session, not split across multiple Redis data structures (hash, sorted set, etc.) | `forks.md` Fork #3 only fixes the two fields, not their storage layout, and `STATUS.md` scopes 0.3 to storage plumbing only — the decay/strike-window/escalation math is Phase 3's job. A blob is the simplest shape satisfying 0.3 alone; Phase 3 may need to restructure `strikes` to support windowed expiry (logged as a Follow-up in `.agents/prompts/0.3-redis-client-plan.md`), deliberately deferred rather than guessed now. |
| 2026-08-23 | The default `Workload` row is identified by a fixed sentinel UUID (`DEFAULT_WORKLOAD_ID = 00000000-0000-0000-0000-000000000000`, defined in `app/seed.py`), not a name/slug column | `forks.md` Fork #1's `Workload` field list is locked and has no name/slug field; adding one would reopen that lock, which `forks.md` says to stop and ask about. A fixed value of the existing `workload_id` primary key needs no schema change and gives Phase 1.2's fallback logic a cheap, reliable lookup. |
| 2026-08-23 | The default workload is seeded automatically at app startup (in `app/main.py`'s lifespan, after `create_all`), not via a manual seed script | Matches the project's existing "nothing to hand-run" pattern from 0.2's `create_all`-on-startup decision; a hackathon build spanning many separate sessions is the worst case for depending on someone remembering a one-off script. |
| 2026-08-23 | Default workload's `fail_mode = fail_open` | A hackathon live demo must not go fully dark if ControlPlane's own internals (Redis, an evaluator) hiccup; `forks.md` Fork #4 already scopes `fail_mode` per-workload so a stricter workload can opt into `fail_closed` later without touching this one. |
| 2026-08-23 | Default workload's `latency_budget_ms = 1000` and `cost_budget_per_request = 0.10` | Neither is specified in `forks.md`; per Fork #4, `latency_budget_ms` is governance overhead only (not total request latency), so 1s comfortably covers cheap tier plus a synchronous medium-tier check for a "balanced" profile; `0.10` (USD) is a reasonable per-request ceiling in the absence of a stated requirement. Both are placeholders pending real latency/cost data from Phase 1/2 (logged as a Follow-up in `.agents/prompts/0.4-default-workload-seed-plan.md`). |
| 2026-08-23 | `workload_id` and `session_id` on `POST /v1/chat/completions` are read from HTTP headers (`X-Workload-Id`, `X-Session-Id`), not extra body fields | `forks.md` leaves this genuinely open (not in Fork #1, Fork #3, or the "explicitly not locked" list). Headers keep the JSON body byte-identical to OpenAI's `chat/completions` schema, the strongest form of the "plug-and-play" claim `AGENTS.md` Section 5 requires, and match the convention used by comparable LLM gateways (Helicone, Portkey) for the same kind of out-of-band routing metadata. Ratified directly with the user before building. See `.agents/prompts/1.1-openai-compatible-endpoint-plan.md`. |
| 2026-08-23 | 1.1's `/v1/chat/completions` response is an explicit stub (a labeled placeholder assistant message, `0` usage), not a hardcoded fake model reply | Phase 1.4 (real model forwarding) doesn't exist yet; a response that looked like genuine model output risked being mistaken for one during a later session or a live demo. Same discipline as 0.4's refusal to fake a schema workaround. |
| 2026-08-23 | An `X-Workload-Id` that doesn't match any `Workload` row returns `400`, rather than silently falling back to the default workload | `forks.md` Fork #1 only defines the omitted-header case; a supplied-but-unknown id is almost always a caller misconfiguration, and silently substituting the default risks applying the wrong policy profile/budgets with no signal to anyone. Ratified with the user. See `.agents/prompts/1.2-workload-session-resolution-plan.md`. |
| 2026-08-23 | An `X-Session-Id` that matches an existing `Session` row under a *different* workload than the request's resolved one returns `400`, rather than deferring to either side | Enforces `forks.md` Fork #1's "a Session cannot span two workloads" invariant explicitly instead of silently overriding the caller's request or the session's own history; either silent choice would violate the same invariant in a different direction. Ratified with the user. |
| 2026-08-23 | Every successful `/v1/chat/completions` response carries `X-Workload-Id`/`X-Session-Id` response headers set to the resolved values | Without this, a caller who never supplies `session_id` has no way to ever learn the id ControlPlane generated, so every request stays permanently length-1 — Phase 6.1's "ledger-driven multi-turn escalation" demo scenario needs some mechanism for continuity, and this is the cheapest one available now. Ratified with the user. |
| 2026-08-23 | A resolved/reused `Session.ttl_expires_at` is always refreshed to `now + 15min` on every request that touches it | Mirrors the Redis ledger's existing reset-on-write TTL behavior from 0.3, so Postgres's expiry column doesn't silently drift stale relative to the live ledger's actual expiry. |
| 2026-08-23 | Cheap-tier PII/prompt-injection scanners live in a new `app/evaluators/` package (`pii.py`, `prompt_injection.py`, `cheap.py` orchestrator, `types.py` for the shared `FindingCandidate` dataclass), not inline in `app/routers/chat.py` | Ratified with the user. Phase 2.1/2.2 need this exact reusable-function shape (`scan(text) -> list[FindingCandidate]`), and 2.3 explicitly requires the same detectors to run on response text too — inline router code would need extraction/rewriting later for no benefit now. See `.agents/prompts/1.3-request-side-interception-plan.md`. |
| 2026-08-23 | A request-side block returns `403` with an OpenAI-style top-level `{"error": {"message","type","param","code"}}` envelope, not `400`/FastAPI's default `{"detail": ...}` | Ratified with the user. Matches the shape OpenAI-compatible client SDKs already parse, reinforcing `AGENTS.md` Section 5's plug-and-play claim, and keeps `403` (policy block) semantically distinct from the `400`s 1.2 already uses for caller misconfiguration (unknown workload, cross-workload session). |
| 2026-08-23 | Cheap-tier regex/keyword matches get a fixed confidence of `0.95` rather than a computed score; any match blocks unconditionally (no "inconclusive" cheap-tier state) | Regex matches are deterministic (match or no match), so a computed score would be manufactured precision. `0.95 > 0.7` also satisfies Fork #3's strike-increment threshold on every match. The "inconclusive → escalate to medium/expensive tier" ambiguity in Fork #4 is a response-side concept, not applicable to request-side pure-regex checks. |
| 2026-08-23 | 1.3 creates an `Execution` row only on the blocked path (to satisfy `Finding.execution_id`'s required FK), not on every request | There's no real execution to log on a pass-through yet since 1.4 (model forwarding) doesn't exist; unconditional `Execution` logging regardless of block status is explicitly Phase 4.2's job, once there's a real model call to attach it to. |
| 2026-08-23 | 1.3's ledger updates write only to Redis (`get_ledger`/`set_ledger`), not to `Session.cumulative_risk`/`Session.strikes` in Postgres | Matches the existing code comment in `app/models/session.py` that Postgres is the durable/audit copy (Phase 4) and Redis is the live one (0.3's decision) — writing both now would risk the two silently diverging before Phase 4 defines the reconciliation story. |
| 2026-08-23 | 1.3 does not implement the `cumulative_risk > 0.7 OR strikes >= 3` escalation check or strike-window expiry; a request-side cheap-tier match blocks unconditionally regardless of ledger state | Escalation-check logic is explicitly Phase 3.2's task and strike-window expiry is 3.1's; per Fork #4, request-side and response-side findings use "the same ledger mechanics," but the *block decision itself* on the request side is unconditional on any cheap-tier match (cheap tier has no "inconclusive" state to gate on, unlike the response-side flow). The ledger is still updated so later turns see accumulated risk once 3.1/3.2 exist. |
| 2026-08-23 | Model provider for 1.4 is Ollama (local, zero-cost), targeted via its OpenAI-compatible API at `MODEL_API_BASE_URL` (defaults to `http://localhost:11434/v1`), default test/demo model `minimax-m3:cloud`, no API key required | `forks.md` Fork #4 left the provider choice open ("OpenAI or Anthropic") and no provider/model-routing field exists in the schema or `Workload` model. Ratified directly with the user. Since `ChatCompletionRequest`/`ChatCompletionResponse` already mirror OpenAI's shape and Ollama speaks that same shape, no translation layer is needed. Not a permanent lock — swapping to a real hosted provider later only requires changing `MODEL_API_BASE_URL`/`MODEL_API_KEY`, no code change. See `.agents/prompts/1.4-model-forwarding-plan.md`. |
| 2026-08-23 | The model-forwarding HTTP call lives in a new `app/model_client.py` module (singleton `httpx.AsyncClient`, `call_model()`), not inline in `app/routers/chat.py` | Mirrors 1.3's precedent of pulling evaluator logic into its own package because later phases reuse it; 1.5 (response-side interception) sits directly downstream of this exact call and later Control actions (retry/regenerate/route) will need to invoke it again. New dependency `httpx` added via `uv add httpx` — a raw POST is sufficient since Ollama's endpoint already speaks the OpenAI-compatible shape needed; no `openai`/`anthropic` SDK added, keeping the code vendor-neutral per `AGENTS.md` §5. |
| 2026-08-23 | `MODEL_API_BASE_URL`/`MODEL_API_KEY` are read via `os.environ.get(...)` with a default/`None`, not the bracket-required `os.environ[...]` pattern `app/db.py`/`app/redis_client.py` use for `DATABASE_URL`/`REDIS_URL` | Both are meant to be optional/defaulted for a local Ollama target (no key needed, sensible default URL) rather than hard requirements — a deliberate, documented deviation from the existing required-env-var convention, not an oversight. |
| 2026-08-23 | The outbound model-call timeout is a fixed `httpx.Timeout(120.0, connect=5.0)` in `app/model_client.py`, entirely separate from `Workload.latency_budget_ms` | `forks.md` Fork #4 defines `latency_budget_ms` as evaluator governance overhead only, never the outbound model-call's own network timeout; 120s accounts for local/cloud-tag Ollama inference being slower than a typical hosted API call. Verified empirically against `minimax-m3:cloud` during self-check (a real call completed in ~2.5s, well under the ceiling). |
| 2026-08-23 | `call_model()`'s success response is built field-by-field with `.get(...)` fallbacks, not `ChatCompletionResponse.model_validate(resp.json())` | Every field in `ChatCompletionResponse`/`Usage`/`Choice` is required/non-`Optional`; a naive `model_validate` would raise an opaque `ValidationError` (→ unhandled `500`) on any small shape difference from the model API (e.g. a missing `usage` block, or Ollama's extra `reasoning` field on `message` — confirmed present in a real response during self-check and correctly ignored by field-by-field construction) instead of the clean, typed `502` the router needs. |
| 2026-08-23 | A model-call failure (unreachable, non-2xx, or unparseable response) always returns `502` with an OpenAI-style `{"error": {...}}` envelope, unconditionally — never routed through `Workload.fail_mode`, and no `Execution` row is created on this path | `forks.md` Fork #4 scopes `fail_open`/`fail_closed` to "ControlPlane itself" erroring or timing out (explicitly Phase 3.3's job); a failure to reach the upstream model API is a different failure class (the provider, not ControlPlane's own internals), so 3.3's branching does not apply here. `502` keeps this distinct from 1.2's `400` (caller misconfiguration) and 1.3's `403` (policy block). No `Execution` row on failure matches 1.3's "only log what concretely happened" precedent for its own blocked path; Phase 4.2 is the explicit future owner of deciding whether failed attempts also deserve a row. Verified via self-check: an unreachable-API request returned `502`/`code:"model_unreachable"` with zero new `Execution` rows for that session. |
| 2026-08-23 | On a successful forward, 1.4 creates one `Execution` row with real `tokens` (`usage.total_tokens`) and `latency_ms` (wall-clock time of only the outbound `httpx.post(...)` call — not total request time, evaluator time, or DB-commit time); `retries=0`, `tool_loop_count=0` (no retry/tool-calling logic exists yet); `execution_risk_score=None` (nothing evaluates the model's output until 1.5) | `forks.md` doesn't split model-call latency from total-request latency explicitly, so measuring only the HTTP call is a deliberate, logged interpretation, keeping `Workload.latency_budget_ms` (governance overhead only) unconflated with this operational signal. This is the first milestone to populate `Execution.tokens`/`latency_ms` with real data (0.2 defined the columns; 1.3 only ever set `execution_risk_score` on its own blocked path). |
| 2026-08-23 | 1.5 reuses the same `Execution` row 1.4 already creates for a successful model call (not a second row) — `chat_completions` now builds+flushes the `Execution` before running the response scan, so `execution_id` is available for any `Finding` rows, then commits once after the scan decides `execution_risk_score` | One execution per real model-call attempt matches the data model (1 Session : many Executions, not 1 Execution per interception stage). A response-side block therefore carries real `tokens`/`latency_ms` from the completed call — unlike a request-side block (1.3), which never calls the model and leaves those columns null. | 2026-08-23 | `Execution.execution_risk_score` is set to `0.0` (not left `None`) when the response-side cheap-tier scan finds nothing | `None` was 1.4's placeholder for "not evaluated yet."
