## Major

### 🟠 An in-flight `send()` applies its result to state that has since been reset, `console/src/Playground.tsx` `send()`

**Problem**: `resetConversation()` and `changeWorkload()` are reachable while `pending` is true — the "New conversation" button is disabled only on `isEmpty`, and the workload `<select>` is never disabled. `send()` holds no generation counter, `AbortController`, or at-send-time snapshot check, so when the awaited `sendChatCompletion` resolves it unconditionally runs `setSessionId(result.sessionId)` and `setTranscript(prev => [...prev, assistant])` against whatever state now exists.

**Why it matters**:
- *On camera*: presenter sends Shot 3's PII prompt, the proxy is slow, presenter hits "New conversation" to set up Shot 4; the `403` lands and restores the old **escalated** `sessionId`. Shot 4's turn 1 then returns `controlplane_session_escalated` instead of the `prompt_injection` "Blocked" panel — the two-turn story collapses, and the button looks like it did nothing.
- *Stuck state*: switch workload mid-flight and the old session id is restored under the new `workloadId`; the next send hits `_resolve_session`'s cross-workload guard (`app/routers/chat.py:306-313`) → `400 {"detail": ...}`, which `sendChatCompletion` renders as the opaque "ControlPlane returned 400." with no hint that "New conversation" is the fix.

**Suggested fix**: a `genRef` bumped at the top of `send()` and in `resetConversation()`; after the await, `if (gen !== genRef.current) return` before any `setState`. Disable the workload `<select>` while `pending`; keep "New conversation" enabled so it can abort a slow send (bump the gen, clear `pending`).

### 🟠 A blocked prompt is kept in the outbound payload and forwarded to the model two turns later, `console/src/Playground.tsx` `send()`

**Problem**: on a block, the user turn is pushed into `transcript` and never removed, so the next `nextMessages = [...transcript, newTurn]` resends it. The 8.0 fix means it is not re-*scanned* (`app/routers/chat.py:548` reads `messages[-1]` only), but nothing stops it being *forwarded*.

Verified path on the default `balanced` workload: turn 1 email prompt (confidence 0.95, `app/evaluators/pii.py`) → request-side block, `cumulative_risk` 0.95. Turn 2 any prompt → escalation block, which does a 0.0 decay touch (`chat.py:540`) leaving `cumulative_risk` 0.665. Turn 3 clean prompt → 0.665 < balanced's 0.7 threshold so not escalated, `messages[-1]` is clean, so `call_model` receives the full history **including the turn-1 PII**, and `context_text` (`chat.py:697`) ships that same string to the async LLM judge.

**Why it matters**: `docs/demo-script.md` Shot 3 tells the presenter to say "this is blocked *before* the model is ever called — a violation never costs a model round trip", and Shot 3 explicitly invites continuing in the same conversation ("Same conversation (or press 'New conversation')"). For a governance product this is the wrong thing to demonstrate. It also renders two adjacent `user` bubbles with no assistant between them, which looks broken.

**Suggested fix**: keep the blocked turn in the rendered transcript, but mark it display-only and exclude it from the payload (`transcript.filter(t => !t.blocked)`). Verified safe for the escalation demo: the ledger accrues server-side on turn 1's block regardless of what the client resends, so turn 2 still escalation-blocks. This also removes the double-`user`-bubble artifact.

## Minor

### 🟡 The `error` outcome drops the session id, `console/src/api.ts`

`{ kind: 'error' }` carries no `sessionId`, but `chat.py:160-163` (the 502 path) and the fail-closed 503 both set `X-Session-Id` and have already created real `Session` + `Execution` rows. A first-turn upstream failure therefore orphans that session — the drilldown link never appears and the next send starts fresh. Widen the `error` variant to `{ kind: 'error'; message: string; sessionId: string | null }` and pass it through.

### 🟡 FastAPI `{"detail": ...}` bodies degrade to a generic message, `console/src/api.ts`

`_resolve_workload` / `_resolve_session` raise `HTTPException` (`chat.py:279`, `:284`, `:307`), which FastAPI serializes as `{"detail": ...}`, not the `{"error": {...}}` envelope `sendChatCompletion` parses. So the unknown-workload `400` and the cross-workload `400` both render as "ControlPlane returned 400.". A `record.detail` string fallback is one line and makes the workload-mismatch case self-explanatory.

### 🟡 Typed text is lost on a network error, `console/src/Playground.tsx`

`setPrompt('')` fires before the request. On `kind: 'error'` — including the pure network case where nothing reached the server — the text is gone and the user must retype to retry. Restore it on error.

### 🟡 `Accepted` spec has AC text its own build contradicts, `.agents/prompts/10.1-prompt-playground-page-plan.md`

AC-8 ("transcript unchanged" on error) and AC-9 ("changing the model … clears the transcript") are both contradicted by deliberate, `decisions.md`-logged deviations. The rationale is sound; the AC wording should be amended to match, not left standing.

### 🟡 The "Evaluating…" bubble is not announced, `console/src/Playground.tsx`

The outcome panels correctly use `role="alert"`; the in-flight bubble has no `role="status"` / `aria-live`, so a screen reader gets no signal that a request is running. `LiveFeed.tsx:151` sets the `role="status"` precedent.
