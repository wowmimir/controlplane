# 7.1. Review Fixes (Majors + Minors)

**Date**: 2026-08-25
**Status**: Accepted (built same session)

## Summary

`/check review` on the `phase6` branch (`docs/reviews/2026-08-25-phase6.md`, 71 files, Phases 2.4-6.2, reviewed on opus) returned "Changes requested": 5 Majors, 9 Minors, 9 Nits. The user chose scope **Majors + Minors** — the 9 Nits stay deferred, logged as Known Follow-ups in `STATUS.md`, not built. Of the 9 Minors, 2 are documentation-only (one is a judgment call the project already ratified in 3.2 — not being re-litigated — the other a pure README gap); the remaining 7 Minors and all 5 Majors get real code fixes. This closes out the review, not a new feature milestone — no new `STATUS.md` phase-goal, just "Phase 7 — Review Fixes."

## Context

Full finding details, line numbers, and the reviewer's own reasoning are in `docs/reviews/2026-08-25-phase6.md` — this spec does not repeat that analysis, only records the fix decisions and any judgment calls made while implementing them.

## Requirements

**Major fixes:**
- **AC-M1**: an internal failure during `_run_request_side_interception`'s or `_run_response_side_interception`'s ledger-update step, after a block decision is already finalized (and, for two of the three sites, already committed to Postgres), must not lose that decision — the caller still gets the `403`, and no duplicate `Execution` row is created via a fail_open fallthrough to `call_model`. The `Execution` row for a successful model call is committed immediately after `flush()`, not left pending through response-side interception.
- **AC-M2**: `apply_ledger_update` is atomic under concurrent callers on the same session — two overlapping updates (e.g. a background expensive-tier write racing the next turn's request-side read) must both be reflected, not one silently lost to a last-writer-wins race.
- **AC-M3**: the console never asserts "new turns block immediately" for a session whose Redis ledger TTL has already expired — the escalation banner/pill visibly distinguish live vs. expired ledger state, derived from the already-present `ttl_expires_at`.
- **AC-M4**: README/demo-script/console UI no longer claim `policy_profile`, `latency_budget_ms`, or `cost_budget_per_request` are enforced by the evaluation path — only `fail_mode` is.
- **AC-M5**: following the README quickstart verbatim on a fresh clone produces a working console (`VITE_API_BASE_URL` resolves to a real value, not `undefined`).

**Minor fixes:**
- **AC-N1**: editing a workload through the console UI preserves any metadata key not managed by the form.
- **AC-N2**: clicking Resume in Live Feed issues exactly one feed request, even under React StrictMode's double-invoked updaters.
- **AC-N3**: the first Live Feed page load shows no "just arrived" highlight on any row.
- **AC-N4**: no highlight `setTimeout` fires (or leaks) after the Live Feed component unmounts.
- **AC-N5**: `seed_demo.py`'s `_extract_number` correctly parses the model's actual numeric answer out of a reply that contains other digits (e.g. an echoed multiplication), rather than concatenating every digit in the reply.
- **AC-N6**: `seed_demo.py` accepts a `--model` flag so it can be pointed at a non-default model.
- **AC-N7**: `decisions.md` names the same-turn multi-strike effect the review surfaced as a documented, accepted consequence of 3.2's already-ratified per-`Finding` strike counting. No code change.
- **AC-N8**: `README.md`'s Known limitations names the console write API's lack of authentication, alongside the existing header-spoofing bullet. No code change.
- **AC-N9**: a request with no `X-Workload-Id` header, when the seeded default workload row is somehow missing, returns a clean `503` rather than a raw `500`/`AttributeError`.

## Decision

**Chosen option**: fix all 5 Majors and 7 of the 9 Minors in code; the remaining 2 Minors (N7, N8) get a documentation entry only, since one (N7) is a already-ratified Fork #3/3.2 reading being re-surfaced, not a bug, and the other (N8) is a documentation gap, not a missing behavior this build intends to add (no auth work is in scope for this hackathon build, per the standing decision from 2026-08-23/2026-08-24). Full design for each fix (exact code shape) is recorded in the approved plan this session; see the corresponding commit diff for the final implementation — this spec documents the decision and rationale, not a line-by-line diff.

### M1 — Execution commit timing + ledger-failure resilience (`app/routers/chat.py`)
`db.commit()` now happens immediately after `db.flush()` for a successful model call's `Execution` row (was: flush-only, commit deferred into response-side interception — an exception before that commit rolled the row back under `fail_open`). A new `_safe_ledger_update()` wrapper replaces the raw `apply_ledger_update` + `_sync_session_ledger` pair at the three call sites where a block decision is already final: the request-side escalation early-return, the request-side cheap-tier-violation branch, and the response-side violation branch. On failure it logs and returns `None`; the caller still returns its already-decided block response. The response-side **clean** branch's ledger call is deliberately left unwrapped — no decision is final there yet, so an internal failure correctly falls through to 3.3's existing `fail_open`/`fail_closed` handling in `chat_completions`.

### M2 — Atomic ledger read-modify-write (`app/redis_client.py`)
`apply_ledger_update` now uses a `WATCH`/`MULTI`/`EXEC` optimistic-locking transaction (`redis.asyncio`'s pipeline, `transaction=True`) instead of a plain GET then SET, retrying on `WatchError` (bounded at 10 attempts, raising if exceeded — contention this high would mean something else is badly wrong). The decay/strike-stamp/prune math itself is unchanged; only the read-then-write is made atomic. No new dependency (`redis` already provides `redis.exceptions.WatchError`).

### M3 — Console ledger-liveness display (`console/src/lib/format.ts`, `Sessions.tsx`, `SessionDetail.tsx`)
No backend/schema change. A new `isLedgerLive(ttlExpiresAt)` helper in `format.ts` (same client-side-derivation pattern `Sessions.tsx` already uses for `lastActivity`) compares `ttl_expires_at` against `Date.now()`. `Sessions.tsx`'s `EscalatedPill` shows a muted "Escalated (expired)" variant when the ledger has expired; `SessionDetail.tsx`'s banner switches to past tense and drops the "blocks immediately" claim in the same case.

### M4 — Dead policy fields (`README.md`, `docs/demo-script.md`, `console/src/components/WorkloadForm.tsx`)
Documentation-only plus one small form helper-text addition. No enforcement logic is added — that would be new, unscoped functionality (this build's evaluation path never reads `policy_profile`/`latency_budget_ms` for anything but a no-op stub, and `cost_budget_per_request` is read nowhere at all). The fix is to stop the docs/UI claiming otherwise.

### M5 — Console quickstart (`console/.env.example` new, `README.md`, `console/src/api.ts`)
New `console/.env.example`. README quickstart gains a `cp .env.example .env` step for the console. `api.ts` gains a `?? 'http://localhost:8000'` fallback so a missing env file degrades to a working default instead of `undefined`.

### N1-N9
As designed in the approved plan: `WorkloadForm.tsx`'s `buildMetadata()` preserves unknown keys (N1); `LiveFeed.tsx` moves `poll()` out of the `setPaused` updater into the click handler (N2), adds a first-load guard before computing "arrived" rows (N3), and tracks/clears its highlight timeouts (N4); `seed_demo.py` fixes `_extract_number` to pick the longest contiguous digit run (N5) and gains a `--model` flag (N6); N7/N8 are `decisions.md`/`README.md` entries only; `_resolve_workload` in `chat.py` gets an explicit None-check on the default-workload lookup, mirroring the existing explicit-id branch (N9).

## Rationale

Every fix here targets a concrete, reviewer-verified failure mode, not a style preference — this is why Majors got full code fixes despite the project's hackathon speed norms (`AGENTS.md` §8 explicitly skips test suites and PR docs, not correctness fixes for a completed build). N7 and N8 are the exception: N7 would mean reopening a decision 3.2 already ratified twice (2026-08-24, citing Fork #3's literal wording) on the strength of the same review's own framing ("I'm flagging the *effect*, not the rule"); N8 is a docs gap on top of an already-accepted hackathon-scope limitation (no auth anywhere in the console API), not a new behavior to build. Fixing either in code now would be scope creep the review itself didn't ask for.

## Consequences

**Positive**:
- Closes the two correctness/security-adjacent Majors (M1 audit-trail loss, M2 ledger race) that most directly undermine the product's core claim (a durable, accurate audit trail and risk ledger).
- Console and docs no longer assert things that are false (M3 stale escalation claim, M4 dead policy fields, M5 broken quickstart) — all three were things a demo audience or a fresh clone would hit directly.
- Live Feed's three React bugs (N2-N4) are exactly the kind of thing that surfaces mid-demo under StrictMode/dev conditions.

**Negative / tradeoffs**:
- M2's bounded-retry CAS loop adds a small amount of latency under real contention (negligible at this project's traffic volume) and one new failure mode (`RuntimeError` after 10 failed attempts) that did not exist before — accepted, since silent data loss is strictly worse.
- M1's `_safe_ledger_update` means a ledger write can now fail silently (logged only) on an already-decided block — the block still happens (correct caller-facing behavior), but the ledger/strike state for that turn may not reflect it. This is the same best-effort tradeoff `_sync_session_ledger` already made for the Postgres mirror; extending it to the Redis write itself at these three sites is a deliberate, matching choice, not a new risk class.

**Neutral**:
- No automated test suite, per `AGENTS.md` §8 — verification is live, targeted self-checks (see the approved plan's Verification section) plus the standing regression suite.
