# 0.1. FastAPI skeleton with a health endpoint

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec covers the very first piece of code in the project: a bare FastAPI (a Python web framework) application that starts up and answers `GET /health` with a 200 response. Nothing else lives here yet, no database, no proxy logic, just proof that the app boots and responds. It also locks in the project layout and tooling (dependency manager, folder structure) so every later phase builds on the same foundation instead of needing a rewrite.

## Context

Nothing has been built in this project yet: no source files exist, and the repository is not yet under version control. `forks.md` locks the tech stack (Python, FastAPI, async native) but says nothing about how the project should be laid out on disk, which dependency manager to use, or what a first "it's alive" endpoint should look like. `STATUS.md` names this milestone explicitly: "FastAPI app, `/health` endpoint returns 200", and calls it the entry point for Phase 0, the foundation every later phase (the proxy, evaluators, ledger, audit trail, console) is built on top of.

The project is a hackathon build (`AGENTS.md`): speed matters, automated tests and documentation are explicitly out of scope for now, but the milestones ahead (Phase 1 through 6) will keep adding routers, database models, and background tasks to whatever gets scaffolded here. A structure that has to be reshuffled partway through Phase 1 costs more time than it saves now.

## Requirements

**User stories**:
- As the engineer running this project, I want a FastAPI app that starts locally with one command, so I can begin building the proxy endpoint on top of it.
- As an external process (a load balancer, an orchestrator, or a person during the live demo), I want a `/health` endpoint that confirms the service is up, so I can tell the app is running before relying on it.

**Acceptance criteria**:
- **AC-1**: Running the documented start command launches the FastAPI app with no errors.
- **AC-2**: `GET /health` returns HTTP status 200 while the app is running.
- **AC-3**: The `/health` response body is valid JSON containing `{"status": "ok"}`.
- **AC-4**: The start command and port are written down somewhere in the repo, so a later session (or a teammate) can run the app without guessing.

## Options considered

### Option 1: Minimal single file (`main.py` at repo root, pip + venv)

One file, no package structure, dependencies tracked in a `requirements.txt` installed into a plain `venv`.

**Pros**:
- Fastest possible start, nothing to set up beyond `pip install`.
- Everyone already knows pip and venv, zero new tooling to learn.

**Cons**:
- Phase 1 adds routers, Phase 2 adds database models; a flat file gets restructured almost immediately, and that rework is pure waste.
- `requirements.txt` has no lockfile, so two sessions (or two machines) can silently drift to different dependency versions.

### Option 2: Package layout with `uv` (recommended)

An `app/` package (`app/main.py` as the entry point) that later phases extend with `app/routers/`, `app/models/`, `app/evaluators/`, etc. Dependencies and the Python environment are managed by `uv`, a fast, modern dependency manager that writes a lockfile.

**Pros**:
- The layout already has room for every later phase's additions, no restructuring needed as the proxy, evaluators, and ledger logic arrive.
- `uv`'s lockfile makes the environment reproducible across sessions, important since this project will span many chat sessions per `AGENTS.md`'s workflow.
- `uv` is fast enough that the extra tooling doesn't cost meaningful hackathon time.

**Cons**:
- `uv` is newer and less universally familiar than pip; anyone else touching this repo needs one extra install step (`pip install uv` or the standalone installer).
- Marginally more ceremony than a single file for something this small, though the payoff arrives within the next milestone.

### Option 3: Full production scaffold now (routers/, services/, tests/, Docker, CI)

Set up the complete structure a production service would eventually want, including a test harness and containerization, before writing the first endpoint.

**Pros**:
- Nothing to add structurally later; the shape is "done" from day one.

**Cons**:
- Directly conflicts with `AGENTS.md` Section 8 ("DO NOT write automated test suites", "DO NOT run a full sync reconciliation"); this is explicitly out of scope for a hackathon MVP.
- Spends Phase 0 time on infrastructure with no near term payoff, when `STATUS.md` explicitly asks for a thin end to end slice first.

## Decision

**Chosen option**: Option 2: Package layout with `uv`

Build the skeleton as an `app/` package with `app/main.py` as the FastAPI entry point, managed by `uv`.

## Rationale

`forks.md` already locks FastAPI and Python, so the open question is purely how to lay the project out and what to build with. `STATUS.md`'s own instruction, get a thin end to end slice working before deepening any phase, argues against Option 3's upfront scaffold, and against anything that will need reshuffling once Phase 1 (the proxy) and Phase 2 (the evaluators) land inside this same app. Option 1 is simplest today but fails that test almost immediately: routers and models are two milestones away. Option 2's package layout absorbs both without a rewrite, and `uv`'s lockfile keeps the environment consistent across the many separate sessions this hackathon build will span, which matters more here than in a single sitting project.

## Feature design

**Data model sketch**:
Not applicable to this milestone. No persistence layer exists yet: Postgres models arrive in Phase 0.2, the Redis ledger in Phase 0.3, per `STATUS.md`.

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| /health | GET | none | `{"status": "ok"}`, HTTP 200 | none (public) | none expected; a non 200 means the process itself is down |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| GET /health | `status` field | Literal constant `"ok"`, hardcoded in the handler; no dependency checks run in 0.1 since there is nothing to check yet (no DB, no Redis) |

**Key invariants**:
- `/health` returns 200 whenever the app process is up; it is a pure liveness probe, not a dependency check, since there is nothing downstream to verify yet.
- The endpoint has no side effects; a GET request never mutates state.

**Security model**:
No authentication or authorization. `/health` is intentionally public, standard practice for liveness probes that load balancers and orchestrators must be able to call without credentials. No sensitive data is exposed.

**Configuration required**:
None for this milestone. `DATABASE_URL` and `REDIS_URL` will be introduced in 0.2 and 0.3 respectively; do not add them here.

**Critical test scenarios**:
- Happy path: start the app with the documented command, `curl http://localhost:8000/health` returns 200 with body `{"status": "ok"}`, verifies **AC-1**, **AC-2**, **AC-3**.
- Failure case: an import error or bad dependency is surfaced immediately at process startup (the command exits with a visible traceback), not silently, verifies **AC-1**.
- Auth/permission: not applicable, `/health` is intentionally unauthenticated by design; no AC covers restricting it.

## Build plan

1. Initialize the project with `uv` (`pyproject.toml`, `.venv`, lockfile); add `fastapi` and `uvicorn` as dependencies, satisfies **AC-1**.
2. Create the `app/` package with `app/main.py` instantiating the FastAPI app, satisfies **AC-1**.
3. Implement `GET /health` returning `{"status": "ok"}` with HTTP 200, satisfies **AC-2**, **AC-3**.
4. Document the run command (`uvicorn app.main:app --reload --port 8000`) directly in `app/main.py` or a short note in the repo, satisfies **AC-4**.
5. Self-check: run the app, `curl /health`, confirm the 200 response and JSON body match AC-2 and AC-3 (per `AGENTS.md`'s Slim Workflow, no automated test suite for this milestone).

## Consequences

**Positive**:
- Unblocks Phase 1 (the proxy) immediately; the `app/` package layout absorbs routers and models without restructuring.
- `uv`'s lockfile keeps the environment reproducible across the many separate sessions this hackathon build will span.

**Negative / tradeoffs**:
- `uv` is a newer tool than pip; anyone new to the repo needs one extra install step.
- The package layout is very slightly more setup than a single file, for a milestone this small.

**Neutral**:
- No automated tests are written for this milestone, per `AGENTS.md` Section 8.
- No Docker or CI is introduced; that stays out of scope unless a later milestone calls for it.
