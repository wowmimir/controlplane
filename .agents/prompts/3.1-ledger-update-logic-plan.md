# 3.1. Ledger Update Logic

**Date**: 2026-08-24
**Status**: Accepted

## Summary

This spec closes two real gaps in the session ledger and removes a code duplication problem, all at once, per `STATUS.md`'s own framing of 3.1 as pairing "exact decay math" with "strike-window expiry." First, `cumulative_risk` currently only ever moves when a violation happens; it never decays on a clean turn, so a session's risk score can stay stuck at an old value forever even after many safe exchanges. Second, per-category strikes never expire, even though Fork #3 says only strikes from the last 5 turns or last 2 minutes should count; today's ledger has no way to even know when a strike happened. Third, the same 25-ish lines of ledger-update code are copy-pasted three times in `app/routers/chat.py`. This spec adds a `turn` counter and per-strike timestamps to the Redis ledger, a single shared `apply_ledger_update` helper that does the decay/pruning/strike math once, and touches the ledger on every turn (clean or not) so decay is actually continuous. It does not implement the escalation check itself (blocking on `cumulative_risk > 0.7` or `strikes >= 3`) — that is Phase 3.2's job; this spec only makes sure the numbers 3.2 will read are correct.

## Context

`forks.md` Fork #3 locks the math exactly:
```
cumulative_risk = (cumulative_risk * 0.7) + execution_risk_score
```
and: "Strike window: only strikes from the last 5 turns OR last 2 minutes count. Older strikes expire out of the window." `STATUS.md` names 3.1 as: "Implement exact math from `forks.md` Fork #3... per-category strikes with 5-turn/2-min window expiry."

Read in full this session (not guessed): `app/redis_client.py` (56 lines), `app/routers/chat.py` (383 lines), `app/models/session.py` (42 lines), `app/models/enums.py`, `app/evaluators/types.py`. Confirmed:

- **The live ledger shape has no timestamp or turn data at all**: `{"cumulative_risk": float, "strikes": {category: int}}`. There is no field recording *when* a strike happened, so "expires after 5 turns or 2 minutes" cannot be implemented against today's shape at all — this is new storage, not just new logic.
- **`get_ledger`/`set_ledger` are called from exactly three places, all in `app/routers/chat.py`**: `_run_request_side_interception` (a request-side violation), `_run_response_side_interception` (a response-side violation), and `_run_expensive_tier_task` (an async expensive-tier finding, scheduled via `BackgroundTasks` after the response has already released). All three run the identical sequence: `get_ledger` → `cumulative_risk = cumulative_risk * LEDGER_DECAY_FACTOR + execution_risk_score` → loop candidates incrementing `strikes[category]` when `confidence > STRIKE_THRESHOLD` → `set_ledger`. `LEDGER_DECAY_FACTOR = 0.7` and `STRIKE_THRESHOLD = 0.7` are module constants in `chat.py`, not `redis_client.py`.
- **A clean turn never touches the ledger at all.** In `_run_response_side_interception`, when cheap tier and 2.4's medium-tier stub both find nothing, the code sets `execution.execution_risk_score = 0.0`, commits, schedules the expensive-tier background task, and returns — no `get_ledger`/`set_ledger` call anywhere on this path. `decisions.md`'s 1.5 entry names this exact gap and explicitly defers it here: "Fork #3's 'continuous decay' framing... is a known, explicitly flagged gap left for Phase 3.1... rather than quietly implemented [in 1.5]." `STATUS.md`'s Known Follow-ups (Phase 3.1 line) repeats the same deferral for the code-duplication problem.
- **`Session.cumulative_risk`/`Session.strikes` (Postgres columns) are confirmed dead**: written once via ORM `default=` at row creation, never updated anywhere in the codebase. Redis is the sole live ledger store (matches the inline comment in `session.py` and the 1.3 `decisions.md` entry). `Session.ttl_expires_at`, by contrast, is actively maintained on every request. This spec does not touch the Postgres columns — that reconciliation is explicitly Phase 4's job.
- **The 6-category taxonomy is independently duplicated as raw strings in three places** (`redis_client.py`'s `STRIKE_CATEGORIES`, `session.py`'s `DEFAULT_STRIKES`, and the `FindingCategory` enum itself) with no single source of truth. Out of scope to fully unify here (would touch `session.py`, not part of this spec's job), but the new code this spec adds should not add a fourth copy.
- **Cheap-tier matches are always `confidence=0.95`** (a fixed constant in `types.py`, always `> STRIKE_THRESHOLD`), so every cheap-tier violation is always a strike. Expensive-tier (LLM judge) confidence varies (self-check in 2.5 showed 0.99 on a real finding). Medium tier is a permanent stub, always `[]`, never contributes.
- **The 403 envelope construction is duplicated** between `_run_request_side_interception` and `_run_response_side_interception` (`primary`/`categories` derivation + the `JSONResponse` body), differing only in wording ("Request blocked... in input" vs "Response blocked... in output"). `STATUS.md`'s Known Follow-ups names both the ledger helper and this envelope helper in the same breath (`_update_ledger`, `_policy_block_response`), so extracting both is in scope for this milestone, not separate cleanup.

**Design decisions made before writing this spec** (via `/architect`'s research and one question ratified with the user):

1. **Strike-window semantics are union, not intersection.** A strike survives as long as it is within the last 5 turns *or* within the last 2 minutes — it only expires once *both* conditions have failed. This is the literal grammatical reading of Fork #3's own "OR" wording, confirmed directly with the user (a fast burst of turns won't kill a strike in under 2 minutes; a slow trickle of turns won't kill it before 5 turns pass).
2. **A "turn" is one concluded HTTP request to `/v1/chat/completions`.** The ledger gets touched exactly once per request: either at a request-side block, or at the response-side conclusion (block or clean) of a request-side-clean call. A request-side-clean pass-through never gets its own separate ledger touch, since it always continues on to that same request's response-side conclusion — touching both would double-count one exchange as two turns.
3. **The async expensive-tier task never increments the turn counter**, but does still apply the full decay formula against the ledger's live state when it finds something. This means a turn whose expensive-tier verdict arrives late gets decayed twice for one human exchange (once synchronously at `execution_risk_score=0.0`, once again later for real) — accepted as a deliberate, self-correcting quirk (it fully washes out after one more clean turn) per Fork #4's own wording that the async task "can only... update the session ledger for future turns." What is *not* accepted as a quirk: letting the async task bump the turn counter, since a wrong turn counter would corrupt the 5-turn window for every subsequent strike check for the rest of the session — a much larger and non-self-correcting blast radius.

## Requirements

**User stories**:
- As the engineer building Phase 3.2 next, I want `ledger["cumulative_risk"]` and `ledger["strikes"][category]` to already be correct, windowed numbers, so 3.2's escalation check is a one-line comparison with no ledger logic of its own.
- As the operator of a long, mostly-clean session, I want `cumulative_risk` to actually fade over time instead of freezing at whatever it was after the last violation, so the ledger reflects Fork #3's "continuous decay" intent.
- As the engineer maintaining this codebase, I want the ledger-update sequence and the 403 envelope written once, not three and two times respectively, so a future change to either doesn't require finding and editing every copy.

**Acceptance criteria**:
- **AC-1**: A fresh session's first request-side PII match produces a ledger read back as `cumulative_risk=0.95`, `strikes.pii=1`, `turn=1` (regression on the existing math, plus the new `turn` field).
- **AC-2**: Starting from a nonzero `cumulative_risk`, one fully clean exchange (clean request side, clean response side, no expensive-tier finding) leaves the ledger with `cumulative_risk_after == cumulative_risk_before * 0.7` exactly, `strikes` unchanged, and `turn` incremented by exactly 1. This is the core continuous-decay gap this milestone closes.
- **AC-3**: A response-side violation on an otherwise-request-side-clean request advances `turn` by exactly 1 for that whole HTTP request, never 2.
- **AC-4**: Once real time since a strike already exceeds 120 seconds (its time window has independently closed), that strike is still counted while fewer than 5 turns have passed since it was set, and is excluded the instant the 5th subsequent turn lands — the exact turn-boundary, isolated by first letting the time window close.
- **AC-5**: A strike that has already accumulated 5 or more turns since it was set (many quick turns, little real time elapsed) is still counted as long as under 120 seconds have passed since it was set; only once real elapsed time also exceeds 120 seconds does it get excluded — the exact time-boundary, isolated by first letting the turn window close.
- **AC-6**: Six violating turns for the same category, all fired within roughly 10 seconds of each other (so turns-ago reaches 5 but elapsed time stays under 120s), still counts the turn-1 strike at turn 6 — proof that neither window alone expires a strike while the other is still open (union semantics; this is exactly why AC-4/AC-5 each isolate one window by first closing the other, this would fail under an intersection reading).
- **AC-7**: An async expensive-tier finding's strike is stamped with the *original* request's turn and timestamp (captured when that request's synchronous clean-path ledger touch happened), not the ledger's live turn/time whenever the background task happens to finish — so a slow judge call (2.5's self-check showed up to ~11.6s) doesn't unfairly shrink that strike's remaining window.
- **AC-8**: `ledger["turn"]` is bit-for-bit identical immediately before and immediately after an async expensive-tier ledger write — only `cumulative_risk`, `strikes`, and `strike_events` may change on that path.
- **AC-9**: `set_ledger`'s TTL still resets to 900 seconds on every write, including the new clean-turn touches this spec adds.
- **AC-10**: A never-before-seen session still round-trips correctly through `default_ledger()` → `get_ledger` → `set_ledger` with the new shape, and `ledger["strikes"]["pii"] >= 3` / `ledger["cumulative_risk"] > 0.7` both work as plain Python comparisons on the returned dict, with no unwrapping needed — this is the exact shape Phase 3.2 will read.
- **AC-11**: An old-shape blob already in Redis (written by pre-3.1 code, missing `turn`/`strike_events`) does not crash `get_ledger` or `apply_ledger_update` — it upgrades in place on first read.
- **AC-12**: `_policy_block_response`'s output (status code, headers, and JSON body) is byte-identical to today's two inline envelope constructions, for both the request-side and response-side wording — this refactor changes no observable behavior.
- **AC-13**: No escalation/blocking behavior changes. Every existing block-on-any-cheap-tier-match path still blocks unconditionally, regardless of ledger state; 1.2's `400`s, 1.4's `502`, and all six taxonomy categories' existing block behavior (1.3, 1.5, 2.1, 2.2, 2.5, 2.6) are unaffected.

## Options considered

### Option 1: Add a per-category list of strike-event timestamps, prune on every read/write, keep `strikes[category]` as a materialized int count (recommended)

Extend the ledger with `"turn": int` and `"strike_events": {category: [{"turn": int, "ts": float}, ...]}`. `strikes[category]` stays a plain int, always recomputed as `len(strike_events[category])` immediately after pruning expired entries, so it is never hand-maintained separately from the events that justify it.

**Pros**: `strikes[category]` keeps the exact same shape Phase 3.2 needs to read (`ledger["strikes"]["pii"] >= 3`), zero adaptation required on 3.2's side; the event list is the only new concept, and it lives entirely inside `redis_client.py`.
**Cons**: A small amount of duplication (the int is always derivable from the list) — accepted, since it buys 3.2 a plain-int contract for free instead of pushing windowing logic into escalation-check code that shouldn't need to know about it.

### Option 2: Store only the event lists; anyone who needs a count computes `len()` at the point of use

Drop the materialized `strikes[category]` int entirely; every reader (including 3.2's future escalation check) calls a shared "current strike count" function.

**Pros**: No duplicated state, one clear source of truth (the event list).
**Cons**: Pushes windowing/pruning knowledge into every future consumer of the ledger, including Phase 3.2, which should be able to treat the ledger as "just read the numbers" per this spec's whole purpose. Worse fit for `STATUS.md`'s framing of 3.1 as the phase that finishes the ledger so later phases don't have to.

### Option 3: Track only a single "last strike timestamp/turn" per category, no event list, and expire the whole category's count at once when the window closes

**Pros**: Smallest possible storage shape.
**Cons**: Loses the actual count. If a category takes 3 strikes at turns 1, 2, and 3, then 4 more clean turns pass, "last strike" data alone can't tell you whether 1, 2, or 3 of those strikes are still inside the window — it can only tell you whether *any* strike is still inside it. Fork #3's escalation condition (`strikes[category] >= 3`) genuinely needs a count, not a boolean, so this option can't actually implement the locked requirement.

## Decision

**Chosen option**: Option 1 — per-category strike-event lists with a materialized int count, plus a new top-level `turn` counter, and a single shared `apply_ledger_update` helper (see Feature design) replacing the three duplicated call sites.

## Rationale

Option 3 is eliminated outright: Fork #3's `strikes[category] >= 3` escalation condition needs an actual count of strikes still inside the window, and a single last-strike-time field cannot reconstruct that count once more than one strike has landed. Between Options 1 and 2, the deciding factor is where windowing knowledge should live: `STATUS.md` frames 3.1's entire purpose as finishing the ledger so Phase 3.2 can be "a one-line comparison with no ledger logic of its own" (this spec's own first user story). Option 2 would undercut that by making every future reader, including 3.2's escalation check, re-derive counts from raw event lists. The small duplication Option 1 accepts (an int that is always `len(pruned_list)`) is confined entirely to `apply_ledger_update`, which is the one place responsible for keeping it consistent — the same "materialized view, single writer" shape already used elsewhere in this codebase for computed fields.

The turn-counter design (union semantics, one touch per HTTP request, async task never advances it) was ratified directly with the user for the one genuinely ambiguous point (union vs intersection) and follows expert judgment for the rest: a wrong turn count is worse than a wrong risk score, because it corrupts every future strike-window check for the rest of the session, while a double-decayed risk score self-corrects after one more clean turn.

## Feature design

**Data model sketch**: no Postgres schema change (`Session.cumulative_risk`/`.strikes` remain dead, unaddressed here). New Redis ledger shape:

```json
{
  "cumulative_risk": 0.0,
  "turn": 0,
  "strikes": {"pii": 0, "hallucination": 0, "toxicity": 0, "bias": 0, "prompt_injection": 0, "custom_policy": 0},
  "strike_events": {"pii": [], "hallucination": [], "toxicity": [], "bias": [], "prompt_injection": [], "custom_policy": []}
}
```
`strike_events[category]` entries: `{"turn": int, "ts": float}` (one Unix timestamp per strike-worthy finding).

**Changed file**: `app/redis_client.py` — gains the aggregation math the module's own docstring already earmarks as "Phase 3's job":

```python
import time

STRIKE_WINDOW_TURNS = 5
STRIKE_WINDOW_SECONDS = 120
LEDGER_DECAY_FACTOR = 0.7
STRIKE_THRESHOLD = 0.7


def default_ledger() -> dict[str, Any]:
    return {
        "cumulative_risk": 0.0,
        "turn": 0,
        "strikes": {category: 0 for category in STRIKE_CATEGORIES},
        "strike_events": {category: [] for category in STRIKE_CATEGORIES},
    }


def _upgrade_ledger(ledger: dict[str, Any]) -> dict[str, Any]:
    ledger.setdefault("turn", 0)
    ledger.setdefault("strike_events", {category: [] for category in STRIKE_CATEGORIES})
    return ledger


async def get_ledger(session_id: str) -> dict[str, Any]:
    raw = await redis_client.get(_ledger_key(session_id))
    if raw is None:
        return default_ledger()
    return _upgrade_ledger(json.loads(raw))


def _prune_and_count(events: list[dict], current_turn: int, now_ts: float) -> tuple[list[dict], int]:
    live = [
        e for e in events
        if (current_turn - e["turn"] < STRIKE_WINDOW_TURNS) or (now_ts - e["ts"] < STRIKE_WINDOW_SECONDS)
    ]
    return live, len(live)


async def apply_ledger_update(
    session_id: str,
    execution_risk_score: float,
    strikes_input: list[tuple[str, float]],
    *,
    is_new_turn: bool = True,
    turn_anchor: int | None = None,
    ts_anchor: float | None = None,
) -> dict[str, Any]:
    ledger = await get_ledger(session_id)
    now_ts = time.time()
    ledger["cumulative_risk"] = ledger["cumulative_risk"] * LEDGER_DECAY_FACTOR + execution_risk_score
    if is_new_turn:
        ledger["turn"] += 1
    stamp_turn = turn_anchor if turn_anchor is not None else ledger["turn"]
    stamp_ts = ts_anchor if ts_anchor is not None else now_ts
    for category, confidence in strikes_input:
        if confidence > STRIKE_THRESHOLD:
            ledger["strike_events"][category].append({"turn": stamp_turn, "ts": stamp_ts})
    for category in STRIKE_CATEGORIES:
        live, count = _prune_and_count(ledger["strike_events"][category], ledger["turn"], now_ts)
        ledger["strike_events"][category] = live
        ledger["strikes"][category] = count
    await set_ledger(session_id, ledger)
    return ledger
```

`LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD` move here from `chat.py` (removed from `chat.py`'s module scope, imported instead).

**Changed file**: `app/routers/chat.py` — four call sites:

1. `_run_request_side_interception` (violation): replace the inline `get_ledger`/decay/loop/`set_ledger` block with
   `await apply_ledger_update(str(session.session_id), execution_risk_score, [(c.category.value, c.confidence) for c in candidates])`.
2. `_run_response_side_interception` (violation): same call shape as #1.
3. `_run_response_side_interception` (**new** clean-path branch, where `execution.execution_risk_score = 0.0` is set today): add
   `ledger = await apply_ledger_update(str(session.session_id), 0.0, [])`, then pass `turn_anchor=ledger["turn"]` and a captured `ts_anchor=time.time()` (captured at the same point, immediately after the call) into the existing `background_tasks.add_task(_run_expensive_tier_task, ...)` call as two new keyword arguments.
4. `_run_expensive_tier_task`: accepts the two new `turn_anchor`/`ts_anchor` parameters and calls
   `await apply_ledger_update(str(session_id), execution.execution_risk_score, [(c.category.value, c.confidence) for c in candidates], is_new_turn=False, turn_anchor=turn_anchor, ts_anchor=ts_anchor)`.

**New helper** `_policy_block_response(side: Literal["request", "response"], candidates: list[FindingCandidate]) -> JSONResponse` in `app/routers/chat.py`, replacing the duplicated envelope construction in both interception functions:

```python
def _policy_block_response(side: Literal["request", "response"], candidates: list[FindingCandidate]) -> JSONResponse:
    primary = max(candidates, key=lambda c: c.confidence)
    categories = sorted({c.category.value for c in candidates})
    verb, noun = ("Request", "input") if side == "request" else ("Response", "output")
    return JSONResponse(
        status_code=403,
        content={
            "error": {
                "message": f"{verb} blocked by ControlPlane: {', '.join(categories)} detected in {noun}.",
                "type": "controlplane_policy_violation",
                "param": None,
                "code": primary.category.value,
            }
        },
    )
```
Pure refactor: both interception functions call `_policy_block_response("request", candidates)` / `_policy_block_response("response", candidates)` instead of constructing the dict inline. No behavior change (AC-12).

**Value sourcing**:
| Action | Value produced | Source |
|---|---|---|
| Any ledger touch | `execution_risk_score` | max confidence across the candidates for this call (unchanged, Fork #2 rule already in place) |
| Any ledger touch | `turn` incremented or not | `is_new_turn` flag, decided by call site per the ratified "one touch per HTTP request" rule |
| A strike event's stamp | `turn`/`ts` | current ledger `turn`/`time.time()` for a synchronous call; the captured `turn_anchor`/`ts_anchor` (from the original request's clean-path touch) for the async expensive-tier call |
| Strike-window pruning | "is this event still live" | computed from `ledger["turn"]` (live, current) and `time.time()` (live, current) at the moment of pruning — never from a stale/anchored value, only the event's own stamp is ever anchored |

**Key invariants**:
- Exactly one `apply_ledger_update` call per concluded HTTP request (request-side block, or the response-side conclusion of a request-side-clean call) — never zero, never two, for the same request.
- The async expensive-tier task's `apply_ledger_update` call always passes `is_new_turn=False`; nothing else in the codebase is allowed to pass `is_new_turn=False`.
- Pruning always compares against the ledger's live `turn`/`time.time()` at prune time; only a strike event's *own* stamp may be anchored to an earlier moment.
- `strikes[category]` is never written directly; it is only ever the pruned length of `strike_events[category]`, recomputed inside `apply_ledger_update`.
- No code outside `app/redis_client.py` reads or writes `strike_events`, `LEDGER_DECAY_FACTOR`, or `STRIKE_THRESHOLD` directly — `chat.py` only calls `apply_ledger_update`.

**Security model**: unchanged — no new external exposure, this is internal ledger bookkeeping.

**Configuration required**: none (no new env vars).

**Critical test scenarios** (each maps to an acceptance criterion above):

## Consequences

**Positive**:
- `cumulative_risk` now genuinely decays across clean turns, closing the gap `decisions.md`'s 1.5 entry explicitly flagged and deferred here.
- Strikes now actually expire per Fork #3's locked window, which Phase 3.2's escalation check can rely on without any ledger logic of its own.
- The triplicated ledger-update block and the duplicated 403 envelope are both gone, replaced by one helper each — the exact cleanup `STATUS.md`'s Known Follow-ups asked for.
- `LEDGER_DECAY_FACTOR`/`STRIKE_THRESHOLD`/the window constants now live in the one module (`redis_client.py`) whose own docstring already claimed this job.

**Negative / tradeoffs**:
- A turn whose expensive-tier verdict arrives asynchronously gets its risk score decayed twice for one human exchange (once synchronously at 0.0, once again for real later). Accepted as self-correcting and explicitly logged, not fixed, per this spec's own Rationale.
- The ledger now grows slightly (an event list per category instead of a bare int), still small and bounded by the window (at most a handful of live events per category at any time) and by the existing 15-minute TTL.
- `Session.cumulative_risk`/`.strikes` in Postgres remain dead columns; this spec does not reconcile them, that stays Phase 4's explicit job.
