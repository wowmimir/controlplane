# 0.3. Redis client and session ledger read/write helper

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec connects the app to Redis (Upstash) and adds a minimal read/write helper for the session ledger described in `forks.md` Fork #3, with the 15-minute inactivity TTL that fork requires. It deliberately stops there: the ledger's actual math (decaying `cumulative_risk`, per-category strike windows, the escalation trigger) is `STATUS.md`'s Phase 3 work (`3.1 Ledger Update Logic`, `3.2 Escalation Check`), not this milestone's. This spec only needs a session's ledger to be gettable and settable, with a sane empty default and a TTL that resets on every write.

## Context

`forks.md` Fork #3 locks Redis, keyed by `session_id`, as the storage for the "lightweight risk ledger," with a 15-minute TTL that resets on inactivity, and locks the ledger's two data fields: `cumulative_risk` (float) and `strikes` (all six categories from the locked taxonomy, always present). `STATUS.md` names this milestone directly: "Connect to Redis (Upstash). Ledger read/write helper with TTL support (15 min)." It does not ask for the decay formula, the strike-window expiry logic, or the escalation check — those are separately itemized under Phase 3, later in the same file, and `STATUS.md`'s own instructions say not to reorder phases.

One constraint not in any locked file: the `REDIS_URL` already present in this project's `.env` points at an Upstash database that is **shared with another, unrelated project** (confirmed directly with the engineer in this session). Nothing in `forks.md` or `decisions.md` anticipated this, so every key this app writes must be namespaced to avoid colliding with that other project's keys, resolved below rather than assumed silently.

Nothing calls this helper yet. Phase 1's proxy and Phase 3's ledger logic are the first real callers; this milestone only needs `get_ledger`/`set_ledger` to exist and round-trip correctly.

## Requirements

**User stories**:
- As the engineer building Phase 3's ledger math, I want a `get_ledger`/`set_ledger` pair that already speaks the correct data shape and TTL, so Phase 3 only has to add the aggregation logic, not the storage plumbing.
- As the engineer sharing one Upstash database across multiple projects, I want this app's keys clearly namespaced, so a bug or manual inspection here can never read or clobber the other project's data.

**Acceptance criteria**:
- **AC-1**: Starting the app with the existing `REDIS_URL` connects successfully; a deliberately broken `REDIS_URL` fails fast at startup (not on first request).
- **AC-2**: `get_ledger(session_id)` for a `session_id` with no existing key returns the default ledger shape (`cumulative_risk: 0.0`, all six `strikes` categories at `0`), never an error.
- **AC-3**: `set_ledger(session_id, ledger)` followed by `get_ledger(session_id)` returns exactly the values written (a manual round-trip check, per `AGENTS.md` section 8's skip-automated-tests rule).
- **AC-4**: Every key `set_ledger` writes carries a TTL of 900 seconds (15 minutes) at write time, per Fork #3.
- **AC-5**: Every key this app writes to Redis is prefixed so it cannot collide with keys from the other project sharing this Upstash database.
- **AC-6**: The Redis connection string is read from an environment variable (`REDIS_URL`), never hardcoded.

## Options considered

### Option 1: `redis` (redis-py) async client over the standard TCP/TLS protocol (recommended)

Add the official `redis` package and use its built-in `redis.asyncio.Redis`, pointed at Upstash's `rediss://` URL.

**Pros**:
- Standard, actively maintained client; same connection-pool pattern this project already uses for Postgres (`create_async_engine` in `app/db.py`), so the codebase stays consistent.
- Upstash exposes a normal Redis-protocol endpoint over TLS; no translation layer needed.

**Cons**:
- Holds an open TCP connection pool, which matters for serverless deployments (cold starts, connection limits) — not a concern here since this app runs as a persistent `uvicorn` process.

### Option 2: `upstash-redis` (Upstash's REST-based SDK)

Upstash's own Python client, which talks to Redis over HTTPS/REST instead of the native protocol.

**Pros**:
- Built for serverless/edge environments where holding a TCP connection open is expensive or impossible.

**Cons**:
- Adds a REST hop (higher latency per call) with no benefit for a long-running server process.
- A second, Upstash-specific client API to learn, when the standard `redis` client already works against Upstash directly.

## Decision

**Chosen option**: Option 1, `redis.asyncio.Redis` over the standard protocol.

Alongside that, two smaller implementation choices are settled here:
- **Every key is prefixed `controlplane:`** (e.g. `controlplane:session:{session_id}:ledger`), directly satisfying **AC-5** given the shared Upstash database.
- **The ledger is stored as one JSON blob per session**, not spread across multiple Redis data structures (hash, sorted set, etc.). This is the simplest shape that satisfies this milestone's AC-2/AC-3 exactly as `forks.md` defines the ledger's two fields; Phase 3 owns whatever internal restructuring its windowed strike-expiry logic ends up needing (see Follow-up).

## Rationale

`forks.md`'s tech stack table already locks "Redis (Upstash)" but not a client library, and this project already established the pattern of resolving open implementation choices in a spec rather than guessing (per `AGENTS.md` Rule 9) — the same way 0.2 resolved primary-key types and enum storage. Option 1 wins because this app is a persistent server, not serverless, so the REST hop Option 2 optimizes for buys nothing here and costs latency on every ledger read/write, which matters since Fork #4 puts this on the synchronous request path.

The `controlplane:` prefix directly addresses the one new constraint this session surfaced: `REDIS_URL` is a shared database. A prefix is the simplest, cheapest way to guarantee isolation without provisioning a second Upstash database mid-hackathon, and it costs nothing to add now versus retrofitting it after real keys exist.

Keeping the ledger a single JSON blob (rather than pre-building the windowed strike-timestamp structure Phase 3 will likely need) follows directly from `STATUS.md`'s phase split: `3.1 Ledger Update Logic` is explicitly where "the exact math" gets implemented, and guessing that structure now risks locking in a shape Phase 3 has to undo.

## Feature design

**Data model sketch**:

**Session ledger** (Redis key `controlplane:session:{session_id}:ledger`, JSON string value)
- `cumulative_risk`: float, defaults to `0.0`
- `strikes`: object, all six locked categories always present (`pii`, `hallucination`, `toxicity`, `bias`, `prompt_injection`, `custom_policy`), each an int defaulting to `0`

**State transitions**: none. This milestone only reads and overwrites the whole ledger value; no partial updates, no aggregation logic (Phase 3).

**API surface**: not applicable. No HTTP endpoint added; `get_ledger`/`set_ledger` are plain async functions for Phase 1/3 to call directly.

**Value sourcing**: `session_id` is supplied by whichever caller invokes these functions (Phase 1's session resolution, later); the default ledger shape is generated internally when no key exists yet.

**Key invariants**:
- Every key this app writes to the shared Upstash instance starts with `controlplane:` — no exceptions, so a shared-database audit can always distinguish this project's keys.
- `strikes` always carries all six category keys, mirroring the same invariant already locked for the Postgres `Session.strikes` column in the 0.2 spec, so Phase 3's escalation check can read any category by name without a missing-key check.
- `set_ledger` always writes with a fresh 900-second TTL; there is no partial-TTL-preserving update in this milestone (matches Fork #3's "resets on inactivity" framing — every write is activity).

**Security model**: no new authentication/authorization surface. The one sensitive value is `REDIS_URL` itself, which embeds Upstash credentials; already covered by the existing `.gitignore` exclusion of `.env` (fixed in 0.2).

**Configuration required**:
- `REDIS_URL`: the Upstash Redis connection string, `rediss://` (TLS) form, read from the environment, already present in this project's local `.env`.

**Critical test scenarios**:
- Happy path: start the app with the real `REDIS_URL`, confirm the startup `PING` succeeds and `/health` still returns 200, verifies **AC-1**.
- Default shape: call `get_ledger` for a freshly generated `session_id` that has never been written, confirm it returns the zeroed default shape rather than raising, verifies **AC-2**.
- Round trip: call `set_ledger` with a non-default `cumulative_risk` and non-zero strikes, call `get_ledger` again, confirm every value matches; also confirm the key's TTL reads ~900 seconds immediately after the write, verifies **AC-3**, **AC-4**.
- Namespace check: list keys this app wrote (e.g. `KEYS controlplane:*` or the Upstash console) and confirm none of them resemble the other project's key patterns, verifies **AC-5**.

## Build plan

1. Add `redis` to `pyproject.toml` via `uv add redis`, satisfies **AC-1**, **AC-6**.
2. Create `app/redis_client.py`: build the async Redis client from `REDIS_URL` at module level (mirroring `app/db.py`'s pattern — `load_dotenv()`, `os.environ["REDIS_URL"]`, no fallback), define the `controlplane:` key-prefix helper, `default_ledger()`, `get_ledger()`, and `set_ledger()` (900-second TTL), satisfies **AC-2**, **AC-3**, **AC-4**, **AC-5**, **AC-6**.
3. In `app/main.py`'s lifespan, add a startup `PING` against the Redis client before `yield`, so a broken `REDIS_URL` fails at boot, satisfies **AC-1**.
4. Self check: start the app against the real (shared) Upstash instance, confirm clean startup and `/health` still returns 200; manually round-trip `get_ledger`/`set_ledger` for a fresh session id, confirm the default shape, the round-trip values, the TTL, and the `controlplane:` prefix on the actual key written, satisfies **AC-1** through **AC-5**.

## Consequences

**Positive**:
- Phase 1 and Phase 3 have a ready-made, correctly-shaped, correctly-namespaced ledger store to build on; no storage plumbing left for either later milestone.
- Sharing the Upstash database with another project is now safe by construction (prefix), not by discipline.

**Negative / tradeoffs**:
- The JSON-blob ledger shape may need to change once Phase 3 designs the strike-window expiry mechanism (e.g. timestamped events instead of bare counts); that is an accepted, explicitly deferred cost, not an oversight.
- No Lua script or transaction wraps `set_ledger`; concurrent writers to the same session could race. Acceptable for a hackathon demo with no concurrent multi-writer scenario in scope.

**Neutral**:
- No automated tests are written for this milestone, per `AGENTS.md` section 8; the critical test scenarios above are a manual self check, same as 0.2.
- `/health` is left unchanged (still a pure liveness probe, per the 0.1 decision); the new startup `PING` is boot-time fail-fast, not a per-request dependency check.

## Follow-up

- [ ] Phase 3 (`3.1 Ledger Update Logic`) will very likely need to restructure the `strikes` field to support the "last 5 turns OR last 2 minutes" windowed expiry from Fork #3 — the plain int-per-category shape here has no way to expire an individual old strike. Revisit then, not now.
- [ ] Fork #3's exact wording, "only strikes from the last 5 turns OR last 2 minutes count," is ambiguous (union vs. intersection of the two conditions) and load-bearing for the escalation trigger; resolve with the engineer when Phase 3 actually implements the expiry logic, not silently.
- [ ] No Lua/transaction safety around `set_ledger`'s read-modify-write pattern once Phase 3 adds increment logic on top of it; revisit if the demo ever needs concurrent multi-writer correctness.
