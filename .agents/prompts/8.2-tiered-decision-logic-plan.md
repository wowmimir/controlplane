# 8.2. Tiered Decision Logic (Flag for Review)

**Date**: 2026-08-27
**Status**: Accepted

## Summary

The Round 2 rubric's Decision Logic complexity names four response tiers: allow / edit / flag for review / block. This codebase has only ever built two — a cheap-tier match always hard-blocks (`403`), regardless of `Workload.policy_profile`, even after 8.1 gave that field real per-profile escalation thresholds and per-pattern confidence. 8.2 adds the third tier: a `fast`-profile workload's cheap-tier hit now releases as `200` with the violation still logged (`disposition=flagged`), instead of a hard block; `strict`/`balanced` are unchanged. ("Edit" is 8.5's job, next.)

This needs a new `Execution.disposition` (`clean`/`flagged`/`blocked`) column, which also lets this milestone close two other real, already-diagnosed gaps that share the same root need:

1. **Escalation-block console invisibility.** The *request-side* escalation early-return creates no `Execution` row at all today (no model call happens, nothing to log) — real, and fixed here by writing one (`disposition=blocked`, `execution_risk_score=None`, no `Finding`). The *response-side* escalation early-return, by contrast, already has a real `Execution` row in scope by the time it runs (7.1 made the model-call `Execution` commit immediately, before response-side interception even starts) — it only needs `disposition=blocked` set on that existing row. `STATUS.md`/`decisions.md`'s "response-side also creates no row" framing predates 7.1's fix and is stale; this spec corrects the record.
2. **Judge/disposition co-occurrence.** `_run_expensive_tier_task` is scheduled only from the cheap-tier-clean branch today, so a cheap-tier hit and a hallucination finding can never land on the same `Execution` — contradicting the business proposal's overlapping-categories claim. It gets scheduled from every response-side branch now (clean, flagged, blocked), since it's async/post-release and can't change an already-decided disposition either way.

Two scope questions `STATUS.md` flagged as pending were ratified directly with the user before writing this spec: (1) only `fast` flags instead of blocking a cheap-tier hit — `strict`/`balanced` always hard-block, unchanged (keeps `balanced` byte-identical, the regression guardrail 8.1 already relies on); (2) the flag applies to both request-side and response-side cheap-tier hits, per Fork #4's "input and output are NOT treated differently."

## Context

Read in full this session: `app/models/enums.py`, `execution.py`, `finding.py`, `app/evaluators/types.py`, `app/routers/chat.py` (post-8.1, 636 lines — both interception functions, both escalation call sites, the response-side background-task scheduling, `_safe_ledger_update`), `app/routers/console.py` (350 lines — `get_summary`'s two inline blocked-count queries, `_is_blocked`, both its call sites), `app/schemas/console.py`, `app/redis_client.py` (`is_escalated`, `apply_ledger_update`'s return shape), `app/db.py`, `console/src/types.ts`, `console/src/LiveFeed.tsx`, `console/src/SessionDetail.tsx`. Confirmed:

- **No `disposition` concept exists anywhere.** `Execution` has no column recording what ControlPlane decided about a turn; the console infers "blocked" per-execution by joining `Finding` and checking `evaluator_tier != expensive` (`_is_blocked` in `console.py`, plus two more independently-written inline versions of the identical join inside `get_summary`'s `blocked_count` and `blocked_by_bucket` queries — three sites total, matching the independent review's correction already recorded in `STATUS.md`, not just the one `_is_blocked` helper).
- **The response-side escalation branch already has a real `Execution` row in scope, contradicting `decisions.md`'s 2026-08-24 (4.2-era) claim that both escalation paths "create no Execution row."** Tracing the current control flow: `chat_completions` creates and *commits* the `Execution` row for a successful model call (7.1/Major #1, real `tokens`/`latency_ms`) *before* calling `_run_response_side_interception`, which receives that already-persisted row as its `execution` parameter. Its clean-cheap-tier branch sets `execution.execution_risk_score = 0.0`, commits, updates the ledger, and *only then* checks `is_escalated(...)` — if true, it returns `_escalation_block_response()` without ever touching `execution` again. The row is real and already durable; it is simply missing the right `disposition` label. Only the *request-side* escalation early-return (`_run_request_side_interception`, before any model call) genuinely has no `Execution` row today. This spec fixes both, but by different means — a **new row** for request-side, a **field set on an existing row** for response-side — and flags the stale `decisions.md` framing rather than silently perpetuating it.
- **A cheap-tier hit today always returns a `JSONResponse` (block) from both interception functions**, with no path back to "continue to the model" (request side) or "release the already-computed response" (response side) once a `Finding` has been logged. Fast-profile flagging needs a hit to still be logged (real `Finding` rows, real ledger update — "flagging is still a signal") *without* stopping the turn, which is a genuine control-flow fork, not just a different response body:
  - **Response side** is straightforward: the `Execution` row already exists (the model was already called) — set `disposition`, write `Finding`s, update the ledger, and either return the `403` (blocked) or `None` (flagged, release the already-computed `parsed` response) from the same call site.
  - **Request side** is not straightforward: on a hit, no model call has happened yet and no `Execution` row exists. Today's code creates a *standalone* `Execution` row right there (no `tokens`/`latency_ms`, since no model call happened) and returns `403`. But a *flagged* fast-profile hit must **not** stop the turn — the model still gets called, and `chat_completions` already creates its own, single `Execution` row for that successful call (matching the codebase's "one `Execution` row per real model-call attempt" invariant, established at 1.5/4.2). Creating a second, standalone row here for a flagged hit would violate that invariant and give one turn two audit rows. The candidates therefore need to travel forward and attach to the *real* row once it exists, not be logged against a synthetic one.
- **`_run_expensive_tier_task`'s scheduling call sits only inside the cheap-tier-clean, medium-tier-clean branch** of `_run_response_side_interception`, gated by 8.1's `should_sample_judge`/`FAST_TIER_JUDGE_SAMPLE_RATE` fast-profile sample. Nothing about the judge's own logic (writes a `Finding`, bumps `execution_risk_score` via `max(...)`, touches the ledger with `is_new_turn=False`) assumes the triggering `Execution` was clean — it operates purely on `execution_id`/`context_text`/`response_text`, so moving *where* it gets scheduled from is a control-flow change only, no change to the task itself.
- **`_safe_ledger_update` (7.1/Major #1) already exists precisely for "a decision has already been made and committed, and a later Redis/Postgres failure must not un-make it or double it."** The current code uses it for the request-side and response-side cheap-tier *violation* (block) branches, but the response-side *clean* branch deliberately uses the unwrapped `apply_ledger_update` + `await _sync_session_ledger(...)` instead — per its own 7.1 rationale, "no decision is final there yet, so a failure correctly falls through to 3.3's existing `fail_open`/`fail_closed` handling." A *flagged* outcome is an already-committed decision (real `Finding`s, real `disposition`, response already releasing) exactly like *blocked* — so it needs the same `_safe_ledger_update` protection, not the clean branch's unwrapped one.

## Requirements

**User stories**:
- As the operator of a `fast`-profile, high-volume, cost-sensitive workload (8.4's "Customer Support Bot"), I want a cheap-tier hit to be logged for review rather than hard-blocking the customer, so throughput isn't sacrificed for every low-stakes match while still keeping a real audit trail.
- As the operator of a `strict`/`balanced` workload, I want cheap-tier hits to keep hard-blocking exactly as they do today — no behavior change for the two profiles that aren't `fast`.
- As someone reviewing the console during or after a demo, I want an escalation block to actually show up in the Dashboard/Live Feed/Session Drilldown instead of silently vanishing from every count, so the audit trail is honest about every reason a turn didn't go through cleanly.
- As someone reviewing a session's audit trail, I want a turn that both tripped a cheap-tier pattern *and* got flagged as a hallucination by the async judge to show both, so the "categories can overlap" story is demonstrably true, not just claimed.

**Acceptance criteria**:
- **AC-1**: A `fast`-profile workload's response-side cheap-tier hit (e.g. a PII match in the model's output) returns `200` with the real model response, and a direct Postgres check shows the `Execution` row with `disposition=flagged`, a real `Finding` (`evaluator_tier=cheap`, `evidence_ref.side="response"`), and the Redis ledger updated (strike/decay as usual).
- **AC-2**: A `fast`-profile workload's request-side cheap-tier hit (a PII/injection match in the incoming prompt) still reaches the model — a real model response comes back `200` — and a direct Postgres check shows exactly **one** `Execution` row for that turn (real `tokens`/`latency_ms`), with `disposition=flagged` and a `Finding` (`evidence_ref.side="request"`).
- **AC-3**: The identical request-side and response-side matches against a `strict`- or `balanced`-profile workload still return `403` exactly as before this milestone (regression) — `disposition=blocked` on the resulting `Execution` row (request-side: a new standalone row, unchanged shape from today plus the new field; response-side: the same real row the model call already produced).
- **AC-4**: A session already escalated (per 8.1's per-profile thresholds) that sends a *request that never reaches the model* (blocked before any call) produces a new `Execution` row with `disposition=blocked`, `execution_risk_score=None`, no `Finding` — where today it produces zero rows.
- **AC-5**: A session that escalates on the *response* side (this turn's own content was clean, but accumulated risk trips the threshold) reuses the turn's already-existing `Execution` row (real `tokens`/`latency_ms` from the completed model call) and sets `disposition=blocked` on it, rather than creating a second row.
- **AC-6**: `GET /api/console/summary`'s `blocked_count` and its hourly `over_time[].blocked` both now count executions purely by `disposition == blocked` (no `Finding` join) — confirmed to include the escalation-block rows from AC-4/AC-5, which were invisible to this stat before this milestone.
- **AC-7**: `GET /api/console/sessions/{id}` and `GET /api/console/feed` both surface `disposition` (replacing the old derived `blocked: bool`) for every execution, matching what's actually on the row.
- **AC-8**: A response that is cheap-tier-clean, medium-tier-clean (always true, 2.4's stub), and a genuine hallucination (crafted per 6.1's provably-wrong-multiplication method) still gets its `Finding` (`evaluator_tier=expensive`) — unchanged behavior for the clean path.
- **AC-9**: A response-side cheap-tier hit (`fast`-profile flagged, or `strict`/`balanced` blocked) still gets the async judge scheduled afterward (respecting 8.1's `fast`-tier sample rate the same way the clean branch already does) — confirmed by a crafted scenario where the *same* `Execution` row ends up with both a cheap-tier `Finding` (`pii`, from the initial scan) and an expensive-tier `Finding` (`hallucination`, from the background task), proving overlapping categories can coexist on one row.
- **AC-10**: The `execution` table has a real `disposition` column in Postgres (native enum `clean`/`flagged`/`blocked`), and pre-migration rows are backfilled correctly (`blocked` if a non-expensive `Finding` exists for that execution, else `clean` — no pre-migration row can be `flagged`, since the concept didn't exist yet).
- **AC-11**: Full regression: `/health` `200`, unknown-workload `400`, model-unreachable `502` (its `Execution` row still gets a sensible `disposition`, see Decision), a genuinely clean `balanced`-profile end-to-end pass-through `200` with `disposition=clean`, `balanced`-profile request-side and response-side PII blocks still `403`.

## Options considered

### Option 1: `Execution.disposition` as a new native Postgres enum column, set explicitly at every write site; `_is_blocked`/the two inline blocked-count joins in `console.py` replaced by reading the column directly; request-side flagged candidates deferred and attached to the real post-model-call `Execution` row (recommended)

As described in Decision below.

**Pros**: Matches this codebase's existing native-enum convention for every other fixed-choice field (`PolicyProfile`/`FailMode`/`EvaluatorTier`/`FindingCategory`). Collapses three independent "infer blocked from a Finding join" call sites into one column read, which is both simpler code and the thing that actually fixes the escalation-invisibility gap (a `Finding`-based join can never see an escalation block, since no `Finding` exists for one — a stored `disposition` column can). Preserves the "one `Execution` row per real model-call attempt" invariant for the fast-profile request-side case.
**Cons**: A genuinely non-trivial control-flow change to `_run_request_side_interception`'s return shape (candidates now need to travel forward to `chat_completions` instead of being fully handled locally) — the largest single piece of new complexity in this milestone, but unavoidable given the invariant above.

### Option 2: Keep `blocked: bool`, add a second boolean `flagged: bool` next to it, no `disposition` field

**Pros**: Smaller diff to the existing schemas/frontend; no new enum type.
**Cons**: Two independent booleans can represent an impossible state (`blocked=true, flagged=true`) that the code has to promise never happens instead of the type system ruling it out; doesn't scale to 8.5's already-planned fourth state (`redacted`) without adding a *third* boolean and the same problem again. Rejected — a three(soon four)-state enum is the honest representation of what is fundamentally one decision per execution, not two independent facts.

### Option 3: Derive "flagged" purely from `Finding` data at read time (e.g., "has a non-expensive `Finding`, but the request as a whole still returned `200`"), no new column

**Pros**: No schema change, no migration.
**Cons**: Cannot represent the escalation-block case at all — that block has no `Finding` by design (no per-turn content evidence exists to attach), which is the exact gap this milestone must close. A read-time derivation would need to consult *something* to distinguish "flagged-and-released" from "clean," and the only durable signal available is a stored column — computing it from `Finding` alone reproduces today's three-independent-join situation as a formula instead of a query, without fixing the actual problem. Rejected.

## Decision

**Chosen option**: Option 1.

**1. New enum + column** — `app/models/enums.py`:
```python
class Disposition(str, enum.Enum):
    clean = "clean"
    flagged = "flagged"
    blocked = "blocked"
```
`app/models/execution.py` gains:
```python
disposition: Mapped[Disposition] = mapped_column(
    Enum(Disposition, name="disposition"), nullable=False, default=Disposition.clean
)
```
`app/models/__init__.py` exports `Disposition` alongside the other enums.

**2. Migration** (manual one-off script, run against the real Neon database, deleted after use — same pattern as every prior phase's schema change, since `app/main.py`'s lifespan only runs `Base.metadata.create_all`, which never alters an existing table):
```sql
CREATE TYPE disposition AS ENUM ('clean', 'flagged', 'blocked');
ALTER TABLE execution ADD COLUMN disposition disposition NOT NULL DEFAULT 'clean';
UPDATE execution SET disposition = 'blocked'
WHERE execution_id IN (
    SELECT DISTINCT execution_id FROM finding WHERE evaluator_tier != 'expensive'
);
```
No pre-migration row can backfill to `flagged` — the concept doesn't exist in any historical data, so every historical hit was necessarily a hard block.

**3. `app/routers/chat.py` — request-side** (`_run_request_side_interception`): return type becomes `tuple[JSONResponse | None, list[FindingCandidate]]` — `(blocked_response, flagged_candidates)`. Exactly one of the two is ever non-empty/non-None:
```python
async def _run_request_side_interception(...) -> tuple[JSONResponse | None, list[FindingCandidate]]:
    ledger = await get_ledger(str(session.session_id))
    if is_escalated(ledger, workload.policy_profile):
        execution = Execution(
            session_id=session.session_id, workload_id=workload.workload_id,
            disposition=Disposition.blocked, execution_risk_score=None,
        )
        db.add(execution)
        await db.commit()
        await _safe_ledger_update(db, session, 0.0, [])
        return _escalation_block_response(), []

    text = request.messages[-1].content if request.messages else ""
    candidates = run_cheap_tier(text)
    if not candidates:
        return None, []

    execution_risk_score = max(c.confidence for c in candidates)
    strikes_input = [(c.category.value, c.confidence) for c in candidates]

    if workload.policy_profile == PolicyProfile.fast:
        # Flagged: do NOT create a standalone Execution row (the model
        # still gets called; chat_completions's own post-call row is
        # where these candidates get attached - see below). Ledger still
        # updates now, since flagging is still a real signal.
        await _safe_ledger_update(db, session, execution_risk_score, strikes_input)
        return None, candidates

    # strict/balanced: unchanged from today, plus the new field.
    execution = Execution(
        session_id=session.session_id, workload_id=workload.workload_id,
        disposition=Disposition.blocked, execution_risk_score=execution_risk_score,
    )
    db.add(execution)
    await db.flush()
    for c in candidates:
        db.add(Finding(execution_id=execution.execution_id, category=c.category,
                        confidence=c.confidence, evaluator_tier=EvaluatorTier.cheap,
                        evidence_ref={"side": "request", **(c.evidence_ref or {})}))
    await db.commit()
    await _safe_ledger_update(db, session, execution_risk_score, strikes_input)
    return _policy_block_response("request", candidates), []
```
`chat_completions` unpacks the tuple, and — only on the path that proceeds to call the model — attaches any deferred flags to the real `Execution` row it already creates, both on success and on a model-call failure (the flagged violation was real regardless of whether the call then succeeded):
```python
blocked, request_flags = await _run_request_side_interception(db, session, workload, request)
if blocked is not None:
    ...  # unchanged
    return blocked

# on ModelCallError -> failed_execution: also
#   disposition=Disposition.flagged if request_flags else Disposition.clean
# and write request_flags' Finding rows against failed_execution.execution_id,
# same shape as the success path below.

execution = Execution(
    ..., disposition=Disposition.flagged if request_flags else Disposition.clean,
)
db.add(execution)
await db.commit()
for c in request_flags:
    db.add(Finding(execution_id=execution.execution_id, category=c.category,
                    confidence=c.confidence, evaluator_tier=EvaluatorTier.cheap,
                    evidence_ref={"side": "request", **(c.evidence_ref or {})}))
if request_flags:
    await db.commit()
```

**4. `app/routers/chat.py` — response side** (`_run_response_side_interception`): the cheap-tier-hit branch (today's `else: candidates = cheap_candidates; tier = EvaluatorTier.cheap`) becomes profile-aware and schedules the judge before returning; the escalation branch sets `disposition` on the already-existing row instead of creating a new one; a small `_maybe_schedule_expensive_tier(...)` helper is shared by all three response-side exit points that can reach the model's output (clean, flagged, blocked — never the escalation short-circuit, per Fork #4's "do not run medium/expensive tier" on an escalation trip):
```python
def _maybe_schedule_expensive_tier(background_tasks, execution_id, session_id,
                                     context_text, response_text, workload, ledger, ts_anchor):
    if ledger is None:  # ledger write failed - no reliable turn anchor, skip this turn
        return
    should_sample = (
        workload.policy_profile != PolicyProfile.fast
        or random.random() < FAST_TIER_JUDGE_SAMPLE_RATE
    )
    if not should_sample:
        return
    background_tasks.add_task(
        _run_expensive_tier_task, execution_id=execution_id, session_id=session_id,
        context_text=context_text, response_text=response_text,
        turn_anchor=ledger["turn"], ts_anchor=ts_anchor,
    )
```
```python

execution.execution_risk_score = 0.0

    execution.disposition = Disposition.blocked
    await db.commit()
    return _escalation_block_response()

medium_candidates = run_medium_tier(context_text, response_text, workload.latency_budget_ms)

# medium-tier-violation branch: still dead code (2.4's stub always returns []);
```

**5. `app/routers/console.py`**: `_is_blocked(findings)` is deleted. `get_summary`'s `blocked_count` and `blocked_by_bucket` queries drop their `.join(Finding, ...).where(Finding.evaluator_tier != EvaluatorTier.expensive)` clauses in favor of `.where(Execution.disposition == Disposition.blocked)` directly on `Execution` — no join at all. `get_session_detail`'s `ExecutionOut.blocked=...` and `get_feed`'s `FeedEntry.blocked=...` both become `disposition=execution.disposition.value`.

**6. Schemas & frontend**: `app/schemas/console.py`'s `ExecutionOut`/`FeedEntry` replace `blocked: bool` with `disposition: str`. `console/src/types.ts` mirrors it (`disposition: 'clean' | 'flagged' | 'blocked'`). `console/src/LiveFeed.tsx` and `console/src/SessionDetail.tsx`'s duplicated `BlockedBadge` component becomes a shared `DispositionBadge` (moved to `console/src/components/DispositionBadge.tsx` so both stop duplicating it) with three visual states: `clean` = success/green ("Clean"), `flagged` = a new warning/amber token ("Flagged") — check `console/design.md`'s existing palette for the nearest already-verified-contrast option before inventing a new one — `blocked` = error/red ("Blocked").

## Rationale

Option 2 is rejected because a boolean pair can represent a state that must never occur, and 8.5 is already scoped to add a fourth disposition (`redacted`) — a third boolean now would just be the same problem doubling. A tri/soon-quad-state enum is the honest type for "exactly one decision was made about this execution."

Option 3 is rejected because it cannot fix the actual bug this milestone exists partly to fix: an escalation block has no `Finding` to derive anything from, by design (3.2's own ratified reasoning — there is no per-turn content evidence to attach). Any read-time formula still needs *some* durable per-execution signal to distinguish "flagged" from "clean" or to see an escalation block at all; a stored column is that signal, so building it as a formula instead just defers the same requirement without meeting it.

The request-side deferred-attachment design (rather than, e.g., letting a flagged request-side hit create its own row and accepting two rows per turn) preserves an invariant this codebase has already committed to twice (1.5's "reuses the same Execution row 1.4 already creates... not a second one," 4.2's explicit confirmation) rather than quietly breaking it the first time a genuine reason to create a second row shows up. The extra complexity (a tuple return, a deferred `Finding` write) is the one piece of real new design surface in this spec; everything else is close to a mechanical column-and-callsite change.

Scheduling the judge from all three response-side outcomes (not just clean) is a direct, minimal consequence of the judge being genuinely decision-independent already — it was only ever gated by "did we reach the bottom of the clean branch," an accident of control flow, not a deliberate exclusion.

## Feature design

**Data model sketch**: one new native-enum column, `execution.disposition` (`clean`/`flagged`/`blocked`, `NOT NULL DEFAULT 'clean'`), via the manual `ALTER TABLE`/`CREATE TYPE` above. No other schema change.

**Changed files**:
- `app/models/enums.py`: new `Disposition` enum.
- `app/models/execution.py`: new `disposition` column.
- `app/models/__init__.py`: export `Disposition`.
- `app/routers/chat.py`: `_run_request_side_interception`'s return type and body (per Decision §3); `chat_completions`'s post-model-call `Execution` construction (both success and `ModelCallError` branches) attaches deferred `request_flags`; `_run_response_side_interception`'s cheap-tier-hit branch, clean branch's escalation check, and medium-tier-violation branch (per Decision §4); new `_maybe_schedule_expensive_tier` helper; both `_escalation_block_response()` call sites now set `disposition` (new row vs. existing row, per which side).
- `app/routers/console.py`: delete `_is_blocked`; `get_summary`'s two blocked-count queries simplified to a direct `disposition` filter; `get_session_detail`/`get_feed` read `execution.disposition.value` instead of calling the deleted helper.
- `app/schemas/console.py`: `ExecutionOut`/`FeedEntry`'s `blocked: bool` → `disposition: str`.
- `console/src/types.ts`, `LiveFeed.tsx`, `SessionDetail.tsx`: mirror the schema change; extract a shared `DispositionBadge` component.

**Value sourcing**:
| Action | Value produced | Source |
|---|---|---|
| Whether a cheap-tier hit flags or blocks | `Disposition.flagged` / `Disposition.blocked` | `workload.policy_profile == PolicyProfile.fast` at the point of the hit — never re-derived elsewhere |
| A flagged request-side hit's eventual `Execution.disposition` | `Disposition.flagged` | set when `chat_completions` builds the real post-model-call row, keyed off whether `_run_request_side_interception` returned any deferred candidates |
| An escalation block's `execution_risk_score` | `None` (request-side new row) or unchanged `0.0` (response-side existing row) | the ledger's raw `cumulative_risk` is never written here — it is unbounded (e.g. `1.615`) and would corrupt this column's documented 0–1 max-confidence meaning; the response-side row's `0.0` is a real, already-correct value for that turn's own clean content, not a placeholder |
| Dashboard `blocked_count`/`over_time[].blocked` | a plain count | `Execution.disposition == Disposition.blocked`, no `Finding` join |
| Whether the async judge gets scheduled after a hit | boolean | the same `_maybe_schedule_expensive_tier` helper the clean branch already used, called from all three reachable branches |

**Key invariants**:
- Exactly one `Execution` row exists per real model-call attempt, still — a flagged request-side hit is folded into that same row, never a second one.
- `disposition` is always set explicitly at every `Execution` construction/mutation site; nothing relies on the column default beyond genuinely-clean rows that no branch above ever touches (there should be none, but the default exists as a safety net, not a designed-for path).
- The expensive-tier judge never changes `disposition` — Fork #4's "expensive tier... can never block or alter this response" is unchanged; it can only add a `Finding` and move `execution_risk_score` upward via `max(...)`, same as before this milestone.
- Escalation blocks continue to write no `Finding` (still true — no per-turn content evidence exists to attach, 3.2's reasoning is unaffected).

**Security model**: unchanged from 8.1 — no new auth surface, no new caller-facing distinction beyond the existing `403` vs `200` split (a `fast`-profile caller now silently gets through on a flagged hit, which is the entire intent of "flag for review," not a new gap).

**Configuration required**: none new. Which profile flags vs. blocks is fixed (`fast` only) — 8.6 (`Workload.metadata.category_overrides`) remains the intended future home for making this configurable per-workload/per-category rather than per-profile.

**Critical test scenarios**:

## Consequences

**Positive**:
- The rubric's four-tier Decision Logic bullet is now three-quarters built (allow, flag, block — "edit" is 8.5); `fast`-profile workloads get real behavior distinct from `strict`/`balanced` beyond just escalation thresholds and confidence.
- Escalation blocks are finally visible in the Dashboard/Live Feed/Session Drilldown — closing a gap the business proposal's "clear audit trail" claim was previously undercut by.
- Overlapping categories (a cheap-tier hit plus an async hallucination finding on the same execution) become genuinely demonstrable, not just structurally possible-but-never-observed.
- `console.py`'s three independent blocked-inference call sites collapse to one column read each — less code, and no longer silently wrong about escalation blocks.

**Negative / tradeoffs**:
- `_run_request_side_interception`'s new return shape (a tuple instead of a bare `JSONResponse | None`) is a real, non-trivial change to one of the codebase's most-reviewed functions — worth the callout at the approval gate rather than treating it as a small diff.
- A `fast`-profile workload now silently lets a real cheap-tier violation reach the caller (by design — that is what "flag for review" means) — the console is the only place this becomes visible; there is no alerting/notification for a freshly-flagged `Finding` (that's 8.3's review-queue job, not this milestone's).
- `blocked: bool` disappears from `ExecutionOut`/`FeedEntry` entirely rather than staying as a derived convenience field — any external consumer of the console API depending on the old boolean shape breaks. Accepted: there are no external consumers of this hackathon build's console API.

**Neutral**:
- No automated tests written, per `AGENTS.md` Section 8; manual `curl` plus direct Postgres/Redis inspection self-check, matching every prior phase.
- `Session.cumulative_risk`/`Session.strikes` Postgres sync (4.3) is unaffected — this milestone changes what gets logged per-execution, not the session-level ledger mirror.
