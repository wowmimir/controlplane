# 5.4. Live Feed

**Date**: 2026-08-24
**Status**: Accepted

## Summary

`STATUS.md` describes 5.4 as: *"Real-time (polling or websocket) view of incoming executions and their verdicts, for the live demo."* Today the console has no way to watch traffic happen — 5.1's dashboard only refreshes on demand, and 5.3's session drilldown requires already knowing which session to look at. This is the last Phase 5 milestone: it closes the console before Phase 6 (Demo Polish) and is explicitly built for a live audience watching requests flow through the proxy in real time.

This spec adds one new read-only backend endpoint (`GET /api/console/feed`) plus one new console page (`/feed`) that polls it every ~3 seconds, showing the most recent executions across every workload/session as they land, each with its verdict (blocked/clean, categories), reusing 5.3's `blocked` rule and linking each row to its session's drilldown page.

## Context

Mapped against the current code (`app/routers/console.py`, `app/schemas/console.py`, `app/routers/chat.py`, `console/src/*`) for this spec:

- **No live-update infrastructure exists anywhere in the stack.** Checked `pyproject.toml`/`uv.lock` (no `websockets` direct dependency, no `sse-starlette`), `app/routers/*.py` (no `@router.websocket`, no `StreamingResponse`/`EventSourceResponse`), `console/package.json` (no `swr`/`react-query`/websocket client), and `console/src/*.tsx` (no `setInterval`/timer pattern anywhere — only the manual "Refresh" buttons 5.1/5.2 already built). This milestone is the first to introduce any kind of automatic refresh.
- **`app/routers/chat.py` is the codebase's hardened hot path.** It has at least three separate `Execution`-commit sites (the model-call-failure path, the success path, the request/response-side content-block paths) plus a fourth commit inside the async expensive-tier `BackgroundTasks` callback — all already through multiple `/check review` passes across Phases 1-4. `AGENTS.md`'s locked tech stack explicitly rules out Celery/message-queue infrastructure ("FastAPI `BackgroundTasks` (No Celery for MVP)"), and nothing in the stack today gives this codebase an in-process pub/sub pattern to build on.
- **`app/routers/console.py`'s existing conventions** (5.1/5.2/5.3): `router = APIRouter(prefix="/api/console")`, `Depends(get_db)`, explicit schema construction, a two-query-merged-in-Python pattern for combining `Execution`/`Session`/`Workload`/`Finding` data (`list_sessions`, `get_session_detail`). `blocked` is already a project-wide-consistent derivation: an `Execution` counts as blocked iff it has ≥1 `Finding` with `evaluator_tier != expensive` (2.5's async judge never actually blocks anything, per Fork #4) — this spec reuses that exact rule via the existing `_is_blocked` helper.
- **Escalation blocks (Fork #3, 3.2) write no `Execution`/`Finding` row at all** — Redis-only, no durable Postgres trace. 5.1's dashboard and 5.3's session detail both already document this as an accepted, visible gap rather than solving it; this spec inherits the same limitation and states it the same way.
- **`console/`'s established conventions** (5.1/5.2/5.3): `App.tsx` is the nav shell (`Dashboard`/`Workloads`/`Sessions` `NavLink`s so far) wrapping `<Routes>`; each page owns a `LoadState` discriminated union (`loading`/`error`/`ready`) with a `useCallback`+`useEffect` load pattern; `console/src/lib/format.ts`'s `displayId(id, name?)` is the shared id/name display helper (5.3); `api.ts` holds one fetch function per endpoint behind a shared `parseOrThrow` error handler; `types.ts` mirrors backend Pydantic schemas by hand; one feature gets one nav link and one page so far (no page has been embedded inside another).

## Requirements

- **AC-1**: `GET /api/console/feed` returns the 25 most recent executions across all workloads/sessions (by `created_at`, most recent first), each with `blocked` and `categories` matching 5.1/5.3's existing `evaluator_tier != expensive` rule.
- **AC-2**: The Live Feed page (`/feed`) polls the endpoint automatically on a fixed interval (~3s) with no manual action required, and shows loading/error/ready states consistent with the console's existing `LoadState` pattern.
- **AC-3**: A pause/resume control stops and restarts the polling interval; while paused, the page shows a visible paused indicator and does not fetch.
- **AC-4**: A newly-appeared execution (confirmed by polling twice against real traffic sent between polls) renders at the top of the list without disrupting scroll position or the pause toggle's state, and without remounting already-rendered rows (keyed by `execution_id`).
- **AC-5**: Each row links to `/sessions/:sessionId` for the execution's session, and correctly renders a row with zero, one, and multiple finding categories.
- **AC-6**: The console nav shell shows a fourth link, **Live Feed**, routed to `/feed`.
- **AC-7**: `GET /health`, `POST /v1/chat/completions`, `GET /api/console/summary`, and 5.2/5.3's existing endpoints are unaffected (regression).

## Decision

**Chosen option**: polling, not a push transport (WebSocket/SSE). A frontend `setInterval` polls one new read-only `GET /api/console/feed` endpoint, added to the existing `app/routers/console.py` router, reading Postgres exclusively (same "durable audit trail, not Redis" precedent 5.3 already established) with a flat most-recent-N query and no `since`/cursor parameter.

**Implementation skills**: none — no new library, no new dependency.

### Backend

- **`app/schemas/console.py`** (extend): add
  - `FeedEntry { execution_id: uuid.UUID; session_id: uuid.UUID; workload_id: uuid.UUID; workload_name: str | None; tokens: int | None; latency_ms: int | None; execution_risk_score: float | None; blocked: bool; categories: list[str]; created_at: datetime }`
- **`app/routers/console.py`** (extend, same `router`):
  - `GET /feed` → `list[FeedEntry]`. Query: `select(Execution, Session, Workload)` joined `Execution.session_id == Session.session_id` and `Session.workload_id == Workload.workload_id`, `order_by(Execution.created_at.desc())`, `.limit(FEED_LIMIT)` (`FEED_LIMIT = 25`) — same shape as `list_sessions`'s `SESSION_LIST_LIMIT` pattern. A second `Finding` query (`.where(Finding.execution_id.in_(execution_ids))`) builds each row's `blocked` (reusing the existing `_is_blocked` helper) and `categories` (the distinct `Finding.category` values for that execution, not full finding objects — a feed row is a summary, not a drilldown; the full finding list is already one click away via the session detail page). `workload_name` reuses the existing `_workload_name` helper.
- No `app/main.py` change (the new route is `GET`, already CORS-allowed).

**Value sourcing** (every displayed value has a named source):

| Value | Source |
|---|---|
| `execution_id`/`session_id`/`workload_id`/`tokens`/`latency_ms`/`execution_risk_score`/`created_at` | `Execution` columns verbatim |
| `workload_name` | `Workload.metadata_["name"]` via `_workload_name` (5.2/5.3's convention), `None` if unset |
| `blocked` | `_is_blocked(findings)` — `count(Finding) where evaluator_tier != expensive` > 0, the same rule 5.1's `blocked_count` and 5.3's per-execution `blocked` already use |
| `categories` | Distinct `Finding.category` values for that execution |

### Frontend

- `console/src/App.tsx`: nav gains a fourth `NavLink`, **Live Feed**, routed to `/feed`; add a `<Route path="/feed" element={<LiveFeed />} />` alongside the existing routes.
- **`console/src/LiveFeed.tsx`** (new page): on mount, fetches immediately and then re-fetches every 3s via `setInterval` (cleared on unmount and while paused), following the existing `LoadState`/`useCallback`+`useEffect` pattern. A pause/resume button (styled like `Dashboard.tsx`'s Refresh button) toggles the interval; a visible "Paused" indicator renders while paused. Rows render newest-first, keyed by `execution_id`; a freshly-arrived row (present in this poll, absent from the previous one) gets a brief `border-l-2 border-[var(--color-accent)]` fade transition (~1s) rather than a jarring reflow. Each row shows: workload (via `displayId`), a Blocked/Clean pill (reusing `SessionDetail.tsx`'s `BlockedBadge` styling), category pills, tokens/latency, and a relative/absolute timestamp; the whole row links to `/sessions/:sessionId` (via `displayId`, same pattern as `Sessions.tsx`'s rows).
- `console/src/api.ts`: add `fetchFeed()`.
- `console/src/types.ts`: add `FeedEntry` mirroring the new schema exactly.
- `console/design.md` gets a short addendum during the build describing the feed's composition (the pause control, the new-row transition), continuing 5.1-5.3's precedent.

## Rationale

Polling is the only choice consistent with the codebase's own established boundaries: `app/routers/chat.py` is the most reviewed, most hardened code in this project (multiple `/check review` passes across Phases 1-4), and a push transport would require threading a new in-memory pub/sub through every one of its `Execution`-commit sites — real regression surface on the proxy's hot path, added this late in the build, for a feature whose only consumer is a read-only console page. `AGENTS.md`'s locked stack already rules out message-queue infrastructure, and nothing in this project has ever needed an in-process broadcast mechanism before. At the traffic volume a live hackathon demo actually produces (a handful of requests, watched by a human audience), a 3-second poll is visually indistinguishable from a genuine push — the "wow factor" comes from the UI showing new rows appear and the verdict badges update, not from the transport underneath it. This mirrors the same "simplest reversible path" judgment `AGENTS.md` Section 9 asks for, and was confirmed directly with the engineer before writing this decision.

A flat most-recent-N query (no `since` cursor) is the simplest option that satisfies the actual requirement: a cursor adds real complexity (handling out-of-order commits, gap detection) that only pays off at traffic volumes this project will never see live. This is the same "don't build for hypothetical scale" judgment already applied throughout Phase 5.

## Consequences

**Positive**:
- Closes Phase 5 entirely — the console can now show a live, moving picture of proxy traffic, the single strongest visual for a live demo audience.
- No new dependency, no change to `app/main.py`, and zero lines changed in `app/routers/chat.py` — the hot path this project has spent four phases hardening is completely untouched.

**Negative / tradeoffs**:
- Escalation-only blocks (3.2) still write no `Execution`/`Finding` row, so they will never appear in the feed — the same accepted, already-documented gap from 5.1's dashboard and 5.3's session detail. Documented, not hidden.
- A ~3s poll means a demo audience could, in principle, notice up to a ~3s delay between a request happening and its row appearing — accepted as imperceptible at demo pacing, per the Rationale above.
- Fixed 25-row window with no pagination — matches 5.3's fixed-50-session-cap precedent; not a real limitation for a live-only view (old rows scrolling off is the expected behavior of a feed, not a bug).

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-check described below.
- No database schema change; no new dependency.

## Follow-up

- If a future need requires true instant push (e.g. a genuinely high-traffic production deployment, not a hackathon demo), revisit the WebSocket/SSE option then — this spec's Rationale explicitly names the tradeoff so a future session doesn't have to re-derive it.
- This is the last Phase 5 milestone. Phase 6 (Demo Polish: 6.1 Seed/Simulation Script, 6.2 README + Demo Video Script) is next — 6.1 in particular will be the natural way to prove this feed actually looks "live" during a real demo rehearsal.
