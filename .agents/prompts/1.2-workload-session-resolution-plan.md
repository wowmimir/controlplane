# 1.2. Workload/session resolution

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec resolves the `X-Workload-Id`/`X-Session-Id` headers 1.1 already parses into real, persisted rows: an existing `Workload` (or the seeded default), and an existing-or-newly-created `Session`. `STATUS.md` names this milestone directly: "Resolve `workload_id` → fallback to `default`; resolve/create `session_id` → fallback to session-of-length-1 if absent." It also settles three gaps `forks.md`'s Fork #1/#3 leave open for what 1.2 must actually do beyond the locked happy path: an unknown `workload_id`, a `session_id`/workload conflict, and whether resolved ids are ever surfaced back to the caller.

## Context

`forks.md` Fork #1 locks: "Every incoming request carries `workload_id` (optional). If omitted → resolves to a pre-registered `default` workload," and "A Session cannot span two workloads." Fork #3 locks: "No `session_id` supplied → treated as a session of length 1 (graceful degradation, same pattern as workload fallback)." Both forks describe the omitted-value happy path precisely, but neither says what happens when a *supplied* value doesn't resolve cleanly — an unknown `workload_id`, or a `session_id` that already belongs to a different workload than the one this request resolves to. `forks.md`'s "What Is Explicitly NOT Locked" section doesn't list either case either, confirming these are genuine build-time decisions, not fork reopenings.

1.1 (`Accepted`) already parses both headers into optional `uuid.UUID` values in `app/routers/chat.py`, but explicitly does not touch Postgres or Redis — that was deferred here by design (see 1.1's Feature design: "This handler never imports `app.db` or `app.redis_client`"). `app/seed.py` already guarantees `DEFAULT_WORKLOAD_ID` exists; `app/db.py` already exposes a `get_db` dependency; `app/models/session.py`'s `Session` has no default for `ttl_expires_at`, meaning any code path that creates a row must set it explicitly.

Nothing downstream consumes the resolved values yet — 1.3 (cheap-tier interception) and 1.4 (model forwarding) are still stubbed out entirely. This milestone only needs the resolution to happen and be visible in the response; it does not need to change what the model-facing behavior does.

## Requirements

**User stories**:
- As the engineer building Phase 1.3 next, I want the resolved `Workload` (with its policy profile and budgets) and `Session` (with its id) available by the time interception logic runs, so 1.3 can focus purely on evaluation, not resolution.
- As an AI application developer calling the proxy without ever supplying `session_id`, I want the id ControlPlane generated for me returned somewhere, so a later turn in the same conversation can opt into the same session if my application chooses to.
- As the engineer debugging a misconfigured integration, I want an invalid `workload_id` or a cross-workload `session_id` reuse to fail loudly, not silently apply the wrong policy.

**Acceptance criteria**:
- **AC-1**: A request with no `X-Workload-Id` header resolves to `DEFAULT_WORKLOAD_ID`.
- **AC-2**: A request with a valid, existing `X-Workload-Id` resolves to that row.
- **AC-3**: A request with an `X-Workload-Id` that matches no `Workload` row returns `400`, and creates no `Session` row as a side effect.
- **AC-4**: A request with no `X-Session-Id` header creates a new `Session` row (fresh `uuid4()`, resolved `workload_id`, default `cumulative_risk`/`strikes`, `ttl_expires_at = now + 15min`).
- **AC-5**: A request with an `X-Session-Id` that matches no existing `Session` row creates one using that exact id as its primary key, same field values as AC-4.
- **AC-6**: A request with an `X-Session-Id` that matches an existing `Session` row whose `workload_id` equals the request's resolved workload reuses that row and refreshes its `ttl_expires_at` to `now + 15min`.
- **AC-7**: A request with an `X-Session-Id` that matches an existing `Session` row whose `workload_id` differs from the request's resolved workload returns `400`, and does not mutate that row.
- **AC-8**: Every successful (`200`) response carries `X-Workload-Id` and `X-Session-Id` response headers set to the resolved values, regardless of whether the caller supplied them.
- **AC-9**: No schema change is made to `Workload` or `Session`; resolution is purely application-layer logic against the existing tables.

## Options considered

### Option 1: Fail fast on both unknown-workload and cross-workload-session conflicts (recommended, ratified with user)

An unknown `X-Workload-Id` → `400`. A `X-Session-Id` that exists under a different workload than the one this request resolves to → `400`. Neither case falls back or auto-corrects.

**Pros**:
- Surfaces caller misconfiguration immediately (wrong workload id typo, a session id accidentally reused across two integrations) instead of silently applying the wrong policy profile, budgets, or ledger.
- Never violates Fork #1's "a Session cannot span two workloads" invariant, since neither branch ever writes a session under a workload other than the one it was already created under.

**Cons**:
- Slightly less "graceful" than the omitted-value fallback Fork #1/#3 describe — a caller with a stale or wrong id gets an error instead of a best-effort default. Acceptable: this is a different situation (a caller actively supplied a wrong value) from the one those forks describe (a caller supplied nothing).

### Option 2: Silently fall back / auto-correct on both cases

An unknown `workload_id` silently resolves to `DEFAULT_WORKLOAD_ID`. A cross-workload `session_id` silently defers to whichever workload the existing session row already has (ignoring the request's own resolved workload).

**Pros**:
- Never blocks a request over a resolution mismatch; maximizes uptime for a live demo.

**Cons**:
- Masks real integration bugs (a wrong workload_id could silently apply a `strict` workload's traffic under `balanced` policy, or vice versa) with no signal to the caller that anything was substituted.
- For the cross-workload case specifically, deferring to the session's existing workload silently overrides the caller's own explicit `X-Workload-Id`, which is a confusing, hard-to-debug behavior for exactly the kind of person this proxy is trying to build trust with.

### Option 3: Echo resolved ids back to the caller via response headers (recommended, ratified with user)

Add `X-Workload-Id`/`X-Session-Id` to every `200` response, set to the values actually resolved (not just echoed from the request).

**Pros**:
- Without this, a caller who never supplies `session_id` has no way to ever form a real multi-turn session — every request stays permanently length-1. Phase 6.1's demo requirement ("a ledger-driven multi-turn escalation") needs *some* mechanism for a session to span turns; this is the cheapest one available at this milestone.

**Cons**:
- Technically expands 1.2's surface slightly beyond STATUS.md's literal wording (which only mentions resolution, not response shape). Judged acceptable since it's a small, additive, non-breaking change (extra response headers, not a body/status-code change) and avoids painting Phase 6 into a corner.

## Decision

**Chosen**: Option 1 (fail fast on both unknown-workload and cross-workload-session conflicts) and Option 3 (echo resolved ids back via response headers). Both `400`s use FastAPI's standard `HTTPException` with a short `detail` string naming which id failed to resolve and why.

## Rationale

Fail-fast over silent fallback follows `AGENTS.md`'s own engineering discipline already established in this project (0.4's refusal to fake a schema workaround, 1.1's refusal to fake a model response): masking a real problem behind a plausible-looking success response is worse than a loud, immediate error, especially in a security/governance product where "the wrong policy silently applied" is precisely the class of failure this whole system exists to prevent elsewhere.

Echoing resolved ids back is the minimum viable answer to a real gap neither `forks.md` nor `STATUS.md` addresses: nothing in the locked design gives a stateless caller any way to *learn* the session id ControlPlane picked for it. Without this, Phase 6.1's multi-turn demo scenario would require the demo script to invent its own out-of-band id-sharing mechanism instead of using the one the proxy already returns for free.

## Feature design

**Data model sketch**: no schema change (satisfies **AC-9**). Uses the existing `Workload` and `Session` columns exactly as defined in 0.2/0.4.

**State transitions**:
- `Workload`: read-only in this milestone; never created or mutated by request handling (only `app/seed.py`'s startup seed writes to it).
- `Session`: created (AC-4, AC-5) or reused-with-refreshed-TTL (AC-6); never created under a workload other than the one resolved for that request.

**API surface**:
- `POST /v1/chat/completions` (unchanged path/body from 1.1). New response headers on `200`: `X-Workload-Id`, `X-Session-Id` (resolved values, always present).
- New error responses: `400` with `detail` explaining an unknown `workload_id` (AC-3) or a cross-workload `session_id` conflict (AC-7).

**Value sourcing**:
- Resolved `workload_id`: `X-Workload-Id` header if present and found in Postgres, else `DEFAULT_WORKLOAD_ID` (`app/seed.py`) if header absent, else a resolution failure (header present, not found).
- Resolved `session_id`: `X-Session-Id` header if present (existing row reused, or new row created at that id), else a freshly generated `uuid4()` (new row created).
- `ttl_expires_at`: always set to `now + 15min` (UTC) on every create or reuse — the one numeric value this spec introduces that isn't named elsewhere, chosen to mirror the Redis ledger's existing reset-on-write TTL behavior from 0.3's `decisions.md` entry, so the Postgres and Redis expiry semantics don't quietly diverge.

**Key invariants**:
- A `Session` row's `workload_id` never changes after creation (enforced by AC-7's fail-fast rather than silent reassignment) — this is the concrete mechanism that upholds Fork #1's "a Session cannot span two workloads."
- Resolution happens entirely before any 1.3+ logic runs; the handler never proceeds past a `400` to attempt evaluation or forwarding.
- The response headers in AC-8 always reflect what was actually persisted/looked up, never the raw unvalidated request header.

**Security model**: unchanged from 1.1; `workload_id`/`session_id` remain routing hints, not credentials. A `400` on conflict reveals only that a conflict exists, not details of the other workload's configuration.

**Configuration required**: none beyond the existing `DATABASE_URL`; no new environment variable.

**Critical test scenarios** (one per resolution branch):
- No headers → `200`, response headers show `DEFAULT_WORKLOAD_ID` and a freshly generated session id; a new `Session` row exists in Postgres. Verifies **AC-1**, **AC-4**, **AC-8**.
- Valid, existing `X-Workload-Id`, no `X-Session-Id` → `200`, response echoes that workload id and a new session id. Verifies **AC-2**, **AC-4**, **AC-8**.
- Unknown `X-Workload-Id` → `400`; confirm no `Session` row was created. Verifies **AC-3**.
- Valid workload, `X-Session-Id` for a session that doesn't exist yet → `200`, a `Session` row now exists at exactly that id, `workload_id` set to the resolved workload. Verifies **AC-5**.
- Valid workload, `X-Session-Id` for an existing session already under that same workload → `200`, row reused, `ttl_expires_at` advanced. Verifies **AC-6**.
- Valid workload, `X-Session-Id` for an existing session under a *different* workload → `400`; confirm the existing row's `workload_id` is unchanged afterward. Verifies **AC-7**.

## Build plan

1. In `app/routers/chat.py`, add a `Depends(get_db)` parameter (from `app.db`) to `chat_completions`, satisfies **AC-9** (no new DB helper needed).
2. Resolve `workload_id`: if `x_workload_id` is `None`, use `DEFAULT_WORKLOAD_ID`; else query `Workload` by primary key — not found raises `HTTPException(400, ...)`, satisfies **AC-1**, **AC-2**, **AC-3**.
3. Resolve `session_id`: if `x_session_id` is `None`, generate `uuid4()` and create a `Session` row (resolved `workload_id`, `ttl_expires_at = now + 15min`); else query `Session` by primary key — not found creates a row at that exact id (same fields); found with matching `workload_id` reuses it and refreshes `ttl_expires_at`; found with a different `workload_id` raises `HTTPException(400, ...)`. Satisfies **AC-4**, **AC-5**, **AC-6**, **AC-7**.
4. Update the stub response body to reference the *resolved* ids (replacing the raw-header echo from 1.1), and set `X-Workload-Id`/`X-Session-Id` on the `Response` object, satisfies **AC-8**.
5. Self-check: run the six scenarios from Critical test scenarios above via `curl` against a running `uvicorn` instance backed by the real Neon database, confirming both the HTTP behavior and the resulting Postgres row state for each, satisfies **AC-1** through **AC-8**.
6. Log the three ratified decisions (fail-fast on unknown workload, fail-fast on cross-workload session conflict, echoing resolved ids in response headers) to `decisions.md`.

## Consequences

**Positive**:
- Phase 1.3 can start directly from a resolved `Workload` (policy profile, budgets) and `Session` (id, current ledger state via the existing `get_ledger`), with zero resolution logic of its own to write.
- A caller integrating without any session management still gets a working, audit-linkable session per request, and can opt into real multi-turn sessions later just by reading and replaying the response headers.

**Negative / tradeoffs**:
- Fail-fast on both conflict cases means a caller with a stale cached `workload_id` (e.g. one that was since deleted, which nothing in this project's scope currently supports doing) would start seeing `400`s where a softer system might paper over it. Acceptable given this project's existing preference for loud failures over silent masking (0.4, 1.1).

**Neutral**:
- No automated tests are written for this milestone, per `AGENTS.md` Section 8; the critical test scenarios above are a manual `curl`-plus-database-inspection self-check, matching the pattern from 0.1–1.1.
