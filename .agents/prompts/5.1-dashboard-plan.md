# 5.1. Dashboard

**Date**: 2026-08-24
**Status**: Accepted

## Summary

`STATUS.md` describes 5.1 as: *"Total requests, blocked count, findings by category, over time."* This is the first UI work in the whole project — a full repo search confirmed zero existing frontend scaffolding. It is also the first console API endpoint. This spec adds one new read-only backend endpoint (`GET /api/console/summary`) backed by three Postgres aggregation queries, plus a new `console/` frontend (Vite + React + TypeScript + Tailwind + Recharts) with a single Dashboard page rendering two stat tiles and two charts from that endpoint.

Two real gaps in the audit trail were discovered while designing this, and both are ratified decisions, not oversights: escalation blocks (3.2) write zero Postgres rows (Redis-only, 15-minute TTL, no durable history), and an expensive-tier (2.5) async finding never actually blocks anything but does write a `Finding` row. The dashboard's metrics are defined to be honest about both rather than silently over- or under-claiming.

## Context

Mapped directly against the current code (`app/main.py`, `app/routers/`, `app/schemas/`, `app/models/*.py`, `pyproject.toml`) for this spec:

- **No frontend exists anywhere** — no `package.json`, no `.tsx`/`.jsx`, no `vite.config.*`, no `node_modules` in the repo. `forks.md` locks `Frontend: React` but leaves stack details, styling, charting, and exact screens (beyond "must have workload management view") explicitly open.
- **`app/main.py`** registers only `chat_router`, has no CORS middleware, and its lifespan does `create_all` → seed → Redis ping. Route surface today: `GET /health`, `POST /v1/chat/completions`.
- **`app/routers/`** has only `chat.py`. Convention to match: `router = APIRouter()`, `logger = logging.getLogger(__name__)`, `Depends(get_db)` for the DB session.
- **`app/schemas/`** has only `chat.py` — plain `pydantic.BaseModel` subclasses, no `orm_mode`.
- **Data model** (exact columns this build queries):
  - `Execution`: `execution_id` (PK), `session_id`, `workload_id`, `tokens`, `latency_ms`, `retries`, `tool_loop_count`, `execution_risk_score`, `created_at`. No `blocked` column of any kind — "blocked" must be derived.
  - `Finding`: `finding_id` (PK), `execution_id` (FK), `category` (`FindingCategory` enum), `confidence`, `evaluator_tier` (`cheap`/`medium`/`expensive`), `evidence_ref` (JSONB), `timestamp` (not `created_at` — the one model that names it differently).
- **The escalation-block gap**: `_run_request_side_interception`'s early-return and the response-side equivalent (`app/routers/chat.py`, both ratified in 3.2) only call `apply_ledger_update` (Redis) on that path — no `Execution`, no `Finding` row. Redis's ledger TTL is 15 minutes with no history retained. There is no way, today or after this spec, to recover a historical count of escalation-only blocks from any store.
- **The expensive-tier gap**: 2.5's async judge can only update the ledger/audit trail post-release (Fork #4) — it never blocks. Its `Finding` rows carry `evaluator_tier=expensive`. Counting "blocked" as "any associated Finding" would incorrectly count these.
- **`app/db.py`**: `async_session = async_sessionmaker(engine, expire_on_commit=False)`; `get_db()` yields a request-scoped session, reused identically here via `Depends(get_db)`.
- **`pyproject.toml`**: `fastapi`, `sqlalchemy`, `asyncpg`, `redis`, `httpx`, `python-dotenv`, `uvicorn[standard]`. `fastapi.middleware.cors.CORSMiddleware` ships with `fastapi` already — no new Python dependency for CORS.

## Requirements

- **AC-1**: `GET /api/console/summary` returns `total_requests` equal to `count(Execution)`.
- **AC-2**: `blocked_count` equals the count of distinct `Execution`s with at least one associated `Finding` where `evaluator_tier` is `cheap` or `medium` — explicitly excluding `Execution`s whose only `Finding`(s) are `evaluator_tier=expensive`.
- **AC-3**: `findings_by_category` matches a direct `Finding` `GROUP BY category` count.
- **AC-4**: `over_time` returns hourly buckets (`date_trunc('hour', Execution.created_at)`) for the last 24 hours, each with `total` and `blocked` (same cheap/medium-only definition as AC-2); bucket counts sum to `total_requests`/`blocked_count` for executions within that window, with no double-counting or dropped rows.
- **AC-5**: A request from `http://localhost:5173` (the Vite dev server's default origin) to `GET /api/console/summary` succeeds with the correct CORS header present.
- **AC-6**: The `console/` Dashboard page, run via `npm run dev`, renders two stat tiles (Total requests, Blocked) and two charts (findings by category; over time, `total` vs `blocked`) with real numbers matching the endpoint, and visibly shows a caveat that escalation-only blocks are not included in `blocked_count`.
- **AC-7**: `GET /health` and `POST /v1/chat/completions` are unaffected by the new middleware/router.

## Decision

**Chosen option**: one new backend endpoint (`GET /api/console/summary`, Postgres-only aggregation, no auth, no query params, fixed last-24h/hourly window) plus a new `console/` Vite + React + TypeScript + Tailwind + Recharts frontend with a single Dashboard page. Both ratified with the user before drafting.

**Implementation skills**: none — no ORM/auth/payment library decision is involved beyond what's already in `pyproject.toml`; Vite/React/Tailwind/Recharts are plain, direct dependency additions, not "installed skills" per `AGENTS.md`'s `## Agent skills` convention (none listed there today).

### Backend

- **`app/main.py`**: add `CORSMiddleware` (`allow_origins=["http://localhost:5173"]`, `allow_methods=["GET"]`, `allow_headers=["*"]`) and register the new console router alongside `chat_router`.
- **`app/schemas/console.py`** (new): `CategoryCount { category: str; count: int }`, `TimeBucket { bucket: datetime; total: int; blocked: int }`, `DashboardSummary { total_requests: int; blocked_count: int; findings_by_category: list[CategoryCount]; over_time: list[TimeBucket] }`.
- **`app/routers/console.py`** (new): `GET /api/console/summary`, `Depends(get_db)`, three SQLAlchemy async queries:
  1. `total_requests` = `select(func.count(Execution.execution_id))`.
  2. `blocked_count` = `count(distinct Execution.execution_id)` joined to `Finding` filtered to `evaluator_tier != EvaluatorTier.expensive`.
  3. `findings_by_category` = `select(Finding.category, func.count()).group_by(Finding.category)`.
  4. `over_time` = `Execution` grouped by `date_trunc('hour', Execution.created_at)`, last 24 hours, with the same cheap/medium-only filter as #2 for each bucket's `blocked` count.

**Value sourcing** (every displayed value has a named Postgres source):

| Value | Source |
|---|---|
| `total_requests` | `count(Execution)` |
| `blocked_count` | `count(distinct Execution)` with ≥1 `Finding` where `evaluator_tier in (cheap, medium)` |
| `findings_by_category[].count` | `count(Finding) group by category` |
| `over_time[].total` / `.blocked` | same two counts, grouped by `date_trunc('hour', Execution.created_at)`, last 24h |

### Frontend

- New `console/` directory at the repo root (sibling to `app/`), Vite's `react-ts` template, plus Tailwind (PostCSS config, `tailwind.config.ts`, `@tailwind` directives) and `recharts`.
- `console/.env` (git-ignored): `VITE_API_BASE_URL=http://localhost:8000`.
- One `Dashboard` component, fetches `GET {VITE_API_BASE_URL}/api/console/summary` on mount:
  - Stat tiles: **Total requests**, **Blocked** (with the AC-6 caveat line under Blocked).
  - Recharts `BarChart` for `findings_by_category`.
  - A Recharts chart (line or bar) for `over_time`, two series (`total`, `blocked`).
- No live refresh (5.4's explicit job), no routing/nav shell beyond this one page (5.2/5.3/5.4 introduce that when they land), no per-workload scoping (global view only; 5.2/5.3 add scoped views).

## Rationale

The two metric-definition gaps are real properties of the already-shipped 3.2/2.5 designs, not new problems to solve here — 3.2 deliberately chose not to log escalation blocks (no turn-specific evidence to attach), and 2.5 deliberately made the expensive tier audit-only. A dashboard's job is to report what the audit trail actually contains, honestly, not to paper over what it doesn't. Defining `blocked_count` to exclude `expensive`-tier-only findings and adding a visible caveat for the escalation gap keeps the numbers correct as far as the data goes, without reopening either prior decision or adding new hot-path logging to the proxy just to feed a chart.

Vite + React + TypeScript + Tailwind + Recharts was ratified as the simplest, most standard stack that satisfies `forks.md`'s React lock: Vite needs no separate config to get a working dev server and build; TypeScript catches shape mismatches against the new `DashboardSummary` schema at compile time; Tailwind avoids hand-writing CSS or pulling in a full component library for a first, small page; Recharts is a React-native charting library well suited to the two chart types this milestone needs (a category bar chart, a two-series time series). A fixed last-24h/hourly window (not user-configurable) is the simplest option that stays stable regardless of how compressed a demo data-generation run turns out to be.

## Consequences

**Positive**:
- First real visibility into ControlPlane's own audit trail — closes the loop from Phase 4's data collection to something a person can actually look at.
- Establishes the console's stack and API-prefix convention (`/api/console/...`) that 5.2/5.3/5.4 can build on directly, without re-deciding tooling each time.

**Negative / tradeoffs**:
- `blocked_count` undercounts true blocking activity whenever escalation blocks fire without a fresh content violation in the same turn — an accepted, documented limitation, not a bug.
- Console API has no authentication, matching every other endpoint in this hackathon build (no auth work is in scope anywhere in this project).
- Fixed 24h/hourly window means a demo run outside that window, or one that needs finer granularity, won't show correctly without a follow-up change.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-check described below.
- No database schema change; no new Python dependency (CORS ships with `fastapi`).

## Follow-up

- If a live demo needs finer time granularity than hourly (e.g. a data-generation run compressed into a few minutes), revisit the bucket size — not built now, to keep 5.1 simple.
- Reopening whether escalation blocks should also write a minimal Postgres row (closing the `blocked_count` gap at the source, not just in how the dashboard labels it) is a proxy hot-path decision, not a dashboard one — explicitly declined for 5.1's scope; revisit via `/architect` only if the demo narrative needs it.
- 5.2 Workload Management View is the next milestone — write its spec first via `/architect`. It will need to introduce the console's first navigation/routing shell, since 5.1 is a single page with none.
