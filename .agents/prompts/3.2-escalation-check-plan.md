# 3.2. Escalation Check

**Date**: 2026-08-24
**Status**: Accepted

## Summary

This spec closes the actual gap left after 3.1: the session ledger's *accumulated* state (from previous turns) is written correctly on every turn, but nothing ever reads it to decide anything. Every block today is a reaction to *this turn's own content* (a cheap-tier match on the current prompt or response) — a session that is already over threshold from a prior violation still lets a brand-new, perfectly clean request straight through to the model. 3.2 implements Fork #3's exact escalation trigger (`cumulative_risk > 0.7 OR any strikes[category] >= 3`) as a real gate, wired into both the request-side and response-side flows per Fork #4's literal specified ordering. It adds `is_escalated(ledger) -> bool` to `app/redis_client.py`, a request-side pre-check that blocks fast (before any content evaluation) when a session arrives already escalated, and a response-side reorder so the escalation check runs immediately after the ledger's clean-turn decay touch and before medium/expensive tier are ever invoked. Only "block" is implemented of Fork #3's "block/regenerate/route" — regenerate/route have no underlying mechanism anywhere in this codebase and are explicitly out of scope.

## Context

`forks.md` Fork #3 locks the condition exactly:
```
escalate/block IF (cumulative_risk > 0.7) OR (any strikes[category] >= 3)
```
Fork #4 locks the response-side ordering explicitly: "Cheap tier's findings feed `execution_risk_score` → update the session ledger → check escalation trigger. If the ledger already trips escalation after cheap tier → block/regenerate/route immediately. Do not run medium/expensive tier. If cheap tier is inconclusive → run medium/expensive tier synchronously..." `STATUS.md` names 3.2 as: "`cumulative_risk > 0.7 OR any(strikes) >= 3` → trigger block/regenerate/route."

Read in full this session (not guessed): `app/redis_client.py` (post-3.1, 133 lines — `apply_ledger_update`, `get_ledger`, `default_ledger`, no `is_escalated` yet), `app/routers/chat.py` (post-3.1, 401 lines — `_run_request_side_interception`, `_run_response_side_interception`, `_run_expensive_tier_task`, `_policy_block_response`), `.agents/prompts/3.1-ledger-update-logic-plan.md`. Confirmed:

- **No code anywhere reads `cumulative_risk`/`strikes` to make a decision.** `decisions.md`'s existing entries confirm this explicitly: "1.3/1.5 block unconditionally on any cheap-tier match regardless of ledger state" — true for every phase through 3.1. The ledger is written on every turn (3.1's whole job) but never consulted.
- **Request-side-clean never touches the ledger.** `_run_request_side_interception` only calls `apply_ledger_update` on its own violation branch; a clean scan returns `None` and falls through to the model call. The response side owns the "conclusion" touch for that request (3.1's "exactly one ledger touch per concluded HTTP request" invariant, confirmed by AC-2/AC-3 in the 3.1 spec).
- **Response-side today runs medium tier before any escalation concept exists.** Current order in `_run_response_side_interception`: cheap tier scan → if clean, run medium tier → if still clean, `execution_risk_score = 0.0`, commit, `apply_ledger_update(0.0, [])`, schedule the expensive-tier background task, release. Fork #4's literal ordering (ledger update → escalation check → *then* decide whether medium/expensive tier runs at all) is not what's built.
- **Cheap-tier confidence is a fixed `0.95`** (a module constant in `app/evaluators/types.py`, unchanged since 1.3), always `> ESCALATION_RISK_THRESHOLD (0.7)`. This means a *single* violation immediately pushes `cumulative_risk` to `0.95` — already over threshold — so the very next turn after any single violation is already pre-escalated, until one decay touch (`0.95 * 0.7 = 0.665`) brings it back under `0.7`. This is the concrete, always-reachable scenario the request-side pre-check exists for; it does not require a contrived multi-strike setup to observe.
- **`run_medium_tier` is a permanent stub returning `[]`** (2.4, corrected in the same session to defer real hallucination detection to 2.5's LLM-as-judge instead). The branch "medium tier finds something after cheap tier was clean but the session wasn't escalated" is unreachable dead code today — noted as a Follow-up for whenever medium tier becomes real, not solved here.
- **`STATUS.md`'s Known Follow-ups name two things for this milestone explicitly**: (1) whether `strikes[category]` should keep incrementing once per `Finding` (today's behavior) or cap at one increment per execution — "a design call for 3.2 to make deliberately, not inherit by accident"; (2) that `X-Workload-Id`/`X-Session-Id` are caller-asserted with no auth, "harmless today... becomes load-bearing the moment 3.2 makes the ledger the escalation mechanism."
- **Two judgment calls were ratified directly with the user before writing this spec** (via `/architect`'s staged questions, not silently decided):
  1. **Strike counting stays per-Finding**, matching Fork #3's literal wording ("increment a category's strike when a Finding in that category has confidence > 0.7" — no per-execution cap stated). A single response with 3+ matching Findings in one category can trip that category's threshold by itself, in one turn, not only across turns. No code change needed — this is a ratification of existing behavior, not a new implementation.
  2. **An already-escalated session skips this turn's content scan entirely and blocks fast**, rather than always running the cheap-tier scan first for audit completeness. Matches the existing "cheap tier fails fast, before the model call" philosophy, applied one layer earlier (checking ledger state is even cheaper than a regex scan). Tradeoff: if a pre-blocked turn's content also happened to contain a violation, that specific evidence is never scanned or logged — accepted, flagged as a Phase 4 Follow-up below.
- **The caller-asserted-session-id gap (Follow-up #2 above) is accepted as-is**, per the existing `decisions.md` entry from the 2026-08-23 review response ("No auth work is in scope for this hackathon build"). This spec does not add authentication; it is the point at which that already-logged, already-accepted limitation becomes actually exploitable (a caller could rotate `X-Session-Id` to dodge an escalation block) rather than merely theoretical.

## Requirements

**User stories**:
- As the operator of ControlPlane, I want a session that has already accumulated too much risk to actually be blocked on its next turns, not just have its violating turns individually blocked, so the ledger's whole purpose (tracking risk *across* a session) is real.
- As the engineer building Phase 3.3 next, I want the escalation decision isolated in one predicate (`is_escalated`) so fail-open/fail-closed error handling has one clear place to wrap, not scattered ledger-reading logic.
- As an operator reading logs/audits, I want to be able to tell "this session is in cooldown from prior risk" apart from "this exact message was blocked," so the two failure modes are debuggable separately.

**Acceptance criteria**:
- **AC-1**: A session whose ledger already has `cumulative_risk > 0.7` (e.g. immediately after one prior violation, which alone reaches `0.95`) gets a `403` session-escalation block on its very next request, even though that request's own content is completely clean — no cheap-tier scan runs, no model call happens, no `Execution`/`Finding` row is created.
- **AC-2**: That same escalation-blocked request still touches the ledger exactly once (`apply_ledger_update(session_id, 0.0, [])`): `turn` increments by 1, `cumulative_risk` decays, `strikes`/`strike_events` unchanged — preserving 3.1's "exactly one ledger touch per concluded request" invariant.
- **AC-3**: A session with `strikes[category] >= 3` (from the windowed count 3.1 already maintains) is pre-check-blocked on the request side even when `cumulative_risk <= 0.7` on its own.
- **AC-4**: A session under both thresholds behaves exactly as before 3.2: the pre-check passes through, the cheap-tier scan runs, and clean content reaches the model normally (regression, no observable change).
- **AC-5**: On the response side, when cheap tier finds nothing on this turn but the ledger's state is escalated (checked immediately after this turn's own `0.0`-decay touch, before medium tier runs), the response is blocked with the session-escalation envelope; `run_medium_tier` is never called and the expensive-tier `BackgroundTasks` entry is never scheduled for that request.
- **AC-6**: When cheap tier is clean and the post-decay ledger is *not* escalated, behavior is byte-identical to pre-3.2: medium tier still runs (still empty), the expensive-tier task is still scheduled with the same `turn_anchor`/`ts_anchor` semantics 3.1 established, response releases `200`.
- **AC-7**: A response-side cheap-tier violation still blocks unconditionally exactly as before (regression) — that branch returns before the new escalation check is ever reached, so it is provably unaffected.
- **AC-8**: A request-side cheap-tier violation on a *not-yet-escalated* session still blocks unconditionally exactly as before (regression) — the pre-check passes through (not escalated), then the existing violation path fires unchanged.
- **AC-9**: The escalation-block response body is a `403` OpenAI-style `{"error": {...}}` envelope with `type: "controlplane_session_escalated"` and `code: "session_escalated"`, distinct from a content-violation block's `type: "controlplane_policy_violation"` — so a direct Postgres/log inspection (or a client parsing `code`) can tell "session in cooldown" apart from "this content was blocked" without ambiguity.
- **AC-10**: Full regression: `/health` still `200`, an unknown-workload request still `400`, a model-unreachable request still `502`, and at least one genuinely clean end-to-end pass-through still returns `200` with real model content — all unaffected by this milestone.

## Options considered

### Option 1: Read-only pre-check on the request side + reordered response-side check, sharing one `is_escalated(ledger)` predicate (recommended)

As described in Decision below: a cheap `get_ledger` peek gates the request side before any content scan; the response side's existing clean-path ledger touch is moved earlier and immediately followed by the same predicate.

**Pros**: Preserves 3.1's one-touch-per-request invariant in every branch (the pre-check only ever touches the ledger on its own early-return path, which is that request's sole conclusion). Matches Fork #4's literal ordering on the response side exactly, not approximately. One shared predicate, no duplicated threshold logic.
**Cons**: Two separate call sites to wire (request-side pre-check, response-side reorder) rather than one central chokepoint — accepted, since request-side and response-side are already structurally separate functions per Fork #4's own request/response split, and forcing them through one function would fight the existing architecture for no real benefit.

### Option 2: Single central "is this session allowed to proceed" check called once at the very top of `chat_completions`, before either interception function runs

Move all escalation logic to one gate at the handler entry point, checked immediately after session resolution.

**Pros**: One call site instead of two; simplest possible mental model ("checked once per request, up front").
**Cons**: Cannot satisfy Fork #4's response-side ordering, which requires the escalation check to happen *after* this turn's own cheap-tier result has already been folded into the ledger via `apply_ledger_update` (a response-side violation this turn should still block via the existing unconditional-match path, not get short-circuited by a stale pre-turn ledger read) — a single up-front check would need its own second, later check anyway to satisfy AC-5, collapsing back into Option 1's two-call-site shape but with an extra layer of indirection.

### Option 3: Always run the cheap-tier scan even on an already-escalated session, for audit completeness, before returning the escalation block

Rejected per the ratified answer above (ask 2): skip-scan-and-block-fast was the user's explicit choice over scan-then-block, prioritizing speed and matching the existing "cheap tier fails fast" precedent over full audit fidelity for an already-flagged session. Logged as a Follow-up for Phase 4 to reconsider if audit completeness on pre-blocked turns ever matters for the demo.

## Decision

**Chosen option**: Option 1. Add `ESCALATION_RISK_THRESHOLD = 0.7` and `ESCALATION_STRIKE_COUNT = 3` plus `is_escalated(ledger: dict[str, Any]) -> bool` to `app/redis_client.py` — a pure predicate over the ledger shape, living next to the other Fork #3 constants (matches the module's own docstring split: ledger math and shape live here; the *decision of what to do* about it lives in `chat.py`, same split 3.1 already established between `apply_ledger_update` and `_policy_block_response`).

Two call sites in `app/routers/chat.py`:

1. **Request-side pre-check**, at the top of `_run_request_side_interception`, before the existing `run_cheap_tier` call:
   ```python
   ledger = await get_ledger(str(session.session_id))
   if is_escalated(ledger):
       await apply_ledger_update(str(session.session_id), 0.0, [])
       return _escalation_block_response()
   ```
   This is a read-only peek (`get_ledger`, not `apply_ledger_update`) so a not-escalated session is never touched here — the touch only happens on the early-return path itself, which is that request's sole conclusion, preserving the one-touch invariant.

2. **Response-side reorder**, in `_run_response_side_interception`: keep the cheap-tier-violation branch exactly as-is (unchanged, still returns first). Move the existing clean-path block (`execution.execution_risk_score = 0.0`, commit, `apply_ledger_update(0.0, [])`) to run *immediately* when cheap tier is clean — before `run_medium_tier` is called (today it runs after). Immediately after that touch:
   ```python
   if is_escalated(ledger):
       return _escalation_block_response()
   ```
   Only if not escalated does the function proceed to `run_medium_tier` and the background-task scheduling, exactly as today.

New shared helper in `app/routers/chat.py`, sibling to `_policy_block_response`:
```python
def _escalation_block_response() -> JSONResponse:
    """Session-level block: the ledger's accumulated state (not this turn's
    own content) tripped Fork #3's escalation condition. Distinct `type`/
    `code` from _policy_block_response so logs/audits and any client-side
    handling can tell "session in cooldown" apart from "this content was
    blocked."
    """
    return JSONResponse(
        status_code=403,
        content={
            "error": {
                "message": (
                    "This session is temporarily blocked: accumulated risk has "
                    "exceeded ControlPlane's policy threshold. It will clear "
                    "automatically as recent activity ages out."
                ),
                "type": "controlplane_session_escalated",
                "param": None,
                "code": "session_escalated",
            }
        },
    )
```

No new `Finding`/`Execution` rows on either escalation-block path — there is no turn-specific evidence to attach (matches 1.4's "only log what concretely happened" precedent for its own no-`Execution`-on-failure path). `Finding.confidence`/category strike counting stays per-Finding, unchanged from today (ratified ask 1 above — no code change). Regenerate/route are not built; only block. No mechanism for either exists anywhere in this codebase (no retry-with-different-prompt path, no alternate-model routing) — logged as an explicit Follow-up, not silently dropped per `AGENTS.md` Rule 9.

## Rationale

Option 3 is eliminated by direct ratification with the user, not by default. Between Options 1 and 2, the deciding factor is that Fork #4's ordering is not negotiable: the response-side escalation check must happen *after* this turn's own result is folded into the ledger, so a response-side violation this turn still blocks via the existing unconditional path (AC-7) rather than being pre-empted by a stale ledger read from before this turn happened. A single up-front gate (Option 2) can't satisfy that without adding a second, later check anyway — at which point it has quietly become Option 1 with extra indirection. Keeping the two call sites separate, one per side, mirrors the fact that Fork #4 itself specifies request-side and response-side behavior as two distinct sections with different rules (request-side is cheap-tier-only and fails fast; response-side has the tiered cheap → medium → expensive structure) — the escalation check belongs inside each side's own existing shape, not bolted on as a third layer above both.

The request-side pre-check being a pure read (not a touch) is required by 3.1's already-established invariant, not a new design choice: a request-side-clean turn has never touched the ledger (the response side owns that turn's one touch), and making the pre-check a read-only peek — touching only on its own early-return path — keeps that true in every branch, including the new escalated-block branch, which is itself that request's full conclusion.

## Feature design

**Data model sketch**: no Postgres schema change. No new Redis ledger fields (3.1 already built everything this milestone reads: `cumulative_risk`, `turn`, `strikes`, `strike_events`). This milestone adds only:

```python
# app/redis_client.py, alongside the existing Fork #3 constants
ESCALATION_RISK_THRESHOLD = 0.7
ESCALATION_STRIKE_COUNT = 3


def is_escalated(ledger: dict[str, Any]) -> bool:
    """Fork #3's exact escalation condition, read against an already-current
    ledger (the caller is responsible for calling this against a freshly
    read or freshly updated ledger - this function does not touch Redis).
    """
    if ledger["cumulative_risk"] > ESCALATION_RISK_THRESHOLD:
        return True
    return any(count >= ESCALATION_STRIKE_COUNT for count in ledger["strikes"].values())
```

**Changed file**: `app/routers/chat.py`

1. `_run_request_side_interception` gains the pre-check shown in Decision, as its first statements, before `text = "\n".join(...)`.
2. `_run_response_side_interception`'s clean-cheap-tier branch is restructured:
   ```python
   if not cheap_candidates:
       execution.execution_risk_score = 0.0
       await db.commit()

       ts_anchor = time.time()
       ledger = await apply_ledger_update(str(session.session_id), 0.0, [])

       if is_escalated(ledger):
           return _escalation_block_response()

       context_text = "\n".join(message.content for message in request.messages)
       budget_remaining_ms = workload.latency_budget_ms
       medium_candidates = run_medium_tier(context_text, response_text, budget_remaining_ms)

       if not medium_candidates:
           background_tasks.add_task(
               _run_expensive_tier_task,
               execution_id=execution.execution_id,
               session_id=session.session_id,
               context_text=context_text,
               response_text=response_text,
               turn_anchor=ledger["turn"],
               ts_anchor=ts_anchor,
           )
           return None
       # medium-tier-violation branch: currently unreachable (2.4's stub
       # always returns []), kept for structural completeness — see Follow-up.
       candidates = medium_candidates
   else:
       candidates = cheap_candidates
   ```
   Renaming `candidates` to `cheap_candidates` at the point of the initial `run_cheap_tier` call (and `medium_candidates` for the medium-tier result) makes the reordering unambiguous; the existing violation-path code below (building the `Finding`s, calling `apply_ledger_update`, returning `_policy_block_response("response", candidates)`) is otherwise unchanged, now reached only via `candidates = cheap_candidates` (this turn's own content violated) or the currently-unreachable `candidates = medium_candidates` path.
3. New `_escalation_block_response()` helper, sibling to `_policy_block_response`, as shown in Decision.
4. `is_escalated`, `get_ledger`, `apply_ledger_update` imported from `app.redis_client` (the module already exposes `apply_ledger_update`; add `is_escalated` and `get_ledger` to that same import line).

**Value sourcing**:
| Action | Value produced | Source |
|---|---|---|
| Request-side pre-check | "is this session escalated" | `is_escalated(await get_ledger(session_id))` — a fresh read, not derived from anything already in scope |
| Request-side escalated block | the ledger touch's `execution_risk_score` | fixed `0.0` — no content was evaluated this turn, so there is no real score to report |
| Response-side escalation check | "is this session escalated" | `is_escalated(ledger)` where `ledger` is the exact dict `apply_ledger_update` just returned for this turn's own `0.0`-decay touch — never a second, separate read |
| Escalation block envelope | `code`/`type` | fixed constants (`"session_escalated"` / `"controlplane_session_escalated"`), distinct from `_policy_block_response`'s per-category `code` |

**Key invariants**:
- `is_escalated` never touches Redis itself — every call site is responsible for supplying an already-read-or-updated ledger.
- The request-side pre-check calls `apply_ledger_update` on at most one branch (the escalated one); a not-escalated pre-check performs zero ledger writes, preserving 3.1's one-touch-per-request rule together with whatever the rest of that request's flow does downstream.
- The response-side escalation check is evaluated against the *same* `apply_ledger_update` call already required for the clean-turn decay touch — never an extra read, never a second write for the same request.
- No code outside `app/redis_client.py` computes the escalation condition inline; every caller goes through `is_escalated`.

**Security model**: unchanged from 1.x — `X-Workload-Id`/`X-Session-Id` remain caller-asserted with no authentication (already accepted in `decisions.md`). This milestone is the one `STATUS.md`'s own Follow-up predicted would make that gap load-bearing rather than harmless (a caller could rotate `X-Session-Id` to dodge an escalation cooldown); still explicitly out of scope for this hackathon build, not fixed here.

**Configuration required**: none (no new env vars, no new Workload fields — `ESCALATION_RISK_THRESHOLD`/`ESCALATION_STRIKE_COUNT` are fixed per Fork #3, not per-workload; Fork #1's "category overrides, post-MVP" field is the only place per-workload tuning could live later, and remains unbuilt per 2.2's own precedent).

**Critical test scenarios** (each maps to an acceptance criterion above):
- Manufacture a session with `cumulative_risk > 0.7` (a single real prior violation suffices, per the Context note above), then send a clean request: confirm `403`/`code:"session_escalated"`, zero new `Execution`/`Finding` rows, no model call. Verifies **AC-1**.
- Read the ledger immediately before and after that same blocked request: `turn +1`, `cumulative_risk` decayed by the standard factor, `strikes` unchanged. Verifies **AC-2**.
- Manufacture (or accumulate via 6 rapid same-category violations, mirroring 3.1's own AC-6 method) a session with `strikes[pii] >= 3` and `cumulative_risk <= 0.7`, send a clean request: confirm `403`/`session_escalated`. Verifies **AC-3**.
- Fresh (or decayed-below-threshold) session, clean request: confirm normal `200` model forwarding, unchanged from pre-3.2 behavior. Verifies **AC-4**.
- Manufacture an escalated ledger, then send a request whose content is clean on both request and response side (so it reaches `_run_response_side_interception`'s clean branch): confirm `403`/`session_escalated` at the response-side check, and confirm (via code path / absence of any medium-tier or background-task side effect) neither `run_medium_tier` nor the expensive-tier task ran. Verifies **AC-5**.
- Not-escalated session, fully clean exchange: confirm `200`, medium tier still called (still empty), background task still scheduled with matching `turn_anchor`/`ts_anchor`. Verifies **AC-6**.
- Not-escalated session, a response containing PII: confirm `403`/`code:"pii"` exactly as pre-3.2 (regression). Verifies **AC-7**.
- Not-escalated session, a request containing PII: confirm `403`/`code:"pii"` exactly as pre-3.2 (regression). Verifies **AC-8**.
- Direct comparison of the escalation envelope's `type`/`code` against a content-violation envelope's. Verifies **AC-9**.
- Full 1.2 through 3.1 regression sweep (`/health` `200`, unknown-workload `400`, model-unreachable `502`, one genuinely clean end-to-end pass-through `200`). Verifies **AC-10**.

## Consequences

**Positive**:
- The session ledger's accumulated state finally gates future turns, not just reacts to the current one — the actual point of maintaining a per-session ledger at all, and the last piece Phase 3's own framing ("Session Ledger & Control") promises.
- Fork #4's response-side ordering is now followed exactly (ledger update → escalation check → conditional medium/expensive tier), not approximately.
- Both Known Follow-ups `STATUS.md` flagged for this exact milestone are resolved deliberately (strike-cap question ratified; auth gap explicitly acknowledged as now-active) rather than inherited by accident.

**Negative / tradeoffs**:
- An already-escalated session's turn-specific content (clean or violating) is never evaluated or logged while pre-blocked — a deliberate, ratified tradeoff favoring speed over audit completeness, flagged as a Phase 4 Follow-up.
- The caller-asserted-session-id-with-no-auth gap (already known, already accepted) is now genuinely exploitable rather than merely theoretical — still out of scope for this hackathon build, not fixed here.
- The medium-tier-violation branch this spec's reorder preserves structurally is currently dead code (2.4's stub always returns `[]`); it will need its own escalation re-check design once medium tier becomes real, not solved now.

**Neutral**:
- No automated tests written, per `AGENTS.md` Section 8; manual `curl` plus direct Redis/Postgres inspection self-check only, matching every prior phase.
- No change to `Session.cumulative_risk`/`Session.strikes` (still-dead Postgres columns) — Phase 4 remains their explicit owner.
