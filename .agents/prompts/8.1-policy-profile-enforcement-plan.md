# 8.1. Policy Profile Enforcement

**Date**: 2026-08-27
**Status**: Accepted

## Summary

`Workload.policy_profile` (`strict`/`balanced`/`fast`) has existed since Phase 0 and is fully editable via the 5.2 console, but nothing anywhere reads it — `decisions.md`'s 2026-08-25 (7.1, Major #4) entry already confirmed this by a full-tree grep. Every workload, regardless of its stated profile, escalates at the exact same hardcoded `cumulative_risk > 0.7 OR any strikes[category] >= 3`, and every cheap-tier evaluator match carries the exact same flat `confidence = 0.95` regardless of how deterministic or ambiguous the underlying pattern actually is. 8.1 closes both gaps: escalation thresholds become a per-profile lookup (`strict` tighter, `balanced` unchanged, `fast` unchanged), and the single global `CONFIDENCE` constant is replaced with a per-pattern value across all five cheap-tier evaluator files, reflecting each pattern's real precision. It also gives `fast`'s background LLM-judge scheduling a probabilistic sample rate instead of running it on every clean response — the one piece of profile-driven behavior that isn't a threshold change. This is the foundation 8.2 (tiered flag/block) explicitly depends on: without differentiated confidence, `STRIKE_THRESHOLD=0.7` filters nothing (every match already exceeds it identically), and 8.2 would have no signal-strength dimension to key off beyond profile alone.

## Context

Read in full this session (not guessed): `app/redis_client.py` (post-7.1, 181 lines — `is_escalated`, `apply_ledger_update`, the Fork #3 constants), `app/routers/chat.py` (post-8.0, 616 lines — both interception functions, both `is_escalated` call sites, the response-side background-task scheduling), `app/routers/console.py` (343 lines — two more `is_escalated` call sites in `list_sessions`/`get_session_detail`, both already have a resolved `workload` in scope), `app/evaluators/types.py`, `cheap.py`, and all five pattern files (`pii.py`, `prompt_injection.py`, `toxicity.py`, `bias.py`, `secrets.py`), `app/models/workload.py`, `app/models/enums.py`. Confirmed:

- **`is_escalated(ledger)` takes no profile argument today** — it always compares against the module-level `ESCALATION_RISK_THRESHOLD = 0.7` / `ESCALATION_STRIKE_COUNT = 3`. Four call sites exist: `chat.py`'s request-side pre-check and response-side reorder (both already have `workload` in scope), and `console.py`'s `list_sessions`/`get_session_detail` (both already have a resolved `Workload` row in scope too — `list_sessions` iterates `(session, workload)` pairs from its own join; `get_session_detail` fetches `workload = await db.get(Workload, session.workload_id)` a few lines before calling `is_escalated`). No plumbing gap anywhere — every call site already has the profile available, it's just not passed.
- **Every cheap-tier pattern across all 5 files uses one imported constant, `CONFIDENCE = 0.95`** (`app/evaluators/types.py`), including patterns already known to be false-positive-prone by their own file's documentation (`ip_address`/`fake_role_marker`'s docstrings explicitly accept indistinguishable false positives; `bias.py`'s own module docstring calls its patterns "a weak proxy for bias"). `STRIKE_THRESHOLD = 0.7` (the confidence a `Finding` needs to increment a strike, per Fork #3) is therefore satisfied identically by every single match today, making it dead weight as a filter.
- **Cheap tier's "any match blocks unconditionally" rule is untouched by this milestone** (`decisions.md`, 2026-08-23: "any match blocks unconditionally... no inconclusive cheap-tier state"). Differentiating confidence changes what a match contributes to the ledger (strike-or-not, how much `cumulative_risk` grows) — it does **not** change whether that turn's response/request is blocked right now. That decision stays exactly as-is; 8.2 is the named future milestone that gives disposition (`flagged` vs `blocked`) a reason to consult confidence.
- **The async expensive-tier judge (2.5) is scheduled unconditionally today** whenever cheap tier and the permanently-stubbed medium tier are both clean, via one `background_tasks.add_task(_run_expensive_tier_task, ...)` call in `_run_response_side_interception`. `Workload.cost_budget_per_request` exists on the model, is fully serialized/editable via the console, and is read nowhere in `app/` outside the model/seed/serialization layer (confirmed by `decisions.md`'s 7.1 Major #4 grep) — this milestone is its first real (if narrow) use.
- **`STATUS.md`'s "Assumed Decisions Pending Ratification" section named four open numbers for this milestone.** All four were ratified directly with the user before writing this spec (not silently assumed):
  1. `strict` escalates at `cumulative_risk > 0.5` and `strikes[category] >= 2` (both tighter than today's global `0.7`/`3`).
  2. `fast` keeps the exact same thresholds as `balanced` (`0.7`/`3`) — its leniency comes from 8.2's future flag-not-block tiering and this milestone's judge-sampling, not from looser escalation math. (The alternative — giving `fast` its own looser thresholds too — was explicitly declined in favor of keeping this milestone additive and low-risk.)
  3. `fast`'s background judge samples at a fixed **10%** rate on an otherwise-clean response, rather than running every time (like `strict`/`balanced`) or never (which would leave `fast`-profile traffic with zero hallucination coverage — the expensive tier is the only hallucination detector anywhere in the system).
  4. Per-pattern confidence gets a full proposed table now (below), covering all ~25 patterns across the 5 cheap-tier files, not just the 5 STATUS.md named explicitly.
- **A scope clarification surfaced while designing the table, flagged here rather than silently resolved**: STATUS.md says "`balanced` must stay byte-identical to current behavior... regression guardrail." Read completely literally, this would forbid the per-pattern confidence table too, since a `balanced`-profile session's ledger trajectory *does* change once (say) an `ip_address` match contributes `0.6` instead of `0.95` — the same change applies to every profile, `balanced` included, because confidence is a property of the pattern, not the workload. This spec reads "byte-identical" as scoped to the **escalation-threshold mechanism**: `balanced`'s threshold *numbers* stay `0.7`/`3`, unchanged, and `is_escalated` given a `balanced`-profile ledger makes the identical escalate/no-escalate call it would have before, for any given ledger state. The confidence-differentiation half of this milestone is an explicit, separate, cross-profile improvement STATUS.md lists in the same line item — it necessarily changes what ledger state a given match *produces*, for every profile, which is the entire point (8.2 needs that signal to exist at all). Flagging this plainly at the approval gate rather than assuming it's uncontroversial.

## Requirements

**User stories**:
- As the operator of ControlPlane, I want a `strict`-profile workload (e.g. a decision-support tool) to cut off a risky session sooner than a `balanced` one, so the profile I chose for a use case actually changes its risk tolerance, not just its label.
- As the engineer building 8.2 next, I want cheap-tier findings to carry a confidence value that reflects real detection precision, so a future flag-vs-block decision has an actual signal to key off instead of one constant that's identical on every match.
- As the operator of a `fast`-profile workload (high-volume, cost-sensitive), I want the expensive LLM-judge to run occasionally rather than never, so that use case isn't structurally blind to hallucinations, while still respecting that this profile intentionally trades thoroughness for throughput/cost.

**Acceptance criteria**:
- **AC-1**: A `strict`-profile session with `strikes[category] == 2` (which would **not** escalate today) returns `403`/`session_escalated` on its next request.
- **AC-2**: A `strict`-profile session with `0.5 < cumulative_risk <= 0.7` (which would **not** escalate today) returns `403`/`session_escalated` on its next request.
- **AC-3**: A `balanced`-profile session's escalation behavior is unchanged: it does **not** escalate until `strikes[category] >= 3` or `cumulative_risk > 0.7`, exactly as before this milestone.
- **AC-4**: A `fast`-profile session's escalation thresholds are identical to `balanced`'s (`3` / `0.7`), confirmed by direct comparison — not the tighter `strict` numbers, and not a separately-loosened set.
- **AC-5**: Each of `pii.py`, `prompt_injection.py`, `toxicity.py`, `bias.py`, `secrets.py` assigns confidence per-pattern via a `_CONFIDENCE` map, not the old flat constant. Spot-checked values: `credit_card` `0.99`, `ssn`/`email` `0.95`, `phone` `0.75`, `ip_address` `0.6`, `fake_role_marker` `0.6`, `absolute_group_generalization`/`inherent_trait_claim` `0.65`.
- **AC-6**: A request or response containing only an `ip_address` match (confidence `0.6`, at or below `STRIKE_THRESHOLD`) still returns `403` (today's "any match blocks unconditionally" rule, unaffected) — but the persisted `Finding.confidence` reads back as `0.6`, `strikes.pii` does **not** increment (unlike before this milestone, where the same match would have struck), and `cumulative_risk` grows by `0.6`, not `0.95`.
- **AC-7**: A request or response containing a `credit_card`/`ssn`/`email` match still strikes and contributes to `cumulative_risk` at its (now slightly different, still `> 0.7`) confidence exactly as it would have before this milestone in every way that matters to escalation (regression for the high-confidence bucket).
- **AC-8**: Over a run of ~30-50 repeated genuinely-clean exchanges against a `fast`-profile workload, the expensive-tier background task is scheduled roughly 1 in 10 times (not exactly 10%, but clearly probabilistic and clearly not 0% or 100%) — while the same run against a `strict` or `balanced` workload schedules it every single time (unchanged from today).
- **AC-9**: `app/routers/console.py`'s `list_sessions` and `get_session_detail` both pass the session's actual resolved `workload.policy_profile` into `is_escalated`, confirmed by making a `strict`-profile session cross its tighter threshold and checking the console's `/api/console/sessions` and `/api/console/sessions/{id}` responses both report `escalated: true` — not silently defaulting to `balanced`'s looser numbers.
- **AC-10**: `is_escalated`'s `policy_profile` parameter is required (no default) — a call site that forgets to pass it fails loudly (a `TypeError` surfaced during self-check), not silently falling back to `balanced`.
- **AC-11**: Full regression: `/health` `200`, unknown-workload `400`, model-unreachable `502`, a genuinely clean end-to-end `balanced`-profile pass-through `200`, `balanced`-profile request-side and response-side PII blocks still `403` — all unaffected by this milestone.

## Options considered

### Option 1: Per-profile threshold lookup table + required `policy_profile` param on `is_escalated`; per-pattern `_CONFIDENCE` map per evaluator file; fixed-rate sampling constant in `chat.py` (recommended)

As described in Decision below.

**Pros**: No schema change, no migration. Keeps the existing clean split (`redis_client.py` owns ledger math/predicates, `chat.py` owns what to do about them) that 3.1/3.2 already established. Per-pattern confidence lives right next to each pattern's own regex, in the file that already owns that pattern's tradeoffs (matching `pii.py`'s existing `_VALIDATORS`-by-pattern-name precedent). Required (non-defaulted) profile argument makes a forgotten call site a loud, immediate `TypeError` rather than a silent, wrong "escalated: false" in the console.
**Cons**: Four call sites to update (2 in `chat.py`, 2 in `console.py`) instead of one central chokepoint — accepted, since all four already have the workload in scope and the change to each is one extra argument.

### Option 2: New `Workload` columns (`escalation_risk_threshold`, `escalation_strike_count`, `judge_sample_rate`) instead of a hardcoded profile→value table

Fully custom per-workload tuning, not just per-profile.

**Pros**: More flexible — an operator could tune one specific workload without changing its profile.
**Cons**: Reopens Fork #1's locked `Workload` field list (adding columns needs a stop-and-ask, per `forks.md`'s own rule), needs a manual `ALTER TABLE` migration, and builds tunability nobody asked for — Phase 8.6 (`Per-Workload Category Overrides`) is the already-scoped, already-designed future home for genuine per-workload tuning, via the existing `metadata` JSONB column, not new schema. Rejected on the same precedent 5.2 already set (using `metadata_["name"]` rather than a new column, specifically to avoid reopening Fork #1).

### Option 3: Differentiate confidence by category only (all `pii` patterns `0.9`, all `prompt_injection` patterns `0.85`, ...), not per individual pattern

Simpler — 6 values instead of ~25.

**Pros**: Fewer numbers to justify or maintain.
**Cons**: Throws away the exact signal this milestone exists to create — `credit_card`'s Luhn-validated near-certainty and `ip_address`'s admitted format-ambiguity are both `pii`; collapsing them to one category-wide number reintroduces the "every match looks identical" problem this milestone is fixing, just at a coarser grain. Rejected — STATUS.md's own framing ("today a single global CONFIDENCE=0.95 constant... is used by literally every cheap-tier pattern") is specifically about per-*pattern* differentiation.

## Decision

**Chosen option**: Option 1.

**1. Per-profile escalation thresholds** — `app/redis_client.py`:
```python
PROFILE_ESCALATION_THRESHOLDS: dict[PolicyProfile, tuple[float, int]] = {
    PolicyProfile.strict: (0.5, 2),
    PolicyProfile.balanced: (0.7, 3),
    PolicyProfile.fast: (0.7, 3),
}


def is_escalated(ledger: dict[str, Any], policy_profile: PolicyProfile) -> bool:
    risk_threshold, strike_count = PROFILE_ESCALATION_THRESHOLDS[policy_profile]
    if ledger["cumulative_risk"] > risk_threshold:
        return True
    return any(count >= strike_count for count in ledger["strikes"].values())
```
`ESCALATION_RISK_THRESHOLD`/`ESCALATION_STRIKE_COUNT` (the old flat constants) are removed — `PROFILE_ESCALATION_THRESHOLDS[PolicyProfile.balanced]` is their direct replacement, same values. `STRIKE_THRESHOLD = 0.7` (whether a `Finding` counts as a strike at all, per Fork #3's "confidence > 0.7") stays a single global constant — it is not profile-dependent, only the escalation trigger's own numbers vary.

Four call sites updated to pass `workload.policy_profile`:
- `chat.py`'s `_run_request_side_interception`: `is_escalated(ledger, workload.policy_profile)`.
- `chat.py`'s `_run_response_side_interception`: `is_escalated(ledger, workload.policy_profile)`.
- `console.py`'s `list_sessions`: `is_escalated({...}, workload.policy_profile if workload is not None else PolicyProfile.balanced)` — the `None` guard is defensive only (no delete endpoint exists per 5.2's own decision, so a session's workload row can never actually be missing today), not a real branch this milestone expects to hit.
- `console.py`'s `get_session_detail`: same pattern, `workload` already fetched a few lines above.

**2. Per-pattern confidence** — `app/evaluators/types.py` renames the old flat constant to a documented fallback:
```python
DEFAULT_CONFIDENCE = 0.95  # fallback only, for a pattern name missing from its file's _CONFIDENCE map
```
Each of the 5 pattern files gains a `_CONFIDENCE: dict[str, float]` next to its `_PATTERNS` dict, and `scan()` changes one line:
```python
confidence=_CONFIDENCE.get(pattern_name, DEFAULT_CONFIDENCE),
```
Full proposed table (rationale per bucket below; individual pattern-level judgment calls are logged as this spec's own "Assumed," ratified via the approval gate rather than litigated pattern-by-pattern):

| File | Pattern | Confidence | Why |
|---|---|---|---|
| `pii.py` | `credit_card` | `0.99` | Luhn-checksum validated — near-certain, highest confidence in the system. |
| `pii.py` | `ssn` | `0.95` | Rigid `\d{3}-\d{2}-\d{4}` shape, low collision rate. |
| `pii.py` | `email` | `0.95` | Standard email shape, low collision rate. |
| `pii.py` | `phone` | `0.75` | Already-documented residual false-positive risk (dot/space-grouped digit runs) accepted in 2.1 — still `> STRIKE_THRESHOLD` but visibly less certain than `ssn`/`email`. |
| `pii.py` | `ip_address` | `0.6` | Indistinguishable from a version-like string by regex alone (accepted limitation, 2.1) — below `STRIKE_THRESHOLD`, so a match still blocks this turn but no longer strikes/escalates. |
| `prompt_injection.py` | `ignore_instructions`, `disregard_above`, `dan_jailbreak`, `other_jailbreak_persona`, `new_instructions` | `0.95` | Literal, unambiguous jailbreak framing; low real-world false-positive rate. |
| `prompt_injection.py` | `reveal_system_prompt`, `roleplay_bypass`, `unfiltered_mode`, `extract_instructions` | `0.8` | Still clearly suspicious, but each has a plausible (if unusual) benign framing (e.g. a developer legitimately asking about the assistant's own guardrails). |
| `prompt_injection.py` | `fake_role_marker` | `0.6` | Explicitly documented false-positive case (a pasted transcript starting a line with "System:") — below `STRIKE_THRESHOLD`. |
| `toxicity.py` | `direct_insult`, `death_wish_or_threat`, `dehumanizing_language` | `0.95` | 2.6 already curated this file down to only unambiguous phrasings ("not a slur or profanity word list") specifically for high precision — no further per-pattern split is warranted within an already-narrow, already-high-precision set. |
| `bias.py` | `absolute_group_generalization`, `inherent_trait_claim` | `0.65` | The file's own module docstring calls these patterns "a weak proxy for bias" — a generalization-shaped sentence can be neutral or even corrective in intent, which a regex cannot distinguish. Below `STRIKE_THRESHOLD`: still blocks this turn, no longer strikes/escalates. |
| `secrets.py` | `aws_access_key`, `github_token`, `pem_private_key` | `0.95` | Highly distinctive fixed-prefix/fixed-header shapes, effectively unique to their real format. |
| `secrets.py` | `slack_token` | `0.9` | Distinctive prefix family, slightly broader character class than the above. |
| `secrets.py` | `generic_secret_token` (`sk-...`) | `0.85` | The most generic prefix of the five — a plausible (if unlikely) collision with a non-secret token-shaped string, the same class of residual risk `phone` already accepts. |

**3. `fast`-tier judge sampling** — `app/routers/chat.py`, a new constant near the existing module-level constants:
```python
FAST_TIER_JUDGE_SAMPLE_RATE = 0.10
```
In `_run_response_side_interception`, immediately before the existing `background_tasks.add_task(_run_expensive_tier_task, ...)` call:
```python
should_sample_judge = (
    workload.policy_profile != PolicyProfile.fast
    or random.random() < FAST_TIER_JUDGE_SAMPLE_RATE
)
if not medium_candidates:
    if should_sample_judge:
        background_tasks.add_task(
            _run_expensive_tier_task,
            execution_id=execution.execution_id,
            session_id=session.session_id,
            context_text=context_text,
            response_text=response_text,
            turn_anchor=ledger["turn"],
            ts_anchor=ts_anchor,
        )
    return None
```
`strict`/`balanced` always schedule (unchanged from today); `fast` schedules ~1 in 10 times. `random` (stdlib) is a new import in `chat.py`; `PolicyProfile` is already importable from `app.models`.

## Rationale

Option 2 is rejected for the same reason 5.2 already rejected a new `Workload.name` column: `forks.md` Fork #1's field list is locked, and this milestone's actual ask ("make the profile do something") doesn't require per-workload tunability — Phase 8.6 already exists, already scoped, and already chosen (via `metadata` JSONB) as the correct future home for that. Building it here would duplicate 8.6's job and touch schema for no immediate requirement.

Option 3 is rejected because it defeats the milestone's own stated purpose. STATUS.md is explicit that today's flat confidence means `STRIKE_THRESHOLD` "never actually filters anything" — a category-level bucket would still make every `pii` pattern identical to every other `pii` pattern, which is the exact problem being fixed, just moved up one level of granularity. The whole reason `credit_card` gets a Luhn check in the first place (2.1) is that it is meaningfully more trustworthy than a bare `ip_address` regex; collapsing that distinction back into one shared number throws away real, already-built signal.

Requiring `policy_profile` on `is_escalated` (rather than defaulting to `balanced`) follows this codebase's established fail-loud precedent (1.2's unknown-workload `400` instead of silent default-substitution; `console.py`'s own 7.1-era `_resolve_workload` fix, which turned a silent `None`-dereference into an explicit `503`) — a forgotten fourth call site should break obviously during self-check, not quietly under-report escalation for every non-`balanced` workload in the console forever.

## Feature design

**Data model sketch**: no Postgres schema change, no migration. `Workload.policy_profile` already exists (Phase 0); this milestone only adds code-level lookup tables and per-pattern maps.

**Changed files**:
- `app/redis_client.py`: `PROFILE_ESCALATION_THRESHOLDS` replaces `ESCALATION_RISK_THRESHOLD`/`ESCALATION_STRIKE_COUNT`; `is_escalated` signature gains a required `policy_profile: PolicyProfile` parameter. Needs `from app.models.enums import PolicyProfile` (or wherever it's re-exported from — check `app/models/__init__.py`'s existing export shape before adding the import, matching whatever pattern the file already uses for other enum imports).
- `app/routers/chat.py`: both `is_escalated(...)` calls gain `workload.policy_profile`; new `FAST_TIER_JUDGE_SAMPLE_RATE` constant; new `import random`; the background-task scheduling gains the `should_sample_judge` gate described in Decision.
- `app/routers/console.py`: both `is_escalated(...)` calls (`list_sessions`, `get_session_detail`) gain the resolved workload's `policy_profile` (with the defensive `None` fallback to `balanced` described in Decision); needs `from app.models import PolicyProfile` (or wherever already imported alongside `Workload`/`EvaluatorTier`/etc. in this file's existing import line).
- `app/evaluators/types.py`: `CONFIDENCE = 0.95` renamed to `DEFAULT_CONFIDENCE = 0.95`, docstring updated to describe it as a fallback, not the universal value.
- `app/evaluators/pii.py`, `prompt_injection.py`, `toxicity.py`, `bias.py`, `secrets.py`: each gains a `_CONFIDENCE: dict[str, float]` (values per the table above); `from app.evaluators.types import CONFIDENCE, FindingCandidate` becomes `from app.evaluators.types import DEFAULT_CONFIDENCE, FindingCandidate`; each `scan()`'s `confidence=CONFIDENCE` becomes `confidence=_CONFIDENCE.get(pattern_name, DEFAULT_CONFIDENCE)`.
- `app/evaluators/cheap.py`: `__all__`'s `"CONFIDENCE"` entry becomes `"DEFAULT_CONFIDENCE"` (matches the rename; nothing outside `app/evaluators/` imports this re-export today, confirmed by the full-tree grep done for this spec).

**Value sourcing**:
| Action | Value produced | Source |
|---|---|---|
| Request/response-side escalation pre-check | risk/strike thresholds to compare against | `PROFILE_ESCALATION_THRESHOLDS[workload.policy_profile]` — never re-derived inline anywhere else |
| A cheap-tier `Finding`'s `confidence` | the per-pattern value | `_CONFIDENCE.get(pattern_name, DEFAULT_CONFIDENCE)` in the evaluator file that owns that pattern — same value regardless of which workload/profile received the match |
| Whether a `fast`-profile clean response schedules the async judge | a boolean | `random.random() < FAST_TIER_JUDGE_SAMPLE_RATE`, evaluated fresh per request — never persisted or memoized |

**Key invariants**:
- `is_escalated` never has an implicit default profile — every call site must supply one explicitly.
- `STRIKE_THRESHOLD` (whether a match counts as a strike) and per-pattern confidence values are global constants, identical for every profile — only the escalation *trigger's* threshold numbers vary by profile. A pattern's realism doesn't depend on which workload happened to receive it.
- `balanced`'s threshold *numbers* are unchanged (`0.7`/`3`) from before this milestone; the ledger *values* a `balanced`-profile session accumulates can still change turn-to-turn versus pre-8.1 behavior, because per-pattern confidence is a cross-profile change or affects what a given match contributes — see the Context note on this reinterpretation.
- Cheap tier's "any match blocks unconditionally, regardless of confidence" rule is untouched — confidence differentiation changes ledger math only, never this turn's own block/no-block outcome.

**Security model**: unchanged from 3.2 — `X-Workload-Id`/`X-Session-Id` remain caller-asserted with no authentication (already accepted, `decisions.md`). Tighter `strict` thresholds make the existing session-id-rotation gap marginally more attractive to exploit for a `strict` workload specifically (fewer strikes needed to matter, so also fewer to dodge) — not a new gap, same standing "no auth work in scope" decision.

**Configuration required**: none new. `PROFILE_ESCALATION_THRESHOLDS` and `FAST_TIER_JUDGE_SAMPLE_RATE` are fixed code constants, not per-workload configurable fields — Phase 8.6 (`Workload.metadata.category_overrides`) remains the explicit future owner of real per-workload tuning.

**Critical test scenarios** (each maps to an acceptance criterion above):
- Manufacture a `strict`-profile workload and a session with exactly `strikes[pii] == 2` (2 rapid PII violations, mirroring 3.1's own strike-manufacturing method): confirm the next clean request `403`/`session_escalated`. Verifies **AC-1**.
- Manufacture a `strict`-profile session with `cumulative_risk` landing between `0.5` and `0.7` (a single moderate-confidence violation, e.g. a `phone` match at `0.75`, or two decayed touches): confirm escalation. Verifies **AC-2**.
- Repeat the same manufactured ledger states against a `balanced`-profile workload: confirm no escalation until the old `3`/`0.7` numbers are actually reached. Verifies **AC-3**.
- Repeat against a `fast`-profile workload: confirm identical (not-yet-escalated at 2 strikes / 0.6 risk, escalated only at the old 3/0.7 numbers) behavior to `balanced`. Verifies **AC-4**.
- Direct unit-level check (a small scratch script, deleted after use, mirroring prior phases' precedent) importing each evaluator's `_CONFIDENCE` map and confirming the listed spot-check values. Verifies **AC-5**.
- A request/response containing only an IP address: confirm `403` still returned; query the persisted `Finding.confidence == 0.6`; read the ledger before/after and confirm `strikes.pii` unchanged, `cumulative_risk` increased by exactly `0.6` (times the decay factor already applied that turn). Verifies **AC-6**.
- A request/response containing a `credit_card`/`ssn`/`email` match: confirm it still strikes and still escalates a session at the same strike-count threshold as before. Verifies **AC-7**.
- Against a `fast`-profile workload, send ~30-50 genuinely clean exchanges in a loop; count how many schedule the background task (e.g. via a temporary log line or by checking for a resulting `Finding`/ledger touch after each, since the stub judge only writes on a real finding — may need a monkeypatched `run_expensive_tier` returning a fixed non-empty result for counting purposes during this specific check only). Confirm the count is roughly 1-in-10, and confirm a matching `strict`/`balanced` run schedules every time. Verifies **AC-8**.
- Manufacture a `strict`-profile session past its tighter threshold; call `GET /api/console/sessions` and `GET /api/console/sessions/{id}` directly; confirm both report `escalated: true`. Verifies **AC-9**.
- Read the final `is_escalated` signature and confirm `policy_profile` has no default value (a direct code read, not a runtime test, since a missing-argument `TypeError` is a static property of the signature). Verifies **AC-10**.
- Full regression sweep: `/health` `200`, unknown-workload `400`, model-unreachable `502`, one genuinely clean `balanced`-profile end-to-end pass-through `200`, `balanced`-profile request-side and response-side PII blocks still `403`. Verifies **AC-11**.

## Consequences

**Positive**:
- `Workload.policy_profile` finally changes real behavior — the console's workload management view (5.2) stops being cosmetic for this field.
- Cheap-tier confidence now carries real signal-strength information, which 8.2 needs to exist before it can build a meaningful flag-vs-block split.
- `Workload.cost_budget_per_request` gets its first real (if narrow) functional use, closing part of the gap 7.1's Major #4 flagged.
- The `console.py` `is_escalated` call sites are fixed as a byproduct of this milestone — before this spec, a `strict`-profile session's console view would have kept reporting `balanced`'s looser escalation status even after 8.1 shipped, a real, easy-to-miss bug this spec's own Context section catches before it ships.

**Negative / tradeoffs**:
- A `balanced`-profile session's exact ledger trajectory can differ from pre-8.1 behavior for any turn involving a now-lower-confidence pattern (`ip_address`, `fake_role_marker`, the two `bias` patterns) — accepted and explained in Context as the correct reading of STATUS.md's "byte-identical" wording, but worth the user's explicit sign-off at the approval gate since it's a looser interpretation than the literal words.
- `fast`-tier judge sampling is a fixed 10% constant, not derived from `workload.cost_budget_per_request`'s actual numeric value — a genuine cost-to-sample-rate formula would need an assumed real per-call dollar cost, which doesn't exist for a local, zero-cost Ollama backend. Logged as a Follow-up, not built now.
- ~25 individual pattern confidence values is a real amount of judgment-call surface area in one spec; the table groups patterns by shared reasoning rather than justifying each individually, which keeps the spec reviewable but means any single value could reasonably be argued differently.

**Neutral**:
- No automated tests written, per `AGENTS.md` Section 8; manual `curl` plus direct Redis/Postgres inspection self-check only, matching every prior phase.
- No change to `Session.cumulative_risk`/`Session.strikes` Postgres sync (4.3) — this milestone changes what values flow through that pipe, not the pipe itself.
