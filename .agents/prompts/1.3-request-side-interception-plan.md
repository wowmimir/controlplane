# 1.3. Request-side interception

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec adds cheap-tier evaluation to `POST /v1/chat/completions`: every incoming prompt is scanned for PII and prompt-injection patterns, synchronously, before any model call. A match writes a `Finding` (and a new `Execution` row to satisfy its required FK), updates the session's Redis ledger per Fork #3's exact math, and returns a `403` — the caller never reaches the (still-stubbed) model path. A clean prompt falls through unchanged to 1.2's existing behavior.

## Context

`forks.md` Fork #4 locks the request-side shape: "Cheap tier only. Prompt injection heuristic, input PII scan. Runs synchronously, before the model API is even called... A request-side block counts as a strike, same `Finding` schema, same category (`prompt_injection` or `pii`), same ledger mechanics as a response-side finding." `STATUS.md`'s 1.3 line: "On violation: write `Finding`, update ledger (per Fork #3 math), return blocked response — do not call the model."

Two gaps existed before this milestone that had to be resolved, not just wired up:
- **No evaluator code exists anywhere in the repo.** Phase 2 (2.1 PII regex, 2.2 prompt-injection heuristic) is the "real" home for these evaluators, but it hasn't shipped. `forks.md`'s "Explicitly NOT Locked" list confirms exact regex patterns are fair game to decide now.
- **`Finding.execution_id` is a required, non-nullable FK** to `execution.execution_id` (`app/models/finding.py`), but nothing in the codebase creates an `Execution` row yet — that's nominally 1.4 (model forwarding)/4.2 (execution persistence) territory. A request-side block happens *before* any model call, so there is no execution to attach to unless this milestone creates one itself.

`app/redis_client.py`'s docstring is explicit that decay/strike-window/escalation math is Phase 3's job to *own*, but 1.3 still has to *apply* Fork #3's core two-line formula today, since a request-side block is required to update the ledger per `forks.md`.

## Requirements

**User stories**:
- As the operator of a workload, I want an obviously malicious or PII-leaking prompt blocked before it costs a model call, so cheap-tier governance actually saves money and reduces risk exposure.
- As the engineer building Phase 2 next, I want the cheap-tier detection logic to already be reusable functions rather than throwaway inline code, so 2.1–2.3 extend it instead of rewriting it.
- As an AI application developer integrating with ControlPlane, I want a blocked request's response body to look like a normal API error (not a bespoke shape), so my existing error-handling code degrades gracefully.

**Acceptance criteria**:
- **AC-1**: A prompt with no PII/prompt-injection pattern matches falls through unchanged to 1.2's existing `200` stub response.
- **AC-2**: A prompt containing a PII-shaped string (email, US-shaped phone, or SSN-shaped string) returns `403` with `code: "pii"`.
- **AC-3**: A prompt containing a prompt-injection phrase returns `403` with `code: "prompt_injection"`.
- **AC-4**: A prompt matching both categories returns `403` listing both categories in `message`, with `code` set to whichever category's finding has the highest confidence.
- **AC-5**: Every blocked request persists exactly one `Execution` row (`session_id`/`workload_id` from the already-resolved values, `execution_risk_score` = max confidence across that request's candidates) and one `Finding` row per matched pattern (`category`, `confidence`, `evaluator_tier=cheap`, `evidence_ref` = `{pattern, span}`).
- **AC-6**: Every blocked request updates the session's Redis ledger: `cumulative_risk = cumulative_risk * 0.7 + execution_risk_score`; `strikes[category]` increments once per finding whose `confidence > 0.7`.
- **AC-7**: A blocked response still carries the `X-Workload-Id`/`X-Session-Id` response headers 1.2 already sets.
- **AC-8**: No schema change to `Finding`, `Execution`, or `Session` — this milestone uses only existing columns.
- **AC-9**: `/health` and the AC-1 pass-through path are unaffected (no regression from 1.1/1.2).

## Options considered

### Option 1: Dedicated `app/evaluators/` package with reusable `scan()` functions (recommended, ratified with user)

New `app/evaluators/` package: `pii.py`, `prompt_injection.py` (each a `scan(text) -> list[FindingCandidate]`), `cheap.py` (orchestrator), `types.py` (shared `FindingCandidate` dataclass, to avoid a circular import between `cheap.py` and the two scanners).

**Pros**: Directly reusable by Phase 2.1/2.2 (same detectors, not a rewrite) and Phase 2.3 (explicitly requires the same cheap-tier detectors to run on output text too — a reusable `scan(text)` signature is exactly what that needs).
**Cons**: More files/structure than strictly needed for 1.3 alone.

### Option 2: Inline private helpers in `app/routers/chat.py`

**Pros**: Less code today.
**Cons**: Phase 2 would need to extract/rewrite this logic rather than extend it; 2.3's "run the same detectors on output" requirement becomes awkward if the scan logic is coupled to the request-side router.

### Option 3: `403` + OpenAI-style top-level `error` envelope (recommended, ratified with user)

`JSONResponse(403, {"error": {"message", "type": "controlplane_policy_violation", "param": null, "code": "<category>"}})`.

**Pros**: Matches the shape OpenAI-compatible client SDKs already parse (`.error.message`), reinforcing the plug-and-play claim from `AGENTS.md` Section 5. Keeps `403` (policy block) semantically distinct from the `400`s 1.2 already uses for caller misconfiguration (unknown workload, cross-workload session).
**Cons**: A second error-response convention alongside 1.2's plain `HTTPException(400, detail=str)` — acceptable since the two represent genuinely different failure classes (config error vs. policy block).

### Option 4: `400` + FastAPI's default `{"detail": ...}` shape

**Pros**: Reuses the exact `HTTPException` pattern already in `chat.py` twice; less new code.
**Cons**: Not OpenAI-shaped (`detail`, not top-level `error`); blends together with 1.2's unrelated `400`s for a caller trying to distinguish "you misconfigured this call" from "this call was blocked by policy."

## Decision

**Chosen**: Option 1 (dedicated evaluators package) and Option 3 (`403` + OpenAI-style error envelope).

## Rationale

The evaluators package choice is the simplest path that doesn't create rework: Phase 2's own task names ("2.1 Cheap: PII Regex", "2.2 Cheap: Prompt Injection Heuristic", "2.3 Cheap: Response-Side Reuse — confirm 2.1/2.2 detectors run on OUTPUT text too, not just input") describe exactly the shape this package already has. Building it inline now would mean deleting and rebuilding it in Phase 2 for no benefit.

The `403`/OpenAI-envelope choice follows the same "match the real API's conventions wherever the choice is open" discipline `forks.md` already applies to the base endpoint shape (Fork #4, `AGENTS.md` Section 5), and avoids overloading `400` with two unrelated failure meanings.

## Feature design

**Data model sketch**: no schema change (AC-8). Reuses `Execution` and `Finding` exactly as defined in 0.2.

**New files**:
- `app/evaluators/types.py` — `CONFIDENCE = 0.95` (fixed; regex matches are deterministic, and `0.95 > 0.7` satisfies Fork #3's strike-increment threshold on every cheap-tier hit) and `FindingCandidate` (`category`, `confidence`, `evidence_ref`).
- `app/evaluators/pii.py` — regex `scan()` for email / US-shaped phone / SSN-shaped strings.
- `app/evaluators/prompt_injection.py` — keyword/pattern `scan()` for common override phrases ("ignore previous instructions", "disregard the above", "reveal your (system )?prompt", "you are now DAN"/"developer mode", "new instructions:").
- `app/evaluators/cheap.py` — `run_cheap_tier(text) -> list[FindingCandidate]`, concatenating both scanners' results.

**Changed file**: `app/routers/chat.py` — after 1.2's existing workload/session resolution and response-header assignment (unchanged), a new `_run_request_side_interception(db, session, workload, request)` helper:
1. Joins `request.messages[*].content` into one text blob.
2. Runs `run_cheap_tier(text)`.
3. No candidates → returns `None`; the handler falls through to the existing stub response unchanged.
4. Candidates found → creates the `Execution` row, `flush()`es it (to get `execution_id` for the FK), creates one `Finding` per candidate, commits; reads/updates/writes the Redis ledger via `get_ledger`/`set_ledger` with the Fork #3 formula; returns the `403` `JSONResponse`. The handler attaches the same `X-Workload-Id`/`X-Session-Id` headers to it and returns it directly (satisfies AC-7) — FastAPI passes a returned `Response` subclass through unchanged, bypassing the endpoint's declared `ChatCompletionResponse` return-type serialization.

**Value sourcing**:
- `execution_risk_score` = `max(candidate.confidence for candidate in candidates)` (per Fork #2: "`execution_risk_score` = max confidence across all Findings in that execution").
- Ledger's `strikes[category]` increments once per *finding* above the 0.7 threshold, not once per execution — a request matching two different PII patterns still only increments `pii` once per matching finding (consistent with Fork #3's literal wording: "Increment a category's strike when **a Finding** in that category has confidence > 0.7").
- The response `code` field (AC-4's tie handling) picks the single highest-confidence candidate; since all cheap-tier confidences are the fixed `0.95`, ties are broken by scan order (`pii` scanned before `prompt_injection`), which is stable and acceptable for this MVP.

**Key invariants**:
- The model is never called on a blocked request — structurally guaranteed by `_run_request_side_interception` running, and its `403` returning, strictly before the (still-stub, later real) model-call code.
- `Session.cumulative_risk`/`Session.strikes` in Postgres remain unwritten by this milestone — only the live Redis ledger is updated, matching `app/models/session.py`'s own comment that Postgres is the durable/audit copy (Phase 4) and Redis is the live one (0.3). Logged as an explicit decision below rather than silently deferred.
- An `Execution` row is created **only** on the blocked path in this milestone, not on every request — there is no real execution to log on a pass-through yet, since 1.4 (model forwarding) doesn't exist. Phase 4.2 ("every `Execution` logged... regardless of whether it was blocked") is the explicit owner of unconditional execution logging once there's a real model call to attach it to.
- No escalation-threshold check (`cumulative_risk > 0.7 OR strikes >= 3`, Fork #3) gates the block decision here — a request-side cheap-tier match blocks unconditionally, independent of ledger state, per Fork #4's "input and output are NOT treated differently" combined with the fact cheap-tier regex has no "inconclusive" state. The ledger is still updated so *future* turns see the accumulated risk. Escalation-check logic (Phase 3.2) and strike-window expiry (Phase 3.1) remain unbuilt, as does `fail_open`/`fail_closed` handling around ControlPlane's own internal errors (Phase 3.3) — this milestone does not add try/except-driven fail-mode branching.

**Security model**: unchanged from 1.1/1.2. The `403` body reveals only the triggering category, never the matched text or the workload's configuration.

**Configuration required**: none beyond what 0.2/0.3 already require.

**Critical test scenarios** (one per branch):
- Clean prompt → `200`, unchanged stub body. Verifies **AC-1**, **AC-9**.
- Prompt with an email address → `403`, `code: "pii"`, one `Execution` + one `Finding` (`category=pii`, `evaluator_tier=cheap`) in Postgres, Redis ledger `cumulative_risk > 0`, `strikes.pii == 1`. Verifies **AC-2**, **AC-5**, **AC-6**.
- Prompt with an injection phrase → `403`, `code: "prompt_injection"`, same persistence/ledger shape under `prompt_injection`. Verifies **AC-3**, **AC-5**, **AC-6**.
- Prompt with both → `403`, message lists both categories, both `Finding` rows written, both strikes incremented. Verifies **AC-4**, **AC-5**, **AC-6**.
- Every blocked response still carries `X-Workload-Id`/`X-Session-Id`. Verifies **AC-7**.

## Build plan

1. Create `app/evaluators/types.py` (`FindingCandidate`, `CONFIDENCE`), `app/evaluators/pii.py`, `app/evaluators/prompt_injection.py`, `app/evaluators/cheap.py`. Satisfies the detection half of **AC-1** through **AC-4**.
2. Update `app/routers/chat.py`: import the new evaluator/model/Redis pieces, add `_run_request_side_interception`, call it between session resolution and the stub response, short-circuit on a non-`None` result. Satisfies **AC-5** through **AC-8**.
3. Self-check: run the five scenarios from Critical test scenarios above via `curl` against a running `uvicorn` instance backed by the real Neon database and the real (shared, `controlplane:`-prefixed) Upstash Redis instance, inspecting both the HTTP response and the resulting Postgres/Redis state for each. Confirm `/health` unaffected, satisfies **AC-9**.
4. Log the ratified/assumed decisions below to `decisions.md`.
5. Update `STATUS.md`: check off 1.3, append a Session Handoff Notes entry, set Next Action to 1.4 Model Forwarding.

## Consequences

**Positive**:
- Phase 2.1/2.2 can extend `app/evaluators/pii.py`/`prompt_injection.py` (better patterns, more categories) without touching the router; 2.3 can call the exact same `run_cheap_tier` on response text.
- The core demo path ("block on cheap-tier PII", per `STATUS.md`'s Notes for the Agent) is now real and end-to-end, not stubbed.

**Negative / tradeoffs**:
- Fixed `0.95` confidence and a small hand-picked pattern set are intentionally minimal — false negatives on unlisted injection phrasings or PII shapes are expected and acceptable for an MVP; Phase 2 is the place to improve recall.
- Creating `Execution` rows only on the blocked path (not on every request) means Postgres's `Execution` table is not yet a complete operational log — Phase 4.2 will need to backfill that once 1.4 adds real model calls to attach unconditional `Execution` rows to.
- No strike-window expiry yet means a category's strike count in Redis only ever grows within the 15-minute session TTL — Phase 3.1 must add expiry before the 3-strike escalation trigger (Phase 3.2) is safe to wire up for real multi-turn sessions.

**Neutral**:
- No automated tests written for this milestone, per `AGENTS.md` Section 8; manual `curl`-plus-database/Redis-inspection self-check only, matching every prior phase.
