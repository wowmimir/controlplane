# 3.4. Response Release

**Date**: 2026-08-24
**Status**: Accepted

## Summary

This milestone required no new code. `STATUS.md` describes 3.4 as: *"If not escalated: release response to caller. If escalated: return appropriate blocked/intervened response (status code + body shape — decide and log to `decisions.md`)."* That wording predates Phase 3.2 (Escalation Check). By the time 3.4 was reached, 3.2 had already built exactly this: `chat_completions`'s single `return parsed` release line is reachable only when neither interception function blocks, and `_escalation_block_response()` already has a fully decided status/body shape (`403`, `type: "controlplane_session_escalated"`, `code: "session_escalated"`), called from both the request side and the response side. This spec exists to document that already-verified fact as a deliberate record, the same role `.agents/prompts/2.3-cheap-response-side-reuse-plan.md` played for response-side evaluator reuse (there, 1.5 satisfied 2.3 by construction; here, 3.2 satisfies 3.4 by construction).

## Context

`forks.md` Fork #3's escalation trigger (`cumulative_risk > 0.7 OR any strikes[category] >= 3`) and Fork #4's blocking behavior ("input and output are NOT treated differently") together define exactly what "release if not escalated, block if escalated" means. 3.2 built both halves of that in one milestone: `is_escalated(ledger)` (the pure predicate in `app/redis_client.py`) and `_escalation_block_response()` (the decided `403` envelope in `app/routers/chat.py`), wired into two call sites — the request-side pre-check (before this turn's content is even scanned) and the response-side clean-cheap-tier branch (before medium/expensive tier runs). `STATUS.md`'s own 3.2 handoff note already frames this as closing "the actual gap left after 3.1: the ledger's accumulated state was written correctly on every turn but never consulted to gate anything."

Verified directly against the current code (post the just-shipped 3.3 fail_mode change) for this spec, not just the notes above:

- `chat_completions` (`app/routers/chat.py`) has exactly one line that releases a real response to the caller: `return parsed` at line 117. It is reached only after both `if blocked is not None: return blocked` guards (lines 79-82, request side; 112-115, response side) have passed with `blocked is None`. There is no other exit path that releases a response.
- `_escalation_block_response()` (lines 238-261) is the single, already-decided block shape: `403` / `controlplane_session_escalated` / `session_escalated` / a fixed caller-facing message. It is called from `_run_request_side_interception`'s opening escalation peek (around line 290) and from `_run_response_side_interception`'s clean-cheap-tier branch (around line 388), immediately after that branch's ledger touch.
- Every route to line 117 necessarily passed through both of those checks — `_run_request_side_interception` cannot return `None` without first confirming `is_escalated(ledger)` was false on its opening peek, and `_run_response_side_interception`'s clean branch cannot fall through to scheduling the expensive-tier task (its own only path to returning `None`) without first confirming `is_escalated` was false on the ledger `apply_ledger_update` just returned. There is no bypass.
- 3.1's "exactly one ledger touch per concluded request" invariant is what keeps that escalation state current at each check — a stale or double-counted ledger would be the only way this guarantee could break, and 3.1's own self-check already proved the touch count is exactly one per request.
- 3.3's `fail_mode` wrapping (`.agents/prompts/3.3-fail-open-fail-closed-handling-plan.md`) does not add a second, distinct release path: under `fail_open`, a caught internal exception sets `blocked = None`, which is the *same* fall-through mechanism this spec documents, not a new one. Under `fail_closed`, it returns `_internal_error_response()` (`503`), a third, already-distinct envelope from `_policy_block_response` (`403`, content violation) and `_escalation_block_response` (`403`, session escalation) — already logged under 3.3, not a 3.4 concern.
- No comment, TODO, or Follow-up anywhere in `chat.py`, `STATUS.md`, or `forks.md` flags the release path itself, or its response headers, as incomplete.

`forks.md`'s "explicitly not locked" list leaves exact status codes/body shapes free to decide during the build, but by the time 3.4 was reached, that decision had already been made and shipped under 3.2's own name — there was no second viable shape left open to choose between.

## Requirements

**Verification criteria** (already met; this documents that they are met, not a build to perform):

- **AC-1**: `chat_completions` releases the real model response to the caller if and only if neither `_run_request_side_interception` nor `_run_response_side_interception` produced a block. Met — confirmed by direct code read (line 117, reachable only past both `if blocked is not None` guards).
- **AC-2**: An escalated session is blocked with a decided, consistent status/body shape (`403` / `controlplane_session_escalated` / `session_escalated`) rather than released, on both the request side and the response side. Met — `_escalation_block_response()`, built in 3.2, called from both sites.
- **AC-3**: No code path releases a response to the caller without the session's escalation state having been consulted for that request. Met — confirmed by tracing every route to line 117 through both escalation checks.
- **AC-4**: `fail_mode` handling (3.3) does not introduce a second, distinct release path — an internal failure under `fail_open` reuses the exact same `blocked = None` fall-through this spec documents, not a separate mechanism. Met.
- **AC-5**: Both the release path and the escalation-block path attach `X-Workload-Id`/`X-Session-Id` response headers consistently, per 1.2's decision to always surface the resolved workload/session to the caller. Met — confirmed at lines 69-70 (release) and 80-81/113-114 (block).

## Decision

**Chosen option**: No new option was chosen here. This spec records the release/block behavior already locked by Fork #3/#4 and already implemented by 3.1 through 3.3. There is nothing to decide.

## Rationale

3.2's escalation check and `_escalation_block_response` were built specifically to satisfy Fork #3's exact trigger condition and Fork #4's "block" behavior, gating both the request-side and response-side paths to the model response — which is precisely what "release if not escalated, block with a decided shape if escalated" means. A separate, dedicated "response release" implementation was never a live option to compare against once 3.2 shipped; building one now would duplicate existing, already-correct control flow for no reason, against `AGENTS.md`'s guidance not to add abstractions beyond what the task requires.

## Consequences

**Positive**:
- Phase 3 (Session Ledger & Control) closes with zero new code in `chat.py` for this milestone, and zero new risk introduced.

**Negative / tradeoffs**:
- None new. The only standing limitation in this area — Fork #3's "block/regenerate/route" implemented as block only — is already logged under 3.2's `decisions.md` entry, not repeated here as if it were a fresh finding.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-checks already performed and logged under 3.1, 3.2, and 3.3 — in particular 3.2's live proof that a genuine violation followed immediately by a clean request on the same session returns `403`/`session_escalated`, and every prior phase's routine confirmation that a clean request returns `200` with the real model response.

## Follow-up

- None new. The real next work is already tracked in `STATUS.md`: Phase 4 (Audit Trail) — 4.1 Finding Persistence and 4.2 Execution Persistence.
