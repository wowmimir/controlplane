# 2.5. Expensive: LLM-as-Judge

**Date**: 2026-08-24
**Status**: Accepted

## Summary

Implements the expensive tier as a fire-and-forget async evaluator. `app/evaluators/expensive.py` gets a new `run_expensive_tier(context_text, response_text) -> list[FindingCandidate]` that calls the configured model with a judge prompt and parses a strict-JSON verdict on whether the response contains a hallucination. `app/routers/chat.py` schedules it via FastAPI `BackgroundTasks` at the exact point where cheap-tier and medium-tier are both already clean — the existing `if not candidates: execution.execution_risk_score = 0.0; await db.commit(); return None` branch in `_run_response_side_interception`. This is the real trigger for "medium tier inconclusive": 2.4's stub always reaches this branch whenever cheap tier passed, since it never produces a finding of its own. The task runs after the response is already released to the caller, opens its own DB session (`app.db.async_session()`, independent of the request-scoped one that will already be closed), and on a real finding: updates the `Execution` row's `execution_risk_score`, writes a `Finding` (`evaluator_tier=expensive`), and updates the Redis ledger with the same Fork #3 decay/strike math 1.3/1.5 already use. A clean verdict touches nothing — same "clean = no ledger write" precedent 1.3/1.5 already set. No new HTTP status, no blocking of anything: Fork #4 caps the expensive tier's post-release power at updating the ledger and writing the audit trail.

Two decisions beyond what `forks.md`/`decisions.md` already lock were ratified with the user before this spec was written:
1. **Async-only.** No sync "fits within the workload's latency budget" path is built. No elapsed-time tracking exists anywhere in the app today, and a real local LLM judge call (2-5s, per 1.4/1.5's own self-check latencies) will always exceed a ~1000ms governance budget in practice — a sync branch would be unreachable dead code.
2. **Reuse the existing configured model.** No new `JUDGE_MODEL` env var. The judge calls the same `MODEL_API_BASE_URL`/default model via the existing `call_model()`.

## Context

`STATUS.md` names 2.5 as "Async evaluator, invoked when medium tier is inconclusive AND would exceed `latency_budget_ms` if run sync. Runs via `BackgroundTasks` after response release." `forks.md` Fork #4 restricts the expensive tier to exactly three post-release powers when it can't fit inside the budget: "(a) update the session ledger for future turns, (b) write to the audit trail, (c) trigger a post-hoc review/escalation action" — it "cannot block or retroactively unsend the current response." Fork #2 fixes `execution_risk_score` as the max confidence across all `Finding`s in an execution. Fork #3 fixes the exact ledger math (`cumulative_risk = cumulative_risk*0.7 + execution_risk_score`, strike increment when `confidence > 0.7`). `decisions.md`'s 2026-08-23 entry for 2.4 explicitly deferred real hallucination detection to this milestone: "Phase 2.4 is stubbed; real hallucination detection deferred to 2.5 (LLM-as-judge)."

Confirmed against the current code (read in full, not guessed):
- `app/evaluators/medium.py`: `run_medium_tier(context_text, response_text, budget_remaining_ms) -> list[FindingCandidate]`, always `return []`, `_SIMILARITY_THRESHOLD = 0.3` present but unused, with a `# TODO: Phase 2.5 (LLM-as-judge) implements real semantic judgment.` marker directly above the `return []`.
- `app/evaluators/types.py`: `FindingCandidate(category: FindingCategory, confidence: float, evidence_ref: dict | None = None)` — no `evaluator_tier` field on the candidate itself; the caller stamps tier when writing `Finding` rows.
- `app/evaluators/cheap.py`: `run_cheap_tier(text) -> list[FindingCandidate]` is a pure, synchronous function with no DB/Redis access — all persistence lives in `chat.py`. `run_expensive_tier` follows the same purity convention (async because it calls the model, but no DB/Redis access of its own).
- `app/model_client.py`: `async def call_model(request: ChatCompletionRequest) -> tuple[ChatCompletionResponse, int]` is generic, not chat-specific — reusable for a judge call by constructing a synthetic `ChatCompletionRequest`. Raises `ModelCallError` subclasses (`ModelUnreachableError`, `ModelAPIError`, `ModelResponseInvalidError`) on any failure, never returns a partial result. Reads `MODEL_API_BASE_URL`/`MODEL_API_KEY` from the environment, already optional/defaulted.
- `app/routers/chat.py`: no `BackgroundTasks` import anywhere in the app today. `_run_response_side_interception(db, session, execution, parsed, workload, request)`:
  ```python
  candidates = run_cheap_tier(response_text)
  if not candidates:
      context_text = "\n".join(message.content for message in request.messages)
      budget_remaining_ms = workload.latency_budget_ms
      candidates = run_medium_tier(context_text, response_text, budget_remaining_ms)
  if not candidates:
      execution.execution_risk_score = 0.0
      await db.commit()
      return None
  ```
  This second `if not candidates:` block — reached whenever cheap tier found nothing (medium tier, being a permanent stub, never adds anything) — is the hook point for 2.5. `budget_remaining_ms` is just `workload.latency_budget_ms` verbatim; no real elapsed-time subtraction exists anywhere.
- `app/db.py`: `async_session = async_sessionmaker(engine, expire_on_commit=False)` is a module-level factory usable directly (`async with async_session() as db:`), independent of the request-scoped `get_db` dependency. This is what the background task needs, since the request's own `AsyncSession` will already be closed/torn down by the time a `BackgroundTasks` callback runs (Starlette runs them after the response has been transmitted).
- `app/models/enums.py`: `EvaluatorTier.expensive` and `FindingCategory.hallucination` already exist (added in 0.2) — no schema change is needed.
- Noted but explicitly **not** touched by this spec: `_run_response_side_interception`'s synchronous candidate-writing block hardcodes `evaluator_tier=EvaluatorTier.cheap` even when the candidates came from `run_medium_tier`. This is a latent, harmless bug today since `medium.py` always returns `[]` (nothing ever reaches that branch mislabeled). 2.5's `Finding` rows are written through a new, separate code path (the background task), not through that block, so this pre-existing gap is neither fixed nor made worse here — left as a Follow-up.

## Requirements

**User stories**:
- As the operator, I want a hallucinated response's risk to land in the session's ledger even though the offending response already went out, so a later turn in that session inherits the accumulated risk and can eventually be escalated (Phase 3.2).
- As the engineer, I want every judge verdict to be traceable — a model failure or a malformed judge response should degrade to "no finding," never a crash, and never a silent partial database write.
- As the hackathon demo (Phase 6.1's "async expensive-tier finding" scenario), I want a real, working judge finding to show, not a stub.

**Acceptance criteria**:
- **AC-1**: `app/evaluators/expensive.py` exposes `async def run_expensive_tier(context_text: str, response_text: str) -> list[FindingCandidate]`. It builds a judge prompt asking the model whether `response_text` contains a claim not supported by, or contradicted by, `context_text`, and instructing it to answer in strict JSON: `{"hallucination": bool, "confidence": float, "reasoning": str}`. It calls `call_model()` with a synthetic `ChatCompletionRequest` targeting the existing configured model (no new env var — satisfies the "reuse existing model" decision). It parses the response defensively (`.get()`-based, mirroring `model_client.py`'s own field-by-field pattern, never a blind `json.loads(...)[...]` chain that can raise `KeyError`/`TypeError`). A parse failure, a missing `hallucination` key, or `hallucination: false` all return `[]`. `hallucination: true` returns `[FindingCandidate(category=FindingCategory.hallucination, confidence=<the parsed float, clamped to [0.0, 1.0]>, evidence_ref={"reasoning": <parsed string or None>, "judge_model": <model name used>})]`.
- **AC-2**: Any `ModelCallError` (or subclass) raised by `call_model()` inside `run_expensive_tier` is caught, logged via `logger.error(...)`, and treated as `[]` — the judge function itself never raises.
- **AC-3**: `chat_completions` gains a `background_tasks: BackgroundTasks` parameter (FastAPI-injected, per its standard dependency mechanism — no manual wiring needed). It is threaded into `_run_response_side_interception`'s signature and call site.
- **AC-4**: At the existing cheap+medium-clean branch in `_run_response_side_interception` (`execution.execution_risk_score = 0.0; await db.commit()`), immediately before `return None`, schedule:
  ```python
  background_tasks.add_task(
      _run_expensive_tier_task,
      execution_id=execution.execution_id,
      session_id=session.session_id,
      context_text=context_text,
      response_text=response_text,
  )
  ```
  This is the sole trigger condition for 2.5 — matching `STATUS.md`'s "invoked when medium tier is inconclusive" wording, since 2.4's stub currently reaches this exact branch whenever cheap tier is clean.
- **AC-5**: A new module-level `async def _run_expensive_tier_task(execution_id, session_id, context_text, response_text)` in `app/routers/chat.py`:
  - Opens its own DB session via `async with async_session() as db:` (imported from `app.db`) — **not** `Depends(get_db)`, which is request-scoped and will already be closed.
  - Calls `candidates = await run_expensive_tier(context_text, response_text)`.
  - If `candidates` is empty: does nothing further — no DB write, no Redis write, matching the existing "a clean response does not touch the ledger at all" precedent from 1.3/1.5.
  - If `candidates` is non-empty: re-fetches the `Execution` row by `execution_id`, sets `execution.execution_risk_score = max(c.confidence for c in candidates)` (Fork #2 math — safe to take the max of only these candidates, since cheap and medium tier both contributed zero findings on this path by construction), writes one `Finding` row per candidate with `evaluator_tier=EvaluatorTier.expensive` and `evidence_ref={"side": "response", **(candidate.evidence_ref or {})}` (matching the existing `{"side": ...}` provenance-tagging convention from the phase1 review fix), commits, then updates the Redis ledger using the exact same decay/strike code shape `_run_request_side_interception`/`_run_response_side_interception` already use (`get_ledger` → `cumulative_risk = cumulative_risk * LEDGER_DECAY_FACTOR + execution_risk_score` → increment `strikes[category]` for each candidate with `confidence > STRIKE_THRESHOLD` → `set_ledger`).
- **AC-6**: The entire body of `_run_expensive_tier_task` is wrapped in a single `try/except Exception`, logged via `logger.error(...)`, and swallowed — a background task exception must never propagate or crash the app, and there is no caller left to report an error to since the response was already returned.
- **AC-7**: No new HTTP status code and no response body is ever produced by this path — it is architecturally incapable of blocking or altering a response that has already been sent, per Fork #4's explicit power limits.
- **AC-8**: No sync path is built. `run_expensive_tier` is only ever invoked via `background_tasks.add_task(...)`, never awaited inline in the request-handling path.
- **AC-9**: No new environment variable is introduced. The judge reuses the existing `MODEL_API_BASE_URL`/`MODEL_API_KEY`/default model configuration exactly as `call_model()` already resolves it.
- **AC-10**: Full regression is unaffected: 1.3/1.5's cheap-tier blocks (request-side and response-side), 2.1/2.2's PII/injection patterns, 1.2's `400` unknown-workload path, 1.4's `502` model-unreachable path, and `/health` all behave exactly as before. A cheap+medium-clean response still returns `200` to the caller immediately — the judge's 2-5s latency is invisible to the caller, since it runs strictly after the response is sent.
- **AC-11**: Self-check proves the async path actually fires end-to-end: an engineered prompt/response pair containing a real claim unsupported by the conversation context produces (a) an immediate `200` to the caller, and (b) shortly afterward, a `Finding` row with `evaluator_tier=expensive`/`category=hallucination`, plus a Redis ledger read-back reflecting the updated `cumulative_risk`/strike for that session.

## Options considered

### Option 1: Async-only via FastAPI `BackgroundTasks`

The judge always runs after the response is released, scheduled via FastAPI's built-in `BackgroundTasks` mechanism (which Starlette guarantees runs only after the response has been transmitted — exactly the "cannot unsend the response" semantics Fork #4 requires).

**Pros**: Matches `STATUS.md`'s literal task wording exactly. Requires no new infrastructure — `BackgroundTasks` is already part of FastAPI, no `Celery` needed (`forks.md` locks that). Needs no elapsed-time tracking, since there is no sync branch to decide against.
**Cons**: Never exercises Fork #4's "run synchronously if it fits the budget" language for the expensive tier.

### Option 2: Sync-or-async dual path with real elapsed-time budget tracking

Track actual elapsed time within the request handler; if the expensive tier's call would plausibly finish within `workload.latency_budget_ms` minus time already spent, run it synchronously and let it participate in the existing 403-block logic; otherwise, fall back to `BackgroundTasks`.

**Pros**: Matches Fork #4's fuller language ("run medium/expensive tier synchronously... within budget... expensive tier that WOULD exceed budget must run async") most literally.
**Cons**: Requires inventing a new "time remaining in this request" mechanism that does not exist anywhere in the app today (`app/main.py`'s lifespan does nothing timing-related; `budget_remaining_ms` today is just the raw workload config value, not a computed remainder). A real local LLM call measured at 2.5-4.2 seconds in 1.4/1.5's own self-checks will always exceed a `latency_budget_ms` default of `1000`, so the sync branch would be built but never actually taken in practice — speculative code with no reachable, testable path. Rejected; ratified with the user.

### Option 3: Route the async work through a task queue (Celery)

**Pros**: More production-grade job scheduling, retries, observability.
**Cons**: `forks.md`'s Tech Stack table explicitly locks "Async tasks (expensive-tier): FastAPI `BackgroundTasks` (no Celery for MVP)." Rejected — this option isn't actually open.

## Decision

**Chosen option**: Option 1 — async-only via FastAPI `BackgroundTasks`.

## Rationale

Option 3 isn't a real choice; `forks.md` already locks it out. Between Options 1 and 2, the deciding factor is that Option 2's sync branch would be dead code in this app as it stands today: nothing tracks elapsed request time, and a real local model call is an order of magnitude slower than the workload's governance budget. Building the "time remaining" infrastructure now, only to serve a branch that can never actually execute against present latencies, is speculative work with no way to verify it — directly against `AGENTS.md`'s hackathon-speed instructions and the "don't design for hypothetical future requirements" default. Option 1 delivers exactly what `STATUS.md` asks for, reuses infrastructure the framework already provides, and keeps the expensive tier's real job (judging content, not scheduling) as the only new logic being written.

## Feature design

**Data model sketch**: no schema change. `EvaluatorTier.expensive` and `FindingCategory.hallucination` already exist from 0.2, previously unused; this milestone is the first to actually produce rows with `evaluator_tier=expensive`.

**New file**: `app/evaluators/expensive.py`

```python
"""Expensive tier: LLM-as-judge hallucination detection.

Runs only via BackgroundTasks, after the response has already been
released — it can update the ledger and audit trail but can never
block or alter the response that triggered it (Fork #4).
"""

import json
import logging

from app.evaluators.types import FindingCandidate
from app.model_client import ModelCallError, call_model
from app.models.enums import FindingCategory
from app.schemas.chat import ChatCompletionRequest, ChatMessage

logger = logging.getLogger(__name__)

_JUDGE_MODEL = "minimax-m3:cloud"  # same default model 1.4 already targets

_JUDGE_SYSTEM_PROMPT = (
    "You are a strict fact-checking judge. Given a CONTEXT (the user's "
    "conversation) and a RESPONSE (an AI model's reply to it), decide whether "
    "the RESPONSE asserts any claim that is not supported by, or is "
    "contradicted by, the CONTEXT. Reply with ONLY a JSON object, no other "
    'text, in exactly this shape: {"hallucination": <true|false>, '
    '"confidence": <0.0-1.0>, "reasoning": "<one sentence>"}.'
)


async def run_expensive_tier(
    context_text: str, response_text: str
) -> list[FindingCandidate]:
    judge_request = ChatCompletionRequest(
        model=_JUDGE_MODEL,
        messages=[
            ChatMessage(role="system", content=_JUDGE_SYSTEM_PROMPT),
            ChatMessage(
                role="user",
                content=f"CONTEXT:\n{context_text}\n\nRESPONSE:\n{response_text}",
            ),
        ],
    )
    try:
        judge_response, _latency_ms = await call_model(judge_request)
    except ModelCallError as exc:
        logger.error("expensive-tier judge call failed: %s", exc)
        return []

    raw = judge_response.choices[0].message.content
    try:
        verdict = json.loads(raw)
    except (json.JSONDecodeError, TypeError):
        logger.error("expensive-tier judge returned unparseable output: %r", raw)
        return []

    if not verdict.get("hallucination"):
        return []

    confidence = verdict.get("confidence", 0.0)
    try:
        confidence = max(0.0, min(1.0, float(confidence)))
    except (TypeError, ValueError):
        confidence = 0.0

    return [
        FindingCandidate(
            category=FindingCategory.hallucination,
            confidence=confidence,
            evidence_ref={
                "reasoning": verdict.get("reasoning"),
                "judge_model": _JUDGE_MODEL,
            },
        )
    ]
```

(Exact prompt wording, field names, and clamping logic may be refined during implementation; the shape — sync-free, defensive parsing, `ModelCallError` caught, empty-list-on-any-doubt — is what's locked by AC-1/AC-2.)

**Changed file**: `app/routers/chat.py`

- New imports: `from fastapi import BackgroundTasks` (added to the existing `fastapi` import line), `from app.db import async_session`, `from app.evaluators.expensive import run_expensive_tier`.
- `chat_completions(..., background_tasks: BackgroundTasks)` — new parameter, FastAPI-injected.
- `_run_response_side_interception(db, session, execution, parsed, workload, request, background_tasks)` — one new parameter, threaded from the call site.
- Inside `_run_response_side_interception`, at the existing cheap+medium-clean branch, add the `background_tasks.add_task(...)` call from AC-4 immediately before `return None`.
- New module-level function `_run_expensive_tier_task(execution_id, session_id, context_text, response_text)` per AC-5/AC-6, placed near `_run_request_side_interception`/`_run_response_side_interception` (it belongs to the same "interception helpers" family, just triggered later).

**No changes**: `app/evaluators/medium.py` (stays exactly the permanent stub 2.4 built — not revisited), `app/evaluators/cheap.py`, `app/evaluators/pii.py`, `app/evaluators/prompt_injection.py`, `app/models/*`, `app/redis_client.py` (its existing `get_ledger`/`set_ledger` are reused as-is), `app/model_client.py` (its existing `call_model()` is reused as-is, unmodified).

**Value sourcing**: `context_text` and `response_text` are both already computed by the existing code at the call site (the same `context_text` built for the `run_medium_tier` call, and `parsed.choices[0].message.content` respectively) — no new inputs need to be sourced. `execution_id`/`session_id` are read off the already-resolved `execution`/`session` ORM objects before the background task is scheduled (passed as plain UUIDs, not ORM objects, since ORM objects are bound to the request-scoped session that will close).

**Key invariants**:
- No DB or Redis write occurs when the judge returns `[]`.
- `_run_expensive_tier_task` never raises past its own boundary.
- `execution_risk_score` is only overwritten (from its already-committed `0.0`) if the judge found something.
- Nothing in this code path can block, delay, or alter the response already sent to the caller.

**Security model**: unchanged from 1.4 — the judge call reuses the same unauthenticated `model_client` path; no new external exposure is introduced.

**Configuration required**: none new. Reuses `MODEL_API_BASE_URL`/`MODEL_API_KEY` exactly as already read by `app/model_client.py`.

**Critical test scenarios** (each maps to an acceptance criterion above):
- A prompt/response exchange engineered so the response contains a fact not present in (or contradicted by) the conversation context → caller gets `200` immediately; a `Finding` (`evaluator_tier=expensive`, `category=hallucination`) and a Redis ledger update appear shortly after. Verifies **AC-4**, **AC-5**, **AC-11**.
- A clean exchange with no fabricated claim → no delayed `Finding`, no ledger change, confirming the empty-candidate path does nothing. Verifies **AC-5**.
- Simulate a judge failure (e.g., temporarily point `MODEL_API_BASE_URL` at an unreachable port for just the background task's call, or feed a response that makes the judge return malformed output) → no crash, no partial `Execution`/`Finding` write, an error is logged. Verifies **AC-2**, **AC-6**.
- Full 1.1-2.4 regression (both cheap-tier block paths, `400` unknown-workload, `502` model-unreachable, `/health`) re-run clean, and a cheap+medium-clean request's *visible* latency is unaffected by the judge running afterward. Verifies **AC-10**.

## Consequences

**Positive**:
- Closes real detection for the `hallucination` category — the last of the three evaluator tiers (cheap/medium/expensive) is now genuinely functional, completing Fork #4's full architecture.
- Satisfies Phase 6.1's demo requirement for "an async expensive-tier finding" with real, working behavior rather than a stub.
- No new infrastructure or dependency: reuses `BackgroundTasks`, `call_model()`, `async_session`, and the existing ledger helpers as-is.

**Negative / tradeoffs**:
- Judge latency (2-5s locally) means the flagged response itself can never be blocked — only a later turn's ledger state is affected. This is Fork #4's explicit design, not a gap introduced here.
- Judge reliability depends on the local model actually following the requested JSON format; there is no tool-calling or structured-output enforcement, kept simple deliberately for a hackathon build. If this proves flaky in practice (the model wrapping JSON in prose, adding markdown fences, etc.), the parsing in `run_expensive_tier` may need to grow more tolerant (e.g., extracting the first `{...}` substring) — flagged as a Follow-up rather than over-built now.
- No true elapsed-budget tracking exists, so this path is unconditionally async regardless of the workload's actual configured budget — a deliberate, ratified simplification, not an oversight.

**Neutral**:
- No automated test suite, per `AGENTS.md` §8; verification is the live self-check described in the Build plan.
