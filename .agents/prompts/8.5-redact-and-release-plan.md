# 8.5. Redact and Release ("Edit" Tier)

**Date**: 2026-08-27
**Status**: Accepted

## Summary

The Round 2 rubric's Decision Logic area names four response actions: allow,
edit, flag for review, block. 8.2 built three of them (`clean`, `flagged`,
`blocked`). 8.5 adds the fourth, "edit", as a new `Execution.disposition`
value `redacted`. On a `balanced`-profile workload, when the cheap-tier
scanner finds `pii` or `custom_policy` (a leaked secret) in the model's
*response*, ControlPlane now blanks just the matched span to
`[REDACTED:<category>]` and releases the edited answer as `200`, instead of
the hard `403` balanced returns today. `strict` still hard-blocks these;
`fast` still flags and releases them unredacted. So the three profiles now
differ in what they *do*, not only in how sensitive their thresholds are.

8.5 also stores a `masked_excerpt` inside every cheap-tier finding's
`evidence_ref` (a JSON field, no schema change): the matched span blanked,
plus about 40 characters of surrounding text each side. Session Drilldown
can then show *what* tripped a rule, without ControlPlane ever saving the
raw sensitive string.

This deliberately changes the seeded default workload's behavior for
response-side PII (`balanced` is normally the regression guardrail). That is
the point of the milestone, not a regression.

## Context

The rubric's Solutioning Areas list four decision-logic tiers explicitly:
allow / edit / flag for review / block. Phases 8.1 and 8.2 built profile
based thresholds and three of the four tiers. "Edit" (redact the offending
span and still return an answer) is the one tier with no implementation, and
it is the tier that best fits a real compliance story: a support agent asking
"what's the account contact on file" should get a useful answer with the
email blanked, not a blanket refusal.

Two smaller gaps sit alongside it. First, `Finding.evidence_ref` currently
records only `{"side", "pattern", "span"}` for a cheap-tier hit, and the
console never renders `pattern` or `span` at all, so Session Drilldown can
say "a `pii` rule fired on this turn" but never show the operator the text
that triggered it. The audit-trail pitch in the business proposal leans on
"you can see exactly why a decision was made"; right now you cannot see the
trigger. Second, ControlPlane must not fix this by persisting the raw
sensitive match, which would turn the audit store into a new copy of the
data it is meant to protect.

Compliance framing: this milestone touches `pii` and secret material
(`custom_policy`) in transit. The masked-excerpt design is bound by "no raw
sensitive text is ever written to Postgres". That is a hard invariant, not a
preference.

   (`200`). This is accepted to change the seeded default workload's

2. Mixed findings on `balanced`: if a single response produces any
   non-redactable finding (`toxicity` / `bias` / `prompt_injection`)
   alongside a redactable one, the whole response is hard blocked (`403`),
   unchanged from today. Redaction fires only when every cheap-tier
   candidate on that response is `pii` or `custom_policy`.
3. `masked_excerpt` is written on every cheap-tier finding that has a span,
   both request side and response side, all five categories (user left the
   scope call to the author). The redactor helper is built for the redact
   path anyway, and a uniform excerpt is the stronger audit story.

## Requirements

**User stories**
- As a compliance officer, I want a model answer that happens to contain a
  customer email to come back with just the email blanked, not blocked
  outright, so my support team still gets a usable answer while the PII
  never leaves ControlPlane.
- As a security reviewer, I want the three policy profiles to take visibly
  different *actions* on the same violation (block, redact, flag), so "one
  size does not fit all" is demonstrated, not asserted.
- As an auditor reading Session Drilldown, I want to see the snippet of text
  that tripped each rule, with the sensitive part masked, so a finding is
  explainable without me trusting the category label alone.

**Acceptance criteria**
- **AC-1**: `Disposition` has a fourth member `redacted`; the native
  Postgres enum `disposition` has the value `'redacted'`; existing
  `execution` rows are untouched (no backfill, nothing is retroactively
  `redacted`).
- **AC-2**: `app/evaluators/redact.py` exists with `redact_spans(text,
  spans)` and `masked_excerpt(text, span, category)`. `redact_spans` blanks
  every given span to `[REDACTED:<category>]` with correct offsets when
  there are two or more spans, and drops a span that overlaps an already
  applied one. `masked_excerpt` returns the span blanked with about 40
  characters of context each side, with a leading or trailing ellipsis when
  it truncates mid text. Verified by a direct unit-level call.
- **AC-3**: a `balanced` workload, response-side, single `pii` hit →
  `200`; `execution.disposition == redacted`; the response body contains
  `[REDACTED:pii]` and does not contain the original PII string; exactly one
  `Finding` row (`evaluator_tier == cheap`, `evidence_ref.side ==
  "response"`, `evidence_ref.masked_excerpt` present and containing no raw
  match). Verified by HTTP plus a direct Postgres read.
- **AC-4**: a `balanced` workload, response-side `custom_policy` hit (a
  leaked secret in the model output) → same as AC-3 with token

- **AC-5**: a `balanced` response with two or more `pii` spans → every span
  blanked in the released body, offsets stay correct (no shifted or

- **AC-6**: a `strict` workload on the AC-3 input → still `403`,
  `disposition == blocked`, unchanged from before this milestone.
- **AC-7**: a `fast` workload on the AC-3 input → still `200`,
  `disposition == flagged`, the original PII still present in the body,

- **AC-8**: a `balanced` response that produces both a `pii` finding and a
  `toxicity` finding → `403`, `disposition == blocked`; nothing is redacted

- **AC-9**: a request-side `pii` block (`strict` / `balanced`) writes a

## Options considered

### Option 1: redact the span in place and release, gated by profile (recommended)

On a `balanced` response-side `pii` / `custom_policy` hit, mutate
`parsed.choices[0].message.content` to blank the matched span(s), set
`disposition = redacted`, keep writing the `Finding` and updating the
ledger, and release `200`. `strict` and `fast` branches are untouched.

**Pros**
- Delivers the rubric's named "edit" tier with one new enum value and one
  new small module.
- The caller gets a useful answer; the PII never reaches them and never
  reaches Postgres.
- The three profiles now differ by action, which is the "vary by use case"
  story the demo needs.
- Reuses the existing `Finding` write, ledger update, and judge scheduling
  unchanged.

**Cons**
- Changes the seeded default workload's behavior (was `403`, now `200` for
  this case). Accepted, and called out in Context.
- ControlPlane now rewrites model output. The edit is a fixed, bounded
  substitution (a span → a literal token), but it is a mutation of a
  payload that used to pass through untouched.
- A redacted answer can read oddly if the model built a sentence around the
  now-blanked value. Acceptable: a slightly awkward answer beats both a
  hard block and a leak.

### Option 2: always block, then log a "would have redacted" note

Keep returning `403` for `balanced`, but attach the redacted text to the
`Finding` for the operator to see.

**Pros**
- No mutation of a released payload.
- `balanced` behavior is byte identical to today.

**Cons**
- Does not implement the "edit" tier at all. The rubric asks for an action,
  not a log line.
- The caller still gets nothing, so the compliance story ("useful answer,
  PII removed") is not delivered.
- Storing the redacted text on the `Finding` still means deciding what
  "redacted enough" is, so most of the work with none of the benefit.

### Option 3: redact on both request side and response side

Also blank `pii` / `custom_policy` in the caller's prompt before forwarding
it to the model API.

**Pros**
- The model provider never sees the raw PII at all, which is arguably the
  stronger data-protection posture.

**Cons**
- Changes what the model is answering. It would see `[REDACTED:pii]` in
  place of real content and may refuse, hallucinate around it, or answer a
  different question. That is a distinct and larger design question than
  "blank a span in an answer the model already produced".
- Out of scope for this milestone by the `STATUS.md` 8.5 note; a clean
  future extension, listed in Follow-up.

## Decision

**Chosen option**: Option 1: redact the span in place and release, gated by
profile.

**Implementation skills**: none (`AGENTS.md` names no community skill for
this area).

### 2. `app/evaluators/redact.py` (new)

```python
REDACTABLE_CATEGORIES = {FindingCategory.pii, FindingCategory.custom_policy}
MASKED_EXCERPT_CONTEXT = 40

def redaction_token(category: FindingCategory) -> str:
    return f"[REDACTED:{category.value}]"

def masked_excerpt(text: str, span: Sequence[int], category: FindingCategory) -> str:
    start, end = span
    left = text[max(0, start - MASKED_EXCERPT_CONTEXT):start]
    right = text[end:end + MASKED_EXCERPT_CONTEXT]
    prefix = "…" if start - MASKED_EXCERPT_CONTEXT > 0 else ""
    suffix = "…" if end + MASKED_EXCERPT_CONTEXT < len(text) else ""
    return f"{prefix}{left}{redaction_token(category)}{right}{suffix}"

def redact_spans(text: str, spans: list[tuple[Sequence[int], FindingCategory]]) -> str:
    # sort by start; drop any span overlapping one already accepted; then
    # replace from rightmost to leftmost so earlier offsets stay valid.
    ordered = sorted(spans, key=lambda item: item[0][0])
    accepted: list[tuple[Sequence[int], FindingCategory]] = []
    last_end = -1
    for span, category in ordered:
        if span[0] >= last_end:
            accepted.append((span, category))
            last_end = span[1]
    out = text
    for (start, end), category in sorted(accepted, key=lambda item: item[0][0], reverse=True):
        out = out[:start] + redaction_token(category) + out[end:]
    return out
```
No dependency on `chat.py`; pure functions. Satisfies **AC-2**.

## Rationale

Redact and release is chosen over "block and log" (Option 2) because the
rubric names "edit" as a distinct decision-logic tier and the compliance
story only lands if the caller still gets an answer. The forces from
Context that decide it: the tier is explicitly required and unbuilt; the
audit-trail pitch needs the "useful answer, PII removed" behavior to be
real; and the profile split is the demo's "vary by use case" evidence,
which needs the profiles to differ by *action*.

Request-side redaction (Option 3) is deferred because it changes the
question the model is answering, which is a separate design problem, and the
`STATUS.md` 8.5 note already scoped it out.

The mapping (`balanced` redacts, `strict` blocks, `fast` flags) follows the
8.1 / 8.2 pattern where `strict` is the strictest action and `fast` is the
most permissive, with `balanced` in between. Redaction is the natural middle
action: neither a refusal nor an unmodified leak.

Mixed findings hard block on `balanced` because releasing a response that
still carries a `toxicity` or `prompt_injection` violation, just with the
PII blanked, would be releasing known-bad content. Redaction is only safe
when the only thing wrong with the response is the presence of the
sensitive span itself.

Ledger accrual on a redacted turn is identical to a block because the model
did emit PII; that the caller was shielded does not make the event
harmless, and a session whose model keeps leaking PII should still escalate.

`masked_excerpt` goes on every cheap-tier finding, not just redacted ones,
because the redactor is built regardless, the cost is one function call per
finding, and a uniform "here is the trigger, masked" record is the audit
story the proposal describes. The `[REDACTED:<category>]` token inside an
excerpt for, say, a `toxicity` finding marks the matched span; it does not
imply the live response was edited (only a `redacted` disposition means
that).

## Feature design

**Data model sketch**
- `execution.disposition`: native Postgres enum `disposition` gains a fourth
  value `redacted`. Nullable/required unchanged (`NOT NULL`, default
  `clean`). No new column.
- `finding.evidence_ref` (JSONB): cheap-tier findings gain an optional
  `masked_excerpt: str` key. No schema change.

**State transitions**
`execution.disposition` still only moves forward, never back:
`clean → flagged | blocked | redacted`, and `flagged → blocked`. A
`redacted` value is terminal for the turn (set once in the response-side
cheap branch, never downgraded by the clean branch, which already never
downgrades per the 8.2 fix).

**API surface**
No new endpoints. `POST /v1/chat/completions` gains one outcome: `200` with
`disposition=redacted` and an edited `choices[0].message.content`.
`GET /api/console/summary`, `/sessions/{id}`, `/feed` gain the new
disposition string and (drilldown) the `masked_excerpt` key with no schema
or handler change.

**Value sourcing**
| Action | Value produced / displayed | Source |
|---|---|---|
| response-side redact | `disposition` | `redacted` when `policy_profile == balanced` and every cheap-tier candidate's `category` is in `REDACTABLE_CATEGORIES`; else the existing `flagged` / `blocked` rule |
| response-side redact | edited `choices[0].message.content` | `redact_spans(response_text, [(candidate.evidence_ref["span"], candidate.category) ...])` where `response_text` is the pre-redaction `parsed.choices[0].message.content` |
| response-side redact | redaction token | `f"[REDACTED:{category.value}]"` from the finding's own `category` |
| any cheap-tier finding | `evidence_ref.masked_excerpt` | `masked_excerpt(scanned_text, candidate.evidence_ref["span"], candidate.category)`; `scanned_text` is `request.messages[-1].content` (request side) or `response_text` (response side) |
| redacted turn | `execution.execution_risk_score` | `max(candidate.confidence for candidate in cheap_candidates)`, unchanged from the block path |
| redacted turn | ledger strike / `cumulative_risk` delta | `_safe_ledger_update` with the candidate list, unchanged from the block path |
| console | `disposition` string, `masked_excerpt` | `execution.disposition.value` and the raw `evidence_ref` dict, both already passed through |
| Dashboard | `blocked_count`, `over_time[].blocked` | unchanged, `Execution.disposition == Disposition.blocked` (excludes `redacted` by construction) |

**Key invariants**
- Redaction fires only when `policy_profile == balanced` AND every
  cheap-tier candidate on the response is `pii` or `custom_policy`.
- `evidence_ref["span"]` offsets are always into the pre-redaction text.
  Redaction is applied once, right to left, from a single
  `run_cheap_tier(response_text)` result; the text is never re-scanned.
- No raw sensitive match string is ever written to Postgres. `evidence_ref`
  stores only `pattern`, `span` (offsets), and `masked_excerpt` (span
  already blanked).
- `disposition` only ever moves forward (see State transitions).
- One `Execution` row per model-call attempt still holds; a redacted turn
  reuses the row 8.2/7.1 already created.

**Security model**
Touches `pii` and secret material (`custom_policy`) in transit. Redaction
removes the sensitive span from the released payload; the masked excerpt
removes it from the audit record. The hard invariant is "no raw sensitive
text is persisted". No new caller-facing surface, no new auth question (the
console write API's lack of auth is a standing accepted hackathon decision,
untouched here).

**Configuration required**
None. `MASKED_EXCERPT_CONTEXT` and `REDACTABLE_CATEGORIES` are module
constants in `redact.py`.

**Critical test scenarios**
- Happy path: `balanced`, response-side single `pii` hit → `200`,
  `disposition=redacted`, body has `[REDACTED:pii]`, PII gone, one `Finding`
  with `masked_excerpt`. Verifies **AC-3**.
- Secret variant: `balanced`, response-side `custom_policy` hit → same, token
  `[REDACTED:custom_policy]`. Verifies **AC-4**.
- Multi-span: two `pii` matches in one response → both blanked, offsets
  correct. Verifies **AC-5**, **AC-2**.
- Profile split: `strict` → `403`; `fast` → `200` flagged, PII still
  present. Verifies **AC-6**, **AC-7**.
- Mixed category: `balanced` response with `pii` + `toxicity` → `403`,
  nothing redacted. Verifies **AC-8**.
- Request-side excerpt: a request-side `pii` block writes
  `evidence_ref.masked_excerpt` from the last message. Verifies **AC-9**.
- Ledger: three redacted turns in one `balanced` session → escalation `403`
  on the fourth. Verifies **AC-10**.
- Console: `blocked_count` unchanged by a redacted row; Session Drilldown
  shows the "Redacted" badge and the excerpt line; Live Feed shows the
  badge; `npm run build` clean. Verifies **AC-11**.
- Script: `simulate_use_cases.py` counts `redacted` as caught, reports the
  phone-format prompt as a redacted false positive, exits `0`. Verifies
  **AC-12**.
- Regression sweep. Verifies **AC-13**.

## Consequences

**Positive**
- The rubric's four decision-logic tiers are all implemented.
- The three profiles now take genuinely different actions on the same
  violation, which is the "vary by use case" demo evidence.
- A compliance-shaped outcome exists: useful answer, PII removed, nothing
  sensitive persisted.
- Session Drilldown can finally show *what* triggered a finding, masked.

**Negative / tradeoffs**
- The seeded default workload's response-side `pii` / `custom_policy`
  behavior changes from `403` to `200`. Any demo narration or doc that says
  "balanced blocks PII in output" needs updating (Follow-up).
- ControlPlane now mutates a released model payload. The edit is a bounded
  literal substitution, but the response is no longer byte-for-byte what the
  model produced.
- A redacted answer can read awkwardly when the model wrote a sentence
  around the blanked value.
- `ALTER TYPE ... ADD VALUE` is not cleanly reversible (Postgres has no
  `DROP VALUE`). Rolling back the code leaves an unused enum value, which is
  harmless.
- `masked_excerpt` on every cheap-tier finding grows `evidence_ref` JSONB
  slightly on every hit. Negligible at this project's volume.

**Neutral**
- No automated tests, per `AGENTS.md` §8; live `curl` + direct Postgres /
  Redis inspection + the script's own report.
- No change to ledger math, escalation, the evaluator tiers, the judge, or
  the request-side flow.
- `redact.py` is the first text-transformation helper in the codebase.
- `--color-info` (if added) is the second semantic color token added for a
  disposition state, after 8.2's `--color-warning`.

## Migration plan

**Strategy**: feature-flagged by profile (no data migration).
**Phases**:
1. Add `Disposition.redacted` to the Python enum and run the standalone
   `ALTER TYPE disposition ADD VALUE IF NOT EXISTS 'redacted'` on an
   autocommit connection against Neon. Safe to run before any code uses it;
   an unused enum value is inert.
2. Ship the `chat.py` redact branch. Only `balanced`-profile response-side
   `pii` / `custom_policy` turns change behavior; `strict`, `fast`, every
   request-side path, and every clean turn are byte identical.
**Rollback**: revert the `chat.py` and frontend commits. The enum value
stays in the Postgres type (Postgres has no `DROP VALUE`), unused and
harmless; nothing writes `redacted` once the code is reverted. No data to
undo (no row is ever backfilled to `redacted`).
**Risks**: the `ALTER TYPE` statement run inside a transaction with other
DDL fails on some Postgres versions (mitigated by running it standalone on
an autocommit connection). A wrong span offset in `redact_spans` could
leave part of a match visible (mitigated by right-to-left application from a
single scan result, and AC-5 covers the multi-span case).
