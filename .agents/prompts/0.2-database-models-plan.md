# 0.2. Database models for Workload, Session, Execution, and Finding

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec adds the Postgres (a relational database) tables and Python model classes for the four core objects every later phase depends on: Workload, Session, Execution, and Finding. The shape of this schema, its field names, and its relationships are already fixed in `forks.md`; this spec only settles the handful of implementation choices `forks.md` leaves open: how ids are generated, how fixed choice fields are stored, how the schema gets applied to the database, and whether rows carry a creation time. Nothing reads or writes these tables yet; that starts in Phase 1.

## Context

`forks.md`'s Consolidated Data Model section fixes almost everything about this schema: four entities, their field names, their foreign key chain (a Workload leads to many Sessions, a Session leads to many Executions, an Execution leads to many Findings), and the six category values a Finding can carry. `STATUS.md` names this milestone directly: connect to Postgres (Neon, a managed Postgres provider) and build SQLAlchemy (Python's most common database toolkit) models matching that schema exactly, field names, foreign key chain, and category enum included.

What `forks.md` leaves open, and calls out explicitly as fair game to decide during the build: which migration tool applies schema changes. A few more gaps only become visible once you try to write the actual model classes: `forks.md`'s data model sketch names each primary key but never its type, names several fixed choice fields (`policy_profile`, `fail_mode`, `evaluator_tier`, `category`) without saying how the database should enforce them, and lists no creation timestamp anywhere except `Finding.timestamp`. These were resolved with the engineer in this session rather than assumed silently, since they shape every table `forks.md` locks and are awkward to change once real rows exist.

Nothing consumes this schema yet. The proxy (Phase 1), the evaluators (Phase 2), and the session ledger (Phase 3) all write to these tables in later phases; this milestone only needs the tables to exist and correctly hold a row.

## Requirements

**User stories**:
- As the engineer building later phases, I want the four core tables to exist in Postgres with the exact shape `forks.md` locks, so Phase 1 through 4 can write and read Workload, Session, Execution, and Finding rows without a schema change.
- As the engineer running this project across many separate sessions, I want the schema applied automatically on startup, so no manual migration step is ever needed during the hackathon.

**Acceptance criteria**:
- **AC-1**: Starting the app with a reachable `DATABASE_URL` creates all four tables in Postgres if they do not already exist, with no manual migration step for this milestone.
- **AC-2**: Every table's columns match `forks.md`'s Consolidated Data Model exactly: field names, the foreign key chain (Workload to Session to Execution to Finding), and every value `forks.md` fixes for `policy_profile`, `fail_mode`, `evaluator_tier`, and `category`.
- **AC-3**: Writing one row per table in foreign key order and reading it back returns the same values (a manual check, since `AGENTS.md` skips automated tests for this milestone).
- **AC-4**: Inserting a row with a value outside the fixed set for `policy_profile`, `fail_mode`, `evaluator_tier`, or `category` is rejected by the database itself, not only by application code.
- **AC-5**: The database connection string is read from an environment variable, never hardcoded, and the file holding it locally is excluded from version control.

## Options considered

### Option 1: SQLAlchemy `create_all()` on startup (recommended)

On every app boot, SQLAlchemy's `Base.metadata.create_all()` checks which tables are missing from the target Postgres database and creates them, using the Python model classes as the one source of truth.

**Pros**:
- No extra dependency and no extra files; the schema is defined exactly once, in the model classes.
- Nothing to hand run; the schema exists the moment the app starts, which fits a build that spans many separate sessions.

**Cons**:
- Keeps no history of how the schema changed over time, and offers no safe way to alter an existing column once real rows exist.
- Cannot express a change it cannot infer (renaming a column, backfilling data); fine while a schema is still being defined for the first time, not once it needs to evolve under real data.

### Option 2: Alembic

Alembic is SQLAlchemy's own migration tool: it generates a numbered, versioned script for every schema change and applies them in order.

**Pros**:
- The standard, production grade way to evolve a schema; every change is reviewable and reversible.
- Matches what a team would reach for once this project outgrows the hackathon.

**Cons**:
- Needs its own config file, an `env.py`, and an initial revision before the first table even exists, real setup time this early in the build.
- The schema is still being shaped across Phase 0 through 4; most of that migration history would be pure churn.

### Option 3: Manual SQL scripts

Hand write `.sql` files with `CREATE TABLE` statements and run them by hand against Neon.

**Pros**:
- No new dependency; full, direct control over the exact SQL, including native Postgres features.

**Cons**:
- Two sources of truth, the `.sql` file and the SQLAlchemy model classes, that can silently drift apart.
- Nothing tracks which script has already run against which database.

## Decision

**Chosen option**: Option 1: SQLAlchemy `create_all()` on startup.

Build the four tables as SQLAlchemy model classes and let `create_all()` apply them to Postgres on every app boot; no migration tool for this milestone.

Alongside that, three smaller implementation choices `forks.md` leaves open are settled here:
- **Primary keys are UUIDs** (Python's `uuid4`, stored as Postgres' native `UUID` type), generated when a row is created. `workload_id` and `session_id` travel outside the database, in API requests, per `forks.md` Fork #1 and Fork #3, and a UUID does not leak row count or insertion order the way an auto incrementing integer would.
- **`policy_profile`, `fail_mode`, `evaluator_tier`, and `category` are Python enum classes mapped to Postgres' native `ENUM` type**, through SQLAlchemy's `Enum` column type. `forks.md` calls the category set a "locked taxonomy," and a native `ENUM` rejects an invalid value at the database itself, which is what AC-4 requires, not only in application code.
- **`Workload`, `Session`, and `Execution` each get a `created_at` column** (`Finding` already has `forks.md`'s own `timestamp` field). Postgres is meant to be, in `STATUS.md`'s own words, the durable record behind the session ledger; without a creation time, Phase 4's audit trail cannot say when a Workload was registered or an Execution happened.

## Rationale

Hackathon speed (`AGENTS.md` section 8) and the fact that this schema is still being shaped across Phase 0 through 4 both argue against Alembic's setup cost right now: a migration history is only valuable once the thing it tracks has stopped changing every session. `forks.md` itself names migration tooling as not locked, explicitly fair game to decide during the build, which is why this was resolved here rather than escalated. `create_all()` gets the schema in front of Phase 1 immediately with zero new files, at the cost of not being able to alter a table safely later, a cost this project is not yet paying since no table holds real data. Manual SQL was set aside because it duplicates the schema in two places that can drift, with no offsetting benefit `create_all()` does not already provide for a schema this size.

The three smaller choices each follow directly from a constraint already in `forks.md`: UUIDs from the fact that these ids leave the database in API payloads, native `ENUM` from `forks.md`'s own "locked taxonomy" language plus AC-4's requirement that the database reject a bad value, and `created_at` from the audit trail purpose Phase 4 explicitly gives Postgres.

## Feature design

**Data model sketch**:

**Workload**
- `workload_id`: UUID, primary key, generated by the app
- `policy_profile`: enum (`strict`, `balanced`, `fast`), required, native Postgres enum
- `latency_budget_ms`: integer, required
- `cost_budget_per_request`: float, nullable (`forks.md` lists it without marking it required)
- `fail_mode`: enum (`fail_open`, `fail_closed`), required
- `metadata`: JSONB, nullable, holds the geography/industry tags `forks.md` calls informational only
- `created_at`: timestamp with time zone, required, defaults to now

**Session**
- `session_id`: UUID, primary key
- `workload_id`: UUID, foreign key to `workload.workload_id`, required, indexed
- `cumulative_risk`: float, required, defaults to 0.0
- `strikes`: JSONB, required, defaults to all six categories at 0 (`{pii, hallucination, toxicity, bias, prompt_injection, custom_policy}`, always all six keys present)
- `ttl_expires_at`: timestamp with time zone, required (mirrors the Redis ledger's 15 minute TTL per Fork #3; Postgres holds the durable copy, Redis holds the live one, per `STATUS.md` 4.1's "do not conflate the two stores")
- `created_at`: timestamp with time zone, required, defaults to now

**Execution**
- `execution_id`: UUID, primary key
- `session_id`: UUID, foreign key to `session.session_id`, required, indexed
- `workload_id`: UUID, foreign key to `workload.workload_id`, required, indexed (denormalized, as `forks.md`'s own field list has it, so a workload level query never needs a join through Session)
- `tokens`: integer, nullable (present once the model call completes)
- `latency_ms`: integer, nullable
- `retries`: integer, required, defaults to 0
- `tool_loop_count`: integer, required, defaults to 0
- `execution_risk_score`: float, nullable (set once evaluators run; per Fork #2, the max confidence across that execution's Findings)
- `created_at`: timestamp with time zone, required, defaults to now

**Finding**
- `finding_id`: UUID, primary key
- `execution_id`: UUID, foreign key to `execution.execution_id`, required, indexed
- `category`: enum (`pii`, `hallucination`, `toxicity`, `bias`, `prompt_injection`, `custom_policy`), required, native Postgres enum
- `confidence`: float, required, meant to hold 0.0 to 1.0 (checked at the application layer for this milestone, not a database constraint, since `forks.md` does not ask for one)
- `evaluator_tier`: enum (`cheap`, `medium`, `expensive`), required, native Postgres enum
- `evidence_ref`: JSONB, nullable, an optional span or offset locating the evidence in the input or output text
- `timestamp`: timestamp with time zone, required, defaults to now (this is `forks.md`'s own field name for this one table; the other three use `created_at`, a name `forks.md` never assigned them)

**State transitions**: none in this milestone. No entity here has a state machine yet; the session ledger's escalation logic (cumulative risk, strikes, the block/regenerate/route decision) arrives in Phase 3.

**API surface**: not applicable. This milestone adds no endpoint; nothing reads or writes these tables until Phase 1 wires the first writer.

**Value sourcing**: not applicable, for the same reason. Every column above is either generated by the model itself (the UUID primary keys, the `created_at`/`timestamp` defaults, the zeroed `strikes` default) or will be supplied by whichever Phase 1 code performs the first insert; there is no action in this milestone that produces a value needing a named source.

**Key invariants**:
- A Session's `workload_id` never changes after creation (a session cannot span two workloads, per `forks.md` Fork #1).
- An Execution's `workload_id` must always match its Session's `workload_id`; this milestone does not add a database constraint for that, it is enforced by whichever Phase 1 code performs the insert.
- `Finding.confidence` stays within 0.0 to 1.0, checked at the application layer for this milestone; add a database `CHECK` constraint later if a bad value ever reaches the table.
- `strikes` always carries all six category keys, even at 0, never a partial object, since Phase 3's escalation check reads any of them by name.

**Security model**: no authentication or authorization surface in this milestone; nothing queries these tables yet. The one sensitive concern is the connection string itself, covered under Configuration required.

**Configuration required**:
- `DATABASE_URL`: the Postgres connection string for Neon, in `postgresql+asyncpg://` form (the async driver, matching `forks.md`'s "async native" API/Proxy choice), read from the environment, never hardcoded, held locally in `.env`.

**Critical test scenarios**:
- Happy path: start the app against a real Neon database with `DATABASE_URL` set, confirm all four tables now exist, verifies **AC-1**, **AC-2**.
- Failure case: insert a Finding with `category="not_a_real_category"`, confirm Postgres rejects it with an invalid input value error rather than writing the row, verifies **AC-4**.
- Round trip: insert one Workload, then one Session referencing it, then one Execution referencing that Session, then one Finding referencing that Execution, then read all four back by id and confirm every field matches what was written, verifies **AC-3**.

## Build plan

1. Add `sqlalchemy`, `asyncpg` (the async Postgres driver), and `python-dotenv` (to load `.env` locally) to `pyproject.toml` via `uv add`, satisfies **AC-1**, **AC-5**.
2. Add `DATABASE_URL` to a local `.env` file, and add `.env` to `.gitignore` (currently absent from it), satisfies **AC-5**.
3. Create `app/db.py`: an async SQLAlchemy engine built from `DATABASE_URL`, a session maker, and the declarative `Base` class every model inherits from, satisfies **AC-1**.
4. Create `app/models/` as a package: one file per entity (`workload.py`, `session.py`, `execution.py`, `finding.py`) plus `enums.py` for the four enum classes, matching the data model sketch above field for field, satisfies **AC-2**, **AC-4**.
5. In `app/main.py`, run `Base.metadata.create_all` against the async engine during startup (a FastAPI lifespan handler), satisfies **AC-1**.
6. Self check: with a real `DATABASE_URL`, start the app, confirm the four tables exist, insert and read back one row per table in foreign key order, and attempt one invalid enum insert to confirm it is rejected, satisfies **AC-1**, **AC-3**, **AC-4**.

## Consequences

**Positive**:
- Phase 1 through 4 can start writing real rows immediately; nothing about this schema blocks the proxy or the evaluators.
- Native Postgres enums and a foreign key chain mean a large class of bad data, a wrong category, an Execution pointing at a Session that does not exist, is rejected by the database itself, not only by application code that might have a bug.

**Negative / tradeoffs**:
- `create_all()` cannot alter an existing table; the day this schema needs a real change, a renamed column, a new required field on a table that already holds rows, a migration tool has to be introduced then, not now.
- A native Postgres enum costs slightly more friction to extend than a plain string column would: adding a seventh Finding category later needs a schema change, not just a new value somewhere in the code. That cost is intentional here, it is what makes AC-4's database level rejection possible.

**Neutral**:
- No automated tests are written for this milestone, per `AGENTS.md` section 8; the critical test scenarios above are a manual self check.
- `cost_budget_per_request` and `metadata` stay nullable and loosely typed since `forks.md` does not fix their exact validation rules; tightening them is a later concern, not this milestone's.
