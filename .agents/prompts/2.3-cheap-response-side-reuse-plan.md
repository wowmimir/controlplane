# 2.3. Cheap: Response-Side Reuse

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This milestone required no new code. `STATUS.md` already lists 2.3 as complete: the cheap-tier PII and prompt-injection scanners built in 1.3 (request side) were designed from the start to be reusable, and 1.5 (Response-Side Interception) satisfied 2.3 as a direct structural consequence of calling that same shared function on response text instead of writing a second, response-specific scanner. 2.1 and 2.2 then each proved, as part of their own self-checks, that every pattern they added — old and new — is covered on the response side automatically, with no router change. This spec exists to document that already-verified fact as a deliberate record, since 2.3 never got its own dedicated build spec; 2.2's plan (`.agents/prompts/2.2-cheap-prompt-injection-heuristic-plan.md`, Build plan step 5) closed 2.3 out inline as part of its own work instead.

## Context

`decisions.md`'s 2026-08-23 entry on 1.3 records the deliberate choice to put the PII and prompt-injection scanners in a new `app/evaluators/` package (`pii.py`, `prompt_injection.py`, `cheap.py`'s `run_cheap_tier` orchestrator, `types.py`) rather than inline in `app/routers/chat.py`, specifically because "2.3 explicitly requires the same detectors to run on response text too — inline router code would need extraction/rewriting later for no benefit now." That decision is what made 2.3 essentially free once 1.5 shipped.

1.5's own `decisions.md` entries confirm `_run_response_side_interception` calls `run_cheap_tier` — the identical function `_run_request_side_interception` already used in 1.3 — against `parsed.choices[0].message.content`, "effectively satisfying Phase 2.3 ahead of schedule, same pattern 1.3 set for 2.1/2.2" (per `STATUS.md`'s 1.5 handoff note).

2.1 then proved this live, end-to-end, for real PII values the model generated on its own: a prompt engineered to make Ollama produce a well-known loopback IPv4 address and a well-known payment-sandbox test card number, neither of which appeared in the input, both triggered a response-side `403` with `evidence_ref.side:"response"`, confirmed via a direct Postgres query against the `Execution` and `Finding` rows (`decisions.md`, 2.1 entry; `STATUS.md`, 2.1 handoff note).

2.2 proved the same for its five new injection patterns, but via a different, explicitly logged method: a direct in-process call to `run_cheap_tier()` on response-shaped text, rather than a full live model round trip. `decisions.md`'s 2.2 entry records why a live round trip isn't obtainable for this category of pattern: a jailbreak trigger phrase is the literal string being detected, so any request specific enough to make the model echo it verbatim also trips the request-side block first, before a response is ever produced. This is a methodological ceiling on how the *response* path can be exercised for a literal-phrase detector, not a gap in whether the response path actually runs the pattern — `_run_response_side_interception` calls the exact same unchanged `run_cheap_tier` function either way.

Verified directly against the current code for this spec (not just the notes above):
- `app/evaluators/cheap.py`'s `run_cheap_tier(text: str) -> list[FindingCandidate]` is fully generic — `return [*pii.scan(text), *prompt_injection.scan(text)]` — with no request/response distinction anywhere in it. Its docstring states it is "Reused for both request-side (1.3) and response-side (2.3) text."
- `pii.py` and `prompt_injection.py`'s `scan(text)` functions are pure text scanners; neither references requests, responses, messages, or any side-specific concept.
- `app/routers/chat.py` calls the identical function from both interception paths:
  - Request side: `text = "\n".join(message.content for message in request.messages)` then `candidates = run_cheap_tier(text)`
  - Response side: `response_text = parsed.choices[0].message.content` then `candidates = run_cheap_tier(response_text)`
- The two files' currently uncommitted changes (2.1's Luhn-gated `credit_card`/`ip_address`, 2.2's five new injection patterns) are purely additive entries to the existing `_PATTERNS` dicts — they touch no call site, so they inherit response-side coverage the same way every pattern before them did.

`forks.md`'s "explicitly not locked" list leaves exact cheap-tier patterns free to decide during the build, but the *architecture* that makes response-side reuse automatic — one evaluator package, single-label findings per Fork #2, called identically from both sides per Fork #4 ("Input and output are NOT treated differently") — was already locked before 2.3 was reached. There was no second viable shape to choose between by the time this milestone came up.

## Requirements

**Verification criteria** (already met; this documents that they are met, not a build to perform):

- **AC-1**: `app/routers/chat.py`'s `_run_request_side_interception` and `_run_response_side_interception` both call `run_cheap_tier`, the single shared entry point in `app/evaluators/cheap.py`, differing only in which text they pass in (joined request messages vs. the model's response content). Met — confirmed by direct code read.
- **AC-2**: Neither `app/evaluators/pii.py` nor `app/evaluators/prompt_injection.py` contains any request-specific or response-specific branching; `scan(text)` in each is a pure function of its input text. Met — confirmed by direct code read.
- **AC-3**: At least one PII pattern is proven to block on the response side against a real, completed model call, with the triggering `Finding.evidence_ref.side` recorded as `"response"` and the same `Execution` row carrying real `tokens`/`latency_ms`. Met — 2.1's self-check (loopback IPv4 and sandbox test card, neither present in the input).
- **AC-4**: The five prompt-injection patterns 2.2 added are proven reachable through `run_cheap_tier` on response-shaped text. Met — 2.2's direct in-process check, with the reason a full live round trip isn't obtainable for a literal-phrase detector explicitly logged in `decisions.md` rather than left unexplained.
- **AC-5**: Any pattern added to either evaluator's `_PATTERNS` dict in the future inherits response-side coverage automatically, with no change required to `app/evaluators/cheap.py` or `app/routers/chat.py`. Met by construction — both call sites are pattern-count-agnostic, and 2.1/2.2 already demonstrated this holds when patterns were actually added.

## Decision

**Chosen option**: No new option was chosen here. This spec records the architecture already locked by Fork #2 (independent single-label evaluators) and Fork #4 ("Input and output are NOT treated differently") and already implemented by 1.3's package split and 1.5's reuse of it. There is nothing to decide.

## Rationale

Once 1.3 put the scanners behind a plain `scan(text) -> list[FindingCandidate]` interface specifically so 1.5 could reuse them, and 1.5 did exactly that, a separate response-side implementation was never a live option worth comparing against — building one would have duplicated the request-side scanners for no reason and violated Fork #2's single-purpose-evaluator design. The only real question 2.3 could have raised — do newly *added* patterns (2.1, 2.2) still get response-side coverage, or only the original three — was answered empirically by 2.1's and 2.2's own self-checks, both already logged.

## Consequences

**Positive**:
- Any future cheap-tier pattern (2.6's secret/API-key detection included) gets response-side coverage for free, with no router change, as long as it's added to an existing `_PATTERNS` dict or a new file wired into `run_cheap_tier` the same way.

**Negative / tradeoffs**:
- Literal-phrase injection patterns (2.2's five, and any future ones of the same kind) cannot get a true live, end-to-end response-side self-check, because a prompt specific enough to make the model reproduce the exact trigger phrase also trips the request-side block first. This is a permanent methodological ceiling for this pattern style, not a code gap — already logged in `decisions.md` under 2.2, not new here.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-checks already performed and logged under 1.5, 2.1, and 2.2.

## Follow-up

- None new. The real next work is already tracked in `STATUS.md`: Phase 2.4 (Medium: Embedding Similarity), 2.5 (Expensive: LLM-as-Judge), and 2.6 (Custom Policy Evaluator, which will need its own file such as `secrets.py` since `pii.py`'s `scan()` currently hardcodes one category file-wide).
