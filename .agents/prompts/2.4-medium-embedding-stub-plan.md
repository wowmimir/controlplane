# 2.4. Medium: Embedding Similarity (Stub)

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec stubs the medium tier rather than building it. An earlier attempt at this spec (`.agents/prompts/2.4-medium-embedding-similarity-plan.md`, now removed) built a real local `sentence-transformers` comparison, comparing the model's response against the full conversation via cosine similarity. That was rejected: the user had already decided, in an earlier conversation, that 2.4 should be a stub with real hallucination detection deferred to Phase 2.5 (LLM-as-judge), and the rejected spec picked a different option instead. This version corrects that. It wires the plumbing a real medium tier will eventually need — a call signature, a threshold constant, the `Finding`/ledger shape, a latency-budget parameter — into `app/evaluators/medium.py` and `app/routers/chat.py`, but the function itself always returns no finding. No `sentence-transformers` or `torch` dependency is added.

## Context

`STATUS.md` names 2.4 as "Medium: Embedding Similarity — Grounding/hallucination heuristic. Only invoked when cheap tier is inconclusive (per Fork #4 decision tree)." `forks.md`'s Tech Stack table locks the medium evaluator to "Embedding similarity (sentence-transformer)" for whenever it is actually built, and Fork #4 restricts it to the response side, synchronous, within `latency_budget_ms`.

ControlPlane has no RAG or knowledge base of its own, so there is nothing genuine to fact-check a response against. A real embedding similarity check would have to fall back to a proxy signal (e.g., comparing the response to the conversation itself), which is at best a weak topical-drift heuristic, not real grounding, and would still require adding `sentence-transformers` (and the `torch` dependency it pulls in) for a hackathon build. Phase 2.5 (LLM-as-judge) can reason about the actual content of a response and is a strictly better tool for this category. Building a throwaway heuristic now, only to replace it in the very next milestone, is not worth the dependency cost or the engineering time. This was the decision already made before this spec was written; the correction here brings the spec back in line with it.

Confirmed against the current code (unchanged from the prior spec's research, still accurate): `app/evaluators/` has `__init__.py`, `types.py`, `cheap.py`, `pii.py`, `prompt_injection.py`, no `medium.py`; `app/routers/chat.py`'s `_run_response_side_interception(db, session, execution, parsed)` does not currently receive `workload` or `request`; `EvaluatorTier.medium` and `FindingCategory.hallucination` already exist in `app/models/enums.py`, so no schema change is needed; no ML/embedding dependency is installed in `pyproject.toml`/`uv.lock`, and this spec keeps it that way.

## Options considered

### Option 1: Build a real local `sentence-transformers` embedding comparison now

Compare the response against the full conversation via cosine similarity, as the rejected prior spec did.

**Pros**: Produces some real, working signal for the `hallucination` category immediately.
**Cons**: No RAG/knowledge base exists, so the comparison is a weak topical-drift proxy, not real grounding. Requires `sentence-transformers`/`torch`, a heavy install for a hackathon. Rejected — this is the option the user already ruled out before this spec was (re)written.

### Option 2: Route a similarity check through `model_client.py`'s existing model API instead of a local library

**Pros**: Avoids the local ML dependency.
**Cons**: `forks.md` locks the medium evaluator to "sentence-transformer" by name; an API-based similarity check would not honor that lock even if it avoided the dependency, and it still suffers from the same "no real ground truth to compare against" problem as Option 1. Rejected.

### Option 3: Stub the plumbing now, defer real detection to Phase 2.5

Wire the function signature, threshold constant, and router call site, but always return no finding; let 2.5's LLM-as-judge implement real judgment using this same wiring.

**Pros**: No wasted dependency or engineering effort on a heuristic that would be replaced almost immediately. The router and evaluator package are shaped correctly for 2.5 in advance, so that milestone only has to fill in one function body. Matches the decision the user had already made.
**Cons**: The `hallucination` category has no real detection until 2.5 ships — explicitly flagged as a known gap, not hidden.

## Decision

**Chosen option**: Option 3: stub the plumbing now, defer real detection to Phase 2.5.

## Rationale

Options 1 and 2 both run into the same underlying problem: ControlPlane has no ground truth to check a response's grounding against, so any embedding-based signal built now would be a weak proxy at best, and Phase 2.5's LLM-as-judge is a strictly better fit for exactly this category since it can reason about actual content instead of just semantic distance. Paying for a heavy dependency and a throwaway implementation for the one milestone in between is not worth it. Option 3 keeps the exact shape (`Finding`, `EvaluatorTier.medium`, `FindingCategory.hallucination`, the router call site) that a real implementation would need, so nothing has to be rewired later, while adding no dependency and no behavior change today.
