# 2.6. Toxicity/Bias/Custom Policy Evaluators

**Date**: 2026-08-24
**Status**: Accepted

## Summary

Adds three new cheap tier evaluator files, `toxicity.py`, `bias.py`, and `secrets.py`, each following the exact shape `pii.py` and `prompt_injection.py` already use: a dictionary of compiled regex patterns plus a `scan(text)` function that returns one `FindingCandidate` per match. `toxicity.py` and `bias.py` are deliberately minimal stub heuristics (a handful of patterns each), since `STATUS.md` explicitly allows a stub here. `secrets.py` is the fullest of the three, since concrete secret patterns were already drafted during Phase 2.1 and deferred here. The only other change is a three line addition to `app/evaluators/cheap.py`'s `run_cheap_tier`, splicing the three new `scan()` calls into the list it already returns. No router changes, no schema changes: `FindingCategory.toxicity`, `.bias`, and `.custom_policy` already exist, and `chat.py` calls `run_cheap_tier` generically, so both request side and response side blocking pick up all three new categories automatically, the same way 1.5/2.3 already proved for `pii`/`prompt_injection`.

## Context

`STATUS.md` names 2.6 as the last item in Phase 2: "Minimum viable version of each (even a stub heuristic) so the full 6 category taxonomy has *something* wired end to end for the demo, not just PII + hallucination." Fork #2 in `forks.md` locks the taxonomy: `pii`, `hallucination`, `toxicity`, `bias`, `prompt_injection`, `custom_policy` are the six categories that feed the strike ledger. Today only `pii`, `prompt_injection` (cheap tier, since 1.3/2.1/2.2), and `hallucination` (expensive tier, since 2.5) ever produce a real `Finding`. `toxicity`, `bias`, and `custom_policy` exist in the `FindingCategory` enum (confirmed in `app/models/enums.py`, added back in 0.2) but nothing in the codebase ever sets them.

`decisions.md`'s 2026-08-23 entry for 2.1 already deferred secret and API key detection here, citing the wrong category (`custom_policy`, not `pii`) and drafting three starting patterns: `AKIA[0-9A-Z]{16}` (AWS access key), `sk-[A-Za-z0-9]{20,}` (a generic secret token shape, the style OpenAI style API keys use), `ghp_[A-Za-z0-9]{36}` (a GitHub personal access token). It also flagged that `pii.py`'s `scan()` hardcodes one category for the whole file (confirmed again this session, see below), so a new sibling file is the natural fit rather than retrofitting `pii.py` with a per pattern category map.

Confirmed against the current code this session (read in full, not guessed):
- `app/models/enums.py`: `FindingCategory` already has `toxicity`, `bias`, and `custom_policy` members. No enum or migration change needed.
- `app/evaluators/pii.py` and `app/evaluators/prompt_injection.py`: both follow the identical shape, a module level `_PATTERNS: dict[str, re.Pattern]`, an optional `_VALIDATORS` side table keyed by pattern name (only `pii.py` uses one, for `credit_card`'s Luhn check), and a `scan(text: str) -> list[FindingCandidate]` that loops `_PATTERNS.items()`, and at the single `FindingCandidate(...)` call site hardcodes one category literally inline (`category=FindingCategory.pii` or `category=FindingCategory.prompt_injection`), `confidence=CONFIDENCE` (the shared fixed `0.95` from `types.py`), and `evidence_ref={"pattern": pattern_name, "span": [match.start(), match.end()]}`.
- `app/evaluators/cheap.py` (full contents, 13 lines): `run_cheap_tier(text) -> list[FindingCandidate]` returns `[*pii.scan(text), *prompt_injection.scan(text)]`. There is no registry or plugin mechanism, this is the one file that needs a direct edit to wire in a new scanner module. It has no DB or Redis access of its own, a pure function, same convention every new scanner should follow.
- `app/routers/chat.py`: `_run_request_side_interception` and `_run_response_side_interception` both call `run_cheap_tier(text)` as a single opaque call and pull `candidate.category.value` dynamically when writing the `403` envelope and incrementing `strikes[category]`. Neither function has any per category logic. This confirms, the same way 2.1/2.2 already proved it for two new patterns each, that new categories need zero router changes to reach both the request side block and (via 1.5/2.3's existing reuse) the response side block.
- `app/models/finding.py`: `category` is a native Postgres enum column already covering all six values, `evidence_ref` is free form JSONB. No schema change needed.
- A repository wide search for the three draft secret patterns confirms they exist only as prose in `decisions.md`, `STATUS.md`, and the 2.1 spec's Follow up, not in any `.py` file. This milestone is the first to actually write them as code.

Two scope calls were ratified with the user before writing this spec (via `/architect`'s Asks vs acts):
1. **Three separate files**, `toxicity.py`, `bias.py`, `secrets.py`, matching the existing one file per category convention exactly, rather than one combined `custom_policy.py` with a per pattern category map. `secrets.py` feeds `FindingCategory.custom_policy`.
2. **Toxicity and bias get a minimal stub depth pattern list** (a handful of patterns each), explicitly accepting a high false negative rate as a known, permanent limitation, the same tradeoff precedent 2.1/2.2 already set for the phone/IP address regex gaps. `secrets.py` gets fuller coverage since concrete draft patterns already existed.

## Requirements

**User stories**:
- As the hackathon demo, I want a clearly toxic message, a clearly biased/stereotyping message, and a message containing a leaked secret to each produce a real, visible block, so the full six category taxonomy has something working for every category, not just PII and hallucination.
- As the engineer, I want the new evaluators to slot into the exact same pipeline PII and prompt injection already use, so response side blocking, the ledger update, and the `403` envelope all work for free with no router change.
- As the operator, I want the stub nature of `toxicity`/`bias` to be explicit and documented, not hidden, so nobody mistakes a hackathon keyword list for a real moderation system later.

**Acceptance criteria**:
- **AC-1**: `app/evaluators/toxicity.py` exposes `_PATTERNS: dict[str, re.Pattern]` and `scan(text: str) -> list[FindingCandidate]`, following the exact `pii.py`/`prompt_injection.py` shape (loop, `confidence=CONFIDENCE`, `evidence_ref={"pattern": ..., "span": [...]}`, category hardcoded inline as `FindingCategory.toxicity`). Pattern set is a small, minimal stub: direct insults ("you are worthless", "you're an idiot", "you are pathetic", and similar fixed insult phrasings), explicit threats or death wishes directed at a person ("kill yourself", "i hope you die", "i will kill you"), and dehumanizing language about a person or group ("you are subhuman", "they are vermin"). No slur or profanity word list is included by design (see Rationale).
- **AC-2**: `app/evaluators/bias.py` exposes the same shape, category hardcoded inline as `FindingCategory.bias`. Pattern set is a small, minimal stub: absolute generalizations about a protected or demographic group ("all women are", "all men are", "all muslims are", "all immigrants are", followed by a claim), and explicit inherent trait claims ("women are naturally", "men are inherently", "always/never" paired with a group).
- **AC-3**: `app/evaluators/secrets.py` exposes the same shape, category hardcoded inline as `FindingCategory.custom_policy`. Pattern set covers the three already drafted shapes (AWS access key `AKIA[0-9A-Z]{16}`, a generic secret token shape `sk-[A-Za-z0-9]{20,}`, a GitHub personal access token `ghp_[A-Za-z0-9]{36}`) plus two more common real world secret shapes: a PEM private key header (`-----BEGIN (?:RSA |EC |OPENSSH )?PRIVATE KEY-----`) and a Slack token (`xox[baprs]-[A-Za-z0-9-]{10,}`). None of these formats carry a checksum, so no `_VALIDATORS` entry is needed, unlike `pii.py`'s `credit_card`.
- **AC-4**: `app/evaluators/cheap.py`'s `run_cheap_tier` imports `toxicity`, `bias`, `secrets` and returns `[*pii.scan(text), *prompt_injection.scan(text), *toxicity.scan(text), *bias.scan(text), *secrets.scan(text)]`. This is the only change to this file, and the only change outside the three new evaluator files.
- **AC-5**: No changes to `app/routers/chat.py`, `app/evaluators/types.py`, `app/evaluators/pii.py`, or `app/evaluators/prompt_injection.py`. Request side and response side blocking for all three new categories works purely from AC-4's `run_cheap_tier` change, confirmed by self-check rather than by new router code.
- **AC-6**: A prompt containing a toxicity trigger phrase returns `403` on the request side with `code:"toxicity"`, an `Execution` and `Finding` row are written, and the Redis ledger's `strikes.toxicity` increments. Same for a bias trigger phrase (`code:"bias"`, `strikes.bias`) and a secret shaped string (`code:"custom_policy"`, `strikes.custom_policy`).
- **AC-7**: The response side path blocks the same way when the *model's response* (not the request) contains a toxicity, bias, or secret shaped trigger, reusing the existing `_run_response_side_interception` call to `run_cheap_tier`, the same proof pattern 2.1/2.2 already used for their new patterns.
- **AC-8**: Full regression is unaffected: 1.2's `400` unknown workload path, 1.3/1.5's PII and prompt injection blocks (both sides), 1.4's `502` model unreachable path, 2.5's async hallucination finding, and `/health` all behave exactly as before.

## Options considered

### Option 1: Three separate files, minimal stub for toxicity/bias, fuller coverage for secrets

`toxicity.py`, `bias.py`, `secrets.py`, each mirroring `pii.py`'s exact shape and hardcoding one category inline. Toxicity and bias get a handful of clearly identifiable trigger patterns; secrets gets the already drafted patterns plus a couple more common shapes.

**Pros**: Matches the codebase's established one file per category convention exactly, zero surprises for the next session reading the evaluators package. Keeps each file's single hardcoded category assumption intact, no need to touch `scan()`'s loop shape or add a `_CATEGORIES` side table anywhere.
**Cons**: Toxicity and bias coverage will miss the large majority of real world toxic or biased phrasing, a regex keyword list is a weak proxy for either category.

### Option 2: One combined `custom_policy.py` file covering all three categories with a per pattern category map

A single new file, a `_CATEGORIES: dict[str, FindingCategory]` side table (mirroring how `_VALIDATORS` is already keyed by pattern name in `pii.py`) alongside `_PATTERNS`, so `scan()` looks up each pattern's category individually instead of hardcoding one for the whole file.

**Pros**: One file to open instead of three; a genuinely reusable shape for future ad hoc policy rules beyond just these three categories.
**Cons**: Breaks the established convention every existing evaluator file uses (one file, one hardcoded category), requires extending `scan()`'s loop logic instead of reusing it verbatim, and blurs `custom_policy` (a real, distinct category) together with `toxicity`/`bias` (unrelated categories) in one file for no benefit beyond fewer files.

### Option 3: Real ML based toxicity/bias classification (e.g. a small transformer classifier)

Use an actual trained model for toxicity/bias instead of regex.

**Pros**: Meaningfully better recall and precision than any keyword list could ever achieve.
**Cons**: `forks.md`'s Tech Stack table locks cheap tier evaluators to "Regex/rule based only, no ML dependency." This option isn't actually open at the cheap tier; a real classifier belongs at the medium tier, which `forks.md` already scopes to embedding similarity, not a toxicity/bias model. Rejected on the same "no ML dependency" ground 2.1's `credit_card` Luhn check deliberately avoided.

## Decision

**Chosen option**: Option 1, three separate files, minimal stub for toxicity/bias, fuller coverage for secrets.

## Rationale

Option 3 is not actually available, `forks.md` locks cheap tier evaluators to regex only. Between Options 1 and 2, the deciding factor is convention consistency: every existing evaluator file in this codebase, `pii.py` and `prompt_injection.py`, hardcodes one category inline and neither has ever needed a per pattern category map, because Fork #2 already scopes each evaluator to be single purpose ("A PII evaluator never needs to understand hallucination, and vice versa"). Building a combined file with a category side table for 2.6 alone would be the first departure from that pattern in the codebase, for three categories that are conceptually unrelated to each other (a secret leak, a toxic remark, and a stereotyping claim have nothing in common except that none of them is PII or prompt injection). Ratified with the user directly.

The minimal stub depth for toxicity/bias, versus the fuller depth for secrets, follows `STATUS.md`'s own explicit framing: it names this milestone's job as proving the full six category taxonomy has "something wired end to end," not building production grade toxicity or bias detection, and it distinguishes secrets (which already had concrete draft patterns waiting) from toxicity/bias (which did not). Building out an extensive toxicity/bias keyword list now would spend hackathon time on a component `AGENTS.md`'s "don't design for hypothetical future requirements" guidance already argues against, real coverage for these two categories is properly an ML/classifier problem, explicitly out of reach at the cheap tier per Fork #2's own lock.

## Feature design

**Data model sketch**: no schema change. `FindingCategory.toxicity`, `.bias`, `.custom_policy` already exist (added in 0.2), unused until this milestone.

**New file**: `app/evaluators/toxicity.py`

```python
import re

from app.evaluators.types import CONFIDENCE, FindingCandidate
from app.models.enums import FindingCategory

_PATTERNS = {
    "direct_insult": re.compile(
        r"\byou'?re?\s+(?:a\s+)?(?:worthless|pathetic|an idiot|a moron|disgusting|stupid)\b",
        re.IGNORECASE,
    ),
    "death_wish_or_threat": re.compile(
        r"\b(?:kill yourself|i hope you die|i will kill you|i'll kill you)\b",
        re.IGNORECASE,
    ),
    "dehumanizing_language": re.compile(
        r"\b(?:you are|they are|those people are)\s+(?:subhuman|vermin|scum)\b",
        re.IGNORECASE,
    ),
}


def scan(text: str) -> list[FindingCandidate]:
    candidates = []
    for pattern_name, pattern in _PATTERNS.items():
        for match in pattern.finditer(text):
            candidates.append(
                FindingCandidate(
                    category=FindingCategory.toxicity,
                    confidence=CONFIDENCE,
                    evidence_ref={"pattern": pattern_name, "span": [match.start(), match.end()]},
                )
            )
    return candidates
```

**New file**: `app/evaluators/bias.py`, identical shape, `category=FindingCategory.bias`:

```python
_PATTERNS = {
    "absolute_group_generalization": re.compile(
        r"\ball\s+(?:women|men|muslims|christians|jews|asians|black people|white people|"
        r"latinos|immigrants|gay people|trans people)\s+(?:are|do|want|believe)\b",
        re.IGNORECASE,
    ),
    "inherent_trait_claim": re.compile(
        r"\b(?:women|men)\s+are\s+(?:naturally|inherently|always|never)\b",
        re.IGNORECASE,
    ),
}
```

**New file**: `app/evaluators/secrets.py`, identical shape, `category=FindingCategory.custom_policy`, no validator table needed (none of these formats are checksummed):

```python
_PATTERNS = {
    "aws_access_key": re.compile(r"\bAKIA[0-9A-Z]{16}\b"),
    "generic_secret_token": re.compile(r"\bsk-[A-Za-z0-9]{20,}\b"),
    "github_token": re.compile(r"\bghp_[A-Za-z0-9]{36}\b"),
    "pem_private_key": re.compile(r"-----BEGIN (?:RSA |EC |OPENSSH )?PRIVATE KEY-----"),
    "slack_token": re.compile(r"\bxox[baprs]-[A-Za-z0-9-]{10,}\b"),
}
```

(Exact wording of the toxicity/bias phrase patterns may be refined slightly during implementation, e.g. matching a few more inflections. The shape, category, pattern count, and inclusion of the three drafted secret patterns are locked by AC-1 through AC-3.)

**Changed file**: `app/evaluators/cheap.py`

```python
from app.evaluators import bias, pii, prompt_injection, secrets, toxicity
from app.evaluators.types import CONFIDENCE, FindingCandidate

__all__ = ["CONFIDENCE", "FindingCandidate", "run_cheap_tier"]


def run_cheap_tier(text: str) -> list[FindingCandidate]:
    return [
        *pii.scan(text),
        *prompt_injection.scan(text),
        *toxicity.scan(text),
        *bias.scan(text),
        *secrets.scan(text),
    ]
```

**No changes**: `app/routers/chat.py`, `app/evaluators/types.py`, `app/evaluators/pii.py`, `app/evaluators/prompt_injection.py`, `app/evaluators/medium.py`, `app/evaluators/expensive.py`, `app/models/*`, `app/redis_client.py`, `app/model_client.py`.

**Value sourcing**: no new inputs. Each `scan(text)` receives the same `text` string `pii.scan`/`prompt_injection.scan` already receive at both call sites in `chat.py` (the joined request message content on the request side, `parsed.choices[0].message.content` on the response side), nothing new to source.

**Key invariants**:
- Every new evaluator file hardcodes exactly one `FindingCategory`, matching every existing evaluator file.
- No new evaluator file touches the DB, Redis, or the model client, pure functions only, matching `pii.py`/`prompt_injection.py`'s existing purity convention.
- `run_cheap_tier`'s five scan calls are independent, one file's patterns never suppress or interact with another's.

**Security model**: unchanged. These are additional pure text pattern checks on already flowing request/response text, no new external exposure.

**Configuration required**: none.

**Critical test scenarios** (each maps to an acceptance criterion above):
- A prompt containing a toxicity trigger phrase → request side `403`, `code:"toxicity"`, `Finding.evaluator_tier=cheap`, `strikes.toxicity` incremented in Redis. Verifies **AC-1**, **AC-6**.
- A prompt containing a bias trigger phrase → request side `403`, `code:"bias"`, `strikes.bias` incremented. Verifies **AC-2**, **AC-6**.
- A prompt containing an AWS style key string → request side `403`, `code:"custom_policy"`, `strikes.custom_policy` incremented; repeat for the `sk-`, `ghp_`, PEM header, and Slack token shapes. Verifies **AC-3**, **AC-6**.
- A clean prompt that engineers the model to reproduce a toxicity, bias, or secret shaped string in its response (not present in the request) → response side `403` with the "detected in output" wording, same `Execution` row carrying real `tokens`/`latency_ms`, matching 1.5's existing response side proof pattern. Verifies **AC-7**.
- Full 1.2 through 2.5 regression (unknown workload `400`, PII/prompt injection blocks both sides, model unreachable `502`, a clean exchange still reaching 2.5's async judge, `/health` `200`) re-run clean. Verifies **AC-8**.

## Consequences

**Positive**:
- All six taxonomy categories from Fork #2 now have a real, working code path, not just PII and hallucination, closing Phase 2 entirely.
- The response side, the ledger, and the `403` envelope all inherit the three new categories for free, no router change, extending the same "additive to evaluator files only" precedent 2.1/2.2/2.3 already established.
- Secret leakage (API keys, private keys, tokens) is now actually caught, closing a real security gap that existed since 1.1.

**Negative / tradeoffs**:
- Toxicity and bias coverage is intentionally shallow. A regex keyword list catches only a handful of explicit phrasings and will miss the large majority of real world toxic or biased language, including anything using slurs, coded language, or sentence structures not matching the fixed patterns. This is accepted, not solved, matching the phone/IP address regex precedent from 2.1.
- No slur or profanity word list is included in `toxicity.py`. This narrows recall further but avoids embedding an explicit slur list in the codebase for a hackathon stub whose own milestone description calls for "even a stub heuristic," not real coverage.
- Secret pattern coverage (five shapes) is a starting set, not exhaustive; many other API key/token formats (cloud provider keys beyond AWS, database connection strings, JWTs) remain undetected.
- Strikes from these three new categories still accumulate with no window expiry, the same limitation every existing pattern already has; Phase 3.1 remains the owner of that fix.

**Neutral**:
- No automated tests written for this milestone, per `AGENTS.md` Section 8; manual `curl` plus database/Redis inspection self-check only, matching every prior phase.

## Follow-up

- [ ] `secrets.py`'s pattern set is a starting set; widen it opportunistically (cloud provider keys beyond AWS, JWTs, database connection strings) if a real gap is found during the demo, logged to `decisions.md` when it happens rather than speculatively now.
- [ ] Strike window expiry (Phase 3.1) applies to these three new categories exactly the same as the existing three; no separate follow up needed beyond 3.1 itself.
