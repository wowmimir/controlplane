# 6.2. README + Demo Video Script

**Date**: 2026-08-25
**Status**: Accepted

## Summary

Phase 6 (Demo Polish) has one milestone left after 6.1's seed script. `STATUS.md` names 6.2 as: "README + Demo Video Script — Per the competition deliverables." Cross-referencing `STATUS.md`'s own Known Follow-ups turns up a third piece already explicitly assigned to this same milestone: a `.env.example` documenting `DATABASE_URL`, `REDIS_URL`, `MODEL_API_BASE_URL`, `MODEL_API_KEY`, since a fresh clone currently has no way to learn the variable names. This spec designs all three human-facing deliverables together, since they share one audience (a competition judge or anyone cloning the repo cold) and reference the same underlying facts (the endpoint contract, the tech stack, `scripts/seed_demo.py`): a root `README.md`, a root `.env.example`, and `docs/demo-script.md` — a presenter's script for recording the hackathon demo video. It writes no application code.

## Context

Read this session (not guessed): the current `STATUS.md` in full (all Session Handoff Notes plus the milestone table and Known Follow-ups), `forks.md` in full, and `scripts/seed_demo.py`'s docstring and scenario functions (already built by 6.1). Grepped `decisions.md` for any prior mention of README/demo-video/deliverables — none found, confirming this is genuinely new ground, not a decision already made elsewhere. Confirmed via a repo listing: no `README.md` exists at the repo root, no `.env.example` exists anywhere, and `docs/` currently holds only `docs/reviews/` (two `/check review` output files from Phases 1 and 2) — there is no existing convention for a demo script's location, so this spec settles it.

Facts that directly shape this design:

- **The real `.env` already holds working values** for all four variables this spec's `.env.example` must document (`DATABASE_URL` — a Neon Postgres connection string in `postgresql+asyncpg://...?ssl=require` shape, per 0.2's entry; `REDIS_URL` — an Upstash connection string, per 0.3; `MODEL_API_BASE_URL` — the local Ollama-compatible base, per 1.4; `MODEL_API_KEY` — read via `os.environ.get(...)`, not `os.environ[...]`, so it is optional, per 1.4). `.env` is already `.gitignore`d (fixed as part of 0.2). None of this spec's new files may contain real values from it.
- **The full, real quickstart path** a fresh clone needs, confirmed against what each phase actually built: `uv sync` (project uses `uv`, confirmed by `pyproject.toml`/`uv.lock`), copy `.env.example` to `.env` and fill in real values, `uv run uvicorn app.main:app --reload` (backend on `:8000`), `cd console && npm install && npm run dev` (frontend on `:5173`, per 5.1's Vite scaffold and `CORSMiddleware`'s allowed origin), then `uv run python scripts/seed_demo.py` to populate the console before looking at it.
- **The API contract worth showing in a README**: `POST /v1/chat/completions`, OpenAI-shaped body, optional `X-Workload-Id`/`X-Session-Id` request headers (both echoed back as response headers, per 1.2), a `403` with an OpenAI-style `{"error": {"type", "code", "message"}}` envelope on any block. A single `curl` example demonstrating a clean call and a PII-blocked call gives a reader the whole shape without reading code.
- **Known, real limitations worth stating plainly, not hidden** (a competition README should be honest about scope, not just capability): no streaming — buffered responses only (Fork #4, "Out of scope for the Round 2 prototype"); escalation-only blocks (3.2's session-ledger-driven `session_escalated` blocks) write no `Execution`/`Finding` row at all, so they are invisible to the dashboard, live feed, and session drilldown — a gap documented repeatedly in 5.1/5.3/5.4's own docstrings, not something to paper over in the README. The pre-existing stuck port-8000 dev-process issue that recurs across this project's own self-checks (2.4 through 6.1) is a symptom of *this development environment's* tooling, not a fact about the shipped app — it does not belong in a README aimed at a fresh clone.
- **`scripts/seed_demo.py` already exists and is proven reliable** (6.1, `Accepted`): it narrates four scenarios (clean pass, cheap-tier block, two-turn ledger escalation, async expensive-tier finding) against a running instance and deliberately leaves its traffic in place so the console has real data to show. This is the natural backbone for a demo video script — the video doesn't need a fifth, newly-invented narrative; it needs a shot list built around what this script already proves live, plus a tour of the four console pages (5.1 Dashboard, 5.2 Workloads, 5.3 Session Drilldown, 5.4 Live Feed) that render the results.
- **No `docs/` convention exists yet for a human-facing (non-review) deliverable.** `docs/reviews/` is agent-generated review output (`/check review`), a different kind of artifact than a presenter's script. Placing the demo script under `docs/` anyway (a new `docs/demo-script.md`, not a new top-level directory) keeps human-facing documentation in one place without inventing a second doc root, and keeps it out of `.agents/`, which is the agent's own workflow state (specs, status, decisions), not competition-submission material.

## Requirements

**User stories**:
- As a competition judge or anyone cloning this repo cold, I want a README that tells me what this project is, how to run it, and what its known limits are, so I can evaluate it without reading source code first.
- As the person recording the demo video, I want a written shot list mapped to the four scenarios `scripts/seed_demo.py` already proves reliable, so I don't have to improvise narration or re-derive which console page shows which result.
- As anyone setting up a fresh clone, I want to know the exact environment variable names this app needs, without grepping `app/` for `os.environ` calls.

**Acceptance criteria**:
- **AC-1 (README exists and covers the essentials)**: `README.md` at the repo root includes, at minimum: a one-paragraph project description, a quickstart (`uv sync` → copy `.env.example` → run backend → run frontend → run the seed script), a link/reference to `.env.example` for configuration, a short architecture summary (the proxy shape, the three evaluator tiers, the six-category taxonomy), one worked `curl` example against `/v1/chat/completions`, and a "Known limitations" section naming no-streaming and the escalation-block console-visibility gap explicitly.
- **AC-2 (README contains no real secrets)**: `README.md` contains no real connection strings, API keys, or other values copied from the real `.env` — only placeholder/example values, consistent with `.env.example` below.
- **AC-3 (`.env.example` exists and is complete)**: a root `.env.example` documents exactly the four variables `STATUS.md`'s Known Follow-up names (`DATABASE_URL`, `REDIS_URL`, `MODEL_API_BASE_URL`, `MODEL_API_KEY`), each with a one-line comment explaining its purpose and a placeholder value in the correct shape for its real backing service (Postgres/Neon-style, Upstash-style, an Ollama-compatible base URL, an optional key) — no real values.
- **AC-4 (`.env.example` is a template, not a config that could be run)**: copying `.env.example` to `.env` verbatim must not silently point the app at a real, working shared resource — every placeholder value must be obviously non-functional (e.g. `changeme`, `your-project.upstash.io`), not a disguised real credential.
- **AC-5 (demo script exists and covers all four scenarios)**: `docs/demo-script.md` contains a narrated shot for each of `scripts/seed_demo.py`'s four scenarios (clean pass, cheap-tier block, two-turn escalation, async expensive-tier finding), stating for each: what to say, what command or action to run, and what result on screen proves the point.
- **AC-6 (demo script tours the console)**: `docs/demo-script.md` includes a shot for each of the four console pages (Dashboard, Workloads, Session Drilldown, Live Feed), pointing out what each one shows and, where relevant, which of the four seeded scenarios it should be showing data from.
- **AC-7 (demo script settles the live-vs-pre-seeded choice)**: `docs/demo-script.md` explicitly states whether the presenter runs `scripts/seed_demo.py` live on camera or beforehand (see Options below), rather than leaving it ambiguous for the presenter to guess at while recording.
- **AC-8 (no application code touched)**: this milestone changes no file under `app/`, `console/src/`, or `scripts/` — it is strictly new documentation plus one new config template.

## Options considered

### Option 1: Three separate files — root `README.md`, root `.env.example`, `docs/demo-script.md` (recommended)

Each deliverable in the location a reader would naturally look for it: a README at the root (where every reader looks first), `.env.example` beside the real `.env` it templates, and the demo script under the existing `docs/` directory.

**Pros**: Matches universal convention for the first two (a root README and a root `.env.example` are the standard locations in virtually every project, including ones this hackathon's judges will have seen). Reuses the existing `docs/` directory rather than inventing a new top-level folder for one file. Three independent files means `/develop` can build and self-check each one without the others being in a half-finished state blocking review.
**Cons**: None significant — this is the unsurprising, low-risk choice for all three.

### Option 2: Fold the demo script into the README itself (a "Demo" section) instead of a separate `docs/demo-script.md`

**Pros**: One fewer file; a judge reading the README sees the demo narrative without a second click.
**Cons**: A presenter's shot list (what to say, what to click, in what order, timed to a recording) is a different kind of document from a project README (what is this, how do I run it) — mixing them makes the README longer and harder to skim for the "just tell me how to run it" reader, and makes the shot list harder to use standalone while actually recording (scrolling a long README mid-take vs. having a dedicated, short reference open). `STATUS.md`'s own milestone name ("README **+** Demo Video Script") already treats them as two things.

### Option 3: Put the demo script in `.agents/` alongside specs/status/decisions instead of `docs/`

**Pros**: Keeps every markdown artifact from this build in one place.
**Cons**: `.agents/` is explicitly the agent's own workflow state per `AGENTS.md` Section 2 (`STATUS.md`, `forks.md`, `decisions.md`, `prompts/`) — a human-facing competition deliverable doesn't belong mixed in with the agent's process files, and a judge has no reason to know to look in `.agents/` for it. `docs/` is already the project's designated home for non-`.agents/` documentation (`docs/reviews/`).

## Decision

**Chosen option**: Option 1 — three separate files: `README.md` (root), `.env.example` (root), `docs/demo-script.md`.

## Rationale

Option 2 is eliminated because a README's job (orient a cold reader, get them running) and a demo script's job (drive a specific, timed recording session) have different shapes and different readers-in-the-moment, and the milestone's own name already treats them as two deliverables. Option 3 is eliminated because `.agents/` is reserved for this project's own agent workflow state per `AGENTS.md`, and a competition-facing document has no reason to live where only this build's own tooling looks. Root-level placement for `README.md` and `.env.example` isn't a real decision so much as universal convention — deviating from it would only confuse readers for no benefit.

## Feature design

**New files**: `README.md` (root), `.env.example` (root), `docs/demo-script.md`. No changes to any existing file.

**`README.md` outline**:
1. Title + one-paragraph description: an AI-governance proxy that sits in front of a model API, evaluating requests and responses against a six-category policy taxonomy (PII, hallucination, toxicity, bias, prompt injection, custom policy) across three evaluator tiers (cheap/sync, medium/stubbed, expensive/async LLM-judge), with a session-level risk ledger that can escalate and block based on accumulated behavior, not just single-turn content.
2. Architecture at a glance: the request/response flow (`AI Application → ControlPlane → Model API`, both legs, per Fork #4), the three tiers, the ledger's decay/strike/escalation math (referencing `forks.md` Fork #3 by name, not restating the exact constants — avoid the README drifting out of sync with the one locked source of truth).
3. Quickstart: `uv sync`; copy `.env.example` to `.env` and fill in real values; `uv run uvicorn app.main:app --reload` (backend, `:8000`); `cd console && npm install && npm run dev` (frontend, `:5173`); `uv run python scripts/seed_demo.py` to populate the console with real traffic before looking at it.
4. Configuration: a short table naming the four env vars and pointing at `.env.example` for details, not duplicating the comments there.
5. API example: one `curl` for a clean `/v1/chat/completions` call and one for a PII-blocked call, showing the `403`/`error` envelope shape.
6. Console tour: one line per page (Dashboard, Workloads, Session Drilldown, Live Feed) with what it shows.
7. Known limitations: no streaming (Fork #4); escalation-only blocks aren't visible in the dashboard/feed/drilldown (no durable `Execution`/`Finding` row); this is a hackathon MVP (no auth on workload/session headers, no automated test suite, per `AGENTS.md` Section 8 — state plainly, don't apologize at length).
8. Project structure: a short tree/description of `app/`, `console/`, `scripts/`, `.agents/` (what each top-level directory is, one line each) so a reader can navigate without guessing.

**`.env.example` content** (all placeholder, no real values):
```
# Postgres connection string (Neon or any Postgres-compatible host).
DATABASE_URL=postgresql+asyncpg://user:password@host/dbname?ssl=require

# Redis connection string (Upstash or any Redis-compatible host). Backs the
# session risk ledger (15-minute TTL).
REDIS_URL=rediss://default:password@your-project.upstash.io:6379

# Base URL of an OpenAI-compatible model API. This project was built and
# tested against a local Ollama instance.
MODEL_API_BASE_URL=http://localhost:11434/v1

# Optional. Only needed if MODEL_API_BASE_URL points at a provider that
# requires one (e.g. a hosted API, not local Ollama).
MODEL_API_KEY=
```

**`docs/demo-script.md` outline**:
1. Prerequisites: backend + frontend running, `.env` configured, and (per the Decision below) either "run `scripts/seed_demo.py` now, before recording" or "run it live in the recording."
2. Shot 1 — Introduce the project (10-15s): a sentence on what ControlPlane does, on camera or voiceover, no UI yet.
3. Shot 2 — Clean pass: run/point at scenario 1's request and response; say what proves it's a real model call.
4. Shot 3 — Cheap-tier block: run/point at scenario 2; call out the `403`/`pii` in the response, faster than a full model round trip (the "fails fast" story).
5. Shot 4 — Ledger-driven escalation: run/point at scenario 3's two turns; explicitly narrate that turn 2's content is clean and it's still blocked — the defensibility story from Fork #3/5.3.
6. Shot 5 — Async expensive-tier finding: run/point at scenario 4; narrate the request releasing immediately (`200`), then cut to the session drilldown a few seconds later showing the judge's finding land — the "governance keeps working after release" story.
7. Shot 6 — Console tour: Dashboard (aggregate counts/charts), Workloads (policy profiles), Session Drilldown (the "why was this blocked" view, reusing the escalated session from Shot 4), Live Feed (real-time view, ideally captured while a request is in flight so a row visibly appears).
8. Closing: one line on what's next / known limitations, matching the README's own "Known limitations" section so the video doesn't overclaim.

**Live-vs-pre-seeded choice (AC-7)**: recommend running `scripts/seed_demo.py` live during Shot 3-5 rather than beforehand — the script's own narration (printed to the terminal) doubles as on-screen proof for the audience that this is real traffic, not staged data, and 6.1's self-check already confirmed all four scenarios pass reliably within one run. The one accepted risk (6.1's own Follow-up): the async finding in Shot 5 can take up to ~45 seconds to land, so the script should plausibly be started *before* the Dashboard/Workloads shots (6, first two sub-shots) and revisited for Session Drilldown once the poll reports success — sequencing the recording so the wait isn't dead air. This is a recommendation, not a hard requirement; `docs/demo-script.md` should state it as the chosen approach (satisfying AC-7) while noting the pre-seeded fallback (run the script minutes before recording, narrate from already-populated data) if a live take doesn't go cleanly.

**Value sourcing** (per artifact → content → source):
| Artifact | Content | Source |
|---|---|---|
| README architecture summary | tier names, ledger math description | `forks.md` Fork #2, #3, #4 (referenced, not restated verbatim, so the README can't drift from the locked source) |
| README quickstart commands | exact commands | `pyproject.toml`/`uv.lock` (confirms `uv`), 5.1's Vite scaffold (confirms `npm install`/`npm run dev`), `scripts/seed_demo.py`'s own docstring (confirms its invocation) |
| README known limitations | the two limitations named | Fork #4 ("Streaming: Out of scope"), 5.1/5.3/5.4's own docstrings (the escalation-block visibility gap) |
| `.env.example` variable names | the four names | `STATUS.md`'s own Known Follow-up line (already names all four) |
| `.env.example` placeholder shapes | Neon/Upstash/Ollama-style placeholders | 0.2/0.3/1.4's Session Handoff Notes (describe the real shapes used, without copying real values) |
| Demo script's four scenario shots | what to run, what proves it | `scripts/seed_demo.py`'s own scenario functions and their assertions (6.1, already built and proven) |
| Demo script's console tour | what each page shows | 5.1/5.2/5.3/5.4's own specs/docstrings |

**Security model**: unchanged — no new endpoints, no new code path. The only security-relevant requirement is negative: `.env.example` and `README.md` must contain zero real credentials (AC-2, AC-4).

**Critical test scenarios** (each maps to an acceptance criterion above): a fresh reader (or the engineer, role-playing one) follows the README's quickstart from a clean checkout and reaches a working local instance without consulting any other file; `.env.example` copied to a scratch `.env` is confirmed to contain no functioning credentials; `docs/demo-script.md` is read alongside a live run of `scripts/seed_demo.py` and the console to confirm every named shot actually shows what the script says it will.

## Consequences

**Positive**:
- Closes the last milestone in the build (`STATUS.md`'s full Phase 0-6 checklist complete).
- A fresh clone has everything it needs to run the project and understand its scope without reading `app/` source or `.agents/` build history.
- The demo video script converts 6.1's already-proven scenarios directly into a recordable shot list, so recording the video requires no new improvisation.

**Negative / tradeoffs**:
- The demo script's live-vs-pre-seeded recommendation is exactly that — a recommendation for whoever actually records the video to follow or override in the moment; this spec cannot guarantee a live take goes cleanly (the same accepted, inherited risk 6.1 already flagged for the async scenario).
- README "Known limitations" necessarily repeats facts already documented in code comments/specs (5.1/5.3/5.4's docstrings, Fork #4) — an intentional, small duplication, since a judge reading only the README should not have to cross-reference `app/routers/console.py`'s docstring to learn about the escalation-visibility gap.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-check described above (a real quickstart run-through, a real recorded-or-dry-run of the demo script's shots), not a test file.
- No new dependency.
