## Summary

This branch completes the governance pipeline (medium stub, LLM-judge expensive tier, toxicity/bias/secrets evaluators), the Fork #3 ledger with escalation and fail_mode handling, Postgres audit persistence, the four-page React console, and the demo tooling. The engineering discipline is genuinely high: every non-obvious choice is written down in `decisions.md` with live evidence, the code comments cite the spec that ratified them, and the error-envelope taxonomy is consistent across five distinct failure classes. I found no blockers.

The headline issues are (1) a `flush()`-without-`commit()` window that silently discards an Execution audit row when an internal error hits a `fail_open` workload, (2) a non-atomic read-modify-write on the Redis ledger that the async expensive tier is *designed* to race, (3) the console presenting the never-expiring Postgres ledger mirror as live escalation state, (4) three `Workload` policy fields that are editable and documented but read by nothing, and (5) a README quickstart that cannot produce a working console. Nothing here is architectural — all five are contained fixes.

I deliberately did **not** re-flag the items the project has already ratified in writing: unauthenticated `X-Session-Id`/`X-Workload-Id`, the never-closed `httpx.AsyncClient`, block-only Fork #3, escalation blocks writing no Execution row, the medium-tier permanent stub, the pii/toxicity/bias regex tradeoffs, the double-decay quirk, and 3.3's explicitly-ratified "a detected violation can slip through under `fail_open` if the Redis write fails right after the Finding commit" edge case.

## Major

### 🟠 A response-side internal failure under `fail_open` rolls back the Execution audit row, `app/routers/chat.py:109-134`

**Problem**: `execution` is `db.add()`ed and `await db.flush()`ed at lines 117-118, but never committed at that point. The first `commit()` for that row happens *inside* `_run_response_side_interception` (line 426 on the clean path, line 472 on the violation path). If anything in that function raises before its commit — `run_cheap_tier` throwing, or the commit itself failing — the exception handler at line 124 sets `blocked = None` for a `fail_open` workload and the handler returns `parsed`. `Depends(get_db)`'s `async with async_session()` then closes the session without committing, rolling the flushed INSERT back.

The mirror-image case on the request side is worse in a different way: if `apply_ledger_update` (line 361) throws after the Finding commit at line 359, `fail_open` falls through to `call_model` and creates a *second* `Execution` row at line 109 for the same turn — one row carrying the violation, one carrying the model response.

**Why it matters**: 4.2 exists specifically so that "a request-side-clean request whose model call then fails left zero Postgres rows" can't happen (its own comment, lines 88-93). This path re-opens exactly that hole for the *successful* case: a response that was computed by the model and released to the caller leaves no trace in the audit store at all, and the background expensive-tier task then fails on `db.get(Execution, ...) → None`. For a product whose whole claim is a durable audit trail, a released turn that is invisible is the one thing that must not happen silently. 3.3's spec ratified the *fail-open-releases-the-response* behavior; it did not consider that the audit row disappears with it.

**Suggested fix**: commit the `Execution` immediately after `db.flush()` at line 118 (before entering response-side interception), so the row exists regardless of what happens next; the later `execution_risk_score` assignment is an UPDATE either way. For the request-side duplicate, have `_run_request_side_interception` return its already-built `403` from a variable that survives a later Redis failure, rather than letting the whole function raise after the decision was made.

### 🟠 `apply_ledger_update` is a non-atomic read-modify-write that the async judge is designed to race, `app/redis_client.py:97-139`

**Problem**: The function does `get_ledger()` (line 120), mutates the dict in Python, then `set_ledger()` (line 138) — a plain GET/SET with no `WATCH`/`MULTI`, no Lua script, and no lock. Last writer wins and the loser's update vanishes entirely.

**Why it matters**: this is not a theoretical race. `_run_expensive_tier_task` (`chat.py:484`) is scheduled to run *after* the response releases, and a conversational client sending its next turn immediately will have that turn's `_run_request_side_interception` → `get_ledger` interleave with the background task's read-modify-write on the same key. When they collide, either the judge's hallucination strike or the new turn's decay/strike silently disappears. The lost update is invisible — no log, no error — and it weakens the exact mechanism (`cumulative_risk` accumulation and strike counting) that the product's escalation story rests on. Multiple concurrent turns on one session hit the same problem.

**Suggested fix**: move the whole read-modify-write into a Redis Lua script (`EVAL`, preserving the TTL via `SET ... EX`), or wrap it in a short-lived per-session `SET NX` lock. Redis-py's `redis.asyncio` supports both without a new dependency. Given the ledger is the product's core mechanism, this is worth the ~20 lines.

### 🟠 The console reports the never-expiring Postgres ledger mirror as live escalation state, `app/routers/console.py:226-228` and `:296-298`, `console/src/SessionDetail.tsx:186-202`

**Problem**: `escalated`, `cumulative_risk`, and `strikes` in `/sessions` and `/sessions/{id}` are computed from the `Session` row, which `_sync_session_ledger` only writes when a turn actually happens. The Redis ledger that *actually* gates traffic has a 15-minute TTL (`LEDGER_TTL_SECONDS`). A session that trips escalation and then goes quiet keeps `cumulative_risk = 0.95` in Postgres forever, while its Redis key expires and the next turn on that session reads `default_ledger()` and sails straight through.

`SessionDetail.tsx:191-200` states this as fact on screen: *"This session is escalated … new turns on this session block immediately."* Fifteen minutes after the last turn, that sentence is false.

**Why it matters**: the session drilldown is the console's designated "why was this blocked" view — the one surface an auditor or a demo audience is asked to trust. Asserting a currently-untrue operational fact there is worse than showing nothing. The `/sessions` list has the same problem in its `Escalated` pill with no caveat at all. (5.3's "read Postgres, never Redis" decision is fine for *history*; `escalated` is a claim about *now*, which is the one thing Postgres can't answer here.)

**Suggested fix**: don't change the data source — change the claim. `ttl_expires_at` is already on both payloads: when it is in the past, render the ledger block as "last known state as of <time>; the live ledger has since expired" and suppress the escalated banner's "new turns block immediately" sentence. Alternatively expose a `ledger_live: bool` on the schema derived from `ttl_expires_at > now()`.

### 🟠 `policy_profile` and `cost_budget_per_request` are dead configuration, but README/console/demo script present them as working controls, `app/models/workload.py:19-23`, `docs/demo-script.md:82`, `README.md:94,105`

**Problem**: grepping the whole `app/` tree, `Workload.policy_profile` appears only in the model, `console.py`'s serialization, and `seed.py` — nothing in the evaluation path ever reads it. `cost_budget_per_request` is identical. `latency_budget_ms` is read exactly once (`chat.py:436`) and handed to `run_medium_tier`, which is a permanent stub that ignores all three of its arguments. So `fail_mode` is the only `Workload` field that changes any behavior.

Meanwhile: `README.md:94` says an `X-Workload-Id` header "selects a policy profile"; `README.md:105` describes the Workloads page as editing "policy profiles (`strict` / `balanced` / `fast`), latency and cost budgets, fail mode"; and `docs/demo-script.md:82` instructs the presenter to point at the Workloads page and say **"the policy profile that governed all of the above."** That line is false on camera.

**Why it matters**: this is the one place in the branch where the code and the documentation genuinely disagree, and the disagreement is scripted into the demo narration. It also gives an operator a `strict`/`fast` selector that does nothing, which is the kind of thing that gets discovered at the worst possible moment. Note this is *not* a Fork violation — nothing locked says these fields must be enforced in this build; the problem is purely that the docs claim they are.

**Suggested fix**: add a bullet under README's "Known limitations" saying `policy_profile`, `latency_budget_ms`, and `cost_budget_per_request` are recorded per workload but not yet enforced by the evaluation path (only `fail_mode` is); rewrite `docs/demo-script.md:82` to say the Workloads page is where a real deployment *would* register per-application policy, without claiming it governed the run just shown; and consider a small "not yet enforced" note on those three fields in `WorkloadForm.tsx`.

### 🟠 The README quickstart cannot produce a working console, `README.md:42-52`, `console/.gitignore:16`

**Problem**: `console/src/api.ts:11` reads `import.meta.env.VITE_API_BASE_URL` and uses it as the origin for every request. That variable lives only in `console/.env`, which is git-ignored (`console/.gitignore` line 16, `.env`). There is no `console/.env.example`, and `VITE_API_BASE_URL` is mentioned nowhere in `README.md` or the root `.env.example` — the Configuration table lists only the four backend variables.

A fresh clone that follows the quickstart verbatim (`cd console && npm install && npm run dev`) gets `undefined` interpolated into every URL, so every fetch resolves against `localhost:5173/undefined/api/console/...` and all four console pages render their error state.

**Why it matters**: the README is 6.2's actual deliverable, and this is the first thing a judge or teammate will run. It fails at step 4 of 5 with a confusing error rather than an obvious missing-config message.

**Suggested fix**: add a committed `console/.env.example` containing `VITE_API_BASE_URL=http://localhost:8000`, add a `cp .env.example .env` line for the console in the quickstart, and add the variable to the Configuration table. Optionally default it in `api.ts` (`?? 'http://localhost:8000'`) so a missing file degrades gracefully.

## Minor

### 🟡 Editing a workload silently destroys unknown metadata keys, `console/src/components/WorkloadForm.tsx:58-77`

`buildMetadata()` reconstructs the metadata object from only the three fields the form knows about (`name`, `geography`, `industry`) and the PATCH body always includes it. The API accepts an arbitrary `dict` (`WorkloadCreate.metadata: dict | None`) and `types.ts:24-29` explicitly types it with `[key: string]: unknown`, so any key set via the API and then edited through the UI is dropped — and if all three known fields are blank, `metadata` is sent as `null`, wiping the object outright. Fix: spread `workload?.metadata` as the base in `buildMetadata()` and overwrite only the three managed keys.

### 🟡 `poll()` is invoked as a side effect inside a state updater, `console/src/LiveFeed.tsx:103-109`

`setPaused((prev) => { const next = !prev; if (!next) poll(); return next })` fires a network request from inside the reducer. `main.tsx:8` enables `StrictMode`, which double-invokes updaters in development, so pressing Resume sends two feed requests. Move the `if (paused) poll()` into the click handler after `setPaused(false)`, or into an effect keyed on `paused`.

### 🟡 The first poll highlights every row as "just arrived", `console/src/LiveFeed.tsx:56,66-70`

`knownIdsRef` starts as an empty `Set`, so on the initial load all 25 rows are classified as `arrived` and the whole table flashes the accent highlight for a second. Seed `knownIdsRef` from the first successful response without emitting a highlight (e.g. a `firstLoadRef` guard).

### 🟡 The highlight `setTimeout` is never cleared, `console/src/LiveFeed.tsx:77-83`

Each poll that finds new rows schedules a bare `setTimeout` that is not tracked in a ref and not cleared by the effect's cleanup at line 100. Navigating away within a second leaves a timer holding a closure over `setNewIds`. Harmless in React 19 but inconsistent with the interval cleanup right next to it — track the id and clear it on unmount.

### 🟡 `_extract_number` concatenates every digit in the reply, `scripts/seed_demo.py:111-118`

`re.sub(r"[^0-9]", "", text)` over the whole response means a reply like `"4837 × 6293 = 30438241"` parses as `4837629330438241`, which will never equal `correct`. The script then prints "wrong answer confirmed" and commits to polling for a judge finding that may never land, burning the full 45-second budget on a run where the model was actually right. The prompt asks for a bare number, but the whole point of the retry loop is that the model doesn't always comply. Fix: match the last (or longest) contiguous digit run with a comma/space-tolerant regex rather than stripping everything.

### 🟡 `MODEL` is hardcoded in the demo script with no override, `scripts/seed_demo.py:41`

`MODEL = "minimax-m3:cloud"` while `README.md:62` invites the user to point `MODEL_API_BASE_URL` at any OpenAI-compatible provider. Anyone who does gets four failed scenarios with a 502 and no hint why. Add a `--model` flag alongside `--base-url` (AC-8's portability rationale applies identically).

### 🟡 One message can post multiple strikes in the same category at the same instant, `app/routers/chat.py:361-365`, `app/redis_client.py:129-131`

`strikes_input` carries one entry per Finding, and every cheap-tier hit is `CONFIDENCE = 0.95 > STRIKE_THRESHOLD`, so a single message containing three email addresses appends three strike events with an identical `turn` and `ts` — instantly satisfying `any(strikes[category]) >= 3`. STATUS.md's own 6.2 entry records this happening (`strikes.prompt_injection: 2` from two patterns matching one turn-1 message). This is a faithful reading of Fork #3's literal wording, so I'm flagging the *effect*, not the rule: the "last 5 turns OR last 2 minutes" window is meaningless when all three strikes land in one turn, and the escalation then reads as "accumulated bad behavior" when it was one message. Worth a line in `decisions.md` at minimum; the cheap fix if you ever want it is to de-duplicate `strikes_input` by category per turn.

### 🟡 The console write API has no authentication, `app/routers/console.py:165-198`

`POST /api/console/workloads` and `PATCH /api/console/workloads/{id}` accept unauthenticated writes from anything that can reach the port. This is distinct from the already-accepted header-spoofing gap: it lets a caller flip a workload to `fail_open`, which changes how ControlPlane behaves when its own internals fail. I'm not asking for auth in a hackathon build — but README's "Known limitations" names only the header gap, so this one should be named there too rather than left implicit.

### 🟡 The default-workload lookup is unchecked, `app/routers/chat.py:166`

`return await db.get(Workload, DEFAULT_WORKLOAD_ID)` can return `None` (seed failed, row deleted directly in the DB), and the caller immediately dereferences `workload.workload_id` at line 69 → `AttributeError` → raw 500. The explicit-id branch two lines below already handles the `None` case properly. Mirror it with a clear 500/503 that says the default workload is missing.

## Strengths

- **The decision hygiene is the best part of this branch.** `decisions.md` entry 115 (why the fabrication prompt was replaced with verified-wrong multiplication, with the model's verbatim refusal quoted) and 3.3's spec section 25 (surfacing and *naming* the fail-open edge case rather than quietly shipping it) are the kind of records that make a codebase reviewable by someone who wasn't there. Several findings above were things I could rule out in seconds because the reasoning was already written down.
- **`app/model_client.py:84-116`** — field-by-field construction with a targeted exception tuple, so a malformed upstream body becomes a clean `502` instead of an opaque `ValidationError`/500. The comment explaining *why* it isn't `model_validate` is exactly the right kind of comment.
- **The error-envelope taxonomy is genuinely well-designed**: five distinct `type`/`code` pairs (`400` misconfiguration, `403` policy, `403` escalation, `502` upstream, `503` internal) that a client can actually branch on, all with fixed generic caller-facing text and the real detail logged server-side only. `_model_error_response`'s docstring gets the information-disclosure reasoning right.
- **`_is_blocked`'s single `evaluator_tier != expensive` definition** is reused verbatim across `/summary`, `/sessions/{id}`, and `/feed` — three surfaces that could easily have drifted into three subtly different answers to "was this blocked".
- **The `turn_anchor`/`ts_anchor` threading** (`chat.py:428,440-448` → `redis_client.py:127-131`) so a late-arriving async finding is stamped at the originating turn rather than whenever the judge finished, while pruning still compares against the live turn — that is a subtle, correct piece of design that a lot of implementations would get wrong.
- **Both charts ship an `sr-only` data table** alongside the `aria-hidden` SVG. Unprompted accessibility work in a hackathon build is rare.
- **No secrets in the diff.** `.env.example` uses obviously-inert placeholders and both `.gitignore`s cover the real files.

## Test coverage

`TESTS = none-by-design` per `AGENTS.md` Section 8 — no coverage findings raised, and the absence of a suite is not counted against this branch. The substitute gate here is `tsc -b` plus live self-checks against real Neon/Upstash/Ollama, and STATUS.md documents those per milestone in real detail (which endpoints, which assertions, which rows were verified). That is a credible gate for most of this branch.

Two of the findings above are specifically things that gate cannot catch, and are worth exercising manually before merge:

- **Major #1** (Execution rollback under `fail_open`) — 3.3's self-check forced an exception and confirmed the `200`/`503` status codes, but did not check whether the Postgres row survived. Re-run that forced-exception script and then query `execution` for a row belonging to that session; today there won't be one.
- **Major #2** (ledger race) — needs two concurrent requests on one session, or one request whose expensive-tier task is still running when the next turn arrives. Nothing in `seed_demo.py` sends overlapping traffic, so this has never been exercised. A two-thread variant of scenario 4 would surface it.

**Major #5** (missing `VITE_API_BASE_URL` documentation) is invisible to every existing check because `console/.env` exists locally on the author's machine; it only reproduces from a clean clone.
