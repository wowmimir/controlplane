# 4.2. Execution Persistence

**Date**: 2026-08-24
**Status**: Accepted

## Summary

`STATUS.md` describes 4.2 as: *"Every `Execution` logged with operational signals (tokens, latency, retries, tool_loop_count) regardless of whether it was blocked."* Most of this was already true by the time 4.2 was reached — 1.3, 1.4, and 1.5 already log an `Execution` row on every content block and every completed model call. Investigation found one genuine, previously-flagged gap: a model-call failure (`502`) left zero `Execution` rows, meaning a request that ControlPlane fully evaluated and forwarded could leave no audit trail at all if the upstream model errored. That gap is fixed here. Two other candidate gaps were investigated and deliberately NOT changed, per the user's explicit scoping: the escalation-block paths (already a ratified 3.2 decision) stay as-is, and `retries`/`tool_loop_count` stay at their `0` default since no retry or tool-calling logic exists anywhere in the app to produce a real value.

## Context

Verified directly against the current code (`app/routers/chat.py`, pre-fix, plus `app/models/execution.py` and `app/model_client.py`) for this spec:

- **Request-side cheap-tier block** (`_run_request_side_interception`, chat.py ~298-316): `Execution` created and committed, `tokens`/`latency_ms` left `None` (no model call happened), `execution_risk_score` real, `retries=0`/`tool_loop_count=0` (defaults). Unchanged, matches 4.2's "regardless of whether it was blocked."
- **Model-call success** (`chat_completions`, chat.py ~92-101): `Execution` created with real `tokens`/`latency_ms` (measured inside `call_model`, `app/model_client.py:72-79`), `retries=0`/`tool_loop_count=0` literal, `execution_risk_score` set later by the response-side scan. Committed inside `_run_response_side_interception` (either the clean branch, chat.py ~382, or the violation branch, chat.py ~427). Unchanged.
- **Model-call failure (`502`)** (`chat_completions`, the `except ModelCallError` branch, previously chat.py 86-90): previously created **no `Execution` row at all**. `decisions.md`'s 1.4 entry names this explicitly: *"Phase 4.2 is the explicit future owner of deciding whether failed attempts also deserve a row."* Fixed by this milestone: wraps `call_model()` with `time.perf_counter()` (the same measurement style `model_client.py` already uses internally for its own success path) and, on `ModelCallError`, creates + commits one `Execution` row before returning the `502` — `latency_ms` real (elapsed time up to the failure), `tokens`/`execution_risk_score` left `None` (no usable model response exists), `retries=0`/`tool_loop_count=0`.
- **Response-side block/clean/escalation** (`_run_response_side_interception`, chat.py ~374-433): all reuse the existing `Execution` row from the model-call success path; `execution_risk_score` set to `0.0` (clean) or the max confidence (violation); committed either way. Unchanged.
- **Expensive-tier async finding** (`_run_expensive_tier_task`, chat.py ~467-496): reuses the existing row, updates `execution_risk_score`, commits in its own DB session. A clean verdict touches nothing. Unchanged.
- **Escalation blocks** (request-side pre-check, chat.py ~287-290; response-side clean-branch check, chat.py ~384-388): create no `Execution` row. This was already a ratified 3.2 decision ("no turn-specific evidence to attach — the block reason is the session's accumulated state, not this turn's content"), explicitly logged as *"accepted, logged as a Phase 4 Follow-up in the spec"* for possible revisit. **Ratified with the user this session: leave as-is.** No model call happens and no content is scanned on this path, so there is no real operational signal (no tokens, no latency) to log; the Redis ledger already records why the session is escalated. Reconfirmed, not reopened.
- **Two `400` paths** (`_resolve_workload`, unknown `X-Workload-Id`, chat.py ~153; `_resolve_session`, cross-workload conflict, chat.py ~176-182): create no `Execution` row. Out of scope — no `Session` row exists yet at this point in the request, so there's no valid FK target and nothing resolved to log against. Same reasoning as 1.2's original decision; not revisited here.
- **`retries`/`tool_loop_count`**: grepped the entire `app/` tree — no retry logic, no tool-calling loop exists anywhere in the codebase. `call_model()` makes exactly one HTTP POST per invocation, no wrapper. Every `Execution` row ever created uses the column default (`0`) or an explicit literal `0`; nothing sets either field to a non-zero value, because nothing in the app can produce a retry or a tool-call. `app/models/execution.py` (lines 28-29) already defines both as `NOT NULL, default=0` — the schema is already correct and complete for a codebase with no such logic. Building real retry/tool-loop logic to give these fields something to record would be new, unrequested functionality — the same scope creep already declined for Fork #3's "regenerate/route" (`decisions.md` line 75) — not what "persistence" means.

## Requirements

**Verification criteria** (already met by prior milestones, or fixed here; this documents that they are met, not a build to perform):

- **AC-1**: every successful model call produces an `Execution` row with real `tokens`/`latency_ms`. Met — 1.4, unchanged.
- **AC-2**: every request-side or response-side content block produces an `Execution` row (real operational values where a model call happened, `None` where it didn't). Met — 1.3/1.5, unchanged.
- **AC-3**: a model-call failure (`502`) produces an `Execution` row with a real `latency_ms` and `tokens`/`execution_risk_score` left `None`. Not met before this milestone — fixed here.
- **AC-4**: `retries`/`tool_loop_count` are populated with real, non-default values whenever retry or tool-calling logic actually runs. Not applicable — no such logic exists anywhere in the app; every row correctly defaults both to `0`. Confirmed by a full-tree grep, not assumed.
- **AC-5**: escalation-block paths remain a deliberate no-`Execution`-row design. Re-confirmed with the user this session, not changed.

## Decision

**Chosen option**: ratified with the user — fix the `502` gap now (small, directly on-topic, and `decisions.md` already named 4.2 as this decision's owner); leave the escalation-block paths and the `retries`/`tool_loop_count` columns exactly as they are (no real signal to log on the former, nothing to build for the latter).

## Rationale

The `502` gap was the one place where "regardless of whether it was blocked" genuinely wasn't true yet — a failed model call is a real operational event (an attempt was made, time elapsed, it didn't succeed), and Phase 4's whole purpose is an audit trail that doesn't go silent the moment something goes wrong upstream. Wrapping the existing `call_model()` call with a plain `time.perf_counter()` measurement (mirroring the pattern `model_client.py` already uses internally) is the minimal fix — no change to `model_client.py`'s exception classes or return shape was needed. The escalation-block paths are a different kind of "blocked": no attempt is made and no content is scanned, so there's no operational signal to persist, and 3.2's own reasoning for leaving them alone still holds — reopening it without a fresh, deliberate reason would just be scope creep in the other direction. `retries`/`tool_loop_count` are schema-complete but logic-empty; a persistence milestone populates real signals as they occur, it doesn't invent the signal-producing logic itself.

## Consequences

**Positive**:
- No request that reaches the model call ever leaves zero audit trail again, even on upstream failure — closes a real blind spot in Phase 4's audit trail for the most common failure mode (the model API being unreachable or erroring).

**Negative / tradeoffs**:
- None new. A `502` audit row necessarily carries less data than a completed one (no `tokens`, no `execution_risk_score`) — expected and documented, not a bug.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the targeted self-check below plus the standing regression suite already exercised by prior phases.

## Follow-up

- `retries`/`tool_loop_count` will populate naturally whenever retry or tool-calling logic is eventually built — no such milestone exists yet in `STATUS.md`, and none is implied by this spec.
- Escalation-block logging stays closed per the user's explicit call this session (see AC-5) — should not be silently reopened again without a fresh, deliberate ask.
- Next milestone is **4.3 Session Ledger Durability** (queued during the 4.1 session: `Session.cumulative_risk`/`Session.strikes` in Postgres are never synced from the Redis ledger) — write its spec first via `/architect`.
