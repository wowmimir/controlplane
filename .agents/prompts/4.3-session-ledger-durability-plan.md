# 4.3. Session Ledger Durability

**Date**: 2026-08-24
**Status**: Accepted

## Summary

`STATUS.md` describes 4.3 as: *"Sync `Session.cumulative_risk`/`Session.strikes` in Postgres alongside every Redis `apply_ledger_update` call, so the durable ledger copy `app/models/session.py`'s own schema comment promises actually exists."* Investigation confirmed the gap exactly as flagged during 4.1: `_resolve_session` sets both columns once, at row creation, via their column defaults; no other code path in the app ever writes to them again. Every real ledger update since (1.3, 1.5, 2.5, 3.1, 3.2) touches Redis only, through `apply_ledger_update()` in `app/redis_client.py`.

This spec adds one small, reused helper (`_sync_session_ledger`) in `app/routers/chat.py`, called immediately after each of the 5 existing `apply_ledger_update()` call sites, mirroring the returned ledger's `cumulative_risk`/`strikes` into the matching `Session` row. No schema change, no migration, no new dependency, and no change to Fork #3's math, the escalation check, or any blocking decision.

## Context

Mapped directly against the current code (`app/routers/chat.py`, `app/redis_client.py`, `app/models/session.py`, `app/db.py`) for this spec:

- **`app/models/session.py`**: `Session.cumulative_risk` (`Float`, default `0.0`) and `Session.strikes` (`JSONB`, default `dict(DEFAULT_STRIKES)` — all 6 categories at 0) are set only in the constructor. The column comment reads: *"Postgres holds the durable copy of the ledger; Redis (0.3) holds the live one. Do not conflate the two stores (STATUS.md, Phase 4.1)."* No `turn` or `strike_events` column exists on `Session`, and none should be added — those are Redis-only bookkeeping for windowed strike expiry (3.1), not part of `forks.md`'s locked `Session` schema (`session_id`, `workload_id`, `cumulative_risk`, `strikes`, `ttl_expires_at`).
- **`app/redis_client.py`'s `apply_ledger_update(session_id, execution_risk_score, strikes_input, *, is_new_turn=True, turn_anchor=None, ts_anchor=None) -> dict`** is the single place the Redis ledger is read, mutated, and written back. It returns the full updated ledger dict: `{"cumulative_risk": float, "turn": int, "strikes": {6 categories: int}, "strike_events": {6 categories: [...]}}`. `ledger["strikes"]` is already exactly the same shape as `Session.strikes` (`dict[str, int]` over the same 6 category keys) — the mirror requires no transformation.
- **`app/routers/chat.py`** calls `apply_ledger_update` at exactly 5 sites, all inside `chat_completions`'s call graph:
  - **Site A** — `_run_request_side_interception`'s escalation early-return (decay-only touch, then `_escalation_block_response()`). No Postgres write happens on this path today at all.
  - **Site B** — `_run_request_side_interception`'s cheap-tier violation branch, right after the `Finding`/`Execution` commit, before `_policy_block_response()`.
  - **Site C** — `_run_response_side_interception`'s clean branch (decay-only touch, `ledger` already captured here today for the `is_escalated` re-check and the `turn_anchor` passed to the background task).
  - **Site D** — `_run_response_side_interception`'s violation branch, right after the `Finding`/`Execution` commit, before `_policy_block_response()`.
  - **Site E** — `_run_expensive_tier_task` (async, runs after the HTTP response has already been sent). This function only receives a raw `session_id: uuid.UUID`, never a `Session` ORM object; it opens its own `async with async_session() as db:` block to update `Execution`/`Finding`, which currently closes *before* `apply_ledger_update` is even called.
  - At sites A, B, D, and E, the `apply_ledger_update` return value is discarded today (not assigned to a variable). Only Site C captures it.
- **`app/db.py`**: `async_session = async_sessionmaker(engine, expire_on_commit=False)`. `expire_on_commit=False` is what already lets Site E re-read `execution.execution_risk_score` after that block's own `db.commit()` without a refresh — the same property makes it safe to assign to and re-commit a `Session` object multiple times within one request or one background-task DB scope.
- **Write-ordering precedent already in this codebase**: at every violation site, the `Finding`/`Execution` Postgres commit happens strictly *before* the Redis `apply_ledger_update` call (sequential, not atomic) — an already-accepted pattern (see the 3.3-era `decisions.md` entry: *"a real violation already committed to Postgres as a Finding can still slip through under fail_open if the subsequent Redis ledger write is what actually throws"*). This spec's Postgres sync necessarily comes *after* the Redis call (it needs the dict `apply_ledger_update` returns), extending that same already-accepted sequential-write shape by one more step.
- **Ratified with the user this session**: the new Postgres sync write must **never** be routed through the workload's `fail_mode` (unlike 3.3's wrap around the interception functions as a whole). It is wrapped in its own `try/except`, logged, and unconditionally swallowed. Rationale: this write is a pure audit/durability mirror, not part of the detection or blocking path — a mirror-write hiccup must never cause an already-Redis-recorded violation to slip through under `fail_open`, and must never turn an otherwise-clean turn into a `503` under `fail_closed`. This mirrors the existing philosophy already applied to `_run_expensive_tier_task`'s own catch-log-swallow (2.5/3.3) and keeps AGENTS.md's Security Hard Rule ("cheap-tier failures MUST block the response") scoped to the actual detection path, not this addition.

## Requirements

- **AC-1**: after any request-side cheap-tier violation (Site B), `Session.cumulative_risk`/`Session.strikes` in Postgres exactly match the Redis ledger's `cumulative_risk`/`strikes` for that session.
- **AC-2**: after any response-side violation (Site D), same match.
- **AC-3**: after a clean exchange with no violation (Site C, decay-only), Postgres's `cumulative_risk` reflects the decayed value, `strikes` unchanged from before.
- **AC-4**: a request blocked by session escalation (Site A) still returns `403`/`session_escalated` as today, and Postgres reflects that turn's decay-only ledger touch.
- **AC-5**: after the async expensive-tier background task produces a real finding (Site E), Postgres's `Session` row — fetched by `session_id` alone, since no ORM object is ever passed into that function — matches the Redis ledger once the task completes.
- **AC-6**: a forced failure in the Postgres sync write (fault-injected, then reverted) does not change the HTTP response's blocking behavior in any of the 4 `fail_mode` × violation/clean combinations — the sync failure is logged and swallowed, never surfaced to the caller, never routed through `fail_mode`.
- **AC-7**: the full existing regression suite (clean `200`, request/response-side `403`s, escalation `403`, unknown-workload `400`, `/health` `200`) is unaffected.

## Decision

**Chosen option**: add one reused helper, `_sync_session_ledger(db, session, ledger)`, called right after each of the 5 existing `apply_ledger_update` call sites; wrap it in its own try/except that always logs and swallows, independent of `fail_mode`.

```python
async def _sync_session_ledger(db: AsyncSession, session: Session, ledger: dict) -> None:
    """Best-effort mirror of the Redis ledger into Postgres's durable copy.
    Never raises - a mirror-write failure must not affect any blocking
    decision or the workload's fail_mode (ratified 2026-08-24, Phase 4.3).
    """
    try:
        session.cumulative_risk = ledger["cumulative_risk"]
        session.strikes = ledger["strikes"]
        await db.commit()
    except Exception:
        logger.error(
            "session ledger Postgres sync failed for session %s",
            session.session_id,
            exc_info=True,
        )
```

Call-site changes:
- **Sites A, B, D**: capture `ledger = await apply_ledger_update(...)` (currently discarded) and call `await _sync_session_ledger(db, session, ledger)` right after. `session` is already the correct ORM object in scope at all three (the same one `_resolve_session` returned and threaded through the request).
- **Site C**: `ledger` is already captured — just add the `_sync_session_ledger(db, session, ledger)` call right after it, before the existing `is_escalated(ledger)` check (order relative to that check doesn't matter functionally, since the sync doesn't affect the decision).
- **Site E**: extend the existing `async with async_session() as db:` block (don't open a third DB scope) — after the Execution/Finding commit and the `apply_ledger_update` call, add `session = await db.get(Session, session_id)` and `await _sync_session_ledger(db, session, ledger)`, all before the block closes.

## Rationale

Postgres's `strikes` column already has the identical shape to `ledger["strikes"]` (both `dict[str, int]` over the same 6 Fork #2 categories), so the sync is a direct field assignment — no schema change, no migration, no new library. Centralizing it in one helper (rather than repeating `session.cumulative_risk = ...; session.strikes = ...; await db.commit()` five times) mirrors the exact precedent 3.1 already set when it replaced a triplicated `get_ledger → decay → strike-loop → set_ledger` block with the single `apply_ledger_update` function.

Write ordering (Redis, then Postgres) isn't a real choice — it's forced by the fact that the sync needs the dict `apply_ledger_update` returns. Given that, the interesting decision is what happens if the *second* write throws. Routing it through the same `fail_mode` wrap 3.3 already puts around the interception functions was the simpler option (no new error handling), but it would tie a pure audit-mirror write to the core blocking guarantee: under `fail_open`, an exception anywhere inside `_run_request_side_interception`/`_run_response_side_interception` is caught and treated as "nothing found, proceed" — meaning a genuinely detected, already-Redis-recorded violation could reach the caller unblocked just because the *new* Postgres mirror-write happened to fail after the real detection and Redis update already succeeded. That's a strictly worse risk than the one 3.3 already accepted (a Finding commit followed by a Redis write failure) — this spec would be *adding* a new way to trigger that exact accepted-but-narrow edge case, not just living inside it. Scoping the sync's own failure to a local swallow-and-log keeps the blast radius of "the durability mirror had a hiccup" to exactly that — a stale Postgres value, not an altered blocking decision.

## Consequences

**Positive**:
- Postgres's `Session.cumulative_risk`/`strikes` genuinely become the durable audit copy the schema comment already claims, closing a real gap flagged since 4.1.
- A console/dashboard view built later (Phase 5) can query `Session` alone for "what is this session's risk state right now," without needing a live Redis read — useful for any read path that doesn't want a Redis dependency (e.g. an offline audit report).

**Negative / tradeoffs**:
- Two extra sequential writes per interception call site that has a violation (Postgres commit for Finding/Execution, Redis call, Postgres commit for the sync) — acceptable for a hackathon build; no latency budget is enforced against interception overhead beyond what already exists.
- Postgres's copy can go silently stale if the sync's own commit fails (accepted, logged, swallowed) — a rare, transient-DB-hiccup case, not a design gap.
- Postgres's `Session` row does **not** reset when Redis's ledger naturally expires (15 min TTL) — a session going cold in Redis leaves its last-known values in Postgres indefinitely. This is correct for a durable audit trail (it should record what happened, not re-derive "nothing happened recently"), but is worth naming explicitly so a future session doesn't mistake it for a bug.

**Neutral**:
- No automated test suite, per `AGENTS.md` Section 8; verification is the self-check described below plus the standing regression suite.

## Follow-up

- No reconciliation/backfill job for `Session` rows created before this spec ships (their `cumulative_risk`/`strikes` stay at their creation-time defaults until the next real ledger update touches that session). Not built here — out of scope for a hackathon MVP with no long-lived session data yet.
- Postgres's `Session` row is never purged or reset when its Redis ledger counterpart's TTL expires. If a future phase needs "is this session's audit record still live," that's a different, unbuilt question — not addressed here.
- This closes Phase 4 (Audit Trail) entirely once built and self-checked. Next milestone is **5.1 Dashboard** — write its spec first via `/architect`.
