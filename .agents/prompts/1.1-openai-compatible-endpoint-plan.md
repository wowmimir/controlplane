# 1.1. OpenAI-compatible endpoint

**Date**: 2026-08-23
**Status**: Accepted

## Summary

This spec stands up `POST /v1/chat/completions`, the entry point `forks.md`'s Fork #4 names for the whole proxy (`AI Application → ControlPlane (proxy) → Model API`). It settles the one design gap `STATUS.md` calls out for this milestone: where the two ControlPlane-specific fields, `workload_id` and `session_id`, live on the request, since neither is part of OpenAI's schema and neither location is fixed by any locked fork. Scope is deliberately narrow: the endpoint accepts and validates a request, reads the two fields from wherever this spec decides, and returns a clearly-stubbed response. It does not resolve `workload_id`/`session_id` against Postgres or Redis (Phase 1.2), run any evaluator (1.3), or call a real model (1.4).

## Context

`AGENTS.md` Section 5 locks the constraint this milestone exists to satisfy: "The proxy MUST support the OpenAI API shape (`/v1/chat/completions`) to prove plug-and-play." `forks.md` Fork #1 locks that `workload_id` is "optional per-request" with fallback to a pre-registered `default` workload; Fork #3 locks the same optionality for `session_id`, falling back to "a session of length 1." Neither fork says whether these two optional values arrive as body fields, headers, or something else — `STATUS.md` names this explicitly as still open: "confirm where these live: header vs body extension; log the choice to `decisions.md`."

`forks.md`'s own "What Is Explicitly NOT Locked" section does not list this either, confirming it's a genuine build-time decision, not a fork to reopen.

Nothing upstream of this milestone exists yet to resolve these two fields against real data — `app/seed.py`'s `DEFAULT_WORKLOAD_ID` exists (0.4), and `app/redis_client.py`'s ledger helpers exist (0.3), but wiring them into request handling is explicitly Phase 1.2's job per `STATUS.md`. This spec only needs the endpoint to exist, accept a valid OpenAI-shaped request, and read the two extra values from wherever this spec places them.

## Requirements

**User stories**:
- As an AI application developer evaluating ControlPlane, I want to point my existing OpenAI SDK's `base_url` at ControlPlane with zero changes to my request body, so that adopting ControlPlane costs nothing beyond a config change.
- As the engineer building Phase 1.2 next, I want `workload_id`/`session_id` already parsed into typed values by the time resolution logic runs, so that 1.2 can focus purely on lookup/fallback, not request parsing.

**Acceptance criteria**:
- **AC-1**: `POST /v1/chat/completions` accepts a request whose JSON body is exactly OpenAI's `chat/completions` shape (`model`, `messages`) with no ControlPlane-specific body fields required or added.
- **AC-2**: `workload_id` and `session_id` are each optional, individually, and are read from a location decided in this spec (not the body).
- **AC-3**: A malformed or missing required OpenAI field (e.g. no `messages`) returns a `422` via Pydantic validation, before any ControlPlane logic runs.
- **AC-4**: A malformed `workload_id`/`session_id` (not a valid UUID) returns a `422`.
- **AC-5**: A valid request, with or without the two optional values present, returns `200` with an OpenAI-shaped response envelope (`id`, `object`, `created`, `model`, `choices`, `usage`) whose content is clearly a stub, not a real model reply, since no forwarding logic exists yet.
- **AC-6**: The header-vs-body decision is logged to `decisions.md` with rationale.
- **AC-7**: No DB or Redis calls are made by this endpoint yet — verified by code review of the handler, since 1.2 owns that logic.

## Options considered

### Option 1: HTTP headers — `X-Workload-Id`, `X-Session-Id` (recommended, ratified with user)

Read both values via FastAPI `Header(default=None)`, typed `uuid.UUID | None`.

**Pros**:
- The JSON body sent to ControlPlane is byte-identical to a real OpenAI request — the strongest possible form of "plug-and-play" (`AGENTS.md` Section 5). An application can point its existing OpenAI client at ControlPlane and add these two as extra headers (every major SDK supports `extra_headers` or an equivalent) without touching its message-building code at all.
- Matches the convention used by comparable LLM gateways (Helicone, Portkey) for exactly this kind of out-of-band proxy metadata, keeping model request content and control-plane metadata in separate channels.

**Cons**:
- Slightly more setup for a demo/curl call (two extra `-H` flags vs. two extra JSON keys) — acceptable, this is a one-time integration cost, not a per-request one.

### Option 2: Extra top-level body fields

Add `workload_id`/`session_id` as optional fields directly on `ChatCompletionRequest`.

**Pros**:
- Simpler to implement (no header parsing) and still non-breaking for strict OpenAI clients, since unknown extra fields are ignored by real OpenAI servers and most client libraries pass extras through untouched.

**Cons**:
- The request body ControlPlane accepts is no longer byte-identical to OpenAI's own schema, which is a weaker form of the "plug-and-play" claim `AGENTS.md` explicitly wants proven.
- Conflates model request content with control-plane routing metadata in a single payload, which cuts against `forks.md`'s general pattern of keeping proxy concerns (ledger, findings, workload config) separate from the model call itself.

## Decision

**Chosen option**: Option 1 — HTTP headers `X-Workload-Id` and `X-Session-Id`, both optional, typed `uuid.UUID | None` via FastAPI's `Header()` dependency.

Additionally, since no model forwarding exists yet (Phase 1.4), the response body for this milestone is a **stub**: a valid OpenAI-shaped envelope whose assistant message content explicitly states that model forwarding is not yet implemented, rather than a hardcoded fake reply that could be mistaken for a real model output during a demo or by a later session.

## Rationale

Headers keep the answer to `AGENTS.md`'s plug-and-play requirement unambiguous: nothing about the JSON body differs from calling OpenAI directly. This was ratified directly with the user rather than decided silently, since it shapes every future request into this proxy and is exactly the kind of "annoying to re-litigate later" choice `AGENTS.md` Section 7 asks to log rather than leave implicit.

The stub-response choice follows `AGENTS.md`'s broader engineering discipline in this project (e.g. 0.4's explicit refusal to fake a schema workaround): a fake but structurally-real-looking model reply risks a future session — or a live demo — mistaking stubbed output for an actual forwarded call, silently masking that Phase 1.4 hasn't been built yet.

## Feature design

**Data model sketch**: no schema change; this milestone touches no Postgres or Redis table. New in-memory-only Pydantic schemas:
- `ChatMessage`: `role: str`, `content: str`
- `ChatCompletionRequest`: `model: str`, `messages: list[ChatMessage]`
- `ChatCompletionResponse`: `id: str`, `object: str`, `created: int`, `model: str`, `choices: list[Choice]`, `usage: Usage`
- `Choice`: `index: int`, `message: ChatMessage`, `finish_reason: str`
- `Usage`: `prompt_tokens: int`, `completion_tokens: int`, `total_tokens: int` (stubbed to `0` for now — real accounting is Phase 1.4/4.2's job)

**State transitions**: none; this endpoint is stateless at this milestone (no ledger read/write, no DB row created).

**API surface**:
- `POST /v1/chat/completions`
  - Headers: `X-Workload-Id: <uuid>` (optional), `X-Session-Id: <uuid>` (optional)
  - Body: `ChatCompletionRequest`
  - `200` → `ChatCompletionResponse` (stub content)
  - `422` → FastAPI/Pydantic validation error (bad body shape, or a header value that isn't a valid UUID)

**Value sourcing**: `workload_id`/`session_id` come from request headers only; no default-resolution logic runs yet (that's 1.2) — an absent header simply yields `None` for now, and the handler does not yet look up `DEFAULT_WORKLOAD_ID`.

**Key invariants**:
- The request body schema never gains ControlPlane-specific fields — it must stay identical to OpenAI's `chat/completions` shape indefinitely, per the Decision above.
- This handler never imports `app.db` or `app.redis_client` — resolution logic belongs entirely to 1.2, keeping milestone boundaries real rather than nominal.

**Security model**: unchanged; no new secret, no new external call. `X-Workload-Id`/`X-Session-Id` are not authentication — they're routing hints, matching `forks.md`'s framing of `workload_id` as an optional identifier, not a credential.

**Configuration required**: none beyond what already exists (`DATABASE_URL`, `REDIS_URL`); this milestone adds no new environment variable.

**Critical test scenarios**:
- Happy path with both headers present and a valid body → `200`, OpenAI-shaped envelope, stub content, verifies **AC-1**, **AC-2**, **AC-5**.
- Happy path with neither header present → `200`, same shape (graceful degradation, foreshadowing 1.2), verifies **AC-2**, **AC-5**.
- Missing `messages` in body → `422`, verifies **AC-3**.
- Malformed (non-UUID) `X-Workload-Id` → `422`, verifies **AC-4**.
- `/health` still returns `200` after the router is added, confirming no regression.

## Build plan

1. Create `app/schemas/__init__.py` and `app/schemas/chat.py` with the Pydantic models from Feature design, satisfies **AC-1**, **AC-5**.
2. Create `app/routers/__init__.py` and `app/routers/chat.py`: `POST /v1/chat/completions` handler using FastAPI `Header(default=None)` typed `uuid.UUID | None` for the two headers, validating the body against `ChatCompletionRequest`, and returning a stubbed `ChatCompletionResponse`, satisfies **AC-2**, **AC-3**, **AC-4**, **AC-5**, **AC-7**.
3. Register the router in `app/main.py` via `app.include_router(...)`, satisfies **AC-1**.
4. Self-check: start `uvicorn`, run the five scenarios from Critical test scenarios via `curl`, confirm each result matches, satisfies **AC-1** through **AC-5**.
5. Log the header-vs-body decision (and the stub-response choice) to `decisions.md`, satisfies **AC-6**.

## Consequences

**Positive**:
- Phase 1.2 can start immediately from typed, already-validated `workload_id`/`session_id` values with zero request-parsing work left to do.
- The OpenAI-compatibility claim is provable today with a real `curl`/SDK call against an unmodified request body.

**Negative / tradeoffs**:
- The stub response means this milestone alone is not demoable as "a working AI call" — it only proves the endpoint shape and header contract. Acceptable: `STATUS.md` explicitly sequences real forwarding as 1.4, after resolution (1.2) and interception (1.3) exist to gate it.

**Neutral**:
- No automated tests are written for this milestone, per `AGENTS.md` Section 8; the critical test scenarios above are a manual self-check via `curl`, matching the pattern from 0.1–0.4.

## Follow-up

- [ ] Phase 1.2 must import and use these same `Header`-sourced `workload_id`/`session_id` values (do not re-parse headers a second time in a later router/dependency).
- [ ] The `Usage` stub (`0` tokens) needs real values once Phase 1.4 (forwarding) and 4.2 (execution persistence) exist to measure actual token counts.
- [ ] Revisit whether `X-Workload-Id`/`X-Session-Id` should later gain an `Authorization`-style validation layer (e.g. confirming the caller is allowed to use that workload) — out of scope for this hackathon MVP, not mentioned in `forks.md`.
